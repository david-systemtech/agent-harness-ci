# Forge accounts are keyed by origin, their capabilities are learned, and runs reach forges through a harness credential helper

Decided 2026-09-24 on the map ticket "Forge account model: shape, storage, selection by banks and skill repos, migration" (david/agent-harness issue 41), which ADR 0012 re-scoped to the environment-owned forge account. One credential per memory bank is kept today (a stored token or a key-manager reference with a username), matched to a remote by host string, with no idea what the token may do until an operation fails, and runs inherit whatever git credential helpers the machine has accumulated. The harness **keys a forge account by its canonical origin** (scheme, host, port) with **verified aliases**: any remote URL, ssh forms included, normalises to an origin and matches the canonical origin or an alias, and an alias is accepted only when the account's credential answers the user endpoint on it with the same login and provider user id. The account's **identity is the login plus the provider's user id**, re-verified on every verification; its **slug** (derived from the host, editable, unique per environment) names the variables a run receives: `FORGE_<SLUG>_URL`, `FORGE_<SLUG>_TOKEN` and `FORGE_<SLUG>_KIND`, with the primary forge also exposed bare as `FORGE_URL`, `FORGE_TOKEN` and `FORGE_KIND`, and `GH_TOKEN` added for the github.com account alone (a GitHub Enterprise origin is a GitHub-kind account that gets only its slug variables). **Capabilities replace scope strings**: each of read repository, write issues, pull requests, create repository and read releases is `verified`, `failed` or `unknown`; reads are probed with harmless calls at verification, writes start unknown and flip on the first operation of their kind (verified on success; failed, with a notice, on 401 or 403, or on a 404 for a target the account had just read, since GitHub hides a denied resource behind 404), a read probe that answers 404 counts as failed, and a scope header is only a hint. The **record is environment state**: `forge.accounts.list` at `read` returns id, origin, aliases, kind, slug, identity, credential source kind, capabilities with their verified-at, primary flag and problem, never a secret; add, update, remove, setPrimary and verify are `admin` calls, and every change is a `forge.account.*` event on the environment stream. A pasted token **crosses the wire once**, in the add or update call over the paired connection, is written to the environment's vault and is never returned; a key-manager reference carries no secret and is **resolved per operation** through the registry, registered with the scrub registry and disposed when the operation ends, with only status cached by the fifteen-minute verification. Git's username is **derived per kind**, never stored: `x-access-token` for GitHub, the identity login for Forgejo and Gitea, `oauth2` for GitLab later. **Runs authenticate git through a harness credential helper**: the run's process receives, in process-only `GIT_CONFIG_COUNT` entries, a reset of the helper chain for each account's origins and the absolute path of `agent-harness git-credential`, which answers over loopback from the environment's vault, proving itself with a **run-scoped secret** placed in the same process environment, valid while the environment-owned provider process executing the run (ADR 0015) lives, accepted only on an internal route that serves the run's account set, and registered with the scrub registry; on git's `erase` verb the helper reports the rejection as an event and forgets nothing. An origin may be http (a LAN or tailnet address of a self-hosted instance) as well as https; the helper serves git's http transport for every origin the account lists and nothing else, so ssh remotes keep the user's own keys and agent, and the harness's own operations always use the canonical origin and the API derived from it. An origin with **no account** gets an anonymous read first, then a typed `forge_account_missing` failure naming the origin and deep-linking the Forges step, a client notice and a health-check failure; runs receive no injection for that origin and git there is left to the machine's own configuration. The Set up checklist gains an eleventh milestone-1 step, **Forges**, after Your machines and before Memory bank, amending ADR 0016: skippable, done when every account verifies (identity resolves and the read capabilities pass) and exactly one primary is set, needs attention on a failed verification with the reason, a re-run re-verifying; the Memory bank step offers repository creation only when a verified account exists, and the Key manager step later offers to move any stored token into a reference. The **state import** makes one account per canonical origin from the per-bank credentials: a key-manager reference wins over a stored token, then the credential whose probe passes the most capabilities; the losers are named in the import report with their bank and discarded, the source files are never modified, and the tailnet origins found on bank remotes are proposed as aliases for the matching login. The **bulk copy** to other environments carries origin, aliases, kind, slug and the primary flag, which is the user's one choice (ADR 0012) and so becomes the primary on the target and clears any other; a reference copies as is and resolves at once where that environment has the same key manager; a stored token copies as needs credential for the target's Forges health check to ask; identity and capabilities are re-verified per environment. **Routines and the completions surface use the environment's account**; a per-bot forge account is a milestone-2 override on the Bot object.

## Considered options

- Keying on a bare hostname or an exact URL string: rejected; two instances on one host with different ports would collide, and the tailnet clones of one Forgejo would not match.
- A forge step inside the Memory bank or Key manager step: rejected; skills, the tracker and releases would reach the forge through a step named for something else, and the milestone-1 order puts Memory bank before Key manager.
- Declared scope strings, alone or beside probes: rejected; fine-grained GitHub and Forgejo tokens do not report scopes, so a declaration is unverifiable until an operation fails. Probing writes on a harness-owned scratch repository: rejected, it litters every forge.
- Writing the per-host reset and a plaintext `store --file` helper into the user's global gitconfig (the 2026-09-18 gaming-PC fix): rejected; a token on disk and config the user owns. Extraheaders for harness operations only, with runs inheriting the machine chain: rejected; it leaves the hang possible in every run.
- Rewriting ssh remotes to the http transport per run, or offering it as a setting: rejected for milestone 1; it changes how a user's repository pushes.
- The helper proving itself with the bootstrap grant, or not at all on loopback: rejected; any process of the OS user could then read every forge token.
- A parked ask when an origin has no account, or falling back to `git credential fill`: rejected; a routine would sit on the ask, and the fallback reintroduces hidden credentials and the hang.
- Copying stored tokens between environments encrypted in transit, or an environment-side paste page, or tokens only through a key manager: rejected; a secret must not cross between environments, a headless box has no browser, and ADR 0011 never forces a key manager.
- Resolving a reference once and storing the value, or caching resolved values across operations: rejected; rotation in the manager must be live at once.
- Per-routine account overrides in milestone 1, or bots that never get an identity: rejected; the Bot object is the place for the override, and Hermes's separate token exists because attribution mattered.
- Asking the user on every import conflict, or taking the first bank's credential: rejected; the import stays unattended and a weaker token must not win by order.

## Consequences

- The client runtime's capability query for git in a terminal pane and the orientation block both read `forge.accounts.list`; the block names each forge's slug and variable names, which is primary, and a `failed` or `unknown` write capability.
- Repository identity (issue 85) must normalise the ssh, scp, http and https forms of one repository to one identity, since the helper leaves ssh alone.
- The ForgeService lists a user's organisations live for owner pickers (issue 46); nothing about organisations is stored on the account.
- The run-scoped secret and the helper path are two more process-only variables under ADR 0011's injection setting; denying injection for an account, routine or bot also removes the helper, and git in that run is the machine's own.
- The slug is derived from the host (lower case, non-alphanumerics to underscores, `github` for github.com) and must be unique per environment; the bulk copy carries it.
- The Set up spec (issue 88) covers eleven steps; the ForgeService spec (issue 87) implements this record, the helper and its internal route; the import task (issue 56) implements the migration rule.
