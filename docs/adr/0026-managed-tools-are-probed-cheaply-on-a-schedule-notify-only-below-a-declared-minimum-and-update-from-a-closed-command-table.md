# Managed tools are probed cheaply on a schedule, notify only below a declared minimum, and update from a closed command table in a terminal pane

Decided 2026-09-24 on the map ticket "CLI updates: launch notice, About pane layout, ignore-version, the update runner" (david/agent-harness issue 47), which ADR 0016 re-scoped onto the Managed tools registry of ADR 0011. A launch check of the user's `claude` and `codex` was planned, with a dismissable per-version notice, About rows beside the desktop app's own updater, and a one-click update in a visible terminal. The 2026-09-22 research found three things that reshape it: on a packaged build the harness runs the Claude Code binary bundled with the Agent SDK, so the `claude` on the user's path is a different binary and updating it changes nothing the harness runs; both CLIs' `doctor` commands misreport the install method on ordinary machines, so detection needs corroboration; and both CLIs self-update on their primary install methods while Codex ships several releases a week, so "outdated" is the steady state and a nag is noise. **Probing is cheap and scheduled.** Each environment's registry runs the `--version` probe for every registered tool at start and whenever a client opens Set up or About, at most every fifteen minutes (the key-manager cadence, ADR 0011), with a five-second timeout and failure recorded as unknown; the `doctor` call, slow and in Codex's case networked, runs only when the user opens a row's detail or clicks Update; "latest" is fetched at most once a day per tool from the source that matches the detected install method (the npm registry, Homebrew, WinGet, GitHub releases), from the vendor's release feed when the method is manual or unknown, and cached on the environment; clients never probe, they read the registry. **Notices exist only below a declared minimum.** The harness declares, per tool, the minimum version it needs (`bao` or `vault` with AppRole, `op`, `bws`, `doppler`, `gh` where a forge account uses a signed-in gh session); a required tool missing or below its minimum is a health-check failure on the step that needs it (Key manager, Forges) and a dot on the Set up row; a newer version merely existing is an informational badge on the About row; there is no launch notice and no ignore-this-version state; the path `claude` and `codex` are never required, since the harness runs its own. **About shows the harness first, then the tools.** This client's version; then the focused environment, with a picker for others: its version, channel, auto-update and Update now (the Your machines card's controls mirrored, ADR 0025) and "Claude Code (bundled) 2.1.x, updates with this environment"; then Managed tools for that environment, one row per tool with the installed version, install method, latest, status (current, update available, below minimum, not installed, method unknown) and one action: Update, Install, or Copy the command when the method is manual, unknown or copy-only (mise, asdf). The Claude row is labelled "claude in your terminal" so nobody expects it to change what the harness runs; each wizard step that needs a tool links to its row.

## Considered options

- A full probe with `doctor` and "latest" at every start, or manual checks only: rejected; network calls nobody asked for, or a missing tool found by a failing run.
- The planned launch notice with ignore-this-version, or a notice for every newer version: rejected; Codex's release pace would make the notice permanent, and the per-version state exists only to silence it.
- A Managed tools pane under Access, or rows only inside the wizard steps that need them: rejected; versions would split across two panes, or there would be nothing to find when a CLI breaks.

## Consequences

- Chosen defaults for review: detection corroborates `doctor` with a realpath check and ignores any path under the harness's own resources, spawning `codex` by name so its shim runs; commands come from a closed per-method, per-platform table in the registry, never from a fetched string; "manual or unknown" is a real state that shows the version comparison against the vendor's release feed and a copyable vendor command; the one-click action runs the exact command in an environment-owned terminal pane on that environment (a real PTY, since `claude install` renders a TUI and installers prompt), waits for exit, re-reads the login shell's path (the User path on Windows), re-probes and runs the tool's verify command; Codex and local-model tools appear when their adapters ship (milestone 2).
- The launcher spec (issue 86) mirrors the environment's version, channel and auto-update rows into About; the Set up spec (issue 88) holds the Key manager and Forges steps' tool rows and their minimum-version checks; the key-manager spec (issue 91) declares the minimums and the verify commands.
- Fog: whether the harness should offer to switch a Claude Code channel (stable or latest) on the user's own install.

## Amended 2026-10-08: every documented update is driven, and the rest runs in a terminal pane (#1833)

Hands-on testing of the released app found the common installs ending as Copy: a `claude` or `bao` placed by its native installer or by hand, or installed by Scoop, mise or asdf, showed only a command to paste into a terminal on the Windows desktop and in the server container. The closed table was meant to keep the harness from running an invented command, not to leave those installs without an action. So:

- **The table drives every method whose update the vendor or the package manager documents**, on every platform where the method exists: Homebrew, WinGet, Scoop (`scoop update`), mise (`mise upgrade`, within the version its configuration asks for), asdf 0.16 or later (`asdf install <name> latest`, then `asdf set --home`), npm, apt and dnf, and a bare binary's own self-update (`claude update`, `doppler update`). Scoop, mise and asdf name the package the tool's realpath is installed under (`scoop/apps/<name>/`, `mise/installs/<name>/`, `.asdf/installs/<name>/`) where that is the tool's own (the tool's name or the registry's), else the registry's name for it (a shim). A package of another name, such as the Node that `npm i -g` installed the tool into, is never upgraded in the tool's place. The commands are still fixed argument lists; the package name read from the path must be a plain name, never an option or a path.
- **A bare `bao`** updates from OpenBao's release archive for the platform and architecture (`openbao_<version>_<os>_<arch>`), its SHA-256 checked against the release's `checksums.txt` before anything is replaced, its `bao` put where the current one resolves to (under `sudo` where that directory is not writable). The version is the latest release's tag, read inside the run, so the table holds a fixed script, not a fetched string.
- **`vault` stays without a command**: it is under the Business Source License, and the harness neither downloads its releases nor runs an update for it. Its row keeps Install `bao`, and an installed `vault` row says the harness has no command for it.
- **Where the table still cannot drive a method** (`unknown`; a bare `op`, `gh` or `bws`; a tool npm installed into a Node that Scoop, mise or asdf installed; and a file no dpkg or rpm owns in a place pacman, apk, MacPorts, Nix, snap, cargo or Chocolatey may own, `/usr` but its `local`, `/bin`, `/sbin`, `/opt/local`, `/nix/store`, `/snap`, `.cargo/bin` or Chocolatey's directory, which detection reads as manual and whose documented command is never the bare binary's update), the row's action is **Run in a terminal pane**: `tools.run` opens the tool terminal with the vendor's documented command written out and runs it only once a person presses Enter there (Ctrl+C or closing the terminal cancels), so sudo prompts and output are visible and the run is probed and verified like any other. Copy is the row's menu item, never its only action. The command is held back rather than typed into an interactive shell so that the harness still learns when it has finished and re-probes the tool.
- **In the server container** the same applies: the image ships none of the managed tools (`test/container.test.ts`), so none is pinned by the image and an update runs in the container's tool terminal as on any machine.
