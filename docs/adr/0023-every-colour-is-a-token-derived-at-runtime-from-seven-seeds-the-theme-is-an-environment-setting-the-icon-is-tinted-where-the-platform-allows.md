# Every colour is a token derived at runtime from seven seeds; the theme is an environment setting; the icon is tinted where the platform allows

Decided 2026-09-24 on the map ticket "Decision: theme tokens, the default palette and the tinted app icon" (david/agent-harness issue 161), opened on David's instruction that every colour in the UI be a token so a person can re-theme the harness, one change recolouring everything, the app icon in the dock or taskbar included. Today's renderer is already close: it names every colour in one stylesheet, derives about twenty tokens offline from a canvas seed and an accent seed in OKLCH with five fixed hues for status and activity, guards the result with a contrast, gamut and hue-separation test and a test that every colour class names a token, and paints its icon from the same two colours; its only picker is light, dark or system, and nothing changes the icon at runtime. The harness makes the derivation live. A **theme** is a name and **seven seeds**, each one OKLCH hue and chroma: Canvas (the neutral base, today's abyss), Accent (the blue, today's beam), Machine (tool and terminal activity, cyan) and Thinking (sage) as the four roles, and Success, Warning and Danger (mint, amber, signal) as status seeds that ship fixed and may be overridden; the defaults are today's two seeds and five fixed hues exactly, so a fresh install looks the same as it does today. A **shared theme package**, with no UI and no session state, holds the seed-to-ladder maths in OKLCH, the contrast rules the current palette test enforces (WCAG 2 AA: 4.5:1 for text, 3:1 for components, moved into the derivation so a seed that cannot reach them is clamped and the clamp reported), both the light and the dark ladder from the same seeds, and the **token** names; the GUI and the web tab apply the tokens as CSS variables on the root through Tailwind's inline theme mapping, so changing Accent to orange recolours fills, hover, links, focus rings, selection and the icon together, and today's offline build is retired. The terminal UI keeps the terminal's own sixteen colours; the package supplies only the role-to-ANSI mapping (Accent to magenta today) and derives the diff backgrounds from the Canvas seed where truecolor is available. **The theme is an environment setting**, `appearance.theme`, pushed to other environments by the bulk edit; a client paints the theme of its **home environment** (the desktop's and the terminal's local environment, the web tab's serving environment), caches it locally for first paint, and never recolours as the user moves between environment headings; light, dark or system stays a preference on each client, since system means that client's OS. **The icon is tinted where the platform allows**: the package renders the SVG master (tile from Canvas, bow from Accent) to PNG, ICO and ICNS when the theme changes, and the desktop shell applies it behind a capability flag: on macOS the Dock icon at runtime, with Finder and Launchpad keeping the shipped icon and the Appearance pane saying so, since a signed bundle cannot be rewritten; on Windows the generated ICO written under the app's data directory, set as the taskbar relaunch icon through the window's app details and written onto the Start-menu shortcut, since the signed executable cannot change; on Linux the PNG under the user's icon directory with a user-level desktop entry, which every launcher follows. **Phasing**: the theme package, the tokens, the setting and a lint that refuses a literal colour in any renderer package land with the GUI's first build (milestone 1, phase B); the Appearance step and pane gain the seed picker with swatches, three shipped themes, import and export, live preview and a health check that the theme passes contrast in phase D; the tinted icon is milestone 2.

## Considered options

- Four literal tiers with status fixed, or every token editable: rejected; the tiers would hide what the current palette actually varies, and twenty editable tokens can break contrast in twenty places.
- Authored ladders per shipped theme, or runtime derivation inside the GUI renderer alone: rejected; the first makes "my secondary is orange" a request to the maintainers, the second has the icon and the terminal mapping re-implement the maths.
- A client-local theme with import and export: not chosen; David wants one theme pushed to every environment by the bulk edit. Painting the focused environment's theme, or the first paired one: rejected; the whole window would change colour on a click, or the choice would be arbitrary.
- The terminal painting its whole surface in truecolor from the seeds, or a setting to choose: rejected; a terminal user's theme is the terminal emulator's, and the one truecolor use already in place, the diff backgrounds, is the one place the seeds reach.
- Runtime-only icon tinting with nothing installed touched, or shipped icon variants only: rejected; the pinned or launcher icon would stay the shipped blue, or orange would not exist unless shipped.
- Everything in phase B, or tokens only in milestone 1: rejected; the GUI spec would grow by a workstream, or milestone 1 would ship with no picker at all.
- The light, dark or system mode travelling with the theme, or one-ladder themes: rejected; a laptop in dark mode beside a desktop in light mode must stay possible, and the OS switch is not ignored.

## Consequences

- The GUI spec (issue 84) builds the renderer shell on the theme package from its first commit, with the lint in CI; the settings information architecture (issue 48) and the Set up spec (issue 88) hold the Appearance pane and step; the client runtime spec's line on theme now reads that mode is client-local and the theme is an environment setting.
- Chosen defaults for review: the lint (`agent-harness/no-literal-colour`, modelled on the organisation-state lint) refuses hex, rgb, hsl and oklch literals, Tailwind's built-in palette classes and black or white utilities in every renderer package, allowlisting the terminal pane's xterm fallbacks and the preview iframe; in-app logos use `currentColor`; the desktop shell takes the window background from the Canvas seed instead of following the OS; environment badge colours (ADR 0005) stay data, not theme; a theme file is JSON holding the name and the seven seeds; the setting is registered under the Appearance step's entry.
- Fog: a theme following a person across clients without an environment (a client that reaches several environments with different themes paints its home one); per-account or per-bot accent hints. The terminal's diff backgrounds on light terminals, fog until David decided it on 2026-09-28 (#392): a light-background terminal gets the theme's light ladder; at launch the terminal UI sends the standard background-colour query (OSC 11) and draws the light or dark ladder by the reply, dark with no reply, and a terminal UI setting (`AGENT_HARNESS_TUI_BACKGROUND`) overrides the choice.
