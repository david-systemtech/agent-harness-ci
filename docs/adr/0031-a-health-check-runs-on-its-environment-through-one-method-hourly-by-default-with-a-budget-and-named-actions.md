# A health check runs on its environment through one method, hourly by default, with a budget, three states and named actions; re-run jumps to the first that needs attention

Decided 2026-09-25 on the map ticket "Health checks: what each step tests and what re-run does when a check fails" (david/agent-harness issue 38), which ADR 0016 re-scoped to the step registry once every step's own decision named its check. Those decisions did: the Account step reads sign-in status (ADR 0018), Carry over the directory and the last import (ADR 0021), Your machines the discovery URL, version and name (ADR 0025), Forges the identity and read capabilities (ADR 0020), Skills the sources and the own directory (ADR 0029), Key manager the token lookup and the CLI minimum (ADR 0028), Instructions whether the block renders (ADR 0030), Browser the paired Chrome and its version (ADR 0024), Appearance the contrast rules (ADR 0023), and the Memory bank step the bank's remote and its `BANK.md` (ADR 0010, ADR 0013). What was left was the pattern they share. **A check runs on the environment being checked**, never on a client (the one exception is a step with no environment state, which has none in milestone 1; see the chosen defaults). Two wire paths keep running and reading apart: `setup.check` (one step or all) runs a check now and answers with its result, and the `setup` subscription on the environment stream carries every step's latest result to clients as it changes, so reading the subscription never triggers a check: a client starts one only by calling `setup.check`, which it does when Set up or a step's pane opens, on Check now and on re-run. A result is the **state** (done, needs attention, skipped), a **one-line reason** naming the failing check, **named actions** drawn from a fixed vocabulary in the contracts package (Sign in again, Pull now, Check again, Unpair, Pair another, Install, Update, Reload, Set up this machine, Restore, Move) of which a step's registry entry selects its subset, a new verb being a contracts change, and **checked-at**. **It runs** on environment start, when a client opens Set up or the step's pane, on Check now and on re-run (each a `setup.check` call), and at once when the feature's own event fires (an account's status changed, a Chrome paired, a source synced); otherwise **every hour by default**, a step declaring a shorter cadence only with a stated reason in the registry, which the Key manager and Account steps do at fifteen minutes because the orientation block reports token and sign-in freshness (ADR 0011, ADR 0018). Clients read the cached result from the subscription and show its age once it is older than the step's cadence; only Check now and re-run call `setup.check`. **Pending after half a second, a budget per check**: five seconds for a local read or version probe, ten for a network call, thirty for a git probe or clone; past its budget a check reports needs attention with "could not check: timed out after N s" and Check again, the last good result kept beneath, dated, so the three states stand. **Re-run** checks every step fresh for the picked environment, jumps to the first that needs attention with its actions, and treats done and skipped as passing; the Set up row's dot is the worst state across the steps of the picked environment; actions are commands, so the terminal UI runs them from its summary. **Preference steps are done once set or preset** and turn amber only on an inconsistency: Permissions when a mode that needs containment is chosen where none can be enforced or the denylist fails to parse; Appearance when a custom theme fails the contrast rules, naming the seed; neither is ever skipped.

## Considered options

- Clients running the checks, or checks on demand only: rejected; every client would re-implement the probes and a headless environment would be checked only while someone looked, or the Set up row's dot would always be stale.
- A fourth state for a timed-out check, or no budget: rejected; every colour rule and the re-run jump would need a fourth case, or a sleeping machine would leave a step pending indefinitely.
- Free-text reasons with no action list, or a re-run that pages through all eleven steps: rejected; every client would invent its own buttons, or a green checklist would be walked for nothing.
- Preference steps always done, or needing an explicit confirm: rejected; an unenforceable containment setting would stay green, or a click would exist for its own sake.
- A fifteen-minute cadence for every step: not chosen; David set an hour unless a step has a reason.

## Consequences

- The Set up spec (issue 88) carries the per-step table (check, budget, cadence, actions) compiled from the decisions above, the `setup.check` method and its result schema, the pending and age rendering, and the re-run rule; each feature's spec names its check's events.
- Chosen defaults for review: a check never writes the state it checks, though it may write scratch (a shallow probe clone into a temporary directory that is removed after); a step's registry entry declares its check, budget, cadence and action set, and the contract test of ADR 0016 covers all four; a step with no environment state (none in milestone 1) would declare a client-side check; the result cache lives on the environment and survives its restart with its checked-at.
- Fog: a what's-new checklist after an update (ADR 0016); checks that run on a schedule the user sets.
