# The Browser step loads the extension from a folder the environment unpacks, stamps the port into it, and pairs on one card that ticks itself

Decided 2026-09-24 on the map ticket "Browser step: download, Chrome walkthrough, pairing, dev sites, health and the usage screen" (david/agent-harness issue 53), which ADR 0014 left to pin the step's copy and mechanics. Today the extension ships as a zip inside the desktop app, which has the user save it, unzip it and load the folder unpacked at `chrome://extensions`, shows an eight-character pairing code good for five minutes behind a "Show a code" button, listens on a fixed loopback port that a second instance cannot take, and tells an outdated extension apart only by a suffix on the paired row; a window served by another machine can do none of it. In the harness the environment on the user's machine owns the listener (ADR 0014), so the step changes shape. **The local environment ships the extension inside its own artefact and unpacks it on demand to a stable folder in its data directory** (`extension/current`), updated in place by the environment's self-update (ADR 0007) so Chrome only needs Reload; there is no zip and no unzip. **The environment stamps its listener port into a small config file inside that folder**: it takes 47615 first and the next free port otherwise, the extension reads the file, and the options page shows the port with an override for odd cases, so two environments on one machine (ADR 0001) unpack two folders with two ports. **The step is one card with four sub-steps that tick themselves.** Load the extension: the folder path with a Copy button and the existing three Chrome lines (open `chrome://extensions`, turn on Developer mode, Load unpacked and choose the folder), ticking when an unpaired extension opens its socket to the environment, which happens before pairing. Pair: the code (eight characters from the unambiguous alphabet, five minutes, single use, five wrong guesses) minted when the card opens and renewed on expiry with a fresh countdown, no button, typed into the extension's options page; the listening line and the port-in-use error under it; ticking on the paired-Chrome event with the Chrome's name. Sites you are developing: the one-host-per-line field with the note that loopback and private addresses count without being listed; optional. Done: My Chrome set as the reach default for every account on this environment whose reach setting is still the preset, said in a line, an account already set staying as it is; then the usage text, which is the picker's labels and notes plus the reach setting's two explanations. The step is **skippable on first run and resumable from Settings**. **Health**: done when a paired Chrome is connected; needs attention when a Chrome is paired but none is connected, with the line "The extension only runs while Chrome is open. Open Chrome and, if it asks, dismiss the developer-mode notice; this turns green by itself.", or when the version the extension reported on its last connection differs from the folder the environment ships, with "Chrome is running version X of the extension; this environment has Y. Open chrome://extensions and click Reload." and the pairing kept; skipped when nothing is paired; a re-run offers Check again, Unpair and Pair another. **The copy reuses the existing Browser pane copy with the product name as the placeholder, three edits and the new lines this decision names**: the zip and unzip lines give way to the folder step, the not-connected state gains the developer-mode line, the dev-sites text drops "request and response bodies", which the driver never captures, and the outdated line, the Done sub-step's default-browser line and the dropped Show-a-code button are this decision's own; the usage text is the picker's notes and the reach setting's explanations, both already written. Chrome-only copy until Edge and Brave are tested.

## Considered options

- A zip download as today, or both a folder and a zip: rejected; every update would mean a new zip and a new folder, and the environment already holds the files on the machine the Chrome is on.
- Blocking browser verbs until an outdated extension is reloaded, or saying nothing: rejected; a run would break on the day of an update, or fail with the driver's error and no explanation.
- Setting the default browser for the default account only, or asking on a final card: rejected; the other accounts would keep the preset unexplained, or the step would grow a screen.
- Four separate wizard steps, or one form with no detection: rejected; a fourteen-row checklist, or a step that cannot tell the user how far they got.
- A fixed port with the options-page override (today's approach), or discovery through the environment's health URL: rejected; a second environment on the machine could not pair a Chrome, and discovery needs the extension to know a port anyway.
- Reusing the copy unchanged, or rewriting it fresh: rejected; the zip wording would be wrong on day one and the bodies claim is false, while the rest of the pane's text was written for exactly this feature.

## Consequences

- The browser spec (issue 93) specifies the unpack, the port file and its reader in the extension, the unpaired-connection signal, the version comparison against the shipped folder, and the pairing store as environment state; the Set up spec (issue 88) holds the card, the sub-step ticks, the health check and the copy.
- Chosen defaults for review: dev sites, blocked sites and the allowed defaults are environment settings (`browser.devSites`, `browser.blockedSites`, `browser.allowedDefaults`), not pushed to other environments unless the user bulk-edits them; a web tab on a machine with no environment sees "Install the harness on this machine to pair your Chrome"; the terminal UI shows the step's summary and pointer only (ADR 0016), the web tab served by the local environment being the path without a GUI; the paired-row name, unpair and rename keep their current behaviour.
- Fog: the unlisted Web Store listing, Edge and Brave copy once tested, a `/browser pair` command in the terminal UI.
