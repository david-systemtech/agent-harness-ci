# Carry over imports the adopted directory in one click: records now, history on first open, memory and skills copied, nothing in the directory touched

Decided 2026-09-24 on the map ticket "Carry-over step: detection, adopt versus link, the Codex equivalent, and what does not carry" (david/agent-harness issue 39), re-scoped by ADR 0016 and ADR 0018 to what happens after the machine's Claude Code directory is adopted. Artemis lists a directory's sessions through the SDK on every open, keeps the archive as the SDK session tag `archived` inside that directory, bridges the directory's skills and commands into a plugin it builds, ignores its subagents (the `agents/` folder), and knows nothing of its auto memory beyond the path pattern. The harness's **Carry over** step, second in milestone 1, is **one click on the adopted directory**: every session the SDK lists (orphaned and superseded files excluded) becomes an **imported session** record at once, from the SDK's session info (custom title, summary, first prompt, working directory, tag, created-at, last-modified; the git branch it also carries is not kept), reading a transcript's first lines only when that info lacks the working directory, as Artemis does: title from the custom title, else the generated summary, else the first prompt; workspace of kind directory at the transcript's working directory, flagged missing when that directory is gone; repository identity from that directory's git remote when it exists, else null; created-at and last-activity from the info's created-at and last-modified; the provider session id linked to the adopted account. A session tagged `archived` imports with `archivedAt` at its last-modified time, and a session Artemis's scheduler spawned (first prompt a scheduled-task marker) imports archived too. **History enters the log on first open**: the first client to open an imported session has the adapter's history module read the transcript, and its subagent transcripts, from the adopted directory and append them once; from then on every client reads the log, and the first harness run resumes by provider id from the account's directory before the session store takes over. A missing workspace lists and opens read-only; resuming asks for a workspace first, which becomes the session's. **Auto memory is copied, never moved**: Claude Code keys memory by git repository root under `projects/<encoded>/memory/`, the folder name is a lossy encoding, so the path is recovered from a transcript in the same project folder, the repository identity from that path's git remote, and `MEMORY.md` with its topic files is copied into the environment's memory directory for that identity (else the workspace path); an existing file is never overwritten, a second source for one identity or a changed source on a re-run lands under `carried/<encoded-source>/` with a pointer line appended to `MEMORY.md`, and a memory folder with no transcript left to name its path is reported as unmappable with an assign-to-a-repository picker. **Skills and commands are copied into the environment's own skill directory** under one tick, on by default when any are found, as environment state editable and updatable from the harness; a skill folder that is itself a git checkout is offered as a tracked skill source (branch or pin, pull on launch) instead of a copy; the originals stay for the terminal `claude`, and the card says the harness copy is now the one to edit. The card shows a **full inventory with counts**: sessions (archived, missing directory), memory (repositories found, unmappable folders), skills and commands, with subagents and plugins listed as not carried, then hooks, personal MCP servers and permission rules counted under what does not carry, ending with: "Not carried from your Claude Code directory: hooks, personal MCP servers, permission rules and the approvals you gave the CLI, your settings (model, theme, status line, key bindings), plugins and marketplaces, subagents, prompt history and trust decisions. Your terminal claude keeps using all of them. Repository instructions and hooks load in the harness once you trust the repository; MCP servers and permissions are set per environment in Set up." The step is **done after the click**, skipped when no adopted account exists or the directory holds nothing to carry; a **re-run** refreshes the report and offers to import the sessions and memory that appeared since, deduplicated by provider session id so nothing imports twice; needs attention only when the directory is unreadable or the last import failed part way, naming what failed. There is no watcher on the directory. Identical on Windows, macOS and Linux, with nothing created, linked or deleted in the adopted directory.

## Considered options

- Continuous sync of the adopted directory, or a single import with no re-run: rejected; a watcher on a directory the harness does not own shows terminal sessions mid-flight as harness sessions with no run, and a single shot lets the terminal diverge silently.
- Parsing every transcript into the log at the click, or never copying and rendering from the file: rejected; a large directory would take minutes for conversations nobody opens, and a transcript tied to the file vanishes when Claude Code's age sweep prunes it.
- Skipping sessions whose directory is gone, or resuming them in a scratch workspace: rejected; "every existing session" must hold, and a scratch workspace is a place the conversation was never about.
- Turning the step amber whenever the directory holds unimported sessions, or moving the import to a button on the Accounts pane: rejected; the first nags anyone who also uses the terminal, the second takes the one click out of the checklist.
- Copying only the first memory source per identity, or merging by appending to `MEMORY.md`: rejected; memory would stay behind, or the index would grow past the window Claude Code loads.
- Registering the adopted directory's skills as a read-in-place source, copying and then deleting the originals, or leaving skills to the Skills step: rejected; David wants the skills migrated into the environment's own directory so they are kept up to date there, the adopted directory is never modified, and a report without an action would leave the migration to a later step.
- Leaving the archive tag to the Artemis import task: rejected; it is read at zero cost in the listing the import already runs, and an Artemis user would otherwise see archived sessions surface as active until phase D.

## Consequences

- The Artemis import task (issue 56) narrows to what lives outside the Claude directory: Codex and local-provider archive keys, desktop groups and pins from `prefs.json`, terminal-UI pins, the memory-banks registry, saved connections and the browser-extension pairing.
- Chosen defaults for review: the import is an environment command the checklist calls at `admin` scope, appending session events with origin `import`; the Set up spec (issue 88) holds the card, the Claude adapter's history module (issue 82) the lazy read, and the skills spec (issue 89) the copy and the checkout-as-source offer; Codex carry-over stays hidden until its adapter arrives in milestone 2.
- After an imported session's first harness run, the harness copy is authoritative; a continuation of the same provider id from the terminal is never re-imported.
- Whether the terminal `claude` should follow the environment's skill set and memory, and subagents as environment state, stay in the fog.
