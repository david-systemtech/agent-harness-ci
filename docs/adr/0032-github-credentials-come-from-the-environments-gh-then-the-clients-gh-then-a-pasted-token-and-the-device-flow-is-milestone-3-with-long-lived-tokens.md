# GitHub credentials come from the environment's gh, then the attending client's gh, then a pasted token; the device flow is milestone 3 with one app and long-lived tokens

Decided 2026-09-25 on the map ticket "GitHub OAuth device flow: app ownership, client id in the release, fallback" (david/agent-harness issue 49), which ADR 0012 placed in milestone 2 with the app under the harness's own organisation once the name lands. The 2026-09-22 forge research established that the device flow needs only a public client id and no secret, that "Expire user access tokens" is a property of the registered app (eight-hour tokens with a six-month refresh when on, long-lived tokens when off) rather than of a request, that classic OAuth scopes `repo` and `read:org` cover issues, pull requests, contents, releases, repository creation and organisation listing, that `gh auth token` yields a token of unknown provenance that must be probed, and that Forgejo has no device flow and should not get one. **Without the device flow a GitHub credential comes from three places in order.** First the environment's own signed-in `gh`, read through the Managed tools registry (ADR 0026), its token probed for `repo` and `read:org` with fine-grained tokens told apart by the missing scope header and accepted on their own terms. Then, for a remote or headless environment, the `gh` signed in on the attending client: the Forges step offers "Use the gh signed in on this computer", the client reads its local `gh` token and sends it once in the add call exactly as a pasted token travels (ADR 0020), the environment stores it in its vault, and the account's card says it came from that client's `gh` and will not follow `gh`'s rotations. Then a pasted token, the universal fallback. Milestones 1 and 2 ship these paths only. **The device flow is milestone 3**: one OAuth app registered under the harness's own GitHub organisation once ticket 33 names the harness, Device Flow enabled, a harmless callback URL, **expiry off so tokens are long-lived until revoked** (David's preference; a person wanting a short-lived credential pastes a fine-grained token with an expiry date), scopes `repo` and `read:org`, the public client id shipped in the environment artefact as a build-time setting so a fork can ship its own, and no device flow for GitHub Enterprise hosts. **The prompt is environment-driven and shown by any client**, as the Claude sign-in is (ADR 0018): the environment requests the device code, publishes the user code, the verification link and a fifteen-minute countdown; whichever client is attending shows them with Open GitHub (the client opens the browser when it is on the same machine) and Copy the code; the environment polls at the interval GitHub sets, honours `slow_down`, and on success creates or updates the forge account with source OAuth and probes its capabilities (ADR 0020); expired or denied offers Try again; "Paste a token instead" is always beside it; one device flow runs at a time per environment.

## Considered options

- Registering the app under David's existing GitHub organisation now, or each environment registering its own app: rejected; a rename would mean a new client id for every install, and a registration form for every user is the cost the device flow exists to remove.
- Two registered apps so the user picks expiring or long-lived at sign-in, or expiring tokens only: not chosen; David prefers long-lived tokens, and the fine-grained token path already gives anyone an expiring credential without a second app.
- `repo` alone, or the CLI's full default scope set: rejected; the owner picker needs organisation listing, and `workflow` and `gist` are broader than the harness uses.
- A client-driven or browser-only flow: rejected; the terminal UI and a headless environment could not run it.
- Reading any connected client's `gh` silently: rejected; a credential must not cross from a machine the user did not name.
- Keeping the device flow in milestone 2: not chosen; David pushed it to a later phase, since `gh` and pasted tokens carry the switch-over.

## Consequences

- The ForgeService spec (issue 87) specifies the `gh` probe on the environment, the client-handed `gh` token as an add-call source with its provenance recorded, and the milestone-3 device flow as direction: the OAuth app, the build-time client id, the environment-side polling and the account update. The Set up spec (issue 88) holds the Forges step's "Use the gh signed in on this computer" card.
- ADR 0012's consequence placing the device flow in milestone 2 is superseded by this record; ADR 0017's milestone list gains the device flow under milestone 3 when it is next amended.
- Chosen defaults for review: a client-handed token is probed like a pasted one; the client reads `gh auth token` through its own Managed tools detection, never a config file; a fine-grained token's capabilities are learned from use as ADR 0020 has it; the countdown, the code and the link are the same shape as the pairing card (ADR 0025).
- Fog: GitHub App user-to-server tokens bounded by installed repositories; a device flow on Forgejo if upstream ships scopes and the device grant.
