# Accounts are environment-owned directories that share sessions and memory natively; the harness performs no login

Decided 2026-09-23 on the map ticket "Account step: hosted sign-in in the wizard and the local model probes" (david/agent-harness issue 51), re-scoped by ADR 0016 to Claude accounts in milestone 1. Artemis isolates each profile in its own `CLAUDE_CONFIG_DIR`, holds no credential, strips the three variables that would outrank a login, and has two sign-in paths: the desktop hands the user a command to run in a terminal, the headless server spawns `claude auth login`, publishes the verification URL and takes the code back through the client. Profiles share history, skills and memory only through a user-run script that symlinks nine entries back to `~/.claude` (junctions and a hard link on Windows), which the desktop observes and never runs. The harness keeps the invariant and drops the links. An **account** is one provider login held by an environment in one config directory of its own: the machine's own Claude Code directory **adopted in place**, offered as the first card when it is signed in, or a harness-owned directory under the environment's data directory for a fresh sign-in. Every environment is a service with no terminal attached, so the environment drives the login itself with the **SDK-bundled Claude binary**, publishes the URL, takes the code from whichever client is attending, runs one sign-in at a time with a ten-minute expiry and a cancel, and shows the exact command as a fallback for a terminal on that machine. The harness never holds a Claude credential, always strips `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN`, and in milestone 1 offers only subscription sign-in. An account's **identity** is the provider plus the login it signed in as (email, and organisation when present), read from the CLI's status after sign-in; one account per identity per environment, labels editable and unique per environment, and the same identity on several environments pools plan usage (ADR 0005). **Accounts share natively through the environment**: transcripts live in the environment's log and reach any account's process through the SDK session store on resume, every account on an environment writes one environment-owned auto-memory directory per repository, skills, standing instructions and tool servers come from environment state (ADR 0009, 0015), and the workspace belongs to the session (ADR 0005), so accounts are interchangeable on Windows, macOS and Linux with no sharing scaffolding created, moved or linked anywhere; an adopted directory is read and written only by the provider's own CLI, and the harness creates new directories only under the environment's data directory.

## Considered options

- Artemis's split, a copied command locally and a driven login remotely: rejected; the local environment has no terminal either, and one path serves local, remote and headless alike.
- The user's installed `claude` through the Managed tools registry for sign-in: rejected; the bundled binary matches the run binary and needs no install on a headless environment. If the pinned SDK's bundled CLI turns out not to run `auth login`, the managed tool is the fallback.
- Console sign-in or a pasted API key in milestone 1: rejected; a picker most users get wrong at the worst moment, and a key field makes the harness a credential holder and reopens the metered-billing trap. A Console user signs in by the fallback command with `--console`. A pasted key for an account is wanted much later (milestone 4 or 5).
- Carrying the shared-config link script, as the mechanism or as an advanced option: rejected; the environment already owns everything the links shared, and the script needs platform-specific link kinds.
- Two accounts for one login on one environment: rejected; it is the two-gauges limit ADR 0005 removed.

## Consequences

- The Account step is step one: it probes the environment's ambient Claude directory and offers to adopt it, signs in fresh accounts, requires at least one signed-in account to continue, and ends with the environment's **default account and default model family**, chosen from any connected provider's catalogue, preset to the highest tier the account offers at high effort, changeable in the Accounts pane and pushed to other environments by the bulk edit. A new session and the LLM step (issue 40) take that default. Carry over (issue 39) no longer adopts; it reports what the adopted directory brought, copies its per-repository auto memory into the environment-owned memory directory, and says what does not carry.
- Health: done when every account reports signed in; needs attention naming the account when one is signed out, expired or unreadable, with sign-in again on its card; status re-read when the step or the Accounts pane opens and at most every fifteen minutes otherwise, carried into the orientation block (ADR 0011). Removing an account keeps its directory: an adopted directory is never touched, a harness-owned one stays unless the user also chooses to delete its sign-in and history.
- The step registry entry: writes accounts, the default account and family; checks signed-in status per account; links the Accounts pane. The terminal UI can start a sign-in and take the code, since both are commands on the wire.
- The Claude adapter specification (issue 82) verifies session-store resume across two config directories and the bundled CLI's `auth login` before either is relied on.
- Whether the user's own `claude` in a terminal, outside the harness, should see the environment's skills and memory is left in the fog.
