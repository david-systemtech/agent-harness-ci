# Settings are eight bands of registered rows, each with a scope, reached by a rail with search, and every existing address maps totally onto a row

Decided 2026-09-24 on the map ticket "Settings information architecture: final bands, the Set up pane, deep-link migration" (david/agent-harness issue 48), on the verdict of the settings navigation prototype (issue 37) and the bands ADR 0016 named. The current settings dialog is a rail of fifteen panes in two bands whose sixteen addresses form a closed union with a total map to the pane that answers today, so a renamed pane never breaks a deep link, while its persisted allowlist of fifteen entries misses one address and sends that preference back to Profiles. The harness keeps the rail and the total map and regroups everything. **Eight bands in this order, with these rows.** Set up: the checklist pane. Accounts: Accounts; Default account and model, which absorbs the existing Models catalogue and quick-access list and the speed (effort) of the existing Runs pane; Usage, which absorbs Runs' spend and hand-off threshold. Knowledge: Memory banks, Skills, Instructions. Access: Permissions, Browser, Key managers, Forges as a pane of its own. Routines and bots: Routines, which has no Set up step and shows its own health from notices (ADR 0008); Bots, shown dim as a placeholder until the milestone-2 Bot object lands. Environments: Your machines, which absorbs Remote and This machine's updates and workspace folders (ADR 0025); Access, which absorbs Server as program pairings beside the user's client sessions and the access log; Service. Appearance: Theme; Keyboard shortcuts (ADR 0022, ADR 0023). About: this client's version pinned at the top, then the picked environment's version, channel, auto-update, bundled Claude Code and Managed tools (ADR 0026). **The Set up pane** is the checklist hero: the eleven steps with a health dot and one-line status each, every step linking to the pane that owns it, the counts, Re-run to the first step needing attention, Open the full checklist, and the environment it checks with a link to set up another machine; it is always the first row and cannot be hidden; the what's-new checklist stays fog. **Rows are registered.** Every row has an id of the form `band.row` in a row registry (band, label, hint, scope, the step that owns it if any, the pane) and a row without an entry fails the same contract test as a setting without a step (ADR 0016). **Each row declares a scope**: `environment` (the pane shows an environment picker, the client's home environment by default, following the last choice within the session; the rail's health dots follow it and show only on a step's home row), `everywhere` (no picker; the pane shows every environment at once, grouped by environment: Usage, Your machines), or `client` (no picker: the light, dark or system mode and Keyboard shortcuts). About is `environment`-scoped, its picker choosing whose version, channel and auto-update it shows, with this client's own version pinned above the picker as the one line that belongs to no environment. **The rail has a search box at its top** that filters every row across bands and matches the old section names, so typing "secrets" finds Key managers. **Every existing address maps totally.** The sixteen addresses stay a closed union with a map to a row, exhaustive at compile time, published as a table in the GUI spec: `profiles` → accounts.accounts; `models` → accounts.default-model; `runs` → accounts.usage (spend, hand-off) with its speed on accounts.default-model; `agents` → knowledge.instructions; `skills` → knowledge.skills; `memory-banks` and the legacy `cerebro` → knowledge.banks; `permissions` → access.permissions; `browser` → access.browser; `secrets` → access.key-managers; `server` → environments.access (program pairings); `remote` → environments.machines; `routines` → routines.routines; `advanced` → environments.machines (updates, folders) with its service verbs on environments.service; `appearance` → appearance.theme; `about` → about.about. The persisted last-opened row stores a new id validated against the registry, so no allowlist can drift; the state import (issue 56) maps a stored `settingsSection` through the same table.

## Considered options

- Reusing the existing ids where they match, or no legacy map: rejected; the ids would stop describing their bands, or every existing deep link would break on day one.
- A Set up pane with only the checklist and Re-run, or with a health feed: rejected; step rows that do not link out waste the click, and a feed would be a second notices surface beside the runtime's.
- A twelfth Routines step, or routines folded into the Instructions step: rejected; the checklist just gained an eleventh step, and the fold would muddle both.
- Hiding the Bots row until milestone 2, or renaming the band until then: not chosen; David wants the placeholder to show where bots will live.
- Keeping Models and Runs as rows under Accounts, or a Runs row under Access: rejected; they would duplicate Default model and Usage, or keep a grouping the harness no longer has.
- One environment picker for the whole of Settings, or a picker on every pane: rejected; the pooled usage view would be lost, or a control that does nothing would sit on client-scoped panes.

## Consequences

- The GUI spec (issue 84, now unblocked) holds the rail, the search, the per-pane picker, the row registry, the scope rule and the address table; the Set up spec (issue 88) holds the Set up pane; the state import (issue 56) maps `settingsSection`.
- Chosen defaults for review: worktree setup scripts (This machine's "scripts") stay fog; a row's hint is one line as the existing ones are; search matches ids, labels, hints and the old addresses; the terminal UI's `/settings` opens the generic editor by row id (tui spec) and needs no rail.
- Fog: the what's-new checklist after an update (ADR 0016); a Bots step when the Bot object lands.
