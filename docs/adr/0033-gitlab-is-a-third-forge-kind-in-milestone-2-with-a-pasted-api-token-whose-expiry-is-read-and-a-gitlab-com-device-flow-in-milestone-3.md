# GitLab is a third forge kind in milestone 2 with a pasted api-scoped token whose expiry is read, detected by OpenID discovery, synced by iid; the gitlab.com device flow is milestone 3

Decided 2026-09-25 on the map ticket "GitLab: repo creation and tokens as a third forge (minor, late)" (david/agent-harness issue 50), which ADR 0012 kept late and minimal. The 2026-09-25 GitLab research established that a personal access token with the `api` scope covers project creation, issues, merge requests, releases, group listing and git over HTTPS on a personal token (group and project access tokens need `write_repository` beside it), that such tokens expire within at most a year and report their own scopes and expiry, that git over HTTPS takes any username with `oauth2` recommended, that the version and metadata endpoints need a token but answer an unauthenticated call with GitLab's own 401 body while the OpenID discovery document answers unauthenticated on gitlab.com and self-managed alike, that GitLab has had the OAuth device grant since 17.9 but only for a non-confidential application registered per instance, and that merge requests carry `state` and an asynchronous `detailed_merge_status` beside a deprecated `merge_status`. **GitLab lands in milestone 2 as a third forge kind** in the ForgeService (ADR 0012): detection tries the OpenID discovery document, then the version endpoint's 401 body, then the unauthenticated projects list with GitLab's page headers, and once a token exists reads the metadata endpoint for version and edition to gate features; the credential is **a pasted personal access token with the `api` scope**, the Forges step deep-linking the token page with the scope named and the card saying `api` covers git over HTTPS on a personal token, group and project access tokens accepted with `api` plus `write_repository`, the card saying so; **the environment reads the token's own record for its scopes and expiry**, the card shows "expires in N days", and the Forges step turns needs attention thirty days before expiry with a link to mint a new one; git over HTTPS uses the username `oauth2` with the token as the password; projects are created under the user or under a group picked from the groups where the user is at least Developer, a group's project-creation level shown when it refuses; issues, merge requests addressed by their project-scoped iid with `web_url` as the link, merged read from `state` for settle-on-merge (ADR 0003) and the badge from `detailed_merge_status` polled until mergeability settles, never the deprecated field, and releases. **The gitlab.com device flow is milestone 3** beside GitHub's (ADR 0032), with its own registered non-confidential application and a build-time client id; **self-managed instances never get a device flow**, since an application must be registered per instance, the reason Forgejo has none.

## Considered options

- GitLab entirely in milestone 3, or in the fog with no milestone: not chosen; the provider is small once the ForgeService exists, and the token path needs no app.
- Any token with capabilities learned from use, or fine-grained tokens only: rejected; the walkthrough should name the one scope that works, and fine-grained tokens are absent below 19.2.
- Authenticated detection only, or sync on `state` alone: rejected; the Forges step could not pick the right walkthrough from the URL, and the mergeability badge would be lost.

## Consequences

- The ForgeService spec (issue 87) carries the GitLab provider as milestone-2 direction: detection order, the token-record read for expiry and scopes, the `oauth2` username, group listing by minimum access level, iid addressing and the two merge-request fields; the Set up spec (issue 88) holds the GitLab walkthrough and the expiry warning.
- Chosen defaults for review: bank join-by-URL and skill sources work on a GitLab host through the same account; tokens travel in the `PRIVATE-TOKEN` header and OAuth tokens as Bearer; project paths are URL-encoded and a renamed project's redirect is followed; pagination follows the `Link` header; a 429 honours `Retry-After`; fine-grained GitLab tokens are accepted where the instance has them, their capabilities learned from use as ADR 0020 has it; the expiry warning uses the same needs-attention shape as an expired key-manager token (ADR 0028).
- Fog: group and project access tokens as bot identities for the milestone-2 Bot object; whether a device-flow token on gitlab.com comes with a refresh token, undocumented.
