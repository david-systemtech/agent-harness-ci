# Spec: Launcher and auto-update

Milestone 1 (Switch-over), phase B (daily use). Written 2026-09-28 from map ticket 86 of `david/agent-harness`. Implements ADR 0007 whole (idle, the deferral cap and drain, parked prompts across the restart, continuation, channels and pin, the launcher, trial, rollback, the crash-loop watch, the desktop and host-side updaters), ADR 0017 (phase B, the placeholder), ADR 0025 (the install script's asset, variants, service install and health wait; the card's update controls) and ADR 0026 (About's top rows, no launch notice), citing ADR 0001, 0012, 0016, 0020, 0027 and 0031 and the Resolutions of tickets 21, 47 and 52. Builds on main at 863ab8f without re-deciding it: the environment spec (#112's lifecycle, #113's service verbs and script), the claude-adapter spec (`drained`, the recovery sweep), the permissions spec (parked prompts across a restart, the run of the queue after one), the client-runtime spec (`bye: updating`, the `update-environment` action, the shell's `update` and `installer`) and #141's image and compose file. Peers: the server-self-update research (T3 Code's launcher, Codex's continuation, the EXAMPLE-VM tracker), and the memories: the server-auto-update write-up, the release-and-update-feed write-up, the updater-bin-rm write-up (Windows), the server-update-wipes-apt-packages write-up, `forgejo-repos-all-private-2026-09-23` and `forgejo-actions-runner-pool`.

## Problem Statement

The server never updated itself. David updated it by hand until a host-side tracker on EXAMPLE-VM took over, and that tracker waits for a moment with no run starting, running or awaiting permission and never forces. The server parks a permission prompt forever, so one unanswered question holds an update indefinitely. When an update does run, the server exits within ten seconds and every live run is lost ("The server no longer has this run"). Nothing checks health after the recreate, nothing rolls back, nothing tells the clients. Before the tracker the server fell silently behind the desktop and attachments broke. Outside tooling hurt too: the Unraid updater left `hermes` stuck in Created, and an image update wiped every `apt` package on the agent box. The desktop updater once shelled out to a POSIX `rm` on Windows, so three releases could not update themselves.

Phase A built what an update needs and none of the update. The environment reports idle, busy and draining and keeps parked prompts as events, but the service runs `serve` with nothing owning versions, no release publishes an artefact, and #141 left publishing the image here.

## Solution

Every environment keeps itself current, on by default, without losing work. A native install runs a small stable launcher that owns the installed versions. The environment checks its channel on the public GitHub repository hourly, stages a new release in the background and waits for idle: nothing starting or running, nothing started or ended for ten minutes, a parked prompt counting ten minutes only. Busy work defers it at most 24 hours; then the environment drains, giving running runs up to 30 minutes. The new version is a trial that must pass its startup gate in 120 seconds, or the launcher restores the database snapshot and restarts the old version; three crashes in the first ten minutes do the same. After the restart parked prompts are where they were, and a run the drain cut continues with one turn when its provider can resume it.

Clients see "updated from A to B" or "could not be updated, back on A" with the reason. The Your machines card and About show version, channel, auto-update and Update now; a newer client offers to update the environment to its version. The desktop takes its update from its local environment and hands it its bundled server artefact, so both move together. A container never updates itself: a published host-side updater follows the environment's plan, recreates, checks health and rolls the image back on failure. One GitHub release carries it all: artefacts, a manifest, desktop builds, install scripts, the compose file, the host-side updater and a registry image.

## Implementation Decisions

### The pieces

The **release** is what one version publishes on the public GitHub repository `david-systemtech/agent-harness`. The **launcher**, the native service's process, owns the installed versions, the service state and the database snapshots, and runs the chosen version's `serve` as its child. The **update coordinator**, a module of the environment, holds the policy: channel, staging, the moment, the drain and the settle after the restart; it knows runs, the launcher never does. The **host-side updater** carries out the coordinator's plan for a container. The **desktop updater** is the shell's `update` member, fed by the local environment.

### The release

The public release decisions of 2026-10-02 (#1258, #1259) supersede the historical Forgejo publication defaults recorded below.

It installs `public/.github-workflows/release.yml` from the private tree as `.github/workflows/release.yml` in the public repository, whose push uses a token with `workflow` scope. The private root has no GitHub workflow files; no CI relay credential change is needed. The installed workflow runs on `v*` tag pushes only, plus manual dispatch for a dry run. It re-runs typecheck, lint, tests and the schema export check, builds everything on hosted runners, uploads every asset to one draft and publishes last, flagged prerelease exactly when the version has a prerelease part. Its schema lives in the contracts package.

The environment reads through the forge service anonymously; a configured GitHub account is used when present for a higher rate limit. See `docs/agents/releases.md` for the release procedure.

### Versions and the launcher

- **In the data directory**: the versions directory (complete only with a sentinel written last, T3), a staging area, the service state (active, previous and launcher versions, the pending-update record, the watch deadline), snapshots by update id, the restore marker, the outcome record, a stable **launcher entry** script the service definition runs, which starts the launcher of the version its one-line **launcher version file** names, and a `bin` shim running the active version (the install prints the path line and edits no profile). State writes are temp file, fsync, rename, directory fsync; invalid state stops the launcher starting anything.
- **Writers**: while the service runs, the launcher is the only writer of the versions directory, the state and the launcher version file. `service install` writes them only when no launcher runs (a first install, or a stopped service); on a running service it rewrites just the definition and the entry. The entry writes only its start counter, and the launcher version file when it falls back. Of these files the environment writes only the staging area, and deletes the outcome record once settled.
- **The launcher** is the `launch` verb, on Node built-ins with no dependency on the environment package. It spawns the active version's `serve` with an IPC channel and restarts a child that exits unexpectedly after 5 seconds, doubling to 5 minutes. A child that exits cleanly after a drain the launcher did not ask for (`environment.drain`, a signal) restarts at once: under a launcher a drain is a graceful restart. The launcher exits only when the service manager stops it, after draining the child. The service definition gains a 31-minute stop timeout where the platform has one (systemd, launchd); a shutdown still cuts runs, which the recovery sweep ends as `restart`.
- **The launcher channel** adds to #112's pairs; unknown messages are ignored both ways. `prepared {version}` is now answered `committed`, and the child waits for it before appending `environment.started` and opening the wire: T3's command gate, the one change to #112's handshake, so a trial answers no command before commit (without a launcher, no wait). `install? {version, staged}` is answered `installed` or `refused` (`launcher-protocol`, `incomplete`, `preflight`, `disk`, `io`). `switch? {updateId, version}` is answered `switching` or `refused`, after which the child closes, the channel last (#112). `versions?` lists the installed versions.
- **Preflight**: `install?` runs the staged version's `preflight` verb (30 seconds), which prints its version, protocol, launcher protocol and schema and loads SQLite, `node-pty` and the Claude binary's `--version`. Only a passing version is renamed into versions.
- **Launcher protocol**: one integer. Each release's child runs under the previous release's launcher, so a breaking launcher change ships across two releases; `install?` refuses a higher requirement.
- **Handover**: once the active version has held through its watch and carries a different launcher build, the launcher asks `idle?` every ten minutes; at the first idle it writes the active version into the launcher version file and exits with a relaunch code, and the service manager's restart-on-failure starts the new launcher on the same version. The entry counts starts of a handed-over launcher until it confirms its child passed the gate; at the third unconfirmed start it names the previous version again, and the old launcher records the handover failed.
- **Kept**: the active version, the two before it, the launcher's own and any staged or pending one; the rest are pruned when a watch ends.

### Version staging and power loss

First install and update staging use the same completion rule (#1383). Finish copying or unpacking every file, discard any sentinel from the source, rename the staged folder into `versions/<version>`, then write `.complete` last through a flushed temporary file and rename. Until that marker exists, the folder is not a version and can be replaced on retry. A process crash before completion leaves a partial folder or a version without its marker; a process crash after completion leaves the whole copied tree.

On macOS and Linux, flush every staged regular file and directory before the rename, then the rename's parent directories and the sentinel's directory. This orders payload durability before completion. Windows skips the payload walk and directory flushes, using NTFS's journaled rename and one flush for the sentinel, so flush count is independent of the number of staged files. This is process-crash safety, with best-effort payload durability on sudden power loss: the sentinel flush does **not** flush other files, and NTFS's journal protects metadata rather than payload bytes. A power loss may therefore leave a marked version with missing or damaged payload; reinstall that version from the artefact if it cannot start. An update still has its previous version and the trial/rollback rules of ADR 0007. A volume-wide flush would need administrator privileges, which the user service does not have. See the [FlushFileBuffers documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) and [NTFS recovery explanation](https://devblogs.microsoft.com/oldnewthing/20130101-00/?p=5673).

This exception applies only to replaceable version payloads. Service state, launcher-version, restore markers, outcomes and database snapshots retain their existing explicit file flushes and rollback ordering. The desktop window reads service status before starting: when no service is installed, it says “Installing the environment (first start only)…”, then switches to the starting line after install settles.

### The update coordinator

- **States**: `current`, `staging`, `waiting`, `draining`, `switching`, `blocked` with a reason.
- **Reading the channel**: the newest 50 non-draft releases through the forge service, ordered by semver precedence, unparseable tags ignored; `stable` takes the newest without a prerelease part, `beta` the newest of all (beta means earlier, not a separate product); then that release's manifest. First check 2 minutes after start, then hourly, and on `updates.check` (at most once a minute; a repeat answers the last result). A failed check is state, never a notice.
- **The target**: auto-update is effective when `updates.autoUpdate` is on and nothing is pinned. A pin targets its exact version on any channel; otherwise the channel's newest, when newer. Nothing moves backwards on its own (a beta environment switched to stable waits until stable passes it). A version that failed its trial or watch is never retaken automatically; the next newer one is, and Update now can retry it.
- **Refused before downloading**: a version whose database schema is below the database's (`schema`; the event log refuses a newer database). A version needing a newer launcher is reached by **stepping stones**, the newest release the running launcher hosts, then the handover, then onward; with none the coordinator is `blocked` (`launcher`) and names `service install` from the target.
- **Staging** downloads the platform artefact through the forge service, checks size and SHA-256 against the manifest, unpacks it and sends `install?`; a failure retries at the next check. Staging ignores idle.
- **Waiting** appends `environment.update-pending {updateId, toVersion, source, since, deferUntil}`, `source` being `channel`, `pin`, `request` or `desktop`. `since` is when an update first became pending and carries over, read back from the log, when a newer release replaces the target (with a new update id) and across restarts, so frequent releases never reset the clock; `deferUntil` is `since` plus the cap. On every run-registry change and every minute the coordinator drains when idle, past `deferUntil`, or asked by `updates.apply` with `when: now`. The environment's start counts as activity for the idle window as a run's start does (#445), so an update read back from the log as pending waits a full idle window after a start.
- **Recovered channel targets**: before opening the wire at startup, withdraw a stored channel update whose target is equal to or below the running release, appending `environment.update-cancelled` with cause `superseded`. Requests, pins and desktop targets retain their explicit version-change semantics; a newer channel target still waits across restarts.
- **Draining**: in the tick that read the activity, the coordinator appends `environment.update-started {updateId, fromVersion, toVersion, cause}` (`idle`, `cap`, `requested`) and starts #112's drain with a new trigger, `update`, so new runs are refused before one can slip in (the EXAMPLE-VM guard's lesson without a second check). Running runs get the 30-minute cap; parked runs are not waited for. The drain ends with `bye: updating`, then `switch?`. If the launcher refuses, the coordinator appends `environment.update-failed` (stage `switch`) before closing and the launcher restarts the same version.
- **Settle**: once a start passes the gate, as the wire opens, the coordinator settles the latest `environment.update-started` in two parts, each idempotent on its own. The outcome, when that update has none yet: running its target, it appends `environment.updated {fromVersion, toVersion, updateId}`; otherwise `environment.update-failed {updateId, fromVersion, toVersion, stage, reason, rolledBack}` with the stage (`trial` or `crash-loop`) and reason the outcome record gives, or `unknown` with none (at stage `switch`, not rolled back: only a rollback writes a record, #344), and deletes the record. The runs, whatever the outcome and whoever recorded it (a refused switch appends its own `switch` failure): every run the update cut that has no `run.update-interrupted` yet gets one, below. So a power loss after the commit, or after a failure the coordinator recorded itself, settles at the next start, and continuation follows whichever version runs: the runs were cut either way.
- **Managed outside** (a container with no launcher, #112): the same plan, but the coordinator never drains on its own or sends `switch?`; a pending update reads `ready` when it would drain and waits for the host-side updater's `updates.begin`. That update's drain does not end the process by itself, since the container's restart policy would bring the old version straight back: it ends at the SIGTERM of the updater's stop. With no stop five minutes after the drain has finished waiting, the coordinator appends `environment.update-failed` (stage `switch`) and exits, and the restart policy brings the same version back.

### Trial, commit, rollback and the watch

- On `switch?` the launcher writes the pending record, answers `switching` and waits for the child to exit (killing it at the drain cap plus a minute), then snapshots the database's main, WAL and shm files once per update id through a staging folder and a rename, never overwriting a completed snapshot (T3). It refuses `disk` below the database's size plus 256 MiB free.
- The target starts as a trial: migrations, projectors, the recovery sweep, the bind, then `prepared` within 120 seconds of spawn (ADR 0007). The launcher commits durably (active and previous swapped, pending cleared, a watch of ten minutes) and answers `committed`.
- **Trial failure** (an exit, the deadline, `prepared` for another version): kill, write the restore marker (exclusive create, fsync), copy the snapshot back (removing a sidecar it lacked), fsync, write the outcome record, clear the marker, restart the old version, whose settle reports it.
- **The watch**: three unexpected exits within ten minutes of the commit trigger the same restore (`crash-loop`). Writes since the commit are lost; files outside SQLite (workspaces, the attachment stage, account directories, the vault) are outside the rollback, T3's boundary. At the watch's end the snapshot is discarded, versions pruned and the handover considered.
- **A launcher restarted mid-update** finishes a marked restore before starting anything and treats a pending record with no commit as a failed trial.

### Interrupted runs and parked prompts

- The runs an update cut are those ended `drained` after its `environment.update-started` and before the next start (a later drain's runs are not the update's, #345), parked runs included, since the drain ends them `drained` as it closes (claude-adapter spec). The settle appends one `run.update-interrupted {runId, updateId, toVersion, outcome, reason, continuationRunId}` to each one's session, a transcript event, not `list`-flagged:
  - `waiting-on-prompt`: a prompt of the session is still parked; a person's answer to it resumes the session at once, as the permissions spec's TTL answer does (decided by David on 2026-09-28, #345). Continuation never answers a prompt.
  - `next-message` with a reason: `no-resume` (no `resume` capability or no linked provider session), `account` (another account, or signed out), `mode` (the mode resolved now differs), `workspace` (gone), `deleted`, or `completions` (the caller got 503 as the drain cut it, and owns the retry).
  - `continued`: one run as `system:updates`, with a new origin, `update`, under the cut run's policy and model read from the log under the ceiling it resolved, as the permissions spec's run of the queue after a restart, resuming the linked provider session (Codex's continuation, under ADR 0007's same account, mode and workspace). Its prompt is a message the environment sends, shown in the transcript: "<environment> was updated to <version> while you were working and your turn was cut off. Check the current state before repeating anything that may already have finished, then continue." The session's queued messages follow. A firing continues like any run.
- The transcript snapshot and client projection keep the mark as an `update-interrupted` item at its sequence, with the outcome, reason and continuation run. Message items keep the event actor as `sender`, so the continuation is drawn as the environment's message. The terminal and GUI transcript specs define their shared outcome lines and sender labels (#452).
- After a rollback past a commit the restored log never saw the continuation, so the restored version continues again; the lost turn's file changes may remain, which "check the current state" covers.

### Containers: the host-side updater

- `host-updater.sh`, POSIX shell, runs every five minutes from cron or a systemd timer under one `flock` (the EXAMPLE-VM cadence), logs one line per state change, runs an optional `AGENT_HARNESS_NOTIFY_COMMAND` on each outcome, and stops with `AGENT_HARNESS_UPDATER=0`. Channel, pin and auto-update stay the environment's settings, so the card governs containers too.
- **A tick**: `docker compose exec` runs `update status --json --host-updater` in the container, whose call the environment remembers as the updater's last poll. On a `ready` pending update the updater pulls the target by reference and digest and checks the digest against the manifest, so a failed pull leaves the container untouched. `update begin` calls `updates.begin`, refused if no longer ready, else appending `environment.update-started` and draining; `docker compose stop` joins the drain and waits out the 31-minute `stop_grace_period` #141's compose file already sets (Docker's own default would kill at ten seconds), and the stopped container stays stopped. A one-off `docker compose run --rm` of `update snapshot` on the old image then snapshots the stopped volume (refused while an environment holds the database). The updater writes the target reference into the compose env file, keeping the old one as previous, runs `up -d`, waits 120 seconds for the health URL to say `ready` at the target, and watches ten minutes: three restarts, or two minutes not ready, is a crash loop.
- **Rollback**: stop, `update restore` with the stage and reason on the previous image (restoring the snapshot, writing the outcome record), put the reference back, `up -d`, check health; the old version's settle reports it. After a good watch `update discard` removes the snapshot and images older than the previous go.
- **A tick cut short** (a reboot, a kill) is finished by the next one, as a launcher restarted mid-update finishes its own: from just before `update begin` to the update's outcome the updater keeps a record of the update in flight beside its lock, with the step reached. A tick that finds it starts the old container again as it was until the snapshot is taken (`abandoned`), rolls back as a failed trial for the reason `interrupted` until the target said ready, and after that resumes the watch to its deadline, then discards and prunes or rolls back a crash loop.
- The published `compose.yaml` is #141's file, its 31-minute stop grace kept, with the image defaulting to that release's reference and a header naming the host-side updater's documentation and its `docker login` (ADR 0025). It passes `AGENT_HARNESS_NAME` and `AGENT_HARNESS_CHANNEL` into the container from compose's own variables, which `serve` reads as a new environment's name and channel at the start that creates it, and a later start leaves as they are (#846; the Set up spec's #846 notes). A declared container that has never exchanged a pairing prints `pair`'s link, QR and code to its log at each start until the first exchange, how it pairs from its own log output (ADR 0025).

### The desktop moves with its local environment

- The desktop holds no Forgejo token. `updates.desktop.stage` makes the local environment resolve the desktop artefact for the platform and format the shell reports, from the release it targets (its pin, else the channel's newest), download and verify it into its data directory, and answer path, version and SHA-256. The channel is the local environment's by construction (ADR 0007).
- The desktop checks at launch and hourly, stages a newer build in the background, shows "Restart to update" and applies it on that click or the next quit through `update.apply`, each platform its own way: a macOS bundle swap by rename with rollback, a silent Windows NSIS hand-over, an Arch `pacman -U` through `pkexec` (the package depends on `polkit`, which provides it; when the install fails, for `pkexec` missing, no polkit authentication agent running or the authentication refused, the failure carries the command that installs the staged package by hand, `sudo pacman -U <path>`, #1692); an AppImage, a `.deb` or a read-only bundle is `unsupported` and points at the release page. Temporary folders go through the runtime's file calls, never a shelled `rm`; a cleanup failure never reads as an unreachable feed; and the tests drive each platform's path with the platform injected, never skipped by the runner's own (the updater-bin-rm write-up, Windows).
- A desktop starting with a bundled server artefact newer than its local environment calls `updates.apply` with that version and path: automatically when auto-update is effective, under the idle rules, else as the card's offer. The environment preflights it and hands it to the launcher, no download; a local session's path is trusted as the bootstrap grant is.
- The local window survives the bundled environment's restart even if the new process rejects its earlier local session. After an `updating` or `draining` close, the runtime exchanges the local bootstrap grant once when the first handshake is refused, then reconnects. A refusal of that fresh session stays blocked for explicit retry; paired credentials and an explicit revocation of an open local session keep their ordinary rules (client-runtime spec, #1600).
- The shell members left here: `update` becomes `current()` (version, platform, arch, the installable format or null) and `apply(staged)`, replacing the stub's `check` and `install`; `installer` becomes `bundledServer()` (version and path). Installing the local service stays `service.install` (ADR 0001).

### Settings, methods, notices and flags

- **Settings**, written by the Your machines step in its `environments.machines` row (ADR 0027), only through `updates.settings.set`: `updates.autoUpdate` (preset on); `updates.channel` (`stable` or `beta`, preset `stable`); `updates.pinnedVersion` (a version without the `v`, or null; refused when the release or this platform's artefact is missing or by the schema rule; while set, auto-update is off, and unpinning returns to the switch); `updates.idleWindowMinutes` (1 to 120, preset 10, read by #112's idle computation for both the quiet window and the parked-prompt bound, which the glossary's Idle calls the idle window); `updates.deferralCapHours` (1 to 168, preset 24, no "never", ticket 21). The drain cap stays 30 minutes.
- **Methods**, one scope each, commands with a `commandId`:
  - `updates.status` (`read`, query; `hostUpdater: true` marks the host-side updater's poll): current version, protocol and bundled Claude Code version; the manager (`launcher` with its version, `outside` with the last host-updater poll, or `none`); the channel's newest; the last check; the pending update, its state and what it waits on; `blocked`; the last outcome; installed versions.
  - `updates.check` (`read`, query): a check, then the same document.
  - `updates.apply` (`admin`, command): optional version, optional artefact path (an archive, or the folder one is unpacked in; local sessions only), `when` `idle` (Update now, a newer client's version) or `now` (Drain and update now); answers the update id and target; errors `not_found` and `conflict` (`pinned`, `current`, `schema`, `launcher`, `in_progress`, `no_release_access`). In a container it makes a pending update for the host-side updater.
  - `updates.cancel` (`admin`, command) withdraws a pending update not yet draining; a channel- or pin-sourced one also withdraws when the settings stop calling for it; both append `environment.update-cancelled`.
  - `updates.settings.set` (`admin`, command), appending `settings.updated`; `updates.begin` (`admin`, command), only when managed outside; `updates.desktop.stage` (`admin`, query), refused `forbidden` to any but a local client session.
- **Across a protocol gap**: `POST /api/update`, a stable HTTP route outside the wire like the pairing exchange, takes a client session token with `admin`, a version and, from a local session, an artefact path, and does what `updates.apply` does with `when: idle`. The runtime's `update-environment` action uses it when blocked `protocol-mismatch`, the method otherwise.
- **Notices** on the environment stream: `environment.update-pending`, `environment.update-started`, `environment.updated` (gaining `updateId`), `environment.update-failed`, `environment.update-cancelled`. The code puts the updated-to event here, a stream every client subscribes to, not on the session list ADR 0007 names; the code wins. The runtime raises one new notice, "<name> could not be updated to B (<stage>: <reason>). It is running A."; the rest change the card and About, and older clients already ignore unknown notices.
- **Also added**: the run origin `update`, the drain trigger `update`, the session event `run.update-interrupted`; `bye: updating` is said at last. The `self-update` flag is present under a launcher, or when managed outside with a host-updater poll in the last fifteen minutes; absent under a foreground `serve`, the manager field saying why.
- **CLI verbs**: `launch` and `preflight`; `update status`, `apply`, `settings`, `credential`, `begin`, `snapshot`, `restore` and `discard`, those that reach the environment exchanging the bootstrap grant for a local client session and revoking it after, as `pair` does. `service install` lays out the entry, state, shim and a launcher definition and takes `--name`; `service status` adds the active and launcher versions and a pending update.
- **Set up** (ADR 0025, ADR 0031): the Your machines entry writes the five keys and gains three state checks. `your-machines.updates`: auto-update effective or the channel's newest running, no drain past its cap, not `blocked`, not behind after a failure (action `update`). `your-machines.release-channel`: with auto-update on, a successful check within 24 hours (action `check-again`). `your-machines.host-updater`: in a container, a poll within the hour. Reachability, the name and the copy are Set up's.
- **About** (ADR 0026, ADR 0027): this workstream supplies the rows above Managed tools: the client's version; the picked environment's version, channel, auto-update and Update now; "Claude Code (bundled) x.y.z, updates with this environment". As with managed tools, no launch notice and no skip-this-version; a pin holds a version.

### macOS stored credentials across a desktop replacement (#1572)

A replacement signed with another identity cannot promise unattended access to the previous build's OS credential item. The update contract accepts either a retained read, or a refusal/deadline reported inside the product's 30-second access bound while the window stays responsive. Pending access explains that answering the macOS prompt keeps the stored credentials. Unavailable access explains that those credentials could not be read and offers Pair again for the previously paired environments; fresh OS-protected storage and the local grant keep the local environment usable. The stored-credential details and ciphertext preservation are owned by the GUI spec's Secrets decision.

The hosted update smoke replaces a differently signed fixture app whose earlier credential uses the synchronous format. It first locks its test Keychain and proves independent main/window responsiveness and desktop/helper exit while that specific read is still pending. It then unlocks before relaunch and reads normally, without rewriting item ACLs or answering an OS prompt automatically. Either retained access or bounded, explained recovery with the working repair action passes; both must prove fresh OS-protected write/readback, a real upgrade from the lower-stamped carried server, local readiness and the same environment identity. A hang, crash, missing message/action, failed fresh item or unavailable local environment fails. Stable Developer ID signing and notarisation are the human follow-up #1571; its acceptance includes the retained-read branch passing on the hosted runner.

### The install scripts

- `install.sh` (macOS, Linux) and `install.ps1` (Windows) are assets of every release. The card's copyable line fetches the script from its environment's own release with the token on stdin, passing `--channel` (that environment's) and `--name` when given. The script resolves the channel's newest at run time (`--version` pins), downloads, verifies and unpacks it into versions (`--prefix` goes: the launcher owns that directory), runs `service install --name` and `service start`, waits up to 60 seconds for the health URL to say ready, sets the channel with `update settings`, and hands its token over with `update credential --stdin`, which adds it as the forge account for the release origin through the forge workstream's add method unless one exists. It ends with the link, ASCII QR and code of `pair --preset own-client` on the tailnet address, or the Tailscale warning when only loopback is bound, then the path line.
- A re-run over a running service unpacks nothing into versions: it repairs the definition and entry, and changes the version only when `--version` asks, through `update apply`, which stages it as any update. Both scripts refuse root.
- The first launcher release needs one `service install` per native machine, since a phase-A service runs `serve` without a launcher (T3's v0.0.42 needed the same).

## Testing Decisions

- **A good test** asserts what is visible from outside (the wire, the discovery and health URLs, the launcher's channel, a script's calls and output, the files a verb leaves), never a table or a private structure.
- **Primary seam: the in-process environment** on a temporary data directory, loopback port 0, the scripted fake provider and the typed client over a real WebSocket, plus a **fake release source** (a loopback HTTP server on port 0 answering Forgejo's release API shape with manifests and assets, reached through a forge account for its origin) and a **scripted launcher channel** answering `install?`, `switch?` and `committed` as each test says. Under the injectable clock: channel choice by precedence; pins; no automatic downgrade; a failed version not retaken; stepping stones; the schema refusal; `since` kept across a target change and a restart; the cap at 23:59 and 24:00; a parked prompt past the window letting the update go and still present after a stop and start on the same directory; `bye: updating` then `switch?`; the settle both ways, with and without an outcome record; a refused `switch?` and a container stop that never comes, each marking and continuing the cut runs at the next start; every continuation outcome; `updates.begin` refused unless managed outside; `updates.desktop.stage` refused to a paired session; `POST /api/update`; the `self-update` flag; the host-side updater's last poll. Prior art: T3 Code's `buildAppUnderTest` and `withWsRpcClient` in `apps/server/src/server.test.ts` and its `selfUpdate.test.ts`.
- **Lower seam: the launcher** against a temporary data directory and a scripted child (a small Node program standing in for `serve` that sends `prepared`, exits or crashes on cue and answers queries), since supervision and file durability cannot be driven through the wire: commit; the trial deadline on an injectable timer; restore after a trial exit; a marked restore finished after the launcher is killed mid-restore; one snapshot per update id; the watch; the clean-drain restart; stop; pruning; the handover and the entry's fallback; invalid state. Prior art: T3 Code's `serviceLauncher.test.ts` and `pinnedRuntime.test.ts`; Codex's `daemon_update_recovery.rs`.
- **Scripts**: `install.sh` and `host-updater.sh` against fake `curl`, `docker`, `uname` and `id` on the path and a fake release, and `install.ps1` the same way under PowerShell: the calls in order, the digest check, rollback after a failed health wait, the container kept stopped between drain and recreate, the root refusal. - **Contracts**: one scope per new method; every `updates.*` key written by Your machines; the new notices, origin and trigger parse; the manifest round-trips through the schema export. **Client runtime**, against a scripted fake environment: the failure notice, and `update-environment` taking the HTTP route when blocked.
- **Manual**: new service-install checklist sections per platform on a real release pair (a self-update, a rollback forced by a release built to fail its gate, the handover) and the host-side updater on a real Docker host, never the shared agent box.

- **Chosen defaults not decided on a ticket, from the launcher (#337)**: the service state is `service-state.json`, `{activeVersion, previousVersion, launcherVersion, pendingUpdate, watchDeadline}` with null for none, the pending-update record `{updateId, fromVersion, toVersion}` and the watch deadline an ISO time; its versions are release versions (the contracts' `RELEASE_VERSION_PATTERN`, shared with the release schema), and a part it does not know is passed over. A version is `versions/<version>`, complete once `.complete` is in it, and runs as its own Node (`node/bin/node`, `node\node.exe` on Windows, as Node's archives lay it out) on `packages/cli/dist/main.js`, never through `bin/agent-harness`, so the IPC channel reaches the CLI on Windows too; the server artefacts build to that layout. `launch --data-dir <path> [--port <n>]` needs the data directory named (its default is the environment package's) and passes both to `serve`. The launcher's lines, `<ISO time> launcher: <step>`, go to its standard output, which the definition sends to the service log, and the child inherits it. A service state the launcher cannot use, or an active version not complete, starts nothing, and the launcher stays until it is stopped. A clean exit is code 0 from a child the launcher committed; anything else, a signal or an exit 0 before the commit included, is unexpected. The wait doubles over unexpected exits in a row and is 5 seconds again after a drained restart or a child that ran 5 minutes. A stop asks `drain?` each second until `draining` or the channel closes, since a child just committed answers queries only once its wire is open, and ends with SIGTERM a child not yet committed, which has served nothing. `install?` goes unanswered until #339.
- **Chosen defaults not decided on a ticket, from the switch (#340)**: an update's snapshot is `snapshots/<updateId>` in the data directory, copied into `snapshots/<updateId>.staging` first; `switch?` and the outcome record take only a version 4 UUID as the update id, since it names that folder. The room `disk` asks for is the size of the database's main, WAL and shm files plus 256 MiB, checked only when the update has no snapshot yet. The restore marker is `restore-marker.json`, holding the outcome record the restore will write, so a restore cut short is finished with its own stage and reason; it is created as a hard link of a temporary file already on disk, so it is whole or absent, and a second restore does not begin while one is marked. The launcher clears the pending-update record after the outcome record is written and before the marker is cleared. A child answered `switching` that has not exited 31 minutes later, and a trial that missed its deadline or said `prepared` for another version, are ended with SIGKILL. The outcome record's reasons for a trial: `exit`, `deadline`, `version`, `commit` (the commit could not be written, so `committed` was never answered), `snapshot` (it could not be taken, so the target never ran and nothing is restored) and `interrupted` (the launcher found the update pending at its start: restored when a snapshot exists, otherwise the target never ran). A stop during the switch or the trial ends the child and leaves the rollback to the next start. A `switch?` from a child not committed, or a second one while a switch is under way, is passed over in the service log and not answered. A marked restore that cannot be finished, or a rollback that fails, starts nothing, as an untrusted state does. The snapshot of a rolled-back update is kept until the next watch ends, which discards every snapshot (#341, #443). Since a second `switch?` under an update id reuses its snapshot, a failed retry under the same id would restore the database to before the first attempt, so the coordinator mints a new update id for a switch after a rollback (#443).
- **Chosen defaults not decided on a ticket, from #342**: `update settings` takes one flag per key (`--auto-update on|off`, `--channel stable|beta`, `--pinned-version <version|none>`, `--idle-window-minutes`, `--deferral-cap-hours`), checks each against its key's schema before it reaches the environment, and prints all five after; the `update` verbs take `pair`'s `--data-dir` and `--port`, and exit 1 with a sentence when no environment answers or it refuses. The bundled Claude Code's version is the bundled binary's `--version` (`2.1.283 (Claude Code)` on SDK 0.3.283, with no sign-in and nothing written to an empty home), read once, on the first `updates.status`; the SDK's per-platform package carries the SDK's version, not Claude Code's. The run registry keeps an ended run for the longest idle window the setting can name, 120 minutes, so a window raised after a run ended still counts it. A launcher that no longer answers `versions?` reads as the manager `none`, saying so.
- **Chosen defaults not decided on a ticket, from #338**: the launcher version file is `launcher-version`, the version and a line feed. The launcher entry is `launcher-entry.sh`, which the launchd and systemd definitions run with `/bin/sh` so it needs no execute bit, and `launcher-entry.cmd` on Windows, which the logon task runs as `conhost.exe --headless cmd.exe /d /c .\launcher-entry.cmd` in the data directory, its working directory (conhost re-quotes the rest of its command line as the C runtime reads it, quoting a path only for a space, and cmd would read an `&` or `^` in a bare path or strip the quotes of a quoted one, so no command line carries the path). The entry runs the named version's own Node on its CLI as `launch --data-dir <path> --port <n> [--name <name>]` (`launch` takes `--name` and passes it to each `serve`, which names only a new environment with it); with no launcher version file, a line that is not a version, or a version not complete, it says so in the service log and exits 0, which every definition leaves stopped, rather than failing every few seconds. The Windows entry starts the launcher again 5 seconds after any non-zero exit, a handover's relaunch code included (the line that runs it ends `&& exit /b 0 || goto restart`, since cmd reads a batch file by offset and install may replace the entry while the launcher runs), since Task Scheduler's restart-on-failure restarts a task only when it could not start it (Microsoft's forum answer; the schema says only "fails for any reason"), and appends the launcher's output to `logs/service.log`, so Windows has a service log too. The systemd unit sends a stop's SIGTERM to the launcher alone (`KillMode=mixed`), which drains its child, and kills what is left at `TimeoutStopSec=31min`; launchd's `ExitTimeOut` is 1860. The shim is `bin/agent-harness` (`bin\agent-harness.cmd`), reading the active version from the service state's JSON at each run; install prints `export PATH="<bin>:$PATH"` for a shell profile, or on Windows a PowerShell line that puts the folder first on the user Path through the registry, read unexpanded and written back as an expandable string, since .NET's `SetEnvironmentVariable` would write the expanded Path back as a plain one. Install takes a launcher to be running when the service manager says the service runs and the service record names the entry it runs (`launcherEntry`, absent from a record written before the launcher): a service from before the launcher is laid out and, when running, restarted onto the launcher, as #113's install restarts a running service; over a running launcher install rewrites its own files (the definition, the entry, the shim and the record) and restarts nothing, so they take effect at the next start. The version install names is its folder's name when it runs from the versions directory, which must be complete, else its CLI package's version, copied in through a `.<version>.<uuid>.partial` folder, files and folders synced under the platform rule in "Version staging and power loss", renamed into place, the sentinel written durably last; a complete copy already there is taken as it is. A service state already there keeps its pending-update record, which the launcher rolls back at its next start, its active version becomes the previous one, and its watch deadline is cleared; one that cannot be used is replaced. A refused install puts back every file it wrote. `service status` prints `Active version`, `Launcher version` and `Pending update` from the state, or `Versions: unknown (<why>)` for an installed service with no state it can use, and notes a service from before the launcher; `--json` adds `activeVersion`, `launcherVersion`, `pendingUpdate` and `serviceStateProblem`. Uninstall keeps the versions, the service state and the launcher version file. **Verified** (#338, from sources; the checklist confirms on each platform): systemd honours a user unit's `TimeoutStopSec` for a stop of the unit, but a logout with lingering off, or a shutdown, stops the whole user manager within `user@.service`'s own `TimeoutStopSec`, 120 seconds by default (systemd's default user timeout of 90 seconds times four thirds), so a drain is cut there; launchd is reported to clamp a gui-domain agent's `ExitTimeOut` to 60 seconds (215, 90 and 60 all read back as 60, 30 as 30, measured by the hermes-agent project on macOS 26.6.1), so a stop through launchd cuts a drain at a minute (#461 asks for the measurement on David's Mac and his call). Either way a cut run is ended `restart` by the recovery sweep, as a shutdown's is. Updates never stop the service: the launcher switches versions itself.
- **A terminal running a command holds an update.** Decided by David on 2026-09-28 (#343): a terminal whose foreground process is still running (a build, a watcher) counts as busy for the idle wait, like a run, so the update waits for it up to the deferral cap; a terminal at an idle shell prompt holds nothing and starts again after the update. The idle report says it as the busy reason `terminal-running`, which outranks the windows and yields to a run starting or running. It is read from the terminal's foreground process group (`/proc` on Linux, `ps` on macOS): a command the shell starts leads a group of its own, while a shell at its prompt holds the foreground itself. Windows keeps no foreground group, so there a terminal holds nothing. The drain does not wait for terminals: past the cap they end with the restart.
- **The start counts as activity.** Decided by David on 2026-10-01 (#445): the environment's start counts as activity for the idle window, a `recent-activity` hold from `environment.started` as a run's start holds one, so an update read back from the log as pending waits a full idle window after a start instead of draining at the coordinator's first minute. The run registry is in memory and starts empty, while the runs the stop before cut are ended in the log, so with no hold a restart mid-work read idle at once. The hold runs from the instant this start appended its `environment.started` (an event of that type appended later is not a start), and `environment.status`, the launcher's `idle?` and `updates.status`'s `waitsOn` all read it.

The coordinator reads the activity right after `updates.apply` makes an update pending, on every run-registry change, at each minute from the start and at `deferUntil`, so an update read back from the log is still pending just after a start. `environment.update-started` and its drain's `environment.draining` name `system:updates` for `idle` and `cap`, and the asking client session with its command id for `requested`. An update's drain that the environment's own close cut short ends with `bye: draining` and no `switch?`; a drain another trigger began holds a pending update to the next start, and `updates.apply` meanwhile is `unavailable` (`draining`). `updates.status` reads `staging` while `updates.apply` unpacks and installs, when nothing else is pending. `update apply` takes `--version <version>`, `--path <artefact>` (with `--version`, read from the working directory) and `--now`; a `bye: updating` or `bye: draining` after the verb's call settles the verb with its answer, and leaves its local client session to be revoked an hour after its connection closed, as a terminal UI's is.

With no outcome record of the update, the failure is stage `switch`, reason `unknown`, `rolledBack: false`: the launcher writes a record at every rollback (a restore writes it under the restore marker, and a launcher that cannot write it starts nothing), so with none the switch never came, as when a stop or a power loss cut the update's drain, and the version it went from ran on. A record naming another update is not that update's and is not read for it; a file that is not an outcome record is read as none and said on standard error. Either way the record is deleted once the latest update has its outcome, whatever it names, since only the latest update is ever settled; a failed append leaves the record for the next start, and neither failure stops the start. `updates.status` reads its `lastOutcome` and `failedVersions` from the log at each call: the last outcome is the newest `environment.updated` or `environment.update-failed` (`at` its time); a version is marked failed by a failure at stage `trial` or `crash-loop` only, which the target rule's "failed its trial or watch" names, not by a refused switch or one that never came, and stays marked until an update to it takes (Update now retrying it). `environment.updated`'s payload is the contracts' `EnvironmentUpdatedPayload`, exported beside the other update events. On the client, `environment.update-failed` raises the notice kind `update-failed` with no action, and every update notice is in `QUERY_REFRESH_NOTICES` for `updates.status`.
- **Chosen defaults not decided on a ticket, from #345**: the runs an update cut are those ended `drained` after its `environment.update-started` and before the first `environment.started` after it, so a later drain's runs are never taken for the update's; each is settled in a transaction of its own, its `run.update-interrupted` correlated to it and a continuation's start appended with it, all as `system:updates`, and a run whose settling fails is left for the next start, which settles it while no other update has begun (only the latest update is ever settled, its runs as its outcome, #344, since a run an older update cut may be long past what its session has done since). The outcome is decided in this order: `deleted`; `completions`; `waiting-on-prompt` for any prompt of the session still parked; `account` when the session's account now (its own, else the default) is another than the run's, is not on the environment, is signed out or no longer offers the run's model; `no-resume` when that account's adapter lacks `resume` or the cut run itself linked no provider session (resuming an earlier run's would lose the cut run's message); `workspace` when the session's workspace is marked missing, the availability watcher having looked at it just before (#691); `mode` when the policy resolved now differs in its effective mode from the cut run's (resolved for the actor the cut run's policy names, under the ceiling it was resolved under, in the session's mode as it is now and under the queued senders' ceilings, as the run of the queue is), or when the run has no recorded policy. The continuation keeps the cut run's actor kind on its policy (a routine's stays unattended, with its name) and its model, and its effort while the model still takes it; containment is resolved afresh; it resumes the provider session its runs last linked, as any next run does. Its message is a `message.sent` appended as `system:updates` with the ceiling the continuation resolved under, and the decider reads it before the queued messages (`messageFirst`). When the update did not take (the start runs another version than its target: a refused switch, a rollback, a switch that never came) the message does not say it was updated: "<environment> was restarted for an update to <version>, which did not take, while you were working and your turn was cut off. Check the current state before repeating anything that may already have finished, then continue." A person's answer to a prompt of a session whose latest run is marked `waiting-on-prompt` starts the session's next run once it commits, through the TTL's continuation (David's decision, above; the permissions spec's notes). A completions caller the drain cut is answered 503 with the code `closing`, not `drained`: the surface answers its open requests as the environment closes, before the host ends the run (#138's order). **Verified**: the run of the queue after a restart (`AdapterHost.continueSession`, #131) reads the run before it from the log (the actor its policy names under the ceiling it was resolved under, and its model), appends the start as the host's own actor, `system:adapter-host`, and starts with no message of its own, only the answers kept for the session and its queue; the policy's actor kinds have no system kind. So the continuation reuses its parts rather than the path: the actor read from the policy (`actorOfPolicy`, now shared with the host), the host's `startFacts` and `launch`, and the decider's `decideStart`, which takes a message; the system actor is the events' (`system:updates`), not the policy's.
- **Chosen defaults not decided on a ticket, from #691**: the settle still finishes before the wire opens, and the start now waits for it. - From the desktop idle-wait control (#1487): an accepted update across a protocol gap remains `updating` in the connection machine, while its projection distinguishes an idle hold from the restart. For a local environment, the desktop reads the pending update through the installed active version's own CLI (`update status --json`), every five seconds until the connection leaves the update wait. The window shows its reason, idle deadline and deferral cap in the sidebar, empty workspace and machine card. During a hold on recent activity, a parked prompt or nothing, Update immediately rechecks the hold and runs that CLI's `update apply --now`; a running run or terminal is never advanced by this control. Both verbs resolve the installed version afresh from the service state and use its Node, so the desktop's protocol need not match it. A progress read failure is visible and withdraws the immediate offer. Without that desktop capability, the client says the update was requested and waits for idle; discovery starting, draining or becoming unreachable switches the words to restarting. The environment's startup still counts as activity; the idle policy is unchanged.
