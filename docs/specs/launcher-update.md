# Spec: Launcher and auto-update

Milestone 1 (Switch-over), phase B (daily use). Written 2026-09-28 from map ticket 86 of `david/agent-harness`. Implements ADR 0007 whole (idle, the deferral cap and drain, parked prompts across the restart, continuation, channels and pin, the launcher, trial, rollback, the crash-loop watch, the desktop and host-side updaters), ADR 0017 (phase B, the placeholder), ADR 0025 (the install script's asset, variants, service install and health wait; the card's update controls) and ADR 0026 (About's top rows, no launch notice), citing ADR 0001, 0012, 0016, 0020, 0027 and 0031 and the Resolutions of tickets 21, 47 and 52. Builds on main at 863ab8f without re-deciding it: the environment spec (#112's lifecycle, #113's service verbs and script), the claude-adapter spec (`drained`, the recovery sweep), the permissions spec (parked prompts across a restart, the run of the queue after one), the client-runtime spec (`bye: updating`, the `update-environment` action, the shell's `update` and `installer`) and #141's image and compose file. Peers: the server-self-update research (T3 Code's launcher, Codex's continuation, the MNL tracker), and the memories: the server-auto-update write-up, the release-and-update-feed write-up, the updater-bin-rm write-up (Windows), the server-update-wipes-apt-packages write-up, `forgejo-repos-all-private-2026-09-23` and `forgejo-actions-runner-pool`.

## Problem Statement

The server never updated itself. David updated it by hand until a host-side tracker on MNL took over, and that tracker waits for a moment with no run starting, running or awaiting permission and never forces. The server parks a permission prompt forever, so one unanswered question holds an update indefinitely. When an update does run, the server exits within ten seconds and every live run is lost ("The server no longer has this run"). Nothing checks health after the recreate, nothing rolls back, nothing tells the clients. Before the tracker the server fell silently behind the desktop and attachments broke. Outside tooling hurt too: the Unraid updater left `hermes` stuck in Created, and an image update wiped every `apt` package on the agent box. The desktop updater once shelled out to a POSIX `rm` on Windows, so three releases could not update themselves.

Phase A built what an update needs and none of the update. The environment reports idle, busy and draining and keeps parked prompts as events, but the service runs `serve` with nothing owning versions, no release publishes an artefact, and #141 left publishing the image here.

## Solution

Every environment keeps itself current, on by default, without losing work. A native install runs a small stable launcher that owns the installed versions. The environment checks its channel on the project's Forgejo hourly, stages a new release in the background and waits for idle: nothing starting or running, nothing started or ended for ten minutes, a parked prompt counting ten minutes only. Busy work defers it at most 24 hours; then the environment drains, giving running runs up to 30 minutes. The new version is a trial that must pass its startup gate in 120 seconds, or the launcher restores the database snapshot and restarts the old version; three crashes in the first ten minutes do the same. After the restart parked prompts are where they were, and a run the drain cut continues with one turn when its provider can resume it.

Clients see "updated from A to B" or "could not be updated, back on A" with the reason. The Your machines card and About show version, channel, auto-update and Update now; a newer client offers to update the environment to its version. The desktop takes its update from its local environment and hands it its bundled server artefact, so both move together. A container never updates itself: a published host-side updater follows the environment's plan, recreates, checks health and rolls the image back on failure. One Forgejo release carries it all: artefacts, a manifest, desktop builds, install scripts, the compose file, the host-side updater and a registry image.

## Implementation Decisions

### The pieces

The **release** is what one version publishes on the project's Forgejo. The **launcher**, the native service's process, owns the installed versions, the service state and the database snapshots, and runs the chosen version's `serve` as its child. The **update coordinator**, a module of the environment, holds the policy: channel, staging, the moment, the drain and the settle after the restart; it knows runs, the launcher never does. The **host-side updater** carries out the coordinator's plan for a container. The **desktop updater** is the shell's `update` member, fed by the local environment.

### The release

- Tag `v<semver>` on `david/agent-harness` at `git.systemtech.dev:5526`, flagged prerelease exactly when the version has a prerelease part; drafts are never read. A Forgejo Actions workflow on the tag push re-runs typecheck, lint and test, builds everything, uploads to a draft and publishes last, so no reader sees a partial release.
- **Server artefacts**: `agent-harness-<os>-<arch>` for `linux-x64` and `darwin-arm64` (gzipped tar) and `win32-x64` (zip), #113's names, each self-contained: a pinned Node runtime, the packages with this platform's production dependencies (`node-pty`, the SDK's Claude Code binary) and `bin/agent-harness`. No Node is needed on the machine.
- **Also published**: the GUI build's desktop artefacts (macOS zip, Windows NSIS setup, Arch `.pacman`); `install.sh`, `install.ps1`, `compose.yaml`, `host-updater.sh`; the contracts' JSON Schema export; a `.sha256` sidecar per asset (#113's format); and the **release manifest**, `release.json`: version, protocol version, launcher protocol, database schema version (the last migration's number), bundled Claude Code version, each asset's name, platform, kind, size and SHA-256, and the image's reference and digest. Its schema lives in the contracts package.
- **Image**: built from the Dockerfile on the `build` runner with `david/ci`'s image template, pushed to Forgejo's registry as `david/agent-harness`, tagged with the exact version only. No `latest` or channel tag (`hermes:latest` is rebuilt on every push to main; rollback needs an exact reference). linux/amd64 only.
- **Integrity** is SHA-256 from the same private release over TLS, T3's level; signing is fog until releases are public.
- **The release source** (origin and repository) is compiled into each build; a move to GitHub changes it in one release (ADR 0007). Every Forgejo repository is private, so every read authenticates: the environment through the forge service with the forge account for the release origin and its read-releases capability (ADR 0012, ADR 0020), the scripts with `AGENT_HARNESS_TOKEN` on stdin, registry pulls after `docker login` with a read-package token.

### Versions and the launcher

- **In the data directory**: the versions directory (complete only with a sentinel written last, T3), a staging area, the service state (active, previous and launcher versions, the pending-update record, the watch deadline), snapshots by update id, the restore marker, the outcome record, a stable **launcher entry** script the service definition runs, which starts the launcher of the version its one-line **launcher version file** names, and a `bin` shim running the active version (the install prints the path line and edits no profile). State writes are temp file, fsync, rename, directory fsync; invalid state stops the launcher starting anything.
- **Writers**: while the service runs, the launcher is the only writer of the versions directory, the state and the launcher version file. `service install` writes them only when no launcher runs (a first install, or a stopped service); on a running service it rewrites just the definition and the entry. The entry writes only its start counter, and the launcher version file when it falls back. Of these files the environment writes only the staging area, and deletes the outcome record once settled.
- **The launcher** is the `launch` verb, on Node built-ins with no dependency on the environment package. It spawns the active version's `serve` with an IPC channel and restarts a child that exits unexpectedly after 5 seconds, doubling to 5 minutes. A child that exits cleanly after a drain the launcher did not ask for (`environment.drain`, a signal) restarts at once: under a launcher a drain is a graceful restart. The launcher exits only when the service manager stops it, after draining the child. The service definition gains a 31-minute stop timeout where the platform has one (systemd, launchd); a shutdown still cuts runs, which the recovery sweep ends as `restart`.
- **The launcher channel** adds to #112's pairs; unknown messages are ignored both ways. `prepared {version}` is now answered `committed`, and the child waits for it before appending `environment.started` and opening the wire: T3's command gate, the one change to #112's handshake, so a trial answers no command before commit (without a launcher, no wait). `install? {version, staged}` is answered `installed` or `refused` (`launcher-protocol`, `incomplete`, `preflight`, `disk`, `io`). `switch? {updateId, version}` is answered `switching` or `refused`, after which the child closes, the channel last (#112). `versions?` lists the installed versions.
- **Preflight**: `install?` runs the staged version's `preflight` verb (30 seconds), which prints its version, protocol, launcher protocol and schema and loads SQLite, `node-pty` and the Claude binary's `--version`. Only a passing version is renamed into versions.
- **Launcher protocol**: one integer. Each release's child runs under the previous release's launcher, so a breaking launcher change ships across two releases; `install?` refuses a higher requirement.
- **Handover**: once the active version has held through its watch and carries a different launcher build, the launcher asks `idle?` every ten minutes; at the first idle it writes the active version into the launcher version file and exits with a relaunch code, and the service manager's restart-on-failure starts the new launcher on the same version. The entry counts starts of a handed-over launcher until it confirms its child passed the gate; at the third unconfirmed start it names the previous version again, and the old launcher records the handover failed.
- **Kept**: the active version, the two before it, the launcher's own and any staged or pending one; the rest are pruned when a watch ends.

### The update coordinator

- **States**: `current`, `staging`, `waiting`, `draining`, `switching`, `blocked` with a reason.
- **Reading the channel**: the newest 50 non-draft releases through the forge service, ordered by semver precedence, unparseable tags ignored; `stable` takes the newest without a prerelease part, `beta` the newest of all (beta means earlier, not a separate product); then that release's manifest. First check 2 minutes after start, then hourly, and on `updates.check` (at most once a minute; a repeat answers the last result). A failed check is state, never a notice.
- **The target**: auto-update is effective when `updates.autoUpdate` is on and nothing is pinned. A pin targets its exact version on any channel; otherwise the channel's newest, when newer. Nothing moves backwards on its own (a beta environment switched to stable waits until stable passes it). A version that failed its trial or watch is never retaken automatically; the next newer one is, and Update now can retry it.
- **Refused before downloading**: a version whose database schema is below the database's (`schema`; the event log refuses a newer database). A version needing a newer launcher is reached by **stepping stones**, the newest release the running launcher hosts, then the handover, then onward; with none the coordinator is `blocked` (`launcher`) and names `service install` from the target.
- **Staging** downloads the platform artefact through the forge service, checks size and SHA-256 against the manifest, unpacks it and sends `install?`; a failure retries at the next check. Staging ignores idle.
- **Waiting** appends `environment.update-pending {updateId, toVersion, source, since, deferUntil}`, `source` being `channel`, `pin`, `request` or `desktop`. `since` is when an update first became pending and carries over, read back from the log, when a newer release replaces the target (with a new update id) and across restarts, so frequent releases never reset the clock; `deferUntil` is `since` plus the cap. On every run-registry change and every minute the coordinator drains when idle, past `deferUntil`, or asked by `updates.apply` with `when: now`.
- **Draining**: in the tick that read the activity, the coordinator appends `environment.update-started {updateId, fromVersion, toVersion, cause}` (`idle`, `cap`, `requested`) and starts #112's drain with a new trigger, `update`, so new runs are refused before one can slip in (the MNL guard's lesson without a second check). Running runs get the 30-minute cap; parked runs are not waited for. The drain ends with `bye: updating`, then `switch?`. If the launcher refuses, the coordinator appends `environment.update-failed` (stage `switch`) before closing and the launcher restarts the same version.
- **Settle**: once a start passes the gate, as the wire opens, the coordinator settles the latest `environment.update-started` in two parts, each idempotent on its own. The outcome, when that update has none yet: running its target, it appends `environment.updated {fromVersion, toVersion, updateId}`; otherwise `environment.update-failed {updateId, fromVersion, toVersion, stage, reason, rolledBack}` with the stage (`trial` or `crash-loop`) and reason the outcome record gives, or `unknown` with none (at stage `switch`, not rolled back: only a rollback writes a record, #344), and deletes the record. The runs, whatever the outcome and whoever recorded it (a refused switch appends its own `switch` failure): every run the update cut that has no `run.update-interrupted` yet gets one, below. So a power loss after the commit, or after a failure the coordinator recorded itself, settles at the next start, and continuation follows whichever version runs: the runs were cut either way.
- **Managed outside** (a container with no launcher, #112): the same plan, but the coordinator never drains on its own or sends `switch?`; a pending update reads `ready` when it would drain and waits for the host-side updater's `updates.begin`. That update's drain does not end the process by itself, since the container's restart policy would bring the old version straight back: it ends at the SIGTERM of the updater's stop. With no stop five minutes after the drain has finished waiting, the coordinator appends `environment.update-failed` (stage `switch`) and exits, and the restart policy brings the same version back.

### Trial, commit, rollback and the watch

- On `switch?` the launcher writes the pending record, answers `switching` and waits for the child to exit (killing it at the drain cap plus a minute), then snapshots the database's main, WAL and shm files once per update id through a staging folder and a rename, never overwriting a completed snapshot (T3). It refuses `disk` below the database's size plus 256 MiB free.
- The target starts as a trial: migrations, projectors, the recovery sweep, the bind, then `prepared` within 120 seconds of spawn (ADR 0007). The launcher commits durably (active and previous swapped, pending cleared, a watch of ten minutes) and answers `committed`.
- **Trial failure** (an exit, the deadline, `prepared` for another version): kill, write the restore marker (exclusive create, fsync), copy the snapshot back (removing a sidecar it lacked), fsync, write the outcome record, clear the marker, restart the old version, whose settle reports it.
- **The watch**: three unexpected exits within ten minutes of the commit trigger the same restore (`crash-loop`). Writes since the commit are lost; files outside SQLite (workspaces, the attachment stage, account directories, the vault) are outside the rollback, T3's boundary. At the watch's end the snapshot is discarded, versions pruned and the handover considered.
- **A launcher restarted mid-update** finishes a marked restore before starting anything and treats a pending record with no commit as a failed trial.

### Interrupted runs and parked prompts

- The runs an update cut are those ended `drained` after its `environment.update-started` and before the next start (a later drain's runs are not the update's, #345), parked runs included, since the drain ends them `drained` as it closes (claude-adapter spec). The settle appends one `run.update-interrupted {runId, updateId, toVersion, outcome, reason, continuationRunId}` to each one's session, a transcript event, not `list`-flagged:
  - `waiting-on-prompt`: a prompt of the session is still parked; a person's answer to it resumes the session at once, as the permissions spec's TTL answer does (decided by David on 2026-09-28, #345). Continuation never answers a prompt.
  - `next-message` with a reason: `no-resume` (no `resume` capability or no linked provider session), `account` (another account, or signed out), `mode` (the mode resolved now differs), `workspace` (gone), `deleted`, or `completions` (the caller got 503 as the drain cut it, and owns the retry).
  - `continued`: one run as `system:updates`, with a new origin, `update`, under the cut run's policy and model read from the log under the ceiling it resolved, as the permissions spec's run of the queue after a restart, resuming the linked provider session (Codex's continuation, under ADR 0007's same account, mode and workspace). Its prompt is a message the environment sends, shown in the transcript: "<environment> was updated to <version> while you were working and your turn was cut off. Check the current state before repeating anything that may already have finished, then continue." The session's queued messages follow. A firing continues like any run.
- After a rollback past a commit the restored log never saw the continuation, so the restored version continues again; the lost turn's file changes may remain, which "check the current state" covers.

### Containers: the host-side updater

- `host-updater.sh`, POSIX shell, runs every five minutes from cron or a systemd timer under one `flock` (the MNL cadence), logs one line per state change, runs an optional `AGENT_HARNESS_NOTIFY_COMMAND` on each outcome, and stops with `AGENT_HARNESS_UPDATER=0`. Channel, pin and auto-update stay the environment's settings, so the card governs containers too.
- **A tick**: `docker compose exec` runs `update status --json --host-updater` in the container, whose call the environment remembers as the updater's last poll. On a `ready` pending update the updater pulls the target by reference and digest and checks the digest against the manifest, so a failed pull leaves the container untouched. `update begin` calls `updates.begin`, refused if no longer ready, else appending `environment.update-started` and draining; `docker compose stop` joins the drain and waits out the 31-minute `stop_grace_period` #141's compose file already sets (Docker's own default would kill at ten seconds), and the stopped container stays stopped. A one-off `docker compose run --rm` of `update snapshot` on the old image then snapshots the stopped volume (refused while an environment holds the database). The updater writes the target reference into the compose env file, keeping the old one as previous, runs `up -d`, waits 120 seconds for the health URL to say `ready` at the target, and watches ten minutes: three restarts, or two minutes not ready, is a crash loop.
- **Rollback**: stop, `update restore` with the stage and reason on the previous image (restoring the snapshot, writing the outcome record), put the reference back, `up -d`, check health; the old version's settle reports it. After a good watch `update discard` removes the snapshot and images older than the previous go.
- The published `compose.yaml` is #141's file, its 31-minute stop grace kept, with the image defaulting to that release's reference and a header naming the host-side updater's documentation and its `docker login` (ADR 0025). A declared container that has never exchanged a pairing prints `pair`'s link, QR and code to its log at each start until the first exchange, how it pairs from its own log output (ADR 0025).

### The desktop moves with its local environment

- The desktop holds no Forgejo token. `updates.desktop.stage` makes the local environment resolve the desktop artefact for the platform and format the shell reports, from the release it targets (its pin, else the channel's newest), download and verify it into its data directory, and answer path, version and SHA-256. The channel is the local environment's by construction (ADR 0007).
- The desktop checks at launch and hourly, stages a newer build in the background, shows "Restart to update" and applies it on that click or the next quit through `update.apply`, each platform its own way: a macOS bundle swap by rename with rollback, a silent Windows NSIS hand-over, an Arch `pacman -U` through `pkexec`; an AppImage, a `.deb` or a read-only bundle is `unsupported` and points at the release page. Temporary folders go through the runtime's file calls, never a shelled `rm`; a cleanup failure never reads as an unreachable feed; and the tests drive each platform's path with the platform injected, never skipped by the runner's own (the updater-bin-rm write-up, Windows).
- A desktop starting with a bundled server artefact newer than its local environment calls `updates.apply` with that version and path: automatically when auto-update is effective, under the idle rules, else as the card's offer. The environment preflights it and hands it to the launcher, no download; a local session's path is trusted as the bootstrap grant is.
- The shell members left here: `update` becomes `current()` (version, platform, arch, the installable format or null) and `apply(staged)`, replacing the stub's `check` and `install`; `installer` becomes `bundledServer()` (version and path). Installing the local service stays `service.install` (ADR 0001).

### Settings, methods, notices and flags

- **Settings**, written by the Your machines step in its `environments.machines` row (ADR 0027), only through `updates.settings.set`: `updates.autoUpdate` (preset on); `updates.channel` (`stable` or `beta`, preset `stable`); `updates.pinnedVersion` (a version without the `v`, or null; refused when the release or this platform's artefact is missing or by the schema rule; while set, auto-update is off, and unpinning returns to the switch); `updates.idleWindowMinutes` (1 to 120, preset 10, read by #112's idle computation for both the quiet window and the parked-prompt bound, which the glossary's Idle calls the idle window); `updates.deferralCapHours` (1 to 168, preset 24, no "never", ticket 21). The drain cap stays 30 minutes.
- **Methods**, one scope each, commands with a `commandId`:
  - `updates.status` (`read`, query; `hostUpdater: true` marks the host-side updater's poll): current version, protocol and bundled Claude Code version; the manager (`launcher` with its version, `outside` with the last host-updater poll, or `none`); the channel's newest; the last check; the pending update, its state and what it waits on; `blocked`; the last outcome; installed versions.
  - `updates.check` (`read`, query): a check, then the same document.
  - `updates.apply` (`admin`, command): optional version, optional artefact path (local sessions only), `when` `idle` (Update now, a newer client's version) or `now` (Drain and update now); answers the update id and target; errors `not_found` and `conflict` (`pinned`, `current`, `schema`, `launcher`, `in_progress`, `no_release_access`). In a container it makes a pending update for the host-side updater.
  - `updates.cancel` (`admin`, command) withdraws a pending update not yet draining; a channel-sourced one also withdraws when the settings stop calling for it; both append `environment.update-cancelled`.
  - `updates.settings.set` (`admin`, command), appending `settings.updated`; `updates.begin` (`admin`, command), only when managed outside; `updates.desktop.stage` (`admin`, query), refused `forbidden` to any but a local client session.
- **Across a protocol gap**: `POST /api/update`, a stable HTTP route outside the wire like the pairing exchange, takes a client session token with `admin`, a version and, from a local session, an artefact path, and does what `updates.apply` does with `when: idle`. The runtime's `update-environment` action uses it when blocked `protocol-mismatch`, the method otherwise.
- **Notices** on the environment stream: `environment.update-pending`, `environment.update-started`, `environment.updated` (gaining `updateId`), `environment.update-failed`, `environment.update-cancelled`. The code puts the updated-to event here, a stream every client subscribes to, not on the session list ADR 0007 names; the code wins. The runtime raises one new notice, "<name> could not be updated to B (<stage>: <reason>). It is running A."; the rest change the card and About, and older clients already ignore unknown notices.
- **Also added**: the run origin `update`, the drain trigger `update`, the session event `run.update-interrupted`; `bye: updating` is said at last. The `self-update` flag is present under a launcher, or when managed outside with a host-updater poll in the last fifteen minutes; absent under a foreground `serve`, the manager field saying why.
- **CLI verbs**: `launch` and `preflight`; `update status`, `apply`, `settings`, `credential`, `begin`, `snapshot`, `restore` and `discard`, those that reach the environment exchanging the bootstrap grant for a local client session and revoking it after, as `pair` does. `service install` lays out the entry, state, shim and a launcher definition and takes `--name`; `service status` adds the active and launcher versions and a pending update.
- **Set up** (ADR 0025, ADR 0031): the Your machines entry writes the five keys and gains three state checks. `your-machines.updates`: auto-update effective or the channel's newest running, no drain past its cap, not `blocked`, not behind after a failure (action `update`). `your-machines.release-channel`: with auto-update on, a successful check within 24 hours (action `check-again`). `your-machines.host-updater`: in a container, a poll within the hour. Reachability, the name and the copy are Set up's.
- **About** (ADR 0026, ADR 0027): this workstream supplies the rows above Managed tools: the client's version; the picked environment's version, channel, auto-update and Update now; "Claude Code (bundled) x.y.z, updates with this environment". As with managed tools, no launch notice and no skip-this-version; a pin holds a version.

### The install scripts

- `install.sh` (macOS, Linux) and `install.ps1` (Windows) are assets of every release. The card's copyable line fetches the script from its environment's own release with the token on stdin, passing `--channel` (that environment's) and `--name` when given. The script resolves the channel's newest at run time (`--version` pins), downloads, verifies and unpacks it into versions (`--prefix` goes: the launcher owns that directory), runs `service install --name` and `service start`, waits up to 60 seconds for the health URL to say ready, sets the channel with `update settings`, and hands its token over with `update credential --stdin`, which adds it as the forge account for the release origin through the forge workstream's add method unless one exists. It ends with `pair`'s link, ASCII QR and code on the tailnet address, or the Tailscale warning when only loopback is bound, then the path line.
- A re-run over a running service unpacks nothing into versions: it repairs the definition and entry, and changes the version only when `--version` asks, through `update apply`, which stages it as any update. Both scripts refuse root.
