# Spec: Key managers, the orientation block, the scrub registry and managed tools

Milestone 1 (Switch-over), phase C (the organs). Written 2026-09-28 from map ticket 91 of `david/agent-harness`. Implements ADR 0011 (the key-manager registry, injection, orientation from live state, one scrub registry, managed tools), ADR 0026 (scheduled probes, notices only below a declared minimum, a closed command table) and ADR 0028 (the Key manager step: the kept credential, a child token per run, injection on by default, Move), with rules citing ADRs 0009, 0010, 0015, 0016, 0017, 0020, 0027, 0030, 0031, 0034 and 0036 (the state import, on its pull request). Read: decision tickets #25, #42 and #47 with their Resolutions and later comments, #56's Resolution and addendum, this ticket's comments; the code on `main` at a70b82f (the vault, the composer's orientation seam, the Claude adapter's variable scrub and spawn key, the step registry and `setup.check`, terminals, notices); the env, claude-adapter, forge, skills-instructions, routines and launcher-update specs, re-deciding none; the core port audit's key-manager section; the 2026-09-22 research on the key-manager CLIs and on CLI updates; notebook memories on the OpenBao key manager, its secret conventions, the AppRole's scope and login on the agent box, and `bao-cli-env-fallbacks-and-cacert-bytes`. The product name is the placeholder `agent-harness`.

## Problem Statement

David keeps his credentials in OpenBao, and no session knows it. Key-manager connections live in one desktop's data folder; the server and the terminal UI have none; nothing reaches a run; a resolved reference has one consumer, a memory bank's git credential; and sign-in takes userpass or a pasted token, not the AppRole his agents use (core audit, section 3). A session on the agent box therefore starts with no token and has told David it could not approve a pull request for lack of one, when the AppRole sat in a file beside it. A userpass password is spent once on a token that dies when nobody reads for a while, so an unattended routine at night loses its key manager. The model is never told a key manager exists, which forge is primary or which banks it has, so sessions begin by hunting. A `VAULT_TOKEN` or `ENCLAVE_PROJECT` exported by some other tool silently takes over a CLI that was meant to be configured (key-manager CLI research). Values the harness resolves are scrubbed from one desktop's logs and nowhere else. And the CLIs all of this needs are found missing by a failing run.

## Solution

Each environment holds its key-manager connections: OpenBao or Vault by AppRole, userpass or token, Doppler, 1Password and Bitwarden Secrets Manager. The credential entered crosses the wire once and stays in the environment's vault, and the environment logs in, renews and logs in again by itself. Every provider process, terminal and pre-check on the environment receives the connection's environment block, with the stray variables shadowed; for OpenBao the token in it is a child token minted for that process from the policies David ticked and revoked when the process stops. One setting, allow or deny with overrides per account, routine and bot, decides whether a run gets the block and the forge variables. The harness reads references for itself over each provider's API, and a Move card writes stored tokens into the key manager and swaps them for references. Every run's instructions open with an orientation block rendered from live state: this environment, its key managers with their status, its forges and which is primary, its banks, the other environments David's clients know, and the standing rule to check the key manager first. Every value the harness resolves or injects is scrubbed from the log, the logs, terminals and error text. A Managed tools registry probes the CLIs the harness depends on, says when one is missing or below the minimum declared here, and installs or updates it with one click in a terminal pane.

### The connection record

- **Fields** (ADR 0011, ADR 0028): client-minted id; provider (`openbao`, which also covers Vault, `doppler`, `onepassword`, `bitwarden`); label; address; for OpenBao the CA as PEM bytes or none, the auth method (`approle`, `userpass`, `token`), its mount path (preset the method's name, chosen default), the username for userpass and an optional token role; the **ticked policies**; the **base path** for Move; `injects`; status and since; token information (display name, policies, TTL, renewable, expiry; never the token or its id); `canMint`; `copiedFrom` or `importedFrom`; created-at.
- **Address**: OpenBao's server URL, `https` or `http`; Doppler's API host, preset `https://api.doppler.com`; Bitwarden's server URL, preset `https://vault.bitwarden.com`, with the EU cloud and self-hosted allowed; for 1Password, the account URL learned at sign-in. One connection per provider and address, else `conflict` reason `connection_exists` (ADR 0028).
- **Injects**: several connections per environment are allowed, but one `BAO_ADDR` is not, so at most one connection per provider injects; the first signed in does, `keyManagers.connections.setInjected` moves it, and the others serve references only (chosen default).
- **Status**, with since-time and one line: `awaiting-sign-in` (no credential: a copy or an import), `signing-in`, `signed-in`, `credential-rejected` (sign in again), `expired` (a token login past its maximum life), `unreachable`, `sealed` (OpenBao only), `certificate-rejected` (the server no longer verifies against the pinned CA). ADR 0028 names the distinctions; the last is chosen.
- **Verification** (ADR 0011, ADR 0028): after the startup gate, every fifteen minutes, after a sign-in or a change, on `keyManagers.connections.verify` and on a Key manager check; one at a time per connection, within ADR 0031's ten seconds. `key-manager.connection.verified` is appended only when the status, token information, policies or `canMint` change; verified-at times are kept beside the record, as the forge's are.
- **The credential** is one vault entry per connection: role id and secret id, a password, or a token, stored before the command's transaction and removed if it rejects (forge spec's rule). The vault gains delete (forge spec). The derived login token is held in memory only; a restart logs in again (chosen default).
- **The vault on a desktop** (ADR 0011: a keychain on a desktop, a 0600 file on a headless machine): on macOS and Windows, where the environment runs as the user's launch agent or logon task, the OS keychain through a prebuilt native binding, an optional dependency; elsewhere, or where the binding does not load, the file. File entries move into the keychain on its first successful use. The env spec left this to the desktop and the GUI spec did not take it (chosen default). Built in #364: the binding is `@napi-rs/keyring`, and the entries sit under the service `agent-harness <environment id>`, which `keychain.json` in the data directory keeps with the entries' keys (never a value), since the binding lists a service's entries only by reading their values; a keychain that fails its first call leaves the file as the vault for that start; an entry the move could not move stays in the file, read from there, until a later start moves it; each start logs which vault it holds and why.

### Providers

One interface (ADR 0011, core audit): sign in, renew, verify, mint a run token, renew and revoke it, list the login's policies with a write flag each, check write access to a path, resolve a reference, write a value, list names under a path, and the verify command's identity. Errors are categorised: `credential-rejected`, `unreachable`, `sealed`, `certificate-rejected`, `denied`, `not-found`, `rate-limited`. A provider never disables TLS verification; a pinned CA is the only trust it adds.

- **OpenBao and Vault** over the HTTP API (same paths on both). AppRole and userpass log in at their mounts; a token login is looked up. A **root** login is refused `verification_failed` reason `root_token`, since the harness never holds root (chosen default). The login is renewed at two thirds of its TTL; once a third of its maximum life is left (2:40 of the agent box's AppRole logins, an hour to live and eight at most, #369's note), the environment logs in again from the kept credential, raises the connection's **login generation**, and mints new run tokens from the new login; the old one is revoked once no run token of it is held (chosen defaults). A periodic login renewed in time never needs this. A token login past its maximum life is `expired`. Verification reads `sys/seal-status` (sealed is its own status), the token's own lookup and its capabilities on the token-create path. The login's policies come from its lookup, `root` never among them; each is flagged as writing when its text, read where the login may, grants `create`, `update`, `patch` or `delete` on a path outside `auth/`, `sys/`, `cubbyhole/` and `identity/`, and as possibly writing when it cannot be read (chosen rule for ADR 0028's warning). Ticks are preset to all of them. KV versions are detected per mount from the mount's UI endpoint and cached for the process life.
- **Doppler** over its REST API with the token as bearer; `/v3/me` for identity and type, and the names-only secrets list as the proof (key-manager CLI research). Project and config are sent only when a reference names them.
- **1Password** through its official JavaScript SDK with a service-account token: listing vaults proves the token; references are `op://` references.
- **Chosen (#378)**: the SDK, `@1password/sdk` (MIT), is loaded at the first sign-in, never at start (its core is a WebAssembly module of some 14 MB). The connection's address is the account URL its token names: a service-account token is `ops_` and a base64 JSON whose `signInAddress` is the account's host, so an add with a token gives no address, a copy or an import gives the account URL, a sign-in with another account's token is `verification_failed` reason `rejected`, and an update's new address is `invalid_params`. The SDK session made from the token is the environment's own: a call that finds it expired (the SDK's expired-session error class), a verification, a reference read, a browse or a Move's write, signs in again from the kept token once and asks again, one sign-in serving the calls that found it expired together, so a read between verifications recovers without waiting for the next one (#1138); a sign-in again that is refused answers as its own failure does (a read's `credential_source_unavailable`), and the next call signs in afresh. Letting the login go ends the session, never the token. A service account has no policies, no lease and mints nothing (`canMint` null; runs are given the connection's token). SDK failures sort by the SDK's error classes and messages: a rate limit is `rate-limited`, an expired session or a refused token `credential-rejected`, a missing permission `denied`, a vault, item or field that matched nothing `not-found`, anything else `unreachable`. A reference's name an `op://` reference cannot carry (outside letters, digits, `_`, `.`, `-` and spaces) is looked up to its id. `keyManagers.references.browse` takes `vault` and `item` for 1Password: the vaults, a vault's items (each ending in `/`), an item's fields' titles. Move's base is a vault's name, suggested `harness`; the target is an API credential item titled after the entry, its concealed field `credential`, its notes the entry's note; 1Password cannot say what a service account may do in a vault, so a write check answers whether the vault is there, and a vault it may only read refuses the write itself (`reference_denied` at `write`).
- **Bitwarden Secrets Manager** through its official SDK with an access token: listing projects proves it. Where the SDK cannot load, the provider answers `provider_unavailable` and the card says so (chosen default; see Further Notes).
- **The certificate preview** carries a rule from the core audit: `keyManagers.certificate.preview` opens a TLS socket with verification off, reads the chain and closes it without sending a byte, answering the chain's anchor (the issuer walked up to, else the leaf) as PEM with its SHA-256 fingerprint, subject, names, expiry and whether it signs itself. Only when a person accepts does the PEM become the connection's CA; every real request verifies against it.

### Run tokens

- **What a holder gets** (ADR 0028): for OpenBao, a child token of the current login with the ticked policies plus `default` (which its own lookup, renewal and revocation need), renewable, a TTL of one hour or the login's remaining life if shorter, display name `agent-harness` and metadata naming the session and the holder kind; for the other three, the connection's token as it is, the card saying to create a read-only one.
- **A token role**, optional on the connection (chosen addition): when set, run tokens are created against that role, which may make them orphans that outlive the login; the environment still revokes each at its holder's stop. Without one, a child dies with its login, so the login generation joins the process key below and a session's next run after a re-login gets a fresh process; a run in flight keeps its token for at least the third of the login's life that re-login leaves. A run longer than that loses its token: ADR 0028's fog.
- **Holders**: a provider process, a terminal (the forge spec injects terminals), a routine's pre-check (routines spec) and a verify command. ADR 0028 says "a TTL of the run's life, revoked at run end"; a provider process serves many runs of its session with an environment fixed at spawn (ADR 0015, claude-adapter spec), so the run token lives with the process that serves the run, as the forge's run-scoped secret does (ADR 0020): minted when the holder starts, renewed every twenty minutes while it lives, revoked when it stops (the idle stop, a changed key, a rewind, drain). An environment that dies leaves tokens that expire within the hour. This reading is a chosen default for David's review.
- **Minting** needs `update` on the token-create path, or the role's: OpenBao's and Vault's token store register only the update operation there, with no existence check, so their ACL checks `update` alone (verified in #366 against both projects' sources; the ticket had read `create` and `update`). The registry learns it at each verification from the login's capabilities (`canMint`); a login that cannot mint gives runs the address and CA with an empty token, the orientation says why, and `key-manager.run-tokens` fails naming the capability the login lacks (chosen default: never the login's own token, which ADR 0028 rejected).
- **The key**: the process environment's non-secret key (forge spec) gains, per injected connection, its id, a **credential generation** (raised by sign-in, sign-out, address, CA, ticks, token role and the injects flag), its login generation when run tokens are children, and its status; a change gives the next run a fresh process, resuming from the store. The token itself is minted per spawn and never in the key.
- **Starting up**: after the startup gate every connection signs in at once; a spawn waits up to five seconds for a connection still `signing-in`, then goes on with an empty token and the orientation says so (chosen default).
- **Sign out** revokes the login, and with it every run token minted from it, deletes the credential and appends `key-manager.connection.signed-out`.
- **Chosen (#368)**: the key managers' supplier registers with the process environment (#307) as `key-managers`; each holder's scope names what it is (`provider-process`, `terminal`), which the run token's metadata carries as `holder` beside `session`. The supplier serves OpenBao's block alone until #377 to #379 add the others'; with no injecting OpenBao connection it supplies nothing and its part of the key is empty, and the process environment leaves an empty part out of the key, so the key is empty while every part is. Its part names, per injecting connection, its id, its credential generation and its status's kind as the connection stands (`signing-in` while its startup sign-in runs). The credential generation is counted on the store: a person's sign-in with a credential, a sign-out, a new address, CA or token role, new ticks and the injects flag (the first sign-in's, and `injected-set` on both the connection it moves to and the one it moves from) raise it; the environment's own sign-in from the kept credential does not, re-login being #369's login generation. A run token is minted only for a connection signed in, with a login held and `canMint` not false (one not yet verified is tried); a mint that fails is logged, scrubbed, and the holder gets the empty token. Its time to live, and each renewal's increment, is an hour, or for a child of the login what is left of the login's maximum life when that is known and shorter (#369); it renews and revokes itself (`auth/token/renew-self`, `auth/token/revoke-self`, which `default` grants), a renewal the key manager refuses as unknown stopping its renewals, and its scrub registration is let go once its revocation is answered. A sign-out or a removal revokes every run token held from the connection at once, and one whose mint is under way then as it lands, its holder given none, since a token role's orphans outlive the login and a token a person gave is not revoked. The five seconds a spawn waits run from the spawn, on the environment's clock, and only a startup sign-in stands `signing-in`. `keyManagers.connections.setInjected` takes any connection the environment holds, one awaiting its sign-in too, whose holders then get the address and CA with an empty token; its event names the connection it `replaced`, or null. `keyManagers.list` answers `injectedVariables`, the block's names for an injecting OpenBao connection and none otherwise. The configuration both CLIs are pointed at is `<data directory>/key-manager-cli/openbao.hcl`, written again at each spawn, naming the harness's token helper since #716 (Injection); the directory is left out of the denylist's data-directory preset (David's decision on #368, permissions spec). Verified on `bao` 2.6.3 and `vault` 2.1.1 against loopback listeners: an empty `CACERT_BYTES` is absent (the system's CAs verify; a malformed one fails `Couldn't parse PEM`); empty `PROXY_ADDR` and `HTTP_PROXY` leave `HTTPS_PROXY` in force; a `CONFIG_PATH` naming an empty file keeps a configured token helper from running, but with an empty token both CLIs still send what `~/.vault-token` holds, `bao` reading an empty `BAO_TOKEN_PATH` as unset (#716, which the harness's token helper closes). From OpenBao 2.6.3's token store: a role with `orphan` set makes an orphan with no sudo check, where `no_parent` needs sudo; a child without a role inherits its parent's entity, so identity policies on the login's entity or its groups reach every run token whatever is ticked, where a role's orphan inherits none (#717).
- **Chosen (#369)**: the login scheduler (`logins.ts`) holds each connection's login in memory. A login is renewed at two thirds of its lease, asking for the time to live it was created with (its period when periodic), each lease dated from the renewal's asking; a renewal that fails for want of an answer is tried again at two thirds of what is left, a minute later at the soonest, and one the key manager no longer knows ends the renewals and has the connection verified at once. OpenBao names a login's maximum life only as `explicit_max_ttl` in its lookup: the maximum an AppRole or userpass role sets (`token_max_ttl`) shows only as a renewal answering less than it asked, which is where the environment learns it; a login that cannot be renewed ends at its expiry. The maximum a renewal showed plans the connection's later logins at the same address, mount, method and username from their start. The agent box's AppRole, `claude-admin`, gives its logins an hour to live and eight at most, not periodic (#600). While its role named the eight hours only as `token_max_ttl`, the first login after each start was renewed every forty minutes and signed in again at 7:20, when a renewal showed forty minutes left, so a run in flight kept its run token for forty minutes after that re-login instead of 2:40; each later login, planned from its start, was signed in again at 5:20, a third of its eight hours left (#724). So the role carries an explicit maximum (David, 2026-10-01, #724): `token_explicit_max_ttl=8h` was written on it that day, read back as `token_ttl` 3600, `token_max_ttl` 28800 and `token_explicit_max_ttl` 28800, and a fresh login's lookup names `explicit_max_ttl` 28800. Every login, the first after a start included, is now planned from its start: renewed every forty minutes and signed in again at 5:20, with 2:40 left. The effective lifetime is unchanged at eight hours, and the harness did not change. The re-login is a verification that signs in from the kept credential first (#366): its outcome is recorded as the environment's own `signed-in`, and a failure stands as the status its category gives (`credential-rejected`, `sealed`, `certificate-rejected`, and `unreachable` for no answer or a request to slow down) beside what the login was last known by, the old login still held, no run token minted meanwhile, and the next verification trying again. A token a person gave is renewed up to its maximum life and verified at its end, which finds it `expired`. The login generation counts the logins held for the connection, raised by every one held (a start's, a person's, a re-login); the key names it only while the connection has no token role, whose tokens may outlive the login. A replaced login, whoever replaced it, is renewed while a run token minted from it is held and revoked once none is, counted from before each mint; a sign-out or removal revokes every login held at once. A child run token lives, and is renewed by, an hour or what is left of its login's maximum life when that is known, never the login's current lease, which the login's renewals extend; a token role's lives an hour.
- **Chosen (#745)**: what the login scheduler asks for, a login falling due or one the key manager no longer knows, never joins a verification under way: it waits for that one and verifies again, since that one may have looked the login up before. So a token a person gave whose end comes while a verification is under way is still found `expired` at its end, not fifteen minutes later.

### Injection

- **The setting** (ADR 0011, ADR 0028): `credentials.injection`, `allow` (preset) or `deny`, and `credentials.injectionByAccount`, a map from account id to `allow` or `deny`, entries of removed accounts dropped; both keys belong to the Key manager step in the Access band. A routine's `injection` (`inherit`, `allow`, `deny`; routines spec) and later a bot's outrank the account's, which outranks the environment's: the most specific answer wins (chosen default). A completions request cannot ask for injection. The answer and the level that decided it are in the process key, and the same answer governs the forge variables and credential helper (ADR 0020, forge spec).
- **Chosen (#367)**: the level is `environment`, `account` with the account's id, or `routine` (later `bot`) with its id. A routine's `allow` or `deny` rides the request the host's `startRun` takes (`injection`, which #92's firing passes as the routine saved it) and is recorded on its run's policy (`run.policy.resolved`'s optional `injection`, the answer and the routine's id), so a run the environment starts after it for the routine, from its queue or as an update's continuation, keeps it; `inherit`, or none, records nothing. A client-started run, a completions request (whose `agent-harness` fields have no such field) and a terminal carry none. `settings.update` takes an entry for any account id, as `browser.reach` does. An account's removal, by a person or by the sign-in refusal of an identity another account holds, drops its entry in the removal's own transaction as a `settings.updated` beside it. The Key manager step's skip check, `key-manager.present`, comes with its entry (setup spec); its triggers are every `key-manager.*` event and `tools.updated`.
- **The block for OpenBao and Vault**, each variable in both the `BAO_` and `VAULT_` families so either CLI works (key-manager CLI research): address; the run token; `CACERT_BYTES` with the PEM, empty without one; empty `CACERT`, `CAPATH`, `CLIENT_CERT`, `CLIENT_KEY`, `NAMESPACE`, `TOKEN_PATH`, `HTTP_PROXY`, `PROXY_ADDR`, so nothing a user exported takes over and the sandbox's own proxy variables still apply; `SKIP_VERIFY=false`; `MAX_RETRIES=2`, since the CLI otherwise retries nothing; `CLI_NO_COLOR=1`; and `BAO_CONFIG_PATH` and `VAULT_CONFIG_PATH` naming a harness-owned configuration, so no user token helper is in the loop. No output format is forced (chosen: the model asks for JSON when it wants it).

The variable stays in the block, read by 0.5.0 and later and naming the file for a run's shell; the token stays in the environment, never in argv. Through 2.1.0 a server URL builds the profile from itself and reads no configuration, so while the block gave one, of the commands only `bws config`, which writes the file it is given, reached the host's; `main` reads the configuration before applying the server URL. Only `main` parses an empty file (earlier releases require its `profiles` table). The fake `bws` parses its options as each release from 0.3.0 to 2.1.0 does, binding the file's variable from 0.5.0 only, and proves the file and the profile for the verify command and the documented shapes.

Not a per-holder `HOME`: a run's whole home is too broad, and on Windows `bws` ignores it.

### References and resolution

- **Shapes** (contracts), each with the connection id: OpenBao `mount`, `path`, `key`; Doppler `name` with optional `project` and `config`; 1Password `vault`, `item`, `field`; Bitwarden `secretId`, with its `key` for display. The display form is the provider, the connection's label and the locator. The state import's references carry these shapes as they are (ADR 0036).
- **Resolve**, in process, for the forge (ADR 0020), banks (#90), routine endpoints (routines spec), the skills `secret` readiness check (#89) and Move: the caller names the reference, its owner and purpose; the registry reads it with the connection's login, not a run token, within ten seconds, registers the value with the scrub registry and answers it with its release (core audit's lifecycle). Never cached, never a fallback to an earlier value when a read fails. A connection not `signed-in` answers `credential_source_unavailable` (the forge's error), a missing path `reference_not_found`, a refused one `reference_denied` (OpenBao answers 403 for a denied path, an absent path and an absent mount alike, so the message says to check the mount first).
- `keyManagers.references.check` answers whether a reference resolves, never the value; `keyManagers.references.browse` lists names under a path (OpenBao list, Doppler names, 1Password items and fields, Bitwarden projects and keys), never values (chosen additions, for the reference pickers of Forges and banks).

### Move stored tokens

- **Sources** (ADR 0028): forge accounts with a stored token (ADR 0020), banks with one (#90) and, chosen, routine webhook endpoints with a pasted secret. Each owning service registers a Move source: list items, read the stored value, swap to a reference through its own command (`forge.accounts.update` with a `reference`, #90's bank command, `routines.endpoints.set` with a reference), delete the stored value.
- **Targets**: once per connection a base path (`keyManagers.connections.setBasePath`), suggested from the provider: `harness/` on the first KV mount the login can write, a `harness` config, vault or project (ADR 0028); each item's target is `<base>/forge-<slug>`, `<base>/bank-<name>` or, chosen, `<base>/endpoint-<name>`, one level below the base, so that with the base as the project an entry sits two levels under its mount (ADR 0028 as amended 2026-09-28). For an OpenBao or Vault connection the base is therefore a KV mount and exactly one project segment (`personal/harness`), and `keyManagers.connections.setBasePath` refuses a deeper one with `invalid_params`, so an edited base cannot bring the third level back. For Doppler, whose names are upper-case identifiers, the item is `FORGE_<SLUG>_TOKEN`, `BANK_<NAME>_TOKEN` or `ENDPOINT_<NAME>_SECRET` in the base config; for 1Password an item titled `forge-<slug>` (and so on) with a concealed field `credential`; for Bitwarden a secret with that key in the base project (chosen mappings).
- **`keyManagers.move`** (prepared) takes a connection and item ids or all: for each item in turn it writes the value, refusing to replace a different existing value (`conflict` reason `target_exists` unless `overwrite`), reads it back and compares in constant time, swaps the source to the reference, deletes the stored value, and appends `key-manager.moved` (item, connection, locator; never the value). OpenBao entries carry `note`, `service` and `added` fields beside the value, as the notebook conventions require (chosen). A swap that fails leaves the written copy and the stored value, and says so; a delete that fails is retried at the next start.
- **Chosen (#371)**: `keyManagers.move.list` answers each item by its kind (`forge-account` or `endpoint`) and its owner's id, with what people know it by (a forge account's origin) and its target on each connection a Move can write to that has a base path, OpenBao's alone until #377 to #379 map theirs; the value sits at the key `token` for a forge account or `secret` for an endpoint. The base path OpenBao suggests is read at each verification while none is set, from the login's view of the KV mounts in their order, the first under whose `<mount>/harness/entry` the login may create a secret (`create`, which a new entry needs) being suggested, a mount whose path holds a slash skipped; it is kept in memory and answered on the record as `suggestedBasePath` until a base is set. It is read before anything else the verification found is recorded (#689), so a verification is seen whole and only as it ends: a client that reads the records on its event reads the suggestion, and the next verification is already set fifteen minutes from its end. `keyManagers.move` takes the connection, the items or `all`, and `overwrite`; it refuses the whole command only for the connection (`not_found`, `invalid_params` without a base path, `credential_source_unavailable` not signed in, `provider_unavailable` for a provider it cannot write to yet), and answers each item otherwise: `moved`, with its reference and whether the stored token was deleted, or `failed` at a step (`read`, `write`, `read-back`, `swap`), saying whether a copy was left at the target and why. Items are moved one at a time, and one Move at a time per environment. A write reads the entry first, so a Move needs `read` there as its read-back does, and takes anything at the key but the same text for a different value; it keeps whatever else the entry held beside the value and its `note`, `service` (the forge's host) and `added` (the UTC day). The read-back goes through the registry's resolve; a value there other than the one written is `conflict` reason `read_back_differs`. The swap is the owner's command carried out in process for the client session that asked, under a command id of its own, so it asks the forge who the reference's value is (#312) and has its own receipt; the `key-manager.moved` events are appended in the Move's own transaction once every item is done. A delete that fails names the stored value's place (a vault entry, never the value) as `undeleted` on `key-manager.moved`; each start past the gate deletes those again and appends `key-manager.stored-value-deleted` as `system:key-manager`.
- **A connection that cannot write** answers `cannot_write` per item. `keyManagers.move.copyValue` then answers that item's stored value once for a manual paste: `admin`, sent directly, never through the outbox, the one answer the scrub registry lets through, recorded as `key-manager.value-copied` naming the item and client session. `keyManagers.move` with `verifyOnly` then reads back what was pasted, compares, swaps and deletes. This is ADR 0028's Copy the value; ADR 0020's "never returned" otherwise stands.
- **Chosen (#372)**: a Move asks the key manager whether the login may write each item's target before it writes, as the capabilities there answer it: `create`, which a new entry needs, so a login that may only update an entry there is answered `cannot_write` too and ends with a reference the same way; a key manager that cannot be asked fails the item at `write` with nothing written. `cannot_write` is the item's error at the step `write`, naming the connection and the target. A copy is offered once per `cannot_write`: `keyManagers.move.copyValue` takes the connection and one item and answers the item, its target and the value; the offer is held in memory until the copy takes it, the item moves, or a later Move of the item that writes answers otherwise, so after a start or a copy the Move is run again for another; a connection not held, an item holding no stored value or one with no copy offered is `not_found`; a repeat of the command id is answered by its receipt alone, which never holds the value. `key-manager.value-copied` names the connection, the item, the target and the client session. `verifyOnly` asks nothing about write access and writes nothing: nothing at the target's key is `reference_not_found` at the read-back and a different value `conflict` reason `read_back_differs`, each with `written` false; `overwrite` beside it is `invalid_params`; an item it verifies is recorded as `key-manager.moved`, as a Move's.

### The scrub registry

- **Registration** (ADR 0011): an owner registers a value and receives its release, a scope rather than an add and remove pair; values are reference-counted, so two holders of one secret each keep it registered; a release is idempotent. With each value the registry keeps its percent-encoded and JSON-escaped forms and any the owner adds (the forge's Basic-auth forms). A value under eight characters is matched only whole, between non-alphanumerics (chosen default).
- **Who registers**: every vault entry while held, from start before the wire opens (key-manager credentials, forge and endpoint tokens, the pairing signing key); every resolved value for its operation; every run token for its holder's life; the forge's run-scoped secrets.
- **Shape rules**, data in contracts, anchored on recognisable prefixes with a word boundary before them, never on entropy: Anthropic, OpenAI-style, AWS, Google and GitHub keys, PEM private-key headers, bearer tokens, inline key assignments, OpenBao and Vault tokens (`hvs.`, `hvb.`, `hvr.`), Doppler tokens by kind, 1Password service-account tokens, Bitwarden access tokens. Chosen (#363): twelve rules, in the order they are checked, `anthropic`, `openai-style`, `aws` (access key ids), `google`, `github`, `private-key` (from the header to its footer, or to the end of a text cut before one), `bearer`, `key-assignment`, `openbao`, `doppler` (one rule whose prefixes are the kinds), `onepassword`, `bitwarden`; the boundary is no letter or digit before the prefix, so `_` and `-` separate words (`GITHUB_TOKEN`, `X-Api-Key`), and `sk-` takes no hyphen before it either, so a kebab-case name's `-sk-` segment is none. A key assignment is a name ending in `api_key`, `access_key`, `secret_key`, `private_key`, `secret`, `token`, `password` or `passwd`, then `=` and a value, or `:` and a quoted value or one holding a digit, so a type annotation is none; the value is twelve or more characters with no space, quote, `.`, `$` or bracket, and not followed by `.` or `(`, so an expression is none. A bearer token and a key assignment hide only the value, keeping the name. AWS secret keys have no prefix and are found only when assigned inline.
- **Where it applies** (ADR 0011's list), replacing each hit with `[redacted]`:
  - **The event log's append**: registered values in every string of every payload, so transcripts, tool outputs and client renders never see them. Shape rules are not applied to content (prompts, model text, tool output): a secret the model or the user handles on its own is outside the registry (ADR 0011).
  - **Assistant deltas** (chosen, #429): before the host appends them, each open item's text and thinking pass through independent registered-value scrub streams. A tail that could begin a registered form, and any whole value it overlaps, is held for at most fifty milliseconds on the environment's clock from its first hold; further fragments do not restart the timer. Text with no such tail is appended immediately. Held text is released before the item settles or the run ends, including an interrupt, error or environment stop. This covers session subscribers, the stored deltas and the completions surface, which renders those same log events. Shape rules remain off content. Like terminal output, the bounded hold-back covers continuations arriving within that window.
  - **The logger**: registered values, then shape rules.
  - **Terminal output**, live and in scrollback: registered values, with a chunk's tail held back while it is a prefix of one, for at most fifty milliseconds (chosen default). Chosen (#363): the fifty milliseconds run on the environment's clock from when a tail was first held, however much output comes meanwhile; a held tail is shown before the terminal's exit; a whole value the held tail overlaps is held with it; a short value's tail is held only where the value could stand alone; and a catch-up scrubs the scrollback, or the chunks it replays as one text with each keeping its sequence (a value across two is replaced in the later one's place), again as it sends them, so a client connecting later is not sent a value registered after its output was shown. Shape rules are not applied: a terminal is the user's own.
  - **Captured output** the harness keeps (pre-check output, tool runs, verify commands, git's standard error) and **error text** a provider returns, before it becomes a status line or a wire error's message: registered values, then shape rules.
- **Refusal** (ADR 0011): a memory draft (#90), an issue body or pull-request body (#87) holding a shape-rule hit or a registered value is refused `secret_shaped`, naming the rule and the field, never the value. Chosen (#363): a registered value is named by the rule `registered-value`, and it is named before any shape rule; otherwise the rule of the text's first hit. The fields are checked in order (an issue's title, then its body) and the first holding either is named.
- **Where two hits overlap** (chosen, #363), a registered value and a shape rule's hit, or two rules', they are replaced as one `[redacted]`, so nothing of either is left; scrubbed text scrubs to itself.
- **Limits**: the log is never rewritten, so a value registered after an append is not scrubbed from it; the provider's own session store is the provider's history, resumed as written, so a token the model printed stays there, which is one reason run tokens die with their process.

### The orientation block

- **Rendered** by the OrientationRenderer through the composer's orientation seam (ADR 0011, skills-instructions spec), into the user layer ahead of David's owned instructions while `instructions.orientation` is on (#89's key and Orientation row, ADR 0030). The seam answers the text and the sections it could not read.

The skills-instructions spec requires this: the text is in the spawn key, and a changing line would start a fresh process for every run.

When you are given a key, save it into the key manager under this project's folder, never into a file. Never print a secret's value." - **Banks** (#90): name, kind, role, and whether landing works; bank-owned facts come from the bank's orientation memories in #90's layer (ADR 0010, ADR 0034).
- **Other environments**: the union, sorted by name, of what desktop and terminal-UI client sessions report through `environment.knownEnvironments.report` (each report whole, replacing that client session's last; dropped when the client session is revoked or expires): each environment's name and the address the client uses, never this one. Program client sessions cannot report, so a program cannot put text into every run (chosen mechanism for ADR 0011's "the environments this client knows"; it is not the peer list the env spec leaves to fog, since no environment connects to another).
- **Chosen (#380)**: the OrientationRenderer (`instructions/orientation.ts`) takes one provider per section, registered by the section's name (`environment`, `accounts` since #381, `key-managers`, `forges`, `banks`, `other-environments`), which fixes its place; a name registered twice is refused. The block is `# Orientation`, then each section under `## <title>`, paragraphs a blank line apart. A provider answers its section's paragraphs, each a line of prose or a list (an optional heading line over one `- ` line per item); blank prose and an empty list are left out, and a section left with neither is. Every section is asked at once. The second is measured on the environment's clock from when the provider was asked, and a provider that answers at once is given no timer; one that throws, rejects or has not answered at the second renders "Could not be read.", is named in the seam's unread registries in the block's order and is logged, and its late answer is dropped. The cap counts the whole block: past 6,000 characters every list longer than some count is cut to its first that many items and ends "- and N more, see Settings.", the count the most that fits and the same for every list, so the longest lists are cut first; prose is never cut. ### Wire methods

Scope `admin` unless stated; mutating methods take a `commandId`. "Prepared" names the environment's two-phase command, whose `prepare` hears from the provider before the transaction (env spec, as `runs.withdraw`); it says nothing of how a client sends it. Every call that carries a credential or answers a secret (`add` with a credential, `signIn`, `move.copyValue`) is sent directly and never queued in the client's outbox, so a call made while the environment is unreachable fails rather than parking a secret on the client (client-runtime spec; the forge spec's rule for `forge.accounts.add`).

- `keyManagers.list` (`read`): connections without any secret, each with its policies (write flags), ticks, base path, injected variable names, CLI row and status. `keyManagers.move.list` (`read`): items holding a stored value, with each connection's target.
- `keyManagers.certificate.preview` (query): above.
- `keyManagers.connections.add` (prepared; it hears from the provider first): id, provider, label, address, CA, method, mount, username, token role, ticks, base path, `copiedFrom` or `importedFrom`, and an optional credential. Without one the record waits `awaiting-sign-in`, which is how the state import and the bulk copy call it (ADR 0036, ADR 0028). A rejected credential is `verification_failed` and nothing is stored; an unreachable or sealed server keeps the record with its status and credential (the forge spec's rule). A repeated `importedFrom` answers the existing id, so a re-run imports only what is new.
- `keyManagers.connections.signIn` (prepared): a credential, optionally a new method and username, replacing the stored one on success.
- `keyManagers.connections.update` (prepared when address or CA change): label, address, CA, token role. `setPolicies` (ticks, a subset of the login's), `setBasePath`, `setInjected`, `signOut`, `remove` (`conflict` reason `referenced`, naming holders, unless `force`).
- `keyManagers.connections.verify` (one or all): a query that records what it finds, as `forge.accounts.verify` does. `keyManagers.references.check`, `keyManagers.references.browse` (queries).
- `keyManagers.move` (prepared), `keyManagers.move.copyValue` (a command, sent directly).
- `tools.list` (`read`, optional `refresh`); `tools.detail` (`read` query: the `doctor` fields for `claude`); `tools.run` (command: tool, action, terminal id); `tools.verify` (query).
- `environment.knownEnvironments.report` (`read`, refused `forbidden` for program client sessions): the client's other connections, each id, name and address.
- **Chosen (#365)**: a `signIn`, or an `update` of the address or CA, that cannot ask the key manager is refused `unreachable`, `sealed` or `certificate_rejected`, keeping what the connection held, where an add keeps the connection with that status (`certificate-rejected` for a certificate that does not verify) and the credential. A credential for a provider this version cannot sign in to is `provider_unavailable`; a connection without one is added for any provider. The state import sends no credential, and a repeated `importedFrom` is matched among the connections held. An address is an origin; a token signs in at the mount `token`; a pinned CA is the only CA a connection's requests trust, and one is pinned only for an `https` address; an OpenBao base path is exactly two segments, so a KV mount whose path holds a slash cannot hold one. The ticks are null until the first sign-in presets them, and `canMint` until a verification reads it (#366). `signing-in` is held in memory while a sign-in from the kept credential runs, and its outcome, failed or not, is recorded as `key-manager.connection.signed-in` by `system:key-manager`. Sign-out and removal revoke a login the environment made (AppRole, userpass) and let a token a person gave go unrevoked, since it is theirs; a connection signed out stops injecting, so the next of its provider signed in injects.
- **Chosen (#366)**: a verification asks with the login held; with none held (a sign-in the start or an add could not finish), or a login the environment made whose token the key manager no longer knows (it lived out its time to live before #369's re-login), it signs in from the kept credential first and records that as `key-manager.connection.signed-in` by `system:key-manager`, as after a start, so a connection its start found unreachable or sealed signs in once the key manager answers. A token a person gave that the key manager no longer knows is `expired` once the clock is past the expiry its lookup gave, else `credential-rejected`; the start's sign-in reads it the same way. A key manager asking the harness to slow down (`rate-limited`) stands `unreachable` and is refused `unreachable` on the wire. A verification that finds a problem keeps the token information, policies and `canMint` last known beside the new status. The token information's time to live, which moves with the clock, is left out of what counts as changed, so a verification that finds nothing new appends nothing; the record's `verifiedAt` is when the connection was last verified, whatever that found, kept in memory beside the record between recorded verifications. A policy's write flag reads the policy language (comments, nested parameters) and its JSON form; a rule that denies grants nothing; a path pattern that does not start with `auth/`, `sys/`, `cubbyhole/` or `identity/` (`*`, `+/data/*`) counts as outside them; a text neither form reads as possibly writes. `setPolicies` keeps the ticks in the order the login's lookup names them and needs a login looked up. The preview takes an `https` origin, answers `unreachable` naming the address when no handshake completes within ten seconds, gives the names of the certificate's DNS and IP alternative names and its subject on one line, and a pinned CA anchors the chain as it is, root or not, so the leaf or intermediate a preview answered can be pinned. The client runtime's status rows are #384's.
- **Chosen (#1852)**: a sign-in's refusal (`verification_failed`, `unreachable`, `sealed`, `certificate_rejected`, `provider_unavailable`) and the certificate preview's `unreachable` carry setup-copy.md §5.7's sign-in line as their message, and what the key manager or the socket said, with its HTTP status or system error code, and whether anything was kept, in `data.details`, one line each.
- **Errors** besides the shared union: `verification_failed` (reasons `rejected`, `root_token`), `unreachable`, `sealed`, `certificate_rejected`, `provider_unavailable`, `credential_source_unavailable`, `reference_not_found`, `reference_denied`, `cannot_write`, `secret_shaped`, `tool_not_runnable`; `conflict` reasons `connection_exists`, `referenced`, `target_exists`, `read_back_differs` (chosen, #371), `tool_run_in_progress`.
- **Capability flags** `keyManagers` and `managedTools` in `hello` and discovery; without them a client shows the panes absent with a reason (ADR 0004).

### The Key manager step

The registry gains `key-manager`, fifth (ADR 0034), in #141's shape (ADR 0016, ADR 0031):

- **Writes** `credentials.injection` and `credentials.injectionByAccount`, and state through `keyManagers.connections.*` and `keyManagers.move`. **Links** to the Key managers pane in the Access band (ADR 0027), the Forges and Memory bank steps, and About's Managed tools (ADR 0026). **Skippable**: with no connection it answers `skipped`, never forced (ADR 0028).
- **State checks**: `key-manager.signed-in`, every connection signed in, none awaiting sign-in, rejected or expired (`sign-in-again`), and none still signing in or whose provider cannot load here (`check-again`, #1852: the step is not done while one shows); `key-manager.reachable`, none unreachable or sealed (`check-again`) or with a rejected certificate (`check-certificate`, #1852); `key-manager.run-tokens`, every injecting OpenBao login can mint (`check-again`); `key-manager.cli`, each injecting connection's CLI installed at or above its minimum (`install`, `update`). Each line is setup-copy.md §5.7's, naming the connection by its label; its address, id and status line, the path and policy line a run token needs, and the CLI versions found go in the result's details, and a failure offers only the actions its findings need.
- **Budget and cadence** (ADR 0031): ten seconds and fifteen minutes, as for Forges; `setup.check` awaits a verification within the budget, else "Checking took too long. Choose Check again." (details: "Stopped after 10 seconds.") with `check-again` over the last good result; each `key-manager.*` event and `tools.updated` reruns it.
- The tiles, forms, policy ticks, the Move card and the health copy are #88's; the terminal UI shows the summary and pointer (ADR 0028). The step generates no prompt: the orientation block carries the standing rule (ADR 0028).
- **Chosen (#383)**: the four checks await `keyManagers.connections.verify`'s verification of every connection, asked in process and recorded as every verification is (`system:key-manager`), and share it, since a verification asked for while one runs for the same connection joins it; `key-manager.cli` awaits it too, because a verification that signs a connection in for the first time can make it inject. A verification asked for this way stands for the one the connection's schedule had due, the next counted fifteen minutes from its end, and one a check's own verification records re-runs nothing (setup spec). A failing line names each connection as its label at its address's host (`OpenBao at bao.example.com:8200`), and its target is the connection by id. `key-manager.signed-in` names `awaiting-sign-in`, `credential-rejected` and `expired` (with the expiry its lookup gave); `key-manager.reachable` names `unreachable`, `sealed` and `certificate-rejected`; `signing-in` is neither, a verification waiting for the startup's sign-in. `key-manager.run-tokens` names an injecting OpenBao connection signed in whose `canMint` is false, with the capability it lacks (`update` on `auth/token/create`, or on `auth/token/create/<role>` with a token role); one not signed in is the other checks' to name, and one never asked (`canMint` null) is tried at each mint, so it is not named. `key-manager.cli` reads the Managed tools rows only when a connection injects, for every injecting connection whatever its status: a row installed at its minimum or later (`current`, `update-available` or `method-unknown`) of any of its provider's CLIs satisfies it; otherwise the line says what was found and offers Update of the provider's first CLI when that is below its minimum, else Install of it, targeting the tool: `bao` for OpenBao, since `vault` is never installed.

### Copies and the state import

- **Same on every environment** (ADR 0028): the client runtime's bulk copy calls `keyManagers.connections.add` on each chosen environment with address, CA, method, mount, username, ticks and base path and `copiedFrom`, never the credential; each target asks for it once.
- **Chosen (#384)**: the copy also carries the provider, label and token role, each field only when the source holds one, and is a new connection there under an id of its own, so a second copy after a removal is not refused for its id; a target holding the provider and address already reports `conflict` reason `connection_exists`, and the others go on. A connection coming to stand in any status but `signed-in` of another kind than the client last heard raises one client notice, "<label> on <environment>: <the status's line>", offering the Key manager step; an add awaiting its sign-in is one, so each target of a copy asks for its credential once, and a person's sign-out and a return to `signed-in` raise none. `keyManagers.move.list` is fetched again on a forge account's add, update and removal as well as on every key-manager event.
- **The state import** (ADR 0036, this ticket's third comment) calls the add in process without a credential, with `importedFrom` naming the source connection, for address, CA, auth method and username; references carry as they are, mapped to the new connection's id. Encrypted tokens are never read and plaintext ones never copied.
- **A forge account's reference copied (#706)**: the forge account's copy maps its reference the same way, to the target's own connection for the same provider and address, and a target holding none refuses it (client-runtime spec, #320's notes).

## Testing Decisions

A good test is behaviour seen through the wire, in a spawned process's environment or in the fake key manager's record of calls; never the registry's tables, the vault file or the scrub registry's map, except at the lower seam.

- **Primary seam: the in-process environment with fake key managers.** The env spec's helper (temporary data directory, loopback port 0, the scripted fake provider, the typed client over a real WebSocket) plus a **fake OpenBao** on loopback port 0 over TLS under a test CA: AppRole, userpass and token logins, lookup, renew and revoke of self, child-token creation enforcing the policy-subset rule and dying with its parent, capabilities, policies, seal status (sealed on demand), mount detection, KV version 1 and 2 reads, writes and lists; a **fake Doppler API**; and the 1Password and Bitwarden providers behind their SDK seams, scripted. **Fake CLIs** named `bao`, `doppler`, `op` and `bws` on a PATH the test sets print a version and report which variables they saw, by name and a hash of each value. The fake provider reports its spawn environment. Through it: sign-in and every status (credential rejected, expired, unreachable, sealed, certificate changed); re-login before a login's maximum life on the injectable clock; a child token per process, renewed, revoked at the idle stop, and a fresh process after a tick changes; shadowed `VAULT_*` and `ENCLAVE_*` values; the injection setting at each level; references resolved, refused and never cached; Move with read-back, `cannot_write`, `copyValue` and `verifyOnly`; import and copy records awaiting sign-in; the orientation text through `instructions.preview` (#89), byte-identical across a verification that changed nothing and different after a status change; scrubbing in the log, the logger, a terminal's output split across chunks and a provider's error text; `secret_shaped` refusals; tool probes, a tool run in a real PTY (skipped where `node-pty` is unbuilt) running a fake installer from a test table, then the probe and verify; the Key manager checks and budget. Prior art: T3 Code's `apps/server/src/server.test.ts` (`buildAppUnderTest`, `withWsRpcClient`), the forge spec's fake forge, and this repository's install-script test with its fake `curl`.
- **The held clock (#745)**: a test on the manual clock moves it and then waits on the connections' `settled` (the environment handle's `keyManagerConnections`), which settles once every renewal, verification, sign-in and revocation taken up off any request has ended, with what each took up in turn; what the test then reads is what the environment did by that time, never what it managed within a time budget. What a holder's stop or a sign-out sets off is waited on as the fake OpenBao sees it (`until`), and a run's end as the log hears it.
- **The lower seam**: each provider against the fake servers without the wire, for mapping, KV versions, rate limits and error categories.
- **Contract tests** in the contracts package: one scope per method; the reference shapes and display form; the tools table (every required tool has a minimum and a verify command, every command a fixed argument list, `vault` never installable, one Install method per platform); the shape rules against true positives and false ones (a kebab-case name ending in `sk-`, base64 tool output); the Key manager entry's checks and actions from ADR 0031's vocabulary; the JSON Schema round trip.
- **Client runtime**: the bulk copy against two in-process environments; the known-environments report.
- **Not tested here**: live OpenBao, Doppler, 1Password or Bitwarden; real installers; the OS keychain (a manual checklist item per platform, as the service install has).

## Out of Scope

Everything under "What this workstream does not decide"; a read-only secret tool for shell-less models (fog, ADR 0011); rotating a run token for a run that outlives its login's maximum life (fog, ADR 0028), and per-run tokens through a token helper; OpenBao namespaces, client certificates and other auth methods (OIDC, JWT, Kubernetes, cloud); 1Password Connect servers; installing `vault`; Codex and local-model tools (milestone 2); switching Claude Code's channel (fog, ADR 0026); per-bot overrides until the Bot object (milestone 2); rewriting logged events or provider session stores.
