# Spec: Permissions: modes, ceilings, containment, denylist, parked prompts

Milestone 1 (Switch-over), phase A (the spine). Written 2026-09-23 from map ticket 83 of `david/agent-harness`. Decisions it implements: ADR 0006 (ceilings per connection, mode and containment as separate switches, the denylist in every mode, never root), ADR 0007 (parked prompts survive a restart), ADR 0015 (the permission broker in the adapter contract; the completions surface takes a mode under the connection's ceiling), ADR 0014 (a browser verb is a tool call under the run's mode; the denylist's browser section), ADR 0016 (the Permissions step registers what it writes, checks and links), ADR 0017 (phase, placeholder name). It builds on `docs/specs/env.md` (ticket 78, PR 97): the wire, the event envelope, pairing with a ceiling, the `access` stream and `environment.subscribe` are fixed there and referenced here. Peers read: T3 Code at 96c4bfa0 (`auth/RpcAuthorization.test.ts`), the Claude Code documentation as of 2026-09-23 (permission modes, sandboxing, hooks, Agent SDK permissions and TypeScript reference), the Codex and Hermes inventories, the surfaces port audit (section 5) and the server bypass-permissions write-up. The product name is the placeholder `agent-harness` throughout.

## Problem Statement

The permission policy for a run lived in three places and had no owner. A completions request carried an unchecked permission-mode field straight into the run and the only filter kept any mode the serving adapter listed, so any token that could reach an account could run it in `bypassPermissions`, and the same token could create a routine and fire it at once. Server routines defaulted to bypass. A parked prompt waited forever: the deadline was removed on 2026-09-15 and the headless host sends no notifications, so a run on SAMPLE-SERVER that asked a question sat until David opened the window. Remote-mode runs were interrupted 60 seconds after the window's last event stream closed, while a completions run lived six hours detached. The headless container ran as root with `IS_SANDBOX=1` to satisfy Claude's root check, so a bypass run was root with the account credentials, the agent's `.env` and every `/work` repository mounted. No test could assert that a connection cannot request bypass, because none could pass; the sandbox flag became a lie told to get bypass.

## Solution

Every client session carries a ceiling fixed when it pairs, and every run, routine and bot created through it is clamped to that ceiling, with the clamp recorded. A session has a mode, one of four modes, that says what the agent may do without asking, and a containment level, a separate switch, that says where it may reach on the environment. One environment-owned denylist of browser domains, paths, command patterns and hosts is never auto-approved in any mode, bypass included, and never overrides a person's explicit answer. A permission prompt or a question is an event in the environment's log: every connected client is told, a reconnecting client finds it in Parked asks, it survives a restart, and after a configurable TTL it is denied and the run continues. Runs with nobody present (routines, bots, programs on the completions surface) never wait: they run in the unattended default mode within their ceiling, and anything that would have asked is denied at once and recorded. Every decision is an event a client can review in one view. The service never runs as root. The Permissions step of Set up writes these settings and checks that they hold.

3. As David, I want a ceiling raised only by admin scope from another session, never by the session itself, so that a paired client cannot escalate itself.
4. As David, I want the four modes to mean the same thing on every provider, and auto shown as unavailable with a reason where there is no classifier, so that a mode is one word and never silently another.
5. As David, I want containment to be its own switch, so that I can run bypass without a sandbox on a machine I trust and a sandbox in acceptEdits on one I do not.

## Implementation Decisions

### Modules

Seven pieces in the env spec's `environment` package, with schemas, the mode order and the denylist matcher in `contracts`: the **policy resolver** (at run start, turns actor, requested mode and containment, account capabilities, ceiling and settings into the run's effective policy and one `run.policy.resolved` event; also answers `permissions.mode.set` and `permissions.containment.set`); the **tool gate** (consulted by every adapter before the provider's own evaluation, for every tool call in every mode; applies containment as a hard deny and hands every denylist match to the broker, which records an opened and answered pair for it whether it parks or is denied at once; never evaluates the mode, which is the provider's job); the **permission broker** (the one place a provider's prompt or question lands, ADR 0015: opens the prompt event, notifies, waits or auto-decides, returns the decision, runs the TTL sweeper); the **denylist** (list, matcher as a pure module so clients preview a match, presets, provider projections); the **containment prober**; the **review projector**; and the Permissions **step entry** (ADR 0016).

### Modes and the Claude mapping

- The modes are `acceptEdits`, `plan`, `auto`, `bypassPermissions` (ADR 0006); `default` and `dontAsk` never appear on the wire. Their **order for ceilings** is a chosen default: `plan` < `acceptEdits` < `auto` < `bypassPermissions`.
- **Claude mapping**, fixed here and built by the adapter workstream: each mode is the SDK `permissionMode` of the same name. `bypassPermissions` also needs the SDK's `allowDangerouslySkipPermissions`, set only when the run's ceiling is `bypassPermissions`, so a later change to bypass below that ceiling is refused by the provider as well as clamped. `plan` keeps its enforced blocks in SDK sessions; the `ExitPlanMode` prompt reaches the broker as a `plan` prompt whose approval also chooses the mode to continue in, clamped like any request. `auto` exists only on accounts whose capabilities descriptor lists it; when the classifier pauses auto, its fallback prompts reach the broker. The adapter always sets `permissionPrompts: 'host'` with a `canUseTool` callback and never uses `dontAsk`.
- **Absent with reason**: an account lacking a mode lists it as `{mode, available: false, reason}`; the resolver clamps to the next lower available mode with `clampReason: 'unavailable'`.
- **Codex mapping, recorded for milestone 2** (ADR 0006): acceptEdits is `on-request` with a `workspace-write` sandbox; plan is a `read-only` sandbox; auto is `approvals_reviewer: auto_review`; bypassPermissions is approval `never` with `danger-full-access`; `untrusted` is never sent. A provider that cannot express a mode comes back to David as a decision.

### Ceilings

- A ceiling is one of the four modes, set at pairing: `access.pairings.create` (env spec) and the CLI's `pair` verb take `ceiling`, preset from the setting `permissions.defaultCeiling`, whose chosen default is `acceptEdits`. The bootstrap grant's local sessions get the top ceiling, `bypassPermissions` (env spec). **A pairing's ceiling is never above its minter's** (#180, decided by David on 2026-09-25): `access.pairings.create` refuses a ceiling above the caller's own, the default included when none is chosen, with `forbidden` (`data.reason` `ceiling`, `data.ceiling` the caller's). `admin` stays in the default scope set, so `/pair` from a phone still works up to the phone's own ceiling, and the bootstrap grant's sessions, holding the top ceiling, mint any; the CLI's `pair` verb mints through the grant.
- **A pairing grants only scopes its minter holds** (#247, decided by David on 2026-09-28): `access.pairings.create` refuses a requested scope absent from the caller's own set with `forbidden` (`data.reason` `scope`, `data.scope` the requested scope). An omitted scope set becomes the minter's own scopes. The bootstrap grant's local sessions hold every scope, so they may still mint any scope set.
- **Inheritance**: a run's ceiling is that of the client session that started it. A routine records the ceiling of the session that last saved it (`savedUnderCeiling`, carried by the routine workstream) and every firing is clamped to it; a bot does the same in milestone 2, and a Hermes profile paired to a bot connects under the bot's ceiling (ADR 0008). A completions request runs under its token's ceiling (ADR 0015).
- **Clamp**: a requested mode above the ceiling becomes the ceiling, recorded in `run.policy.resolved` and returned by `permissions.mode.set`; never an error.
- **Raising and lowering**: `access.sessions.setCeiling` (scope `admin`) is refused with `conflict` (`own_session`) when the target is the caller's own session, so no session changes its own ceiling whatever its scopes. Raising another session above the caller's own ceiling is refused the same way, `forbidden` with `data.reason` `ceiling` (#180); lowering is always allowed, even to a ceiling still above the caller's, and a value equal to the target's is no raise. The change is an `access.ceiling.changed` event and applies to the session's next run; running runs keep their resolved policy.
- **Changing a grant** (#1632): `access.sessions.setAccess` (scope `admin`) atomically replaces another live client's non-empty scopes and ceiling. The target cannot be the caller (`conflict`, `own_session`); every requested scope must be held by the caller (`forbidden`, `scope`) and the requested ceiling must be at most the caller's (`forbidden`, `ceiling`), even when lowering an existing grant. Unknown targets are `not_found`; revoked or expired targets are `conflict` with that reason. An identical grant changes nothing. The access log's `access.changed` records the previous and new grant, the caller and command id. Existing sockets and subscriptions close and reconnect with the same token; the next authentication receives the new grant. Running runs retain their resolved policy. Another admin client can undo the change through the same method.
- Answering a prompt needs scope `runs:drive` only; the answering session's ceiling does not bound the answer, since an environment belongs to one person (ADR 0001).

### Phone authority and attention

Phone grants `read`, `sessions:write`, `runs:drive` at `acceptEdits`; My own
client keeps all scopes and `bypassPermissions`, even on a phone. Browser kind
never changes a minted grant. Expanded Custom codes require a trusted minter
within its scopes/ceiling. Another admin client may instead change the existing grant in Access without re-pairing; no client edits its own access. Files/Diff/
terminal retain `terminal`, Settings writes/sign-in retain `admin`. Prompt
answers retain the `runs:drive`-only rule above, including another client's ask.

Durable attention follows parked events after six seconds, cancelled on answer
or TTL, deduplicated by event/target across restart and cleaned up on client
revocation/expiry. Generic HTTPS session links contain no prompt/transcript
text or secrets. Clients with `read` manage only their own targets; global
routes need `admin`. Failures are audited/visible and never stop a run. Held-clock
fake transports and hosted real-client tests prove these rules (web-client spec).

### Attended and unattended runs; the unattended default

- A run is **attended** when its starting actor is a client session and **unattended** when its actor is a routine, a bot or the completions surface. Attendance is fixed at run start: a run belongs to the environment and continues in its mode when the client goes (ADR 0006), with no grace timer and no keep-alive.
- The **unattended default** is the setting `permissions.unattended.mode`, `acceptEdits` (preset) or `bypassPermissions` (ADR 0006): the mode of every unattended run that names none (a routine or bot without an override, a completions request without `agent-harness.permissionMode`). A routine or bot may override it within its saved ceiling. It is a setting, not a fifth mode.
- Choosing `bypassPermissions` anywhere shows one sentence, fixed here: "The agent will act without asking and can do anything this account can, within the containment you chose." The first acceptance for the unattended default is recorded as `permissions.unattended.bypassAcknowledgedAt` and in the access log.
- **Prompts on unattended runs never park.** Anything the provider or the gate would have asked a person is denied at once with a message the model sees ("Denied: nobody is present to approve this. Continue without it and say what you could not do."), recorded as `prompt.answered` with `decidedBy: {auto: 'unattended'}`, and the run continues. In `bypassPermissions` what the provider still raises (a critical-path removal, an ask rule in the account's own settings) is denied the same way with `auto: 'bypass'`, on attended runs too, because bypass means "never wait" (ADR 0006).
- **Questions** the model asks its user are not permission checks: on an attended run a question parks in every mode, bypass included, as David's own change of 2026-09-15 decided; on an unattended run it is auto-answered at once ("nobody is present; proceed with your best judgement") and recorded with `auto: 'unattended'`. This reading of "bypass never parks" is a chosen default.

### Containment

- Three levels: `off`, `workspace` and `workspace-no-network`. The setting `permissions.containment.default` is preset to `workspace` where enforceable and `off` otherwise; pickers grey unavailable levels with the reason. A session sets its own level with `permissions.containment.set` under scope `runs:drive`, with no own-session rule: containment is the person's choice of boundary, not a grant, and an environment belongs to one person (ADR 0001), so it is deliberately not treated like the ceiling (a chosen default; a client whose ceiling forbids bypass gains nothing by turning containment off). A routine or bot inherits the default unless it overrides; the level is resolved at run start and fixed for the run.
- **Mechanisms and the probe**: on macOS, Seatbelt. On Linux and WSL2, bubblewrap: `bwrap` on PATH and a probe running a trivial command under an unshared user namespace with a read-only root, recording why it failed (binary missing, user namespaces blocked by the kernel, AppArmor or the container's seccomp profile, `socat` missing). A declared container (the install's compose sets the marker) is reported as the operator's outer boundary, so the Your machines step can say what its mounts expose, but it enforces no level: inside a container both workspace levels need bubblewrap to work there, and without it only `off` is offered. Native Windows reports none. The result is reported as capability flags on the discovery URL and in `hello` (`containment:workspace`, `containment:no-network`) and in detail by `permissions.settings.get`.
- **What each level means, for every provider**: `off` applies nothing. `workspace` lets a run read anywhere except denylisted paths and write only inside its workspace, the session's scratch directory and a temporary directory of the session's runs (one per session rather than per run, #133: a session's runs share one provider process, whose temporary directory is fixed when it starts), and the repository's git directory when it lies outside the workspace (#322), and its commands in the directories made for its provider process alone that a tool injected into it writes (a key-manager CLI's configuration directory, #1119), but never in a repository git directory's hooks, config or `config.worktree` files, wherever it lies (#791), nor in those of a submodule's git directory under it (#933). `workspace-no-network` adds that the model's commands and the provider's fetch and search tools reach no host, while the provider process still reaches its API; the harness's own tool servers are the environment's services, not the run's network, and the browser is governed by its session field and the denylist (ADR 0014), not by containment (a chosen default). A harness tool that reaches the network obeys the no-network level all the same: one that declares a fetch (`web_read`, #546) is denied at `workspace-no-network` as the provider's fetch is, and the model reads that the session's containment forbids it (David's decision on #546, 2026-09-29).
- **Enforcement for Claude**: a level the probe cannot enforce is never resolved for a run, so the mapping has only the Seatbelt and bubblewrap cases. The SDK's `sandbox` option carries the shell side with the mechanism the probe found: `enabled` at both workspace levels with `failIfUnavailable: true`; `allowUnsandboxedCommands: false` so the model cannot ask its way out; `autoAllowBashIfSandboxed: false` so containment changes where a command may reach and never whether it asks (a chosen default); `filesystem.denyRead` carrying the denylist's path section on unattended runs only; `network` open at `workspace` and closed (no domains, unix sockets or local binding) at `workspace-no-network`. File tools, fetch and search do not pass through Claude's sandbox, so the gate denies a write outside the writable set and a fetch or search under no-network. The provider process itself is not wrapped in milestone 1; the local adapter's `bwrap` wrapper (ADR 0015) reuses the probe in milestone 2.
- A containment denial is hard: no prompt, the model is told why, the decision is recorded; widening is a settings change, never an answer to a prompt.
- **The environment's own git** (#212): a level binds the provider's commands and tool calls, and nothing the environment runs for itself is wrapped. So `diffs.workingTree` refuses a repository whose own config names a clean, smudge or process filter (`conflict`, reason `git_filters_refused`, the filters named) rather than run it outside the session's containment; a filter the machine's config names runs.

### The denylist

- One environment-owned list with four sections: `browserDomains`, `paths`, `commandPatterns`, `hosts`; an entry is `{id, pattern, note, preset, enabled}`. Domains and hosts take an optional leading wildcard label and match the resolved hostname after userinfo is discarded, as the existing browser driver did; numeric hosts are read as IPv4 in decimal, hexadecimal or octal after every scheme, including `gopher`, `git`, `sftp` and `ldap`. `permissions.denylist.set` refuses an all-digit host or browser-domain entry that is not a valid IPv4 spelling with `invalid_params` naming the entry (#249). Stored entries and historical events retain their grammar; paths are absolute or `~`-relative with glob segments, matched after `~` and symlinks resolve; command patterns are token sequences matched against the command line split on white space and at every operator (a substitution's bracket, a redirection, `;`, `&&`, `||`, `&`; Further Notes, #132), where a bare `*` matches any run of tokens including none and a `*` inside a token matches within it.
- **Path grammar on Windows** (#1385): patterns are `~`, home-relative (`~/...` or `~\...`), POSIX absolute (`/...`), or drive-letter absolute (`C:/...` or `C:\...`), with no NUL. A drive letter must be followed by a separator; `C:relative`, bare drive letters, `~user`, UNC (`\\server\share` or `//server/share`) and device paths (`\\?\...`, `\\.\...`) are refused as patterns. UNC data directories are unsupported; the default data directory is a drive-absolute path under the environment user's local application data. On Windows both separators, including mixed input, delimit segments; comparisons ignore case. POSIX keeps backslashes literal and its existing case policy. Drive roots are preserved through `..`, different drives never match, a root-relative call path uses the working directory's drive, and local `file:///C:/...` URLs read as drive paths. Presets retain their portable `~/...` spelling and the data-directory preset retains its native absolute path. Its containment-directory exemption uses the same path grammar, boundaries, case folding and symlink resolution as every path match. Windows command path tokens retain backslashes and quotes group paths containing spaces; this is a conservative token reading, not PowerShell evaluation.
- **Presets**, seeded on first start and marked `preset: true`: the browser domains are the existing extension list (password managers, payment processors, the large banks by name); paths are `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config/gcloud`, `~/.kube`, `~/.docker/config.json`, `~/.netrc`, `~/.vault-token`, the configuration directories of the 1Password, Bitwarden and Doppler CLIs, and the harness data directory; command patterns are `sudo *`, `doas *`, `su *`, `mkfs* *`, `dd * of=/dev/* *`, `shutdown *`, `reboot *`, `curl * | *sh *`, `curl * |*sh *`, `curl * | sudo *sh *`, the same three for `wget`, `git push * --force* *` and `git push * -f *`; hosts start empty. Entries are freely edited, disabled or deleted; `permissions.denylist.restorePresets` re-adds missing presets; the key manager step adds its manager's paths (ticket 42).
- **Enforcement in every mode, bypass included**: the gate matches every tool call's inputs (paths of read and write tools, path-like tokens and the whole line of a shell command, every URL and host of fetch, search and browser verbs, what the harness's own tool servers receive) and the browser driver matches every navigation and frame (ADR 0014). A match on an attended run opens a `denylist` prompt naming the section and entry; the person's answer decides, and an explicit allow is honoured in every mode, once, for that call. A match on an unattended run, or a `denylist` prompt past its TTL, is denied, recorded as an opened and answered pair like every prompt, and the run continues (ADR 0006 with its review correction). No mode, rule or classifier ever auto-approves a match. A browser sub-frame resolving to a denylisted domain cannot wait and is blocked outright and recorded; top-level navigation prompts (a chosen default carried to the browser workstream).
- **Provider deny rules where they must apply**: on unattended runs only, the Claude adapter projects the path section into the sandbox's `filesystem.denyRead`, so a sandboxed shell cannot read them even when the gate saw only an opaque command, and the command-pattern section into the SDK's disallowed-tools rules for shell. Neither is projected on attended runs, so a person's explicit allow is never blocked by a rule; the cost, accepted here, is that on an attended run a shell command the gate cannot parse (a script that reads a denylisted path indirectly) is not caught, and the person present chose the mode. For Claude the gate is the SDK's in-process `PreToolUse` hook callback, which runs first for every tool call in every mode, and the broker is `canUseTool` for the provider's own prompts; on a denylist match the gate itself asks the broker and awaits the answer inside the hook (the verify-first fallback, chosen by #132 since it holds in bypass too): the hook returns `allow` or `deny` once the person, the unattended rule or the TTL has answered (Further Notes, #132).

### Prompts, parked prompts and the TTL

- A **prompt** has a kind, `permission`, `denylist`, `question` or `plan`, and these fields: tool name, input, a one-line summary, blocked path, the provider's reason, the question set (header, question, options, multi-select) or the plan text, and the provider's remember-suggestions.
- **Command preview** (#256, decided by David 2026-09-28): when a permission or denylist prompt parks, the environment's broker produces `previewLines` from a read-only preview against the session's workspace. Every adapter receives the same behavior; adapters do not supply these lines. The terminal UI draws them under the command. The preview mechanically expands destructive paths and globs, counts files and directories, reads overwrite sizes and runs only fixed read-only Git queries (including `git clean -n`); network destinations are read from arguments without contacting them. It never runs the requested command or a shell. Reads stay inside the workspace, with symlink resolution, a stricter boundary than containment's read access; a denylisted path is not inspected before consent. Existing per-command caps on segments, entries, directory reads, depth and listed paths hold, and a one-second total budget on the environment clock aborts further reads and child queries. The field is nullable: timeout, an unavailable or outside-workspace preview, a non-command prompt, an automatically answered prompt, an unrecognized command, or Windows' different shell grammar records `null`. Cancellation or a run ending before the preview completes opens no prompt. Older events may omit the field and clients draw no preview for them. Lines describe the current disk, not a guarantee about the disk at approval time.
- **Indirect shell preview** (#1224): subshells, brace groups, executable command substitutions, `eval` and shell command options such as `sh -c` produce a conservative cannot-tell warning for the whole command. Their targets are not inspected, because nested syntax and evaluated text need the shell to resolve them. Quoted literal command-looking data, escaped syntax, comments and quoted here-document bodies do not trigger this warning. The existing read-only queries, workspace boundary and budget still hold.
- **Filesystem-maker preview coverage** (#1225): the curated no-dry-run command list includes `mkfs`, `mkfs.ext2`, `mkfs.ext3`, `mkfs.ext4`, `mkfs.xfs`, `mkfs.btrfs`, `mkfs.vfat`, `mkfs.fat`, `mkfs.msdos`, `mkfs.exfat`, `mkfs.ntfs`, `mkntfs` and `mke2fs`, including absolute executable paths. These receive the existing qualified no-dry-run warning and workspace-scoped target details without executing a formatter. Other `mkfs` prefixes are not implicitly recognized.
- **Every prompt is an event** on its session's stream (`prompt.opened`) resolving with exactly one `prompt.answered`. For an attended prompt the environment also emits a notice on `environment.subscribe` (`prompt.parked` with session, prompt and title; `prompt.resolved` when it ends) so every connected client learns of it whatever it is subscribed to: the desktop raises an OS notification through the shell API, the terminal UI rings its bell and sets its title, the web tab shows it in-app. The session-list summary carries a `parkedPromptCount` (the session-state spec's name, conflict X4), with `activity` `parked` while a prompt waits, so Parked asks and the sidebar badge are projections.
- **Placement** (David's constraint, carried to the renderer specs): below the transcript and above the composer until answered, then in the transcript at the sequence of its `prompt.opened` event. **Parked** means opened and not yet answered; `permissions.prompts.list` returns every parked prompt of the environment or of one session. After a restart the open prompts are rebuilt from the log and presented where they were (ADR 0007); an answer is delivered live when the run that asked still waits on it, else it is kept for the session's next run, whose first message it becomes (#130; Further Notes say why not the SDK's deferred-tool path).
- **TTL**: the setting `permissions.parkedPrompt.ttl` is a duration, preset 24 hours, or `never`; `ttlExpiresAt` is fixed on `prompt.opened`. A sweeper runs every 60 seconds (chosen default) and at startup; an expired prompt is answered `deny` with `auto: 'ttl'` and the run continues: live when its run still waits, else through the session's next run, which the TTL's answer starts itself (#131, Further Notes). This is the **deny-and-continue rule**: every automatic denial is a deny with a message the model sees and never an interrupt. A prompt whose run ends on its own first (the provider completes it, fails or is interrupted, or the environment records its error) closes with `auto: 'run_ended'`. A run the environment stops under a prompt (the parked stop and an admin's process stop, a drain, a deletion, the environment closing, and the recovery sweep's `restart`) leaves it parked (ADR 0007): the provider is denied in memory, and a person's later answer goes to the session's next run, which it starts at once only when an update cut the run (#345, Further Notes).
- **Answering**: `permissions.prompts.answer` carries `allow` or `deny`, an optional message, the answers to a question, for a `permission` prompt an optional edited input, for an approved `plan` prompt the mode to continue in (clamped like any request; absent means `acceptEdits`, a chosen default, so a one-key approval leaves plan), and `remember: 'session'` for no further prompt on that tool in that session. Remembering applies to `permission` prompts only, never to a `denylist` prompt, and is per session only; the harness never writes a permission rule into the repository's or the account's settings files from a prompt (a chosen default). An answer part that does not fit the prompt's kind or decision (remember on anything but an allowed `permission` prompt, edited input on anything but a `permission` prompt, answers on anything but a `question`, a mode on anything but an approved `plan`) is `invalid_params`; `prompt.answered` does not carry its prompt's kind, so its schema cannot hold that fit, and the prompts projection holds it instead: an unfit answer from anyone, a rule's included, fails its append. An approved plan's mode becomes the session's, recorded as `permissions.mode.set` records it (the default counted as asked for, so a lowered one is a clamp). A second answer is `conflict` with reason `already_answered`, an unknown prompt `not_found`.
- Prompt state machine, from the broker prototype:

```
opened ──answered by a person──▶ answered(person)
   ├──unattended run (any kind)───▶ answered(auto: unattended)   at once
   ├──kind permission, mode bypass─▶ answered(auto: bypass)        at once
   ├──TTL elapsed───────────────▶ answered(auto: ttl)
   ├──run ended first──────────▶ answered(auto: run_ended)
   └──provider cancelled it──────▶ answered(auto: cancelled)       (#130)
```

A run that ends on its own takes the `run_ended` branch; a run the environment stops (parked, an admin's stop, a drain, a deletion, closing, a restart) takes none, and the prompt stays opened until a person answers it (#130).

### Methods on the wire

All follow the env spec's registry: one scope each, `commandId` on every mutating method, the shared error union.

- `permissions.settings.get` (`read`) returns the default ceiling, the unattended mode and its acknowledgement time, the TTL, the containment default and availability with reasons, whether the process is root (always false, present so a future exception is loud) and denylist section counts; `permissions.settings.set` (`admin`) takes any subset plus `acknowledgeBypass: true`, which must accompany the first setting of the unattended mode to `bypassPermissions` (the environment then records `bypassAcknowledgedAt`); it answers `containment_unavailable` for an unenforceable default and `invalid_params` for unattended bypass without the acknowledgement.
- `permissions.denylist.get` (`read`), `permissions.denylist.set` (`admin`, one section or all), `permissions.denylist.restorePresets` (`admin`, the sections named or all), `permissions.denylist.test` (`read`: kind and value in, matching entries out).
- `permissions.mode.set` (`runs:drive`): session and mode in, effective mode and clamp out, applied live through the adapter's mode change, else at the next run. `permissions.containment.set` (`runs:drive`): effective at the next run, `containment_unavailable` when unenforceable.
- `permissions.prompts.list` (`read`), `permissions.prompts.answer` (`runs:drive`), `permissions.review.list` (`read`), `permissions.review.seen` (`sessions:write`).
- `access.sessions.setCeiling` (`admin`), added to the env spec's `access.sessions.*` family; `access.pairings.create` gains its `ceiling` value set and preset.

### Events

Session stream, in the env spec's envelope:

- `run.policy.resolved`: run, actor kind, attended, mode (requested, effective, ceiling, clamped, clamp reason), containment (requested, effective, mechanism, reason), whether the unattended default applied, and a routine's or bot's own credential injection when it has one (key-managers spec, #367); exactly one per run, before the first provider event.
- `session.mode.set`: the session's mode in the same shape (requested, never null here; effective; ceiling; clamped; clamp reason) and the live run it reached at once, null when none was live or its adapter cannot change a running run's mode. `session.containment.set`: the user-set fields in the same requested, effective, clamped shape.
- `prompt.opened` and `prompt.answered` as above; `decidedBy` is a client session id or `{auto}` with one of `unattended`, `bypass`, `ttl`, `run_ended`, `reviewer` (reserved for Codex's auto review), `cancelled` (the provider cancelled the request while its run went on, #130).
- `tool.decision`: one per tool call: tool, one-line summary, `allowed` or `denied`, `decidedBy` as one of `person`, `mode`, `rule`, `classifier`, `denylist`, `containment`, `ttl`, `unattended`, `bypass`, `provider`, the prompt id when there was one, the reason when denied. Calls the provider approved without asking are derived from the transcript's tool events as `mode`; rule denials come from the provider's own denial report.

Access stream (the access log, env spec), added here and read through `access.log.list`: `access.settings.changed` (area `permissions`, keys, actor), `access.denylist.changed` (section, entries added, removed or edited, actor), `access.bypass.acknowledged`, and every `access.ceiling.changed`. The `access.` prefix names the stream: on the wire the types are `settings.changed`, `denylist.changed`, `bypass.acknowledged` and `ceiling.changed`, after the env spec's `pairing.created` and the rest (#129).

Environment stream (notices on `environment.subscribe`, #811): `denylist.updated` (the sections that changed), in the transaction of a person's `denylist.changed`, and `review.updated` once a change to what `permissions.review.list` answers commits. A client's request cache reads the denylist, the permission settings (their section counts) and the review again on them.

### The Unattended review view

`permissions.review.list` returns qualifying runs since the watermark, newest first: session and run ids, when it ran, actor kind (routine with its name, bot, completions, client), effective mode and clamp, containment, counts of tool calls, auto-approved, denied, answered by a person and expired, and each denial with tool, summary, decider and reason. A run qualifies when it was unattended and made a tool call or had a denial, or attended with a decision by `ttl`, `denylist` or `containment` (a chosen default so David's own bypass runs do not flood the view). `permissions.review.seen` moves the environment-wide watermark; clients hold no state (ADR 0003).

### Never root

`serve` exits before opening the database when the effective user id is 0 on Linux or macOS or the process token is elevated on Windows, printing one sentence; no flag or environment variable changes this, and a declared container is not an exception. The container image sets a `USER`, the install script's compose sets that user and owns the volumes, and the Your machines step's health check reports it. The harness never sets `IS_SANDBOX` or `CLAUDE_CODE_BUBBLEWRAP`, and the Claude adapter's credential spec strips both from the provider process environment, so Claude's root check never applies and is never worked around.

### The Permissions step

Registry entry (ADR 0016), step id `permissions`, ninth in the milestone-1 order, band Access:

- **Writes**: `permissions.defaultCeiling`, `permissions.unattended.mode` (with the bypass sentence and acknowledgement), `permissions.parkedPrompt.ttl`, `permissions.containment.default`, the denylist's four sections.
- **Checks**: done when the settings record has been saved once here, the containment default is enforceable here, the denylist holds its preset sections or a deliberate emptying, and the environment reports not root; otherwise needs attention naming the failing item, with the Linux package hint (bubblewrap and socat, the Ubuntu 24.04 AppArmor profile) when containment fails; never skipped.
- **Links**: Settings, Access, Permissions pane; the Your machines step for another environment's containment availability.

## Testing Decisions

- **A good test** drives a rule through the wire or the adapter contract and asserts what a client or a provider sees: a `run.policy.resolved` event with `clamped: true`, a `prompt.parked` notice on every connected client, a deny handed to the fake provider with the message the model would read. Never an assertion on a projection table or a private map of open prompts.
- **Primary seam: an in-process environment and a real client.** The env spec's helper starts an environment on a temporary data directory on loopback port 0, with the adapter contract satisfied by a scripted fake provider, and returns the thin typed client from the contracts package over a real WebSocket. The fake provider is scripted per test to make tool calls (a read of `~/.ssh/id_rsa`, a write outside the workspace, a fetch under no-network, `sudo apt install`), to raise a permission prompt, to ask a question and to propose a plan. Cases: a ceiling reported in `hello` and a mode above it clamped and recorded; a session refused when raising its own ceiling and a second admin session succeeding, in the access log; an attended denylist match parking a prompt, notifying two connected clients, answered from the second, the decision recording who; an unattended run denied at once and continuing; a bypass run's residual prompt denied with `auto: 'bypass'` while a question on the same run parks; TTL expiry denying and continuing, and `never` never expiring; a parked prompt present after a stop and start on the same directory; containment denying a write outside the workspace and a fetch under no-network; a completions request without a mode getting the unattended default clamped by its token's ceiling; the review list qualifying the right runs and the watermark moving; the step's check reporting needs attention when the default is `workspace` and the probe finds no mechanism. Prior art: T3 Code's `buildAppUnderTest` and `withWsRpcClient`.
- **Adapter seam** (owned by the adapter workstream; cases named here): with the SDK transport scripted with `vi.hoisted`, assert the option table per mode and ceiling (`permissionMode`, `allowDangerouslySkipPermissions` only at ceiling bypass, `permissionPrompts: 'host'`, the `sandbox` settings per level, `filesystem.denyRead` carrying the path section), that the hook consults the gate before the provider and `canUseTool` hands every prompt to the broker, and that a mode change reaches the SDK's mode setter.
- **Contract tests in the contracts package**: every mode has a Claude mapping and a place in the order; the matcher's grammar on a fixture of paths, commands, hosts and domains including the userinfo and symlink cases; every event type and method above has a schema and exactly one scope (T3 Code's authorization test is the model); the Permissions step's entry names every setting key this spec writes (ADR 0016).
- **Framework**: Vitest; serial files where a listener is bound; the fake provider beside the env spec's tests. Not tested here: the OS mechanisms themselves, Claude's classifier, OS notifications.

Decided in building modes, ceilings and the policy resolver (#129):

- **Where the pieces are**: the four modes, their order and the Claude mapping in `contracts/src/permissions-modes.ts` (a leaf, so the adapter descriptor and the ceiling can name a mode); the resolution, the events and the bypass sentence in `permissions.ts`; the settings' keys and `settings.changed` in `permissions-settings.ts`; the methods in `methods/permissions.ts`, with `access.sessions.setCeiling` in the `access` family. The ceiling is a mode: `default` and `dontAsk` are refused on the wire wherever a mode or a ceiling is taken (`runs.start`, `sessions.create`, `access.pairings.create`, `hello`), with an issue that names the four. Containment's availability is a placeholder module (`environment/src/permissions/containment.ts`) #133 replaces.
- **The resolver** (`environment/src/permissions/resolver.ts`) is pure: `{actor, requested, ceiling, accountModes, settings}` in, `{actorKind, attended, mode: {requested, effective, ceiling, clamped, clampReason}, containment, unattendedDefaultApplied}` out. **Attended follows from the actor's kind**: a client session is attended, a routine or a bot never, and only a completions request says for itself (claude-adapter spec, the completions surface), so nothing can mark a routine attended. An attended run that names no mode, and whose session names none, starts in `acceptEdits` (a chosen default: the harness never hands a provider its own default); an unattended one gets `permissions.unattended.mode`. The start mode is lowered to the ceiling, then down past every mode the account lists unavailable or does not list; `clampReason` is `unavailable` when the second step lowered it, else `ceiling` when the first did. **A default is not a clamp**: when nothing was requested, `clamped` is false and `clampReason` null even when the default was lowered (under a `plan` ceiling a run that asked for nothing reports `plan`, unclamped). Only when no mode at or below the ceiling is available is a run refused, `conflict` with reason `mode_unavailable`: the ceiling is never exceeded.
- **`run.policy.resolved` once per run, before the provider's first event**: it is appended in the same append as `run.started`, right after it, by the decider of `runs.start` and `runs.send` (and of `runs.readNow` for the run of the queue it starts when no run is live, #228) and by the host for a run it starts from the queue (a read-now's after its interrupted run included) or adopts, before the run is launched or consumed. The resolver is the host's policy seam (`PolicySeam`, replacing #119's identity clamp); the environment's reads the permission settings in the transaction. The run's plan holds its policy, so nothing that changes after its start (a ceiling, the session's mode, a setting) touches the record; `RunInput` carries the effective mode and the ceiling it was resolved under, for Claude's `allowDangerouslySkipPermissions`.
- **Runs the environment starts after another are resolved afresh**: a run from the queue carries no mode of its own (a mode `runs.start` named was that run's alone) and asks for the session's mode as it is then, under the actor's ceiling as it is then. A turn the provider opened on its own is resolved the same way; when the result is not the mode the provider runs it in, the turn is changed to it through `setMode` (`modeChange`), and when it cannot be, or the actor's client session has been revoked or has expired, or no mode is available, the turn is let go, its messages come back to the environment's queue (`message.requeued`) and a run from the queue is tried. Both are resolved under the lowest of the actor's ceiling as it is then (the actor is the client session that started the run before it) and the ceiling each message's sender had when it sent it (`message.sent.ceiling`, #119), as every run that reads queued messages is. A run from the queue is not started for a client session revoked or expired since: its messages wait for the next run. A turn let go goes through the host's one requeue path (#119's), which takes back what the provider held.
- **The ceiling is read as it is now**: `runs.start`, `runs.send`, `permissions.mode.set`, `sessions.create` and the runs above read the client session's ceiling from the environment's memory, not from the socket's `hello`, so `access.sessions.setCeiling` applies to that client session's next run even on a socket opened before it; a revoked or expired client session has none. The change updates the `client_sessions` row and appends `ceiling.changed`; the same ceiling again is accepted with no event; a revoked target is `conflict` reason `revoked`, an unknown one `not_found`.
- **`permissions.mode.set`** clamps like a run (the caller's ceiling, the session's account's modes) and appends `session.mode.set` with `{mode: {requested, effective, ceiling, clamped, clampReason}, live}`, `list`-flagged, patching the summary's `mode` field with the effective mode (#179); the result is that payload with the session's id. The mode the session has already appends nothing (receipt `changed: false`). The session's next runs ask for the **effective** mode, so a mode set under a low ceiling is never raised by a run started under a higher one. A live run gets it at once when its adapter declares the new capability flag `modeChange` (the run's `setMode`, Claude's mode setter), clamped to the run's own ceiling as well, and even when the session's mode did not change; `live` names the run and the mode it got, else null and it applies at the next run. The run's `run.policy.resolved` is not re-appended.
- **The session's mode is read from its summary** (#179): the session summary's `mode` field is the effective mode `permissions.mode.set` last gave the session, else the one `sessions.create` recorded, else null, patched on the list stream by `session.mode.set` (`list`-flagged, session-state spec), so a status line shows it after any resubscribe without reading the session's events; the environment's own reads (`readSessionFacts`) answer the same value.
- **`sessions.create`** stores the mode it is given as the caller's ceiling and the account's modes allow (the effective mode, or none when nothing is available), for the same reason: a `plan` client cannot leave `bypassPermissions` for a later run from the desktop to ask for.
- **The account's modes**: the descriptor's `modes` is a list of `{mode, available: true, reason: null}` or `{mode, available: false, reason}`; `sessions.create` still refuses a mode its account's adapter does not list at all.
- **The settings**: `permissions.defaultCeiling` (a mode, preset `acceptEdits`), `permissions.unattended.mode` (`acceptEdits` or `bypassPermissions`, preset `acceptEdits`), `permissions.unattended.bypassAcknowledgedAt` (a time or null, written only by the environment), `permissions.parkedPrompt.ttl` (`{amount, unit}` of 1 to 1000 minutes, hours or days, or `never`; preset 24 hours) and `permissions.containment.default` (preset the environment's since #133: `workspace` where it can be enforced, else `off`, as the #133 note on the default says; a level that cannot be enforced is `containment_unavailable`, whose reason is never empty), each in the settings key table (`settings.ts`, #117) with its schema, preset, place and `writtenBy: "permissions.settings.set"`, so the generic `settings.update` refuses them (as unknown keys, `invalid_params`) while `settings.get` reads them. The place is step `permissions`, band `access`: ADR 0027 puts the Permissions row in the Access band as `access.permissions`. `permissions.settings.get` answers `{values, containment, isRoot: false, denylist: {browserDomains, paths, commandPatterns, hosts}}`, where `containment` is the `ContainmentReport` (`levels`, each with `available`, `reason` and `cause`; `mechanism`; `container`, the #133 notes below) and the counts are zero until #132; `permissions.settings.set` takes `{values, acknowledgeBypass?}`, keyed by setting key, compares values by structure, and answers every value. A change is one `settings.updated` on the settings stream (its aggregate, read back through the settings store) and, in the same transaction, `settings.changed` with the keys that changed and their new values, typed by the key table as #117's `settings.updated` is (the values beside the keys, a chosen default, so the access log says what a setting became); a malformed one fails its append at the projector rather than falling back to a preset unseen. The first bypass appends `bypass.acknowledged` (`{setting, sentence}`) before it. The first bypass without `acknowledgeBypass: true` is `invalid_params` at `acknowledgeBypass`, its message quoting the sentence; an acknowledgement sent without that first setting records nothing.
- **The Permissions step's entry** is in the step registry stub (`steps.ts`): it writes the five keys, checks each with `anyValidValue`, and links to the permissions pane in the Access band, so the registry's contract test holds; #141 gives it its real checks (containment enforceable, the denylist's presets, not root).
- **Left open, for others**: the session's mode is on neither the session summary nor the snapshot, so a client learns it from `session.mode.set` and `run.policy.resolved` only (a follow-up for the session-state workstream). Pre-#129 data is not migrated: `client_sessions` rows with a free-text ceiling fail the start, and `run.started` payloads with `effective: null` no longer parse; nothing was released before #129. The authority of a pairing is not bounded by its minter's ceiling: a leaked `acceptEdits` token that holds `admin` can mint a `bypassPermissions` pairing (or raise another client session's ceiling), so `admin` is the real bound today; a decision for David.

Decided in building the permission broker and parked prompts (#130):

- **Where the pieces are**: the vocabulary in `contracts/src/prompts.ts` (the kinds, `prompt.opened` and `prompt.answered`, `decidedBy`, the delivery, the answer's input, the listed prompt; `ParkedPrompt` moved there from `transcript.ts`), the notices in `notices.ts`, the methods in `methods/permissions.ts`. In the environment: the broker is the adapter host's (`adapter/host.ts`, `brokerFor`, replacing #119's auto-deny placeholder, which is gone with its `broker` seam), with the payloads and the next-run message in `permissions/broker.ts`; the read model in `permissions/prompts-store.ts`, a `prompts` table the permissions projector keeps; the methods in `permissions/prompt-methods.ts`; the notices in `permissions/prompt-notices.ts`. The names are the permissions spec's (conflict X1): the claude-adapter spec's `prompt.raised`, `runs.answerPrompt` and kind `tool` are gone from it.
- **A prompt's fields**: `prompt.opened` carries the run, the prompt's id, its kind, the tool name and tool call id, the input, a one-line summary (at most 300 characters: the adapter's own, else a question's first question, a plan's first line, the tool with the input's command, path, url or pattern, the tool, or a sentence for the kind), the blocked path, the provider's reason, the question set (header, question, options with label and description, multi-select), the plan text, the remember-suggestions in the provider's own terms, the subagent, the run's mode when it asked and the ceiling it was resolved under (which a plan's continue mode is clamped to, and a client can grey modes above), and `ttlExpiresAt` (fixed from the TTL setting by #131, below). An adapter maps its provider onto these fields (`PromptRequest.detail`, now the typed `PromptDetail`); the host records what it is given.
- **Recorded where the ask reaches the host**: `prompt.opened` goes on the session's stream in a transaction of its own as the adapter's request reaches the host, correlated to the session's live run and attributed to the adapter (`adapter:<provider>`), whose ask it is; the run parks after it commits. A request made when no run is live, cancelled before it was made, that the log will not take, or under the id of a request its run holds open (the open one stands and stays answerable; #130's review), is denied at once and parks nothing. The #131 seam is `PromptAutoAnswer` (`adapter/seams.ts`, preset: none): a rule's answer is appended in the same transaction as the opening, attributed to the host, so the prompt never parks and raises no notice; #131 fills it with the unattended and bypass rules (below; the reviewer's is milestone 2's). What is recorded is what the run is handed, every part of it (`mode` and `remember` too; #130's review): a mode a rule gives is clamped to the run's ceiling and its account's modes as a person's plan answer is (`ruledAnswer`), and the live run continues in it; unlike a person's plan approval, it does not append `session.mode.set`: #131's rules give no mode (each is a deny), so none does yet.
- **Exactly one answer**: the prompts projection refuses a `prompt.answered` for a prompt that is not parked and a `prompt.opened` for an id that is, so the rule holds at the log whoever appends; a prompt's id is the adapter's own (Claude's tool use id) when it names one, else a UUID the host mints, and a later prompt may reuse an id once the first is answered (the latest wins a lookup by id).
- **The boundary on a prompt whose run ends** (both specs state it): the host closes a run's parked prompts with `auto: run_ended`, just before the run's `run.ended` and in its transaction, when the run ends on its own: its adapter's end, whatever its reason (`completed`, `error`, `interrupted`, a person's `runs.interrupt` included, since the adapter ends it), or an error the host records for it (the stream failed, stopped without an end, a refused event, a failed start, a failed interrupt). Every other end the host makes is a stop and closes nothing: the parked stop (`interrupted`, cause `parked`), an admin's `providers.processes.stop` (cause `user`, recorded as the admin's, #120's note), a deletion and the environment closing (`disposed`), the drain's cap (`drained`), and the recovery sweep's `restart`. In every case the broker's open requests of the run are denied in memory, so no adapter waits on a run that has gone.
- **Cancelled is a sixth automatic decider**: when the provider cancels a request (its signal aborts: the tool call became moot) and the run goes on, the prompt would otherwise stay parked until the run's end with nobody able to answer it usefully, so it closes at once with `auto: 'cancelled'` and delivery null. A reviewer who wants the five of the ticket only would fold it into `run_ended`, which says something false while the run continues. Named `cancelled`, not the build's first `withdrawn` (#130's review): the glossary's **Withdraw** is the verb that takes a queued message back (`message.withdrawn`, on the same stream), and it gives "cancel" to a prompt; the SDK's own word is the CLI's cancel request. A provider that cancels its request as its turn is interrupted closes the prompt `cancelled` before the run's end can close it `run_ended` (whether Claude's CLI cancels a pending permission request on an interrupt is not verified).
- **The list** answers `not_found` (kind `session`) for a session it names that is not on the environment or is deleted, as every query naming a session does (#124's deleted-session sweep), and leaves a deleted session's prompts out of the environment's list.
- **The answer**: `permissions.prompts.answer` looks the prompt up by id (unknown: `not_found`, kind `prompt`, aimed at the environment's stream; its session deleted: `not_found`, kind `session`), refuses an answered one `conflict` `already_answered`, and refuses `invalid_params` for `remember` on anything but a `permission` prompt or with a deny, `updatedInput` on anything but a `permission` prompt (on a question it would replace the whole tool input), `answers` on anything but a question and `mode` on anything but an approved plan (#130's review). A prompt's id is the adapter's and the projection scopes it per session, so the answer takes an optional `sessionId`: with it, that session's prompt under the id (the session not on the environment or deleted: `not_found`, kind `session`); without it, the one prompt parked under the id, else the latest answered one, and an id parked in more than one session is `conflict` `ambiguous_prompt` with the sessions, aimed at the environment's stream (#130's review; latent for Claude, whose tool use ids are unique per call). An approved plan continues in the mode asked for, `acceptEdits` when none was, clamped to the run's recorded ceiling and its account's modes (the answering session's own ceiling bounds nothing, ADR 0001), recorded as a `ModeResolution` on the answer; and the session is set to that mode with `session.mode.set` in the same transaction (live when the run still waits), so its next runs continue in it, as approving a plan does in Claude Code. The answer is appended in the command's transaction, attributed to the client session and correlated to the prompt's run, with `decidedBy` the client session's id and `delivery` `live` when the run that asked is live and still waits on it (a live run that no longer does is `conflict` `prompt_not_open`), else `next-run`. After the commit the host hands a live answer to the run (`AdapterHost.deliverAnswer`): through the adapter's `answerPrompt` when it declares `interactivePrompts`, and by settling the broker's request whatever the adapter says, so a run never waits on an answer the log holds. It is the host's one answer path (#224): #121's `AdapterHost.answerPrompt` handed the adapter an answer without settling the request, and is gone from the interface. The refusals the host can know are checked in the transaction and become the command's `conflict`; an adapter that refuses after the commit (its turn ended between the check and the hand-over: Claude denies the call itself then) is logged, and the log keeps the person's answer (a known, narrow race).
- **Next-run delivery** (the ticket's "decide and record"): an answer whose run had gone is kept, and the next run the environment launches on the session (`runs.start`, a `runs.send` that starts one, a run of the queue: any `run.started` but a provider-opened turn's, which is open already) takes it as its first message, one message per answer in the order given, before the run's own. The prompts projection marks the answers the run takes on its `run.started`, so each is delivered once; the message says what was asked, what was answered (a question's answers, a plan's verdict and mode, allowed or denied with the edited input) and, for a permission, that the call did not run and should be made again if still needed, with the person's message. It is not an event: the prompt's `prompt.answered` with `delivery: next-run` and the next `run.started` say where it went. A `remember` given this way is recorded but not applied (the provider's session rules were the stopped process's); an answer given while a newer run is live waits for the run after it; a run whose adapter never received its input (its creation failed after its start committed) gives the answers it took back with its messages, which its `message.requeued` for a message it started with marks, so the session's next run takes them again (ADR 0022: nothing is lost; #130's review).
- **The notices**: `prompt.parked` (session, run, prompt, kind, the session's title as listed, the prompt's summary) when a prompt parks, and `prompt.resolved` (session, run, prompt, decision, `decidedBy`) when a prompt that parked is answered, appended to the environment's stream by a log subscriber once the prompt event has committed, caused by it and correlated to the run. A prompt a rule answered in the transaction that opened it raises neither. The prompts parked before a start count as raised, so an answer after a restart resolves them. The kind and summary beside the ticket's session, prompt and title are a chosen default, so a notification can say what is asked without a read.
- **The summary fields** (session-state's, replacing the provisional projections): a prompt opened counts and parks the session (`activity: parked` from its instant); answered, it counts down and moves `lastActivityAt`. While a run is live the session is `parked` exactly while one of that run's own prompts waits, else `running`: a run started while a prompt a stop kept open still waits is `running`, the count kept, and so is a run whose own prompts are all answered (#130's review); with no run live, the last one answered leaves the session `idle`. A run's end leaves the session `parked` while a prompt a stop kept open still waits, else `idle`. The session-list table keeps the session's live run and how many of the parked prompts are its own beside the fields (`live_run_id`, `live_run_prompts`, no summary fields) for that rule, since a projector reads only its own tables.
- **`environment.status`** reports busy (`parked-prompt`) for a run parked on a prompt for ten minutes from the park, through the run registry as #112 built it; a prompt a restart or a stop kept open parks no run, so it holds nothing busy after it.
- **The transcript**: the snapshot's items gain a `prompt` item where each prompt was asked, with its `prompt.opened` and, once answered, its `prompt.answered`; `parkedPrompts` holds the typed `prompt.opened`. Compaction removes neither event.
- **The Claude adapter** (#121's `#canUseTool`, contract kept): it maps the CLI's request onto `PromptDetail` (the permission title as the summary, `decisionReason` as the reason, `blockedPath`, the tool use id, the `AskUserQuestion` question set read tolerantly, `ExitPlanMode`'s plan text, the CLI's suggestions, the subagent), and an allow onto the SDK's result: the edited input, a question's answers under `answers` as `AskUserQuestion` reads them, an approved plan's mode as a `setMode` for the session, and `remember: 'session'` as the CLI's suggestions with their destination set to `session` (an allow rule for the tool when it offers none), never a settings file. The SDK's allow result carries no message, so a person's message with an allow does not reach Claude (it is recorded); a deny's does. `PromptDecision` gained the answer's parts; nothing else of the contract changed.
- **Verify first, the SDK's deferred-tool path**, read in the pinned 0.3.281 declarations and the bundled CLI 2.1.281, not run: `defer` is a decision of a `PreToolUse` hook only (`HookPermissionDecision`); `canUseTool`'s `PermissionResult` is allow or deny, so the adapter's broker, which is `canUseTool`, cannot defer. A deferring hook ends the turn (`terminal_reason: 'tool_deferred'`, the result carrying `deferred_tool_use {id, name, input}`), and a later query resuming the session re-emits that call through `PreToolUse` and the permission check (the CLI's "Deferred tool resume: re-emitting … through PreToolUse"; `tool_deferred_unavailable` when the tool is gone), where a stored answer could be given. It is not used: the choice to defer is made when the prompt opens, before anyone knows a restart will come, so every parked prompt would end its turn and its run, undoing #120's parked process; by the time a restart is known the CLI process and its pending control request are gone; the declarations do not say whether a streaming-input session defers as `-p` does (a sanitiser in the CLI drops `defer` from some hook outputs, which could not be placed); and the session store the resume would read is #137's. Decided in building containment (#133):

- **Where the pieces are**: the levels, their order (`compareContainment`), the mechanisms, the causes, the report (`ContainmentReport`), `session.containment.set`, `tool.decision` and its ten deciders, the adapter's `containment` capability flag and `permissions.containment.set` in `contracts`; in the environment, the probe (`permissions/containment-probe.ts`), what follows from it (`permissions/containment.ts`: the report, the adapters' requirement, the flags, the default's preset, the lowering; it replaces #129's placeholder), the session's directories (`permissions/containment-directories.ts`) and the tool gate (`permissions/gate.ts`: the containment rule and `createToolGate({log, liveRunOf})`, which the adapter host hands each run).
- **This follows the spec, not ADR 0006's or the glossary's "or a container"**: ADR 0006 says a level is "enforced by bubblewrap, Seatbelt or a container" and CONTEXT.md's Containment entry "enforced by the operating system or the container"; this spec, and the code, treat a container as the operator's outer boundary that enforces no level. Both wordings are flagged for domain-modeling.
- **The probe** runs once, as the adapter host starts (inside the env spec's `adapter-host` step, so the startup order is unchanged), through a machine seam (`ProbeSystem`) the tests script; the environment option `probeContainment` replaces it whole, and the helper's preset finds no bubblewrap. On Linux it runs `bwrap --unshare-user --ro-bind / / -- true`, then the same with `--unshare-net`, and needs `socat` on the PATH; all three are needed for either workspace level. The network namespace is required at `workspace` too because the pinned sandbox runtime (the bundled 2.1.281 CLI) unshares the network whenever it restricts it (`needsNetworkRestriction`, which is `network.allowedDomains !== undefined`), and whether #140 can express `workspace`'s open network with no `allowedDomains` and no per-domain prompts is #140's verify-first; #140 may relax it. A failure is read from the kernel's files in this order: `kernel.unprivileged_userns_clone` or `user.max_user_namespaces` at 0 (`userns_blocked`), `kernel.apparmor_restrict_unprivileged_userns` at 1 (`apparmor`), a seccomp filter on the process (`seccomp`), else bwrap's own first line (`failed`); with `bwrap` missing it still tries `unshare --user` to say whether installing it would be enough. Every problem found is named in one reason. A command that runs past the five-second timeout says "timed out after 5 s". On macOS `sandbox-exec -p '(version 1)(allow default)(deny network*)' /usr/bin/true`; native Windows and any other platform report none (`platform`). A probe that throws leaves only `off` (`probe_failed`, the error as the reason); it never fails a start.
- **The adapter's flag**: a workspace level is available only when the probe allows it and every adapter the environment holds declares `containment` in its descriptor; otherwise it is unavailable with cause `adapter` ("the adapter does not enforce containment yet"), the mechanism null, no flag advertised and the preset `off`. A level the probe refused keeps the probe's cause. The fake adapter declares it; the Claude adapter declares `false` until #140 maps the level onto the SDK's `sandbox` option, so until #140 no environment records a mechanism it does not enforce. Requiring every adapter rather than the session's own is stricter than needed while there is one provider; a second provider without the flag (milestone 2) would have to make it per adapter.
- **Availability on the wire**: each level carries `reason` for people and `cause` for code (`binary_missing`, `userns_blocked`, `apparmor`, `seccomp`, `socat_missing`, `failed`, `platform`, `adapter`, `probe_failed`, `not_probed`), and `containment_unavailable` carries both, so #141's step can give the package hint. The flags `containment:workspace` and `containment:no-network` go into the one capability list the discovery document and `hello` share.
- **The default**: its preset is the environment's, `workspace` where it can be enforced, else `off`, answered by `permissions.settings.get` and the generic `settings.get` for a key never set (`readSettings` takes the environment's presets). A value given when none was stored is stored even when it equals the preset (`changed: true`), so an explicit choice no longer follows the probe. `permissions.settings.set` checks the default's availability only when it differs from the stored value, so a stored default a restart found unenforceable does not block saving the rest.
- **Lowered, not clamped**: a run asks for its session's own level, else the stored default, else the preset's `workspace`, and gets the highest level at or below it the environment can enforce; never an error. Unlike the mode, where a lowered default is not a clamp (CONTEXT.md), a lowered level always records `reason`, the preset's `workspace` included ("The preset default is workspace where it can be enforced, and it cannot be ..."): a deliberate difference, since a run with less containment than the rules ask for must never be silent about it, the case of a restart that lost bubblewrap included. On a machine that can enforce nothing every run therefore carries that reason. Since both setters refuse an unenforceable level, `session.containment.set` always has `clamped: false`; the field keeps `session.mode.set`'s shape.
- **`permissions.containment.set`** (`runs:drive`, no own-session rule): `not_found` for a session not here or deleted; the level the session has set already appends nothing (`changed: false`); otherwise `session.containment.set`, not `list`-flagged (the summary has no field for it), kept in the permissions projector's `session_containment` table and read into the session's facts. A live run keeps its level: its provider's sandbox was fixed when its process started.
- **A turn the provider opened on its own** runs in the process, and so the sandbox, of the run it followed: when the policy now resolves another level or mechanism for it, it is let go and its messages go to a run from the queue, as for a mode the adapter cannot change (#129).
- **The container**: `declared` is `AGENT_HARNESS_CONTAINER` set non-empty (a chosen name; the compose that sets it is #86's and #141's), `detected` is #112's file and cgroup rule; `serve/container.ts` holds the rule, which the update logic now reads too (either one is a container; env spec, lifecycle notes). Neither enforces or prevents a level, and an unavailable level's reason says the container is the outer boundary.
- **The seam the Claude adapter reads (#140)** is `RunInput.containment`: `level`, `mechanism`, `scratchDirectory`, `temporaryDirectory`, `writable` (the workspace, the scratch directory and the temporary directory) and `network` (false only at `workspace-no-network`). For #140: a session's runs share its provider process, so an adapter whose process was started under another level or mechanism stops it and starts one; and for a worktree workspace (#85) the repository's git common directory must be writable too, or no commit can be made at `workspace`, so `writable` will need it when worktrees land (paid by #322, below).
- **The session's directories**: `scratch` and `tmp` under `<data directory>/containment/<session id>/`, made owner-only when a run starts at a workspace level, removed once the session's purge commits (asynchronously, off the log's synchronous path), and swept at startup for sessions that are gone. A name that is not a session id names no directory. The adapter host's preset root, for a host with no data directory, is made with `mkdtemp` on first use and removed when the host closes. The temporary directory is the session's runs' rather than each run's, as the level definition above says. The directories sit inside the data directory, which is a denylist preset: #132 must leave `containment/` out of that entry, or every write to them prompts. "The session's scratch directory" is a second meaning beside ADR 0005's scratch workspace (a workspace kind that lives with the session); flagged for domain-modeling, which may make them one when the scratch kind lands.
- **The gate** is `RunContext.gate.check({toolCallId, tool, summary, access})`, where `access` is the adapter's description of the call (`read` or `write` with paths, `shell` with the command, `fetch` with URLs, `search`, `browse` with addresses since #132, `other`), answering `allow` (on to the provider's own evaluation) or `deny` with the model's message. It rules under the containment of the session's run live when asked. At a workspace level a write is denied unless it names a path and every path lies in a writable directory, each read as the file system will read it: relative to the workspace, `~` expanded, one component at a time with every symbolic link followed where it stands before any `..` after it, a dangling link's target read with `readlink`, and a loop of links (more than 40) denied. At `workspace-no-network` every fetch and search is denied; shell commands (the sandbox's), reads (the denylist's, #132), a browser verb and a tool server's call pass, since the browser and the harness's own tool servers are not containment's (the levels' meaning above). A denial asks no one and is recorded as `tool.decision` (`denied`, `decidedBy: containment`, `promptId: null`, the message as `reason`) by the actor `system:tool-gate` through #131's `recordToolDecision`, which records nothing for a call already decided, appended when the gate rules, which may precede the provider's `tool.started`, and is still a denial when its append fails. The gate records only the denials its rules make without asking anyone. Since the merge with #132, containment is the gate's first rule (`containmentRule` in `permissions/gate.ts`, decider `containment`), the recording is the gate's (`createToolGate`, the host's one `gateFor`), not the rule's, and the path walk (`resolvePath`) is the one both rules share (#132's note). When #140's hook denies a call, the provider may report the denial too (its permission-denied message, `permission_denials` on the result); the host skips a report for a call already decided (#131, below), so the call is recorded once. **For Claude until #140** the gate was asked from `canUseTool` (`adapters/claude/gate-access.ts` maps `Write`, `Edit`, `MultiEdit` and `NotebookEdit` paths, `Read`, `Glob` and `Grep` paths, `Bash` commands, `WebFetch` URLs and `WebSearch` queries and allowed domains onto the gate's call, with the input as given), before the broker and with the SDK's abort signal: so only the calls the provider asks about are gated. A call the mode approves without asking (a file edit under `acceptEdits`, anything under `bypassPermissions`) is not gated until #140's `PreToolUse` hook, and for those the SDK's `sandbox` option (#140) is what enforces containment. Since the Claude adapter declared `containment: false` until #140, no Claude run resolved a workspace level before then, so nothing live depended on this partial path. (#140 asks the gate from the `PreToolUse` hook for every call and declares the flag: its notes below.)

Decided in building unattended runs and the automatic decisions (#131):

- **Where the pieces are**: in `contracts`, `tool.decision` (`ToolDecisionPayload`, `ToolDecider`) among the permission events of the session stream, `review.seen` (`ReviewSeenPayload`) on the settings stream, the review's row (`ReviewRun` with `ReviewActor`, `ReviewCounts`, `ReviewDenial`) in `permissions.ts`, and `permissions.review.list` and `permissions.review.seen` in `methods/permissions.ts`; `RunPolicy` gains `actorName`. In the environment: the rules in `permissions/auto-answer.ts`, the sweeper in `ttl-sweeper.ts`, the decisions in `tool-decisions.ts`, the review's read model in `review-store.ts` (part of the permissions projector) and its methods in `review-methods.ts`; blocks in `adapter/host.ts` (the TTL on opening, the decisions) and `serve/start.ts` (the wiring, and `EnvironmentHandle.startRun`).
- **Attendance** is #129's resolver, unchanged: a client session's run is attended, a routine's or a bot's never, a completions request's only when it says so; nothing a socket does afterwards changes the run. `run.policy.resolved` gains `actorName`, a routine's or bot's name (null for anyone else), which the review shows. **`EnvironmentHandle.startRun`** starts a run for an actor that is no client session (its request type excludes a client session), through the same start as `runs.start` (`startRunIn`: the policy resolved for that actor, then launched once it has committed): the seam #92's routines and #139's completions surface start their runs through, and the way the tests start unattended runs. A routine or a bot is named in the log by its id, which does not change as its name may (`routine:<id>`, `system:bot:<id>`; the completions surface is `system:completions`), and by its name on the run's policy; a bot's run has origin `routine` (ADR 0008: bots own routines). Nothing was released before #131, but the review's projection reads a `run.policy.resolved` without `actorName` (a development log's) as naming no one, so a rebuild over one does not fail.
- **The rules** (`autoAnswer`, the environment's `PromptAutoAnswer`; the host's own preset stays none): on an unattended run every kind is denied at once, `auto: 'unattended'`, with "Denied: nobody is present to approve this. Continue without it and say what you could not do."; a question with "nobody is present; proceed with your best judgement". The question's answer is a **deny carrying that sentence**, not an allow with answers: every automatic decision reaches the adapter as a deny with a message (the deny-and-continue rule), and for Claude a denied `AskUserQuestion` hands the model the message as the tool's result; `prompt.answered` records `decision: deny` with the sentence as its message. In bypassPermissions only a residual `permission` prompt is denied at once, `auto: 'bypass'`, on attended runs too, with a chosen sentence: "Denied: this run is in bypassPermissions, which never waits for an approval. Continue without it and say what you could not do." (the unattended one would say nobody is present to a person who is). A question, a plan or a denylist prompt in bypass parks: a person may allow a denylisted call. No reviewer rule exists for Claude; `reviewer` stays reserved.
- **The TTL**: `ttlExpiresAt` is fixed on `prompt.opened` from `permissions.parkedPrompt.ttl`, read as the prompt opens (the host's `promptTtlMs`); null for `never`, and null for a prompt a rule answers in the transaction that opens it, which never waits. The **sweeper** runs at startup (after the startup purge, before the wire opens, so a prompt that expired while the environment was down is answered first) and every 60 seconds on the environment's clock; a prompt is expired when its `ttlExpiresAt` is at or before now. Each is answered in a transaction of its own, `deny` with `auto: 'ttl'` and "Denied: nobody answered within the time allowed. Continue without it and say what you could not do." (a question: "nobody answered in time; proceed with your best judgement"), attributed to `system:permissions`, by #130's path: `live` and handed to the run through `AdapterHost.deliverAnswer` after the commit when the run that asked still waits on it, else `next-run`, whose message now says nobody answered in time rather than that a person did. A deleted session's prompts wait (a restore brings them back, and the next sweep answers them). The `prompt.resolved` notice follows as for any parked prompt.
- **A TTL answer continues its session** (a chosen default, for David): with the presets a parked run is stopped at 30 minutes (`providers.processIdleMinutes`) and its prompt expires at 24 hours, when its run has long gone; a next-run answer starting nothing (#130) would leave the session stopped forever, against user story 12 ("an abandoned run finishes on its own") and the deny-and-continue rule. So a TTL answer whose run has gone starts the session's next run itself (`AdapterHost.continueSession`, after the answer commits), through the host's queue-start path: the run reads the answer first ("Nobody answered in time, so it was denied; carry on without it…"), then whatever is queued, for the actor of the run before it, resolved afresh (#129) in the session's mode, as a run of the queue is. Nothing starts while a run is live on the session (the answer waits for the run after it), for a deleted session, during a drain, or once another run has taken the answer. A person's late answer still starts nothing, but for a run an update cut (next note). The run before it is the host's own record of the run it last ended; after a restart it is read from the log (the latest run's policy and model, under the ceiling it was resolved under, since the client session behind it is not in the log). **For David**: a run of the queue is never started for a client session revoked since (#129), and a local `tui` client session is revoked an hour after its last socket closes, so a run a terminal started, parked and abandoned for a day, does not continue on its own while the environment stays up: its answer waits for the next message (after a restart it does continue, since the log does not say which client session started the run). Whether the continuation of an idle-revoked `tui` session should run under the ceiling it was resolved under is left to him.
- **A person's answer resumes a run an update cut** (decided by David on 2026-09-28, #345, beside #130's next-run delivery and the TTL's continuation above): for a run an update cut while it waited on a prompt, a person's answer to that prompt resumes the run at once, as the launcher spec says: the person did not stop the run, the update did. The settle marks such a run `run.update-interrupted` with the outcome `waiting-on-prompt` (launcher-update spec, "Interrupted runs and parked prompts"); while that run is still the session's latest, a person's `next-run` answer to a prompt of the session starts the session's next run once it commits, through the TTL's path (`AdapterHost.continueSession`): the run reads the answer first, then whatever is queued, for the actor of the run before it, resolved afresh. Everywhere else main's rule stands: a late answer is kept for the session's next run and starts nothing, and only the TTL's automatic answer starts one. Once that run has started, it is the session's latest, so an answer to another prompt still parked is kept for the run after it.
- **`tool.decision`, where it is derived**: the host, which consumes every event a run reports, with three sources, each in the transaction of what it follows. (1) Every path that appends a `prompt.answered` (a person's answer, a rule's, the TTL's, `run_ended`, `cancelled`) appends the call's decision beside it (`answerEvents`). (2) The provider's **denial report** reaches the host as a new adapter event, `denial` (`ToolDenial`: call, tool, `by` one of `rule`, `classifier`, `mode`, `provider`, reason), which is not a transcript event. The Claude mapper reports it from the `permission_denied` frame, by its `decision_reason_type` (`rule`, `classifier`, `mode`, anything else `provider`), just before the call's `tool.ended`, and from the result's `permission_denials` (the CLI's authoritative record, which also holds the denials no frame reports: a path-scoped deny rule on a file tool, a race) as a rule's, before the end, for a call the turn saw and no frame reported. (3) A call nobody was asked about and the provider did not report is the **mode's**: at its `tool.ended` when it ended `ok` (a denied call never does), else at the run's end, in the transaction of its `run.ended` and after the result's denials, so a call that failed is not called allowed before the provider's record can say it was denied. Names read in the pinned SDK 0.3.281 declarations (the spec's verify item): `SDKPermissionDeniedMessage` (`system`/`permission_denied`, `tool_use_id`, `tool_name`, `decision_reason_type`, `decision_reason`, `message`) and `SDKResultMessage.permission_denials` (`tool_name`, `tool_use_id`, `tool_input`).
- **`tool.decision`, its fields**: `decidedBy` from an answer is `person` for a client session, else the rule: `unattended` (a `denylist` prompt no person could answer is `denylist`, ADR 0006: its `prompt.answered` says `auto: 'unattended'`, the rule that answered, since the prompt's deciders have no `denylist`, and its `tool.decision` says `denylist`, what denied the call; the reason on both is the unattended sentence, what the model read; the section and entry are named on the prompt itself, its summary, reason and `denylist`, since #132), `bypass`, `ttl`, `reviewer` as `classifier`, and `run_ended` and `cancelled` as `provider` (the provider's side closed the prompt; neither is on the ticket's list). A denial always has a reason: the answer's message, else what the model read when the provider's side closed it, else the provider's reason for asking, else a sentence per decider; an allow has none. `toolCallId` and `tool` are null for a prompt that named no call (every prompt gets its decision). The summary is the prompt's, else the call's title, else the tool with what its input names (the prompt summary's rule). **Once per call**: the review projection refuses a second decision for a run's call id, and every source reads the log first, so the first decision a call gets is its one. A source outside the host records through `recordToolDecision(log, tx, sessionId, decision, attribution)` (`tool-decisions.ts`), which checks for an existing decision first and says whether it recorded: **the gate records through it the denials a rule makes without asking anyone** (containment's, #133; the denylist's for a path whose links cannot be followed, a rule that failed, or an ask the broker denied before any prompt opened, #132) at hook time, before the provider sees the call; a denylist match is put to a person through the broker, so its decision is the prompt's answer's (#132's note). A hook denial the provider also reports in `permission_denials` is not recorded twice, since the host skips a call already decided. The schema keeps `toolCallId` and `tool` nullable (a prompt that named no call); the gate's decisions always carry both. A person's deny with no message is "A person denied it.", never the provider's reason for asking. Consequences: a call cut by a crash (whose run the recovery sweep ends) gets no mode decision; a call cancelled or never ended, unasked, is recorded allowed by the mode (the provider did not ask; `tool.ended` says whether it ran); and for #132, a call asked about twice (a denylist prompt, then the provider's own) keeps the first answer's decision.
- **The review** (`review-store.ts`): a row per run from its `run.policy.resolved` (when it ran is that event's time), counted up by each `tool.decision`: tool calls, auto-approved (allowed by anything but a person), denied, answered by a person (allowed or denied), expired (`ttl`), and the decisions by `ttl`, `denylist` or `containment` that qualify an attended run; the denials are the run's denied decisions in order. **Since the watermark** means the run's latest decision is after it, so a run seen before it comes back when something new is decided in it (a prompt that expires a day later). Newest first by the run's start; a deleted session's runs are left out and a purge removes them. The list answers the watermark and the log's `head`, read before the rows, which a client hands back to `seen` to mark exactly what it showed.
- **What the review shows, and cannot yet**: a question answered by the unattended rule or the TTL is a denied call (its answer is a deny), so it is counted and listed among the denials; a prompt that named no tool call (`toolCallId` null) is a decision but not a tool call, so it is counted as denied (or answered, or expired) and listed among the denials, but not in `toolCalls`, and an unattended run qualifies with a tool call or a denial, so one whose only decision is such a prompt is listed (#219's review); the branch "attended with a `denylist` decision" fires for an attended denylist prompt the TTL answered (#132 records it `denylist`) and for the gate's outright denylist denials (#132), and will for the browser's sub-frames (#93). `permissions.review.list` takes a `limit` (preset 200, at most 1000) and reads every listed run's denials in one query. The decided check reads a `tool_call_id` column of the prompts table, indexed with the run's id, and the host forgets a call once its decision has committed (a transaction that rolls back leaves it for the run's end to decide). A run started for kept answers alone (the TTL's continuation, which has no message of its own) whose adapter never receives its input has no message to queue again, so the answers it took are not given back for the run after it (#130's requeue marks them by message): a known, narrow gap.
- **The watermark's stream**: `review.seen` on the environment's settings stream, the environment's own state a person moves, beside its settings, not the access log's, which says who could do what. `permissions.review.seen` (`sessions:write`) takes `through`, the head when absent; it never moves back (a position at or below the watermark appends nothing: the receipt says `changed: false`, and the result is the watermark as it stands), and a position past the head is `invalid_params`.

Decided in refusing a workspace diff's filters (#212):

- **Refused, not run contained**: containment can wrap nothing the environment runs itself, and building that is more than this ticket. Today the probe only checks that `bwrap` or `sandbox-exec` can run a trivial command. What a run gets is `RunContainment`, which its adapter hands to the provider's sandbox (#140), plus the tool gate's in-process path checks. No seam turns a level into a `bwrap` command line or a Seatbelt profile for a command of the environment's own. And every environment resolves `off` until #140 sets the Claude adapter's `containment` flag, so "inside the session's level" would mean unwrapped everywhere today. Bubblewrap also does not run on the build box (#133's note), so a contained path could not be tested here. So `diffs.workingTree` asks `git config --show-scope --name-only -z --get-regexp '^filter\..+\.(clean|smudge|process)$'` (`workspace/git.ts`, `repositoryFilters`) before any git call that could run a filter, and a repository whose own config names one answers `conflict`, reason `git_filters_refused`, with `data.filters` (the names, sorted, each once) and a message naming them. Nothing is run and nothing is written. It is a query, so it appends nothing and no rebuild changes it.
- **What counts as the repository's**: every scope but `system` and `global`: the repository's `config`, its worktree's `config.worktree`, and any file either one includes (`include.path`, `includeIf`), which git reports under the including scope. `process` counts beside `clean` and `smudge`, since a long-running filter does both. A filter counts whether or not an attribute points a path at it: the rule is on the config, as the ticket put it, and checking attributes path by path would cost a walk. The machine's own filters (system and global, which the owner writes, as `git lfs install` does) still run, in the scrubbed environment. They are the owner's choice, and refusing them would refuse every diff on a machine with git-lfs installed. The exemption holds only while the global config lies outside every directory a run can write. The scrubbed environment keeps `HOME` and drops `XDG_CONFIG_HOME`, so git reads `$HOME/.gitconfig` and `$HOME/.config/git/config`, and a workspace at or above `$HOME` lets an agent plant a "global" filter. An exempt machine filter such as git-lfs also still reads keys from the repository's config (its `lfs.*` keys). Levels are not consulted: the refusal holds at `off` too, where nothing runs contained anyway. The cost: a repository that configures LFS or another filter in its own config gets no working-tree diff. `diffs.session` still answers, and `files.list` runs no filter.
- **Nested repositories** (#212's review): a committed nested repository (a gitlink, with or without `.gitmodules`) has a config of its own, which the outer check never reads. `git diff HEAD` would run a `git status` inside it to mark it `-dirty`, running its filters, and `diff.submodule=diff` would run a diff, and its external diff, inside it. So the diff passes `--ignore-submodules=dirty` and `--submodule=short`: a nested repository shows only as its two commits, and nothing runs inside it. Its uncommitted changes are not shown.
- **The window it leaves**: the config is read once, just before the diff's own git calls. A filter written into the repository's config after that read and before `git diff` reads the config again would still run. It is a gap of milliseconds that a contained agent would have to time. The command line can blank a filter only by name (`-c filter.<name>.clean=`), and a filter added after the read has a name the environment has not seen, so only running the filters contained closes the gap.
- **Failure**: `--show-scope` needs git 2.26 or later; that branch is not tested, since every runner has a newer git. An older git, or a config git cannot parse, answers `git_failed` with git's complaint, as any git that runs and fails does. `git config`'s exit 1 with nothing said is "no such key".
- **For a later ticket that runs them contained**: a seam that turns a run's containment (`RunContainment`: level, mechanism, writable directories, network) into a wrapped command for the environment's own processes. For bubblewrap: `--ro-bind / /`, `--bind` for each writable directory, `--dev /dev`, `--proc /proc`, `--unshare-net` at `workspace-no-network`, `--die-with-parent`. For Seatbelt: a profile that denies `file-write*` outside the writable subpaths and, at no-network, `network*`. It also needs the session's level resolved for a query that has no run, the way a run's is (its own, else the default, else the preset). The diff's scratch index and object store would have to move into a writable directory (today they are in the operating system's temporary directory; the session's `tmp` would do). And it needs a CI runner where bubblewrap works, so the wire test can show the marker blocked and the diff still answering. Then the refusal could lift at the workspace levels, and `off` would run the filters unwrapped.

Decided in building the denylist and the tool gate (#132):

- **Where the pieces are**: in `contracts`, `denylist.ts`: the four sections and their entry grammar (`Denylist`, `DenylistEntry`, `DenylistInput`), the presets (`denylistPresets(dataDirectory)`), the pure matcher (`matchDenylist(denylist, call, context)` over a normalised call `{browserDomains?, paths?, commands?, hosts?}`, answering every enabled entry matched, in section order, with what matched it), its readers (`hostOf`, `hostToken`, `shellSubjects`), the test method's call (`denylistTestCall`), the one-line naming of a match (`describeDenylistMatch`) and `denylist.changed`'s payload; `prompt.opened` gains `denylist`, a denylist prompt's matches (null for the other kinds); `permissions.denylist.get`, `set`, `restorePresets` and `test` in `methods/permissions.ts`. In the environment: the read model and the seeding in `permissions/denylist-store.ts` (part of the permissions projector), the gate's rule and the tool-input reading in `denylist-gate.ts` (its links followed by containment's `resolvePath`, one walk for both rules, which takes a `LinkReader` a test can give), the methods in `denylist-methods.ts`, the workstream's one actor `system:permissions` in `actor.ts`; the adapter contract gains the gate (`ToolAccess`, `GatedToolCall`, `GateDecision`, `ToolGate` with a cancel signal, `RunContext.gate`: #133's shapes, plus a `browse` kind, a search's `domains` and the call's `input`), the host's seams a gate rule (`ToolGateRule` with its decider, `RuledRun`), all exported from the package; the gate itself in `permissions/gate.ts` (`createToolGate`: containment's rule first, then the environment's, the denials recorded, the cancel signal), blocks in `adapter/host.ts` (`gateFor` over it, a gate's prompt answered to the gate alone) and `serve/start.ts` (the seeding, the rule, the methods, the data directory made absolute).
- **The stream**: a change is `denylist.changed` on the access stream (the spec's `access.denylist.changed`), one per section it touched, carrying the entries added, removed and edited and the section after; the section after is what the denylist is read from, so one event is both the access log's record and the list's source, and a rebuild replays it (a chosen default: the denylist is environment state with methods of its own, not a key of the settings table, and no second event on the settings stream). The projection holds each section to its own grammar, so a malformed change fails its append whoever appends it. The presets are seeded on first start, before any run can be gated, by `system:permissions`, one event per section that has presets (hosts has none); once, so a section a person emptied stays empty across a restart.
- **The presets** are the spec's list and nothing else: the browser domains are the list the surfaces port audit records verbatim; "the configuration directories of the 1Password, Bitwarden and Doppler CLIs" are read as `~/.op`, `~/.config/.op` and `~/.config/op` (1Password's first and second versions), `~/.config/Bitwarden CLI` and `~/Library/Application Support/Bitwarden CLI` (Linux and macOS) and `~/.doppler`; the data directory is its absolute path (`startEnvironment` makes a relative `--data-dir` absolute before anything reads it). A preset's id is `preset:<pattern>`, the data directory's `preset:data-directory`, the same on every environment; `preset: true` says an entry came from the presets and survives its edit, and is set by the environment from the id, never taken from a client. `restorePresets` re-adds, at the end of its section, each preset whose id the section no longer holds, and leaves an edited or disabled one as it is; given `sections`, it re-adds theirs alone, so Set up's Restore, which names the sections the check found wanting, leaves a section a person emptied as it is (#573). **Owed**: the data directory's entry is fixed at the first seed, so an environment moved to another directory keeps the old path, and `restorePresets` skips the entry since its id is held; a start could compare the entry with the directory it runs in and say so.
- **The containment directories** (#133's note): `<data directory>/containment/` is the matcher's `exempt` directory, not an edit of the preset: a path at or under it is not matched by an entry that covers the directory as a whole (the data directory's), while an entry inside it still matches, and so does a link there that leads out, since the path is also matched as resolved.
- **The matcher's reading** (pure; the file system is the caller's):
  - A path is made absolute (`~`, `~<the environment's user>`, `$HOME` and `${HOME}` at a token's start, then the working directory, the run's workspace), matched as written with `..` applied and as the caller's resolver follows its links, one component at a time before any `..` after it; an entry's literal part before its first glob segment is resolved the same way, so a denylisted link and a link to a denylisted directory are both caught; `*` and `?` within a segment, `**` any number of segments, an entry covering its directory and everything under it; no `[...]` classes in patterns; Windows separators follow the grammar above. Case is folded where the file system folds it (macOS and Windows, a context flag). A path written as a glob (`~/.s*h/id_rsa`, `~/.a?s`) also matches an entry it can expand to, a leading dot matched only by a dot as the shell expands it (`~/*` is not `~/.ssh`); a bracket expression is read as any one character (`~/.ss[h]`, `~/.[a-z]ws`, never a leading dot: `~/[.]ssh` is not `~/.ssh`, as in the shell), and braces are expanded as the shell expands them (`~/{.ssh,.aws}`, `~/.s{r..t}h`, nested, empty words dropped), in any path a call names and in a command line's tokens before they are read, so its hosts and command patterns meet the words too (`{sudo,} reboot`); a brace inside quotes, after a backslash or in `${…}` is left as the shell leaves it, so a quoted JSON body is one word. Past 1,024 words, or 1,024 characters with a group in them, the reading is the strict one: a path is read as everything under the directory before its first brace (`~/.{a..z}{a..z}{a..z}` as `~/**`), and a command token is taken to meet every command pattern, so the line is asked about.
  - A command line is split on white space, then at every operator (`$(`, a backtick, `(`, `)`, a redirection `<`, `>`, `>>`, `&>` and the rest, `;`, `&&`, `||`, `&`) and an inner `|` starting a token, so `x>~/.netrc`, `cat<key`, `x=$(sudo ls)` and `FOO="$(sudo cat x)"` read as they run; quotes and escapes are taken out wherever they stand in a token (`"$HOME"/.ssh`). A pattern matches anywhere in the line (as `* pattern *`), by a table over positions, and is matched a second time against the line with each pipe written against the word after it split off that word, as the shell reads it (`x|sudo y` as `x | sudo y`), so `sudo *` and the `| sudo` presets meet the glued spelling while `curl * |*sh *` still meets `curl x |sh`. The line's path-like tokens (absolute, `~`, a dot file, anything with a slash; an option's value taken on its own) are matched against the paths, its URLs and bare hosts against the hosts: a name with a dot, `localhost`, an IPv6 literal (bracketed, with or without a port or scp's `:path`, or bare: `[::1]:8080`, `admin@[::1]`, `[2001:db8::1]:backup`, `2001:db8::1`, a dotted IPv4 tail on either side of the `::` as RFC 3986's grammar allows), a host after a user (`admin@nas`, where one label is enough), before scp's `:path` (`git@host.example:repo.git`) or before a query or a fragment (`169.254.169.254?x=1`, whose `=` is no option's; a `?` or `#` before the last `@` is read both ways, the host before it as curl reads the address and the one after the `@` as ssh does), and a number the network reads as an address (`0xa9fea9fe`, a decimal above the first eight bits such as `2852039166`; an exit code or a count is left alone). Any `file:` address is a URL, with one slash (`file:/home/…`) as with three, and names a path, read from the root when no slash follows the scheme (`file:etc/shadow` is `/etc/shadow`, as a browser reads it); so is a special scheme with fewer slashes than two (`http:/2852039166`, which curl reaches).
  - An address is read as WHATWG's parser reads it, by hand, since contracts has no DOM or Node types for `URL`: tabs, CRs and LFs removed wherever they stand, a special scheme read with its authority however many slashes follow it (`http:2852039166` is 169.254.169.254, while `localhost:8080` stays a host and port), the userinfo discarded, a backslash as a slash in the special schemes, the port dropped, percent-decoded, full-width letters and digits and the ideographic full stops mapped to ASCII (NFKC, then `。．｡` as `.`), lower case, no trailing dot, IPv4 in any spelling as dotted decimal, IPv6 as RFC 5952 writes it, an IPv4-mapped IPv6 host also as its IPv4. The environment also matches the host the platform's own `URL` parser reads where it parses and reads another (the rest of UTS 46: a soft hyphen, and so on). Punycode is not computed: an internationalised name matches an entry written the same way. A browser verb's address is matched against the browser domains and the hosts; a fetch's, a search's and a tool server's only against the hosts; a local `file:` address against the paths.
  - A match's cost is its length: each value is read once, each entry's forms computed once, each path resolved once per call (5,000 tokens match in 20 to 40 ms on the build box; the test allows a second, for a loaded runner).
  - **Accepted gaps**, kept: a bare file name read in a directory the line changes into (`cd ~/.docker && cat config.json`: the `cd` argument is no entry's path, the file entry is `~/.docker/config.json`), since the matcher does not follow `cd` and comparing every bare token with the entries' last segments would ask about every `config.json`; a quote does not hide an operator (a `>` inside a quoted message splits it), which only ever reads more; a script the line runs is not read. These are the unattended runs' sandbox projection's to close (#140), and a person present on an attended run chose the mode.
- **For David, a chosen default**: command patterns match anywhere in the line, so they over-match: `git commit -m 'Document the sudo step'` and `apt-get install sudo` match `sudo *`, and a match may run across `&&`. The ask is then a prompt a person answers on an attended run, and a denial on an unattended one. The alternative is to anchor a pattern at the start of each sub-command (after `;`, `&&`, `||`, `|`, `$(`, `xargs`, `env`, `nohup` and the like), which misses the forms nobody lists.
- **What the gate reads of a call**: the adapter's description (`ToolAccess`): a read's or a write's paths; a shell command's whole line; a fetch's URLs; a search's domains and any URL in its query; a browser verb's addresses; and for any other call (the harness's own tool servers) the input's whole string values that are URLs, absolute or `~` paths, or hosts `hostToken` reads (`db.internal:5432`), a string that merely mentions a path not being one. Past 8 levels or 500 strings the rest of an input is not read, which is logged when a string was left unread or a container too deep to open was not empty, and the call goes on as far as the denylist is concerned. Since #540 a tool of the harness's own servers may declare what a call reaches, `browse` with addresses or `fetch` with URLs, which the adapter hands the gate in place of that reading, so the call is ruled on as a browser verb or a fetch is; one that declares nothing is still `other` (the claude-adapter spec's #540 notes).
- **The gate**: its rules in order under the session's run live when asked; a deny is final and the rules after it are not asked, an allow or nothing passes the call on. A rule records nothing itself: the gate records a denial a rule made without asking anyone as the call's `tool.decision` by the rule's decider, through #131's `recordToolDecision` (skipped when the call is decided already), and a rule that throws denies the call, recorded the same way with the rule's decider (the denylist's rule: `denylist`). A path whose links loop or change while they are read denies the call outright, asking nobody (`denylist`). The denylist's rule asks through the broker, as the run's own prompt (kind `denylist`, the summary and the reason naming the first match's section and entry with the matched value cut to one short line, the matches on `denylist`, the call's input), under an id the host mints; the answer goes to the gate that asked and never to the adapter's `answerPrompt`, since the adapter did not raise it, and the prompt's answer is the call's decision. When the provider gives up on the call (its cancel, a hook's timeout: the signal `check` takes), the prompt closes `cancelled` and the call is denied, so nobody answers for a call that never ran. An ask the broker denies before any prompt opens (the run has ended, the provider gave up on the call before it was asked, or the log refused the `prompt.opened`) has no answer to carry the call's decision, so the broker says so (`BrokerAnswer.unopened`) and the gate records the denial: by `provider` for the first two, as the answer to a prompt either closed would be, and by `denylist` for the third, a rule that could not ask. Without it the run's end would record the call allowed by the mode (#131's rule for a call nobody was asked about), or nothing would, for a call whose `tool.started` the host never saw. An allow lets that one call on to the provider's own evaluation, which may still ask its own question about it (#131: the call keeps the first decision); the next identical call asks again. `remember` and an edited input are refused on a denylist prompt (#130's fit rule). A person's deny reaches the model with their message, else a sentence naming the entry. On an unattended run the broker's unattended rule denies at once; past the TTL the sweeper does; a restart keeps the prompt parked like any other (a stop's in-memory denial records nothing), and a later answer is the next run's first message, whose call is gated afresh when it is made again. Containment's rule (#133) goes first, then the denylist's.
- **The gate awaits the broker**: the spec's first design had the hook return `ask` so the prompt reached `canUseTool`; #132 took its verify-first fallback, the gate awaiting the broker inside the hook, since `ask` from a hook is not known to reach `canUseTool` in bypassPermissions and the fallback holds in every mode. **Owed by #140**: the `PreToolUse` hook's per-matcher timeout at least the TTL (a day by preset), and a TTL of `never` cannot be covered by any timeout, so the hook's timeout closes the prompt through the cancel signal and the call is denied; the settings should say so beside `never`. (Done: #140's notes, "The hook's timeout".)
- **The decision**: a person's answer is `person`; the unattended rule's and the TTL's answers to a denylist prompt are `denylist` (ADR 0006: nobody present to choose; this widens #131's mapping, which gave the TTL's `ttl`, so a denylist call that expired counts in the review as a denylist denial, not as expired, and makes the review's branch "attended with a `denylist` decision" fire for it); a run's end and a cancel stay `provider` whatever the prompt's kind (the denylist did not decide them, and an attended run a person interrupted under a denylist prompt does not belong in the Unattended review).
- **ADR 0006 and bypass**: the ADR says bypass mode never parks; a denylist prompt parks on an attended run in bypassPermissions, as the spec's "an explicit allow is honoured in every mode" requires (#131's rules park it, and the review accepted it). Unattended runs never park, in any mode. The ADR's sentence is to be read as "no provider prompt parks in bypass"; noted for an amendment.
- **What the gate did not see until #140**: only a call an adapter asks it about is gated. The fake adapter asks it for every call it plays. The Claude adapter asks it from `canUseTool` (#133), with the SDK's abort signal and the call's input, and its tool map (`gate-access.ts`) reads Bash as `shell`, Read, Glob and Grep as `read`, Edit, MultiEdit, Write and NotebookEdit as `write`, WebFetch as `fetch`, WebSearch as `search` with its allowed domains, and anything else, an MCP tool among them, as `other` with its input: so on a Claude run every call the provider asks about is gated, a denylist match opens its `denylist` prompt from inside `canUseTool` before the provider's own prompt, which follows only when the person allowed the call (the call keeps the first decision, #131), and a request the CLI withdraws closes the denylist prompt. A call the provider approves without asking (a file edit under `acceptEdits`, every call under `bypassPermissions`) is not gated until #140 wires the `PreToolUse` hook, which also owes the projection of the path section onto the sandbox's `filesystem.denyRead` and of the command section onto the disallowed-tools rules on unattended runs. (#140 wired both: its notes below.)

A denylist match is put to the person inside the gate and waited on in the hook (#132's choice). The CLI reads a hook that failed as one with no opinion and runs the call, so the hook never throws: a gate that cannot rule denies. A call the hook let through is remembered with its input (the last 1,024), so the provider's prompt about it (`canUseTool`) does not ask the gate again and no second denylist prompt opens; one whose input another hook rewrote since (a trusted repository's hook's `updatedInput`) is gated again there, while one of those the provider runs unasked is not (a known gap: only a trusted repository's hooks can rewrite). A subagent's calls pass the hook too. A background subagent's call between the CLI's turns has no live run, so a denylist match there is denied at once and recorded `provider` (#132's rule for an ask the broker could not open) rather than parked: `canUseTool` opens a turn of the provider's own for a subagent's prompt, but a turn per background call would be a run per call.
- **The hook's timeout** (verify first, read in the bundled CLI 2.1.281, not run): a matcher's `timeout` is in seconds, passed through the SDK's `initialize` to the CLI, which arms `setTimeout(timeout * 1000)` for a callback hook with no cap; unset, the CLI's default is ten minutes, so without it a denylist prompt would be cancelled after ten minutes. A JavaScript timer past 2^31 - 1 ms fires at once, so the hook's timeout is the largest whole number of seconds under it, 2,147,483 (24.8 days): above the preset TTL and any TTL up to 24 days. When it passes, the CLI cancels the hook's control request, the SDK aborts the callback's signal, and the gate closes the prompt `cancelled` and denies (recorded `provider`, #132's rule). The CLI does not run the call and hands the model "PreToolUse hook did not respond before its timeout (host client may be unreachable). The tool call was not executed" as the call's error; the turn goes on, and no `permission_denied` frame is sent. So a TTL of `never`, or one over 24.8 days, closes a Claude run's denylist prompt at 24.8 days; the TTL setting's description says so (the schema export changed with it).
- **`ask` from a hook** (verify first, read, not run): it does reach `canUseTool` in `bypassPermissions` on the pinned CLI. The hook's `ask` is handed to the host's permission callback as a forced decision, which the CLI returns as it is without asking the mode, unless a deny or ask rule in the settings overrides it. #132's await-in-hook stays all the same: it holds in every mode without leaning on that path, keeps a person's allow of a denylist prompt separate from the provider's own prompt (an `ask` answered through `canUseTool` would answer both), and keeps the gate's recording in one place. Its cost is the 24.8-day ceiling above.
- **The broker**: every permission prompt, plan and question the provider raises goes through `canUseTool` to the broker as before (#130); `permissionPrompts: 'host'` always, `dontAsk` and `default` never. Under `auto` the classifier's fallback asks are `canUseTool` requests (`decision_reason_type` `classifier`) and reach the broker as `permission` prompts with the provider's reason; they park on an attended run (only bypass's residual prompts are answered at once, #131). `ExitPlanMode` is a `plan` prompt; an approval's continue mode, clamped by the host, reaches the CLI as the result's `setMode` and is now the process's record of its mode too, so a later run on the kept process that asks for `plan` is moved back to it (before, the record still said `plan` and the run went on in the approved mode). A live `permissions.mode.set` reaches `setPermissionMode` (#129).
- **The sandbox** (the options table): none at `off`. At both workspace levels `enabled`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, `autoAllowBashIfSandboxed: false`, and `filesystem.allowWrite` the run's writable set, then the directories the spawn's process environment supplied as its holder's own (#1119). `network` at `workspace` is `{allowLocalBinding: true}`, at `workspace-no-network` `{allowedDomains: [], strictAllowlist: true, allowUnixSockets: [], allowAllUnixSockets: false, allowLocalBinding: false}`, so a host outside the empty list is refused without an ask. The mechanism is the platform's: the SDK has no option naming one, and the CLI uses Seatbelt on macOS and bubblewrap on Linux, the ones the probe tried. A chosen default: unix sockets at `workspace` stay at the sandbox's own default (on Linux its seccomp filter refuses them, on macOS none is listed), since opening them all would hand a command the Docker socket, a way out of the workspace.
- **The network at `workspace`** (verify first, read, not run): the sandbox cannot say "any domain". Once it is enabled the CLI always builds an `allowedDomains` list (its settings' domains, its WebFetch allow rules, the hosts allowed this session), so the runtime restricts the network through its proxy at `workspace` too, and asks the host about each new host (`can_use_tool`, tool `SandboxNetworkAccess`, input `{host}`) unless `strictAllowlist` is set; the runtime refuses `*` and `*.com` as allowed domains. So the adapter answers those asks itself: the gate rules on the host as a fetch (containment's no-network level, the denylist's hosts), and its ruling is the answer. A denylisted host is put to the person as a `denylist` prompt of the session's live run, as any match is; any other is allowed at once, with no permission prompt and no turn opened; the CLI remembers an allowed host for the session. That settles #133's probe note: the network is restricted, and the network namespace needed, at both levels. A denied-domains list exists (`network.deniedDomains`, the same wildcard syntax, `*` allowed there). The hosts section is not projected onto it (a chosen default): the gate already rules on every host a sandboxed command reaches, through that ask, as a prompt on an attended run and a denial on an unattended one, with the matcher's readings (numeric spellings, IPv6), and the runtime's grammar refuses some of the section's entries (a single-label name), where one refused entry would fail the sandbox's start and so the run.

The CLI matches a shell rule against each sub-command from its start (`sudo *` meets `ls && sudo x`, not `echo sudo`), where the gate matches anywhere in the line and asks first. At `off` the paths have no sandbox to go into; the shell rules still apply. Attended runs carry neither. The projection is read as the run starts, and a kept process serves a run only under the same containment and projection (its spawn key): an idle process is let go for a fresh one, and a run it cannot serve while it holds work is refused, as for the bypass opt-in.

Decided in building the carve-out of the repository git directory's hooks and config (#791):

- **What is closed**: at both workspace levels, `RunContainment.readOnly` lists what a run may not write or make even though it lies in `writable`. In the common git directory of the repository holding the workspace, that is its `hooks`, its `config`, the main worktree's `config.worktree` beside `config`, and each linked worktree's `worktrees/<name>/config.worktree`, whether the file is there or not. Git reads a `config.worktree` once the config sets `extensions.worktreeConfig`, which sparse checkout does. The ticket named only the linked worktrees' files; git reads the main worktree's from beside `config` (checked with git 2.39). This holds for every repository workspace: a checkout root, a worktree, a directory below a repository's root, a worktree of a bare repository, a submodule's checkout, and a checkout made with `--separate-git-dir`. The list is empty at `off` and for a directory in no repository. A commit's writes stay open: objects, refs, the index and `HEAD` (a worktree's under `worktrees/<name>/`), and a `config.lock`.
- **How the gate and the sandbox learn the git directory of a checkout-root workspace**: `runContainment` (`permissions/containment-directories.ts`) reads it as each run starts with #322's `commonGitDirectory(workspace)`. It goes into `writable` only when it lies outside the workspace (#322). What it closes goes into `readOnly` wherever it lies, so a checkout root's own `.git` is closed even though `writable` names only the workspace. Neither the gate nor the adapter reads git's files; both read `readOnly`. `RunContainment` gains that one field, and every adapter is handed it.
- **The gate**: a file tool's write at or under a `readOnly` path is denied with `decidedBy: containment`. Both paths are resolved with links followed, as the writable roots are, so a link into the hooks and a hooks directory that is itself a link are both caught. The check comes after the outside check, so a write outside the writable set keeps its message. The model reads "`<path>` is in the repository's git hooks or config, which name programs the user's own git runs outside containment, so this run may not write it", and that asking again will not widen it. On macOS and Windows the match folds case, as the denylist's matcher does, so `.git/HOOKS/pre-commit` is denied there.
- **The sandbox**: `filesystem.denyWrite` is `readOnly`, and is absent when the list is empty. The paths are literal, not globs: the pinned runtime skips a glob in `denyWrite` on Linux ("Skipping glob pattern on Linux/WSL", read in the bundled CLI 2.1.283), so each worktree is listed by name rather than as `worktrees/*/config.worktree`. On Linux, a listed path that is not there yet gets `/dev/null` bound read-only where it would be (an empty directory at a missing parent instead). The runtime makes an empty file on the host as that mount's point, the CLI's "mask file", and removes it once none of its sandboxed commands is running, and again when it exits. One that a killed CLI leaves behind is an empty config, which is harmless to git, and the CLI's doctor lists it.
- **The Claude process key** carries `readOnly` beside `writable`, so a run whose list differs, for instance after a worktree was made, gets a fresh process with the new `denyWrite`.
- **A worktree made during a run** has its `config.worktree` closed from the next run on, not during the run that made it. This is kept as a known gap: git reads that file only in that worktree, and only with `extensions.worktreeConfig`, which is set in the closed config.
- **Left open, filed as #933**: a submodule's git directory under the repository's (`modules/<name>/hooks` and `config`), whose config the superproject's own `git status` reads (checked with git 2.39); a repository the run makes or repoints in its workspace (a nested `.git`, a rewritten `.git` file, a fabricated submodule); and a `core.hooksPath` the repository already points into the workspace, whose hooks are workspace files. #933 closed the submodule part (below) and filed the rest as #1094.

Decided in building the carve-out of a submodule's git directory under the repository's (#933):

- **What is closed**: at both workspace levels, `RunContainment.readOnly` also lists, for each submodule's git directory under the repository's `modules`, what #791 closes in the repository's: its `hooks`, its `config`, its `config.worktree` and each of its linked worktrees' `worktrees/<name>/config.worktree`, there or not. A submodule's own submodules are under its `modules`, and theirs in turn. The superproject's own `git status` runs a `git status` inside each checked-out submodule, which reads that submodule's config: a `core.fsmonitor` set in `.git/modules/vendor/lib/config` ran when `git status` ran in the superproject (checked with git 2.39). The sandbox runtime's own deny list matches `.git/hooks` and `.git/config`, not `.git/modules/<name>/config`, so without this a command could write it on both platforms, and the gate let a file tool write it. A submodule's commit writes stay open, as the repository's do: its objects, refs, index and `HEAD`.
- **How they are found**: `runContainment` walks the git directory's `modules` as each run starts, from the files git keeps, as #322 reads the git directory itself; no git runs. A directory there with a `HEAD` is a submodule's git directory, as git takes it, and so is one with `objects`, so the walk never goes through a damaged one's objects. One with neither is a component of a name and is walked through, since a submodule's name may hold slashes (`modules/vendor/lib`). git puts no submodule's git directory inside another's (git 2.39 refuses a name `vendor/lib` beside `vendor`: "submodule git dir ... is inside git dir"), so the walk stops at one. A link is not walked, nor a `modules` that is one: git makes none there, and one a run made could lead the next run's start anywhere on the host (#1097's review). A `HEAD` a run puts in a name's component hides the submodules below it from the next run; that is #1094's case of a repository the run makes, and gives a run nothing that rewriting the submodule's `.git` file does not. Each submodule adds three paths to the list, and one more per worktree of it. The gate and the sandbox read it as they read #791's: the gate denies a file tool's write there with #791's message, and `filesystem.denyWrite` carries it.
- **This holds at every repository workspace** whose git directory has submodules: a superproject's checkout root, a directory below it, and a worktree of it, whose common git directory holds `modules`. A submodule's own checkout as the workspace had its git directory closed by #791; its nested submodules are now closed under it.
- **A submodule added during a run** (`git submodule add`, `git submodule update --init`) has its git directory closed from the next run on, not during the run that made it, as a worktree's `config.worktree` is (#791). Unlike that file, git reads a submodule's config whenever the superproject's `git status` looks into the submodule, so this gap is not accepted here: it is the case of a repository the run makes, left open.
- **Left open, filed as #1094**: a repository the run makes or repoints in its workspace (a nested `.git`, a rewritten `.git` file, a submodule made from nothing or added during the run), and a `core.hooksPath` the repository already points into the workspace. #933's build was told to land the submodule part first. What it found for them is in #1094: the pinned runtime skips a glob in `denyWrite` on Linux, so a `.git` made during a command cannot be closed to commands there through `denyWrite`.

Decided in building the new or repointed repository paths and workspace hooks (#1094, split from #933):

- **File tools, at both workspace levels**: the gate denies a write to a `.git` entry itself, or to `hooks`, `config`, `config.worktree` or `commondir` beneath it, including those beneath `modules/` and each `worktrees/<name>/`. This is checked on every call, whether the repository existed at run start or was made during the run, throughout the writable set (workspace, scratch, temporary directory and any added common git directory). It prevents rewriting a worktree's or submodule's `.git` file to name a planted git directory, and planting config or hooks in a new nested repository or fabricated submodule. `commondir` is indirection too: changing it would make git read another common directory's config. Denials are recorded with `decidedBy: containment`. The check uses both the requested spelling and the resolved path, so a `.git` symlink pointing to a differently named directory and a differently named link into `.git` are caught. Case is folded on macOS and Windows. Ordinary objects, refs, index, `HEAD`, `config.lock` and `info/exclude` stay open; this closes program paths rather than every `.git` component. Under `modules/`, whose repository names can have multiple components, the check conservatively closes any of those four component names below it.
- **Commands on macOS, at both workspace levels**: in addition to #791's literal `readOnly` paths, the adapter's `filesystem.denyWrite` carries absolute recursive patterns for those four names directly beneath any `.git`, beneath `.git/modules/**`, and beneath `.git/worktrees/*`, each both at the path and beneath it. They cover conventional git paths in the workspace, scratch and temporary directory even when made during a command, without closing ordinary objects, refs, index or `HEAD`. The patterns are absolute so the working directory does not limit them to the workspace; letter character classes cover metadata stored with different case on a case-blind disk. A blanket `**/.git/**` denial was rejected because it would prevent commits as well as creating repositories.
- **Accepted command gaps**: on Linux the pinned runtime skips globs in `denyWrite`, so only #791's and #933's run-start literal carve-outs and the runtime's own command-start scan apply. A repository or submodule made during a command can still receive executable config or hooks; `git init`, `git clone` and `git submodule add` are not refused by the harness. Closing every possible future git directory there requires a runtime capability it does not have, or refusing repository creation. This is an accepted containment gap, not a claim that such a run cannot leave a program for the user's git. On either platform a command can also rewrite a `.git` file to name a differently named planted git directory in the writable set, whose config these patterns do not cover. Denying a `.git` path as a subtree would close a checkout's ordinary metadata too; no type-sensitive future-path denial is available. Arbitrarily named bare repositories and other metadata aliases are likewise not sealed by this rule. At `off`, none of these additional gate or sandbox rules applies.
- **Accepted workspace hooks**: `core.hooksPath` that already points into the workspace (for example `.husky` or `.githooks`) remains editable by file tools and commands. These are versioned workspace files whose edits appear in the session's diff, and the hooks commonly call workspace scripts or tools the run may edit anyway. Closing only the hooks directory would not close the programs it runs. No config parser is introduced to chase `include.path` or `includeIf`. This does not reopen the git directory's own hooks closed by #791.
- **Boundary with #933**: its existing-submodule git directory walk remains separate and unchanged. The dynamic gate and macOS patterns here also cover a newly made submodule's conventional `.git/modules/<name>/` program paths; on Linux commands that create those paths during a run retain the accepted gap above. #933's next-run literal protection still matters, especially on Linux and for git directories reached through indirection.
