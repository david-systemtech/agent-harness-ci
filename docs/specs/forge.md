Milestone 1 (Switch-over), phase B (daily use). Written 2026-09-28 from map ticket 87 of `david/agent-harness`. Implements ADR 0012, ADR 0020, ADR 0032 and, as milestone-2 direction, ADR 0033, with rules citing ADRs 0003, 0011, 0015, 0016, 0019, 0026, 0027, 0028, 0031 and 0034, and ADR 0017 for the phase and the placeholder. Peers read: on main, the step registry with #141's entry, `setup.check`, the vault, the Claude adapter's scrub and spawn key, the reserved pull-request events; T3 Code at 96c4bfa0 (source-control providers); the 2026-09-22 forge research; the core port audit; memories `forgejo-agent-tokens`, `git-credential-helper-chain-forgejo`, the memory-tools forge-landing write-up. The product name is the placeholder `agent-harness`.

## Problem Statement

David works on GitHub and his own Forgejo from several machines, and every session began by hunting for a forge credential. One token or key-manager reference is kept per memory bank, matched to a remote by host string, with no idea what the token may do until an operation fails; skill sources and the tracker the skills drive have no credential at all; the server lands bank changes with whatever git finds, falling back to `git credential fill`, and treats any host but github.com as Gitea (core audit, sections 3 and 4). Runs inherit the machine's helpers: on 2026-09-18 Git Credential Manager answered for Forgejo with an expired browser token and every agent push hung silently. The model is never told which forges exist or which is primary, and a session never sees the pull request it opened, so settle-on-merge (ADR 0003) has nothing to read.

## Solution

Each environment holds one forge account per forge origin, with verified aliases, an identity of login plus user id, and learned capabilities. Its credential is the environment's own `gh`, a `gh` token the attending client hands over once, a key-manager reference, or a pasted token in the environment's vault. One ForgeService, with a provider per kind (GitHub, Forgejo, Gitea; GitLab in milestone 2), is the harness's only way to a forge. A run's git reaches the forge through a harness credential helper named in process-only configuration that resets the machine's helper chain for those origins; tokens arrive as named variables, and the orientation block says which forges exist and which is primary. A session's pull requests are linked and kept current. The Forges step shows a card per forge account and says when one stops verifying.

### Modules

- **CLI**: the verb `git-credential` (ADR 0020).
- **Client runtime**: `forge.accounts.list` in the request cache, refreshed on `forge.account.*`; a platform capability reading the local `gh` token, present in the desktop shell, absent-with-reason in a browser tab (ADR 0032, ADR 0004). As built (#320): the shell's `gh` member (`shell.gh`), `forges.handOverGh` and `forges.copy` with `projections.copyTargets`, and the forge notices; the client-runtime spec's notes on #320 hold their rules. ### The forge account record

- **Fields** (ADR 0020): client-minted id, canonical origin, aliases with verified-at, kind, slug, identity (login and user id), credential source, capabilities, primary flag, problem, the time its status last changed (`statusSince`: the problem's since-time, else when it was last found without one; #311), token information (classic, fine-grained, OAuth or unknown; the scope header as a hint; expiry), created-at, and copied-from (the source environment of a copy, shown on the card).
- **Origin**: `https`, or `http` for a LAN or tailnet instance; lower-cased host; default port omitted. One forge account per origin; an origin already held as another's canonical origin or alias is `conflict` reason `origin_held`.
- **The normaliser** maps every remote git takes (https, http, ssh, `git://`, scp-like, bare `host:port`) to an origin and a repository path without `.git`, dropping and reporting userinfo (a token in a URL). ssh, scp and `git://` forms map to `https` on the same host with no port (`ssh.github.com` to `github.com`), marked ssh-derived. An http or https remote matches the forge account whose canonical origin or alias equals its origin; an ssh-derived one matches by host, canonical origins first, and nothing while two remain (chosen default). Repository identity (#85) must treat the ssh, scp, http and https forms of one repository as one (ADR 0020), may build on this, and owns the identity string.
- **Slug** (ADR 0020): from the host, lower case, other runs to one underscore, `github` for github.com; on a collision the port, then a counter (chosen default). Editable, 1 to 40 of `a-z`, digits and underscore, unique (`conflict` reason `slug_taken`); variables use it upper-cased.
- **Credential sources** (ADR 0012, 0020, 0032): `gh`, the environment's own `gh` for that host and login, read per operation so it follows `gh`'s rotations; `stored`, a vault token with provenance `pasted`, `client-gh` (the handing client session's id and label), `imported` or `oauth`; `reference`, a key-manager connection and path; `none`, a copy awaiting a credential.
- **Capabilities** (ADR 0020): `readRepository`, `writeIssues`, `pullRequests`, `createRepository`, `readReleases`, each `verified`, `failed` or `unknown`, with verified-at and a failure's status. Reads are probed at verification; writes start `unknown` and flip on the first ForgeService operation of their kind: verified on success, failed on 401, 403, or 404 for a target just read. A denied pull-request read also fails `pullRequests`, GitHub's fine-grained permission for both (chosen default).
- **Problem**: null, `needs-credential`, `credential-rejected` (401 on identity), `credential-unavailable` (key manager or `gh` signed out, entry missing), `identity-changed` (another user id answered; unused until replaced), `unreachable` or `expiring` (within thirty days), with since-time, one plain line (setup-copy.md §5.6) and the raw facts behind it as details: what the forge or `gh` answered, HTTP statuses, user ids and exact times (#1850). A verification records the problem again when its kind, its line or its details change, so details follow the forge under an unchanged line (HTTP 502 after 503, a rate limit's pause).
- **Git username**, derived, never stored (ADR 0020): `x-access-token` (GitHub), the login (Forgejo, Gitea), `oauth2` (GitLab, milestone 2).

### Verification

- Resolve the credential, call the identity endpoint, compare the user id, update a changed login (ADR 0020), read the token information, and probe `readRepository` on a repository this environment knows on that origin (a bank, a skill source, a session's repository identity), else by listing repositories, and `readReleases` there, else following `readRepository`, which grants release reads on all three kinds (chosen default). A probe's 404 is failed (ADR 0020). A probe the forge could not answer now (no answer, a server error, a rate limit) leaves the capability as it was and the forge account `unreachable` until a verification reads it, so a forge whose last verification met a server error is never done (#1850).
- It runs after startup's gate, every fifteen minutes (ADR 0020), on `forge.accounts.verify`, the Forges check, a credential change and a git rejection; one at a time per forge account, within ADR 0031's ten-second budget.
- **The Forges check beside that schedule (David, 2026-10-01, #680)**: the Forges step's checks read the last verification's findings when they are younger than the step's cadence, and ask for a verification only otherwise. The verifier keeps its own schedule, so the step adds no verification beside it. A verification the step asks for honours a rate-limited forge account's pause, so a forge that answered 429 is asked nothing until its time. **Chosen defaults (#680)**: "younger than the cadence" holds on the environment's own checks of the step (its start pass, cadence and triggers); a client's `setup.check` (opening Set up or the step's pane, Check now, Check again, re-run) checks fresh, as ADR 0031's re-run does, so it verifies every forge account the forge has not paused, since the verifier's schedule leaves every finding younger than the cadence and Check again would otherwise ask nothing. A finding dates from when its verification recorded it; a forge account given a credential since has none until that credential's verification, and one recorded later than now (a clock set back) counts as older, as the Set up scheduler counts such a result due.
- Recorded as the account store records its reads (claude-adapter spec, #134): `forge.account.verified` as `system:forge`, no command id, only when identity, a capability, token information or problem changed; verified-at times are kept beside the record.
- An alias is verified on its own origin and accepted only on the same login and user id (ADR 0020), else `alias_identity_mismatch`.
- **Chosen defaults not decided on a ticket, from the verification (#311)**: "a credential change" includes an add's first credential, so a forge account is verified at once after it is added with one, as after its credential is replaced; that verification and the start's go through the environment's clock (due at once), the fifteen minutes run from the end of each verification, and a request for a credential given while one runs waits for it and verifies again, the replaced credential's findings never recorded. The ten seconds run from reading the credential to the last answer; past them nothing found is taken, only `unreachable`. A 429, or GitHub's 403 once its limit is spent, is `unreachable`, never a refusal, and its `Retry-After` or reset pauses only the scheduled verifications, until a credential is given. A capability the forge could not answer now keeps its state; a problem of the kind there was keeps its since-time and so `statusSince`; an expiry already passed or within thirty days is `expiring`. An identity-changed forge account is not verified again until its credential is replaced. A token whose prefix GitHub names nothing and that sends a scope header reads classic. The repository probed is the most recently updated session's identity on the forge account's host (the identity rule's host matching). `forge.accounts.verify` answers every record, as `accounts.refresh` does. Aliases are given as `url` is (any form, the origin kept), at most sixteen, and `update`'s replace the list: an alias already verified keeps its verification, any other is asked with the credential given, else the one held; a refusal on the alias's origin is `alias_identity_mismatch` too, and one that does not answer, or any while the forge account has no identity, waits unverified. A verification that makes an alias verified, or unverified once it answers as someone else or refuses, appends `forge.account.updated` with the aliases as `system:forge`. The state import's probe takes a URL, whose `owner/name` path is the repository probed.

### Credentials

- **A pasted token crosses the wire once** (ADR 0020), in `forge.accounts.add` or `update`, `admin` calls sent directly, never through the client's outbox (client-runtime spec). It is scrubbed on arrival, written to the vault before the command's transaction, removed if it rejects, and never in an event, receipt, log line, answer or `invalid_params` issue.
- **The vault** gains delete (env spec: get and set). Removal or replacement deletes the entry after commit; a start removes entries of forge accounts gone (chosen default).
- **The environment's `gh`** (ADR 0032): `gh auth token` for the host and recorded login, run without `GH_TOKEN`, `GITHUB_TOKEN` and `GH_ENTERPRISE_TOKEN` so it reports the stored login (chosen default), probed like a paste. `gh` is a Managed tools row, minimum 2.40 (the first taking a user on `gh auth token`, chosen default), verified by `gh auth status` (ADR 0026); whether it is installed, where and which version are the Managed tools registry's `gh` row (#373), which `forge.gh.probe` and the credential source read.
- **The attending client's `gh`** (ADR 0032): read through the client's own tools detection, sent once in the add call as `stored` with provenance `client-gh`; the card says it will not follow `gh`'s rotations.
- **References** resolve per operation through the key-manager registry, are scrubbed and disposed when the operation ends, never cached (ADR 0020). The registry is #91's; while it holds no connection, a reference is rejected `credential_source_unavailable`.
- **The scrub registry** (ADR 0011) is #91's. The forge puts the first secret into a run, so its build lands the registry's core if #91's is absent: register a value under an owner, dispose it, scrub at the log's append (so transcripts, tool outputs and client renders) and in the logger. A stored token is registered while held, a resolved one for its operation or process, each also Basic-auth and percent-encoded (chosen default). No build injects a token without that core.

### Runs: the injection

- **A provider process receives**, process-only, never on disk, in the log or in the user's git configuration (ADR 0012, ADR 0020):
  - `GIT_CONFIG_COUNT` entries after inherited ones: for the canonical origin and every verified alias of each injected forge account, an empty `credential.<origin>.helper`, resetting the machine's chain for that origin only (the 2026-09-18 fix, moved into the process), then the helper: the absolute path of the `agent-harness` command the service runs, `git-credential` and the slug. ssh is untouched.
  - The environment's loopback address and port, and the **run-scoped secret**.
  - `FORGE_<SLUG>_URL` (the canonical origin), `FORGE_<SLUG>_TOKEN`, `FORGE_<SLUG>_KIND`; the primary's also bare as `FORGE_URL`, `FORGE_TOKEN`, `FORGE_KIND`; `GH_TOKEN` for the github.com forge account alone (ADR 0020). A token unresolvable at spawn is left out and the orientation says so. Inherited `FORGE_` variables are removed; the Claude scrub already removes names holding `_TOKEN`.
- **The injected set**: every forge account without `identity-changed` or `needs-credential`, for attended runs, routines, the completions surface and minted sessions alike (ADR 0020, ADR 0019); per-bot forge accounts are milestone 2. The tracker the skills drive reaches the forge through these variables; its doc stays the setup skill's (ADR 0012).
- **ADR 0011's injection setting** governs it: denying injection for the run's account, routine or bot removes the variables and the helper (ADR 0020). The setting is #91's; until then the ForgeService reads its preset, which injects (ADR 0028).
- **Per provider process.** A provider process is the environment's, not the run's (ADR 0015), and a Claude process serves many runs with an environment fixed at spawn (claude-adapter spec, #120, #140). The run input gains a **process environment**: a non-secret key (injected ids, origins, slugs, kinds, primary, a credential generation each, the setting's answer) and a function the adapter calls once per spawn, which mints the process's secret, resolves the tokens (ADR 0020's operation) and answers the variables. The adapter layers them after its scrub and adds the key to its spawn key, so a differing process is let go for a fresh one, as for changed instructions or containment; the pool's stop disposes secret and values. #91's key-manager block can join the seam.
- **The run-scoped secret** (ADR 0020): 32 random bytes in memory, valid while its provider process lives (ADR 0015), naming the injected forge accounts; no client session, no scopes, scrubbed; a restart voids all.
- **Terminals** (chosen default): a session's terminal gets the same injection, its secret living with the terminal, so git in a pane or run with `!` behaves as the model's (ADR 0020's "git in a terminal pane").
- **Containment** (permissions spec, #140): at `workspace` the helper honours the sandbox's proxy variables, so its loopback call passes the proxy and the gate like any host; at `workspace-no-network` neither it nor git reaches anything. Where an unattended run's denied reads cover the helper's executable (the data directory, if versions live there), its directory joins the run's exempt directories.
- **Chosen defaults not decided on a ticket, from the process environment (#307)**: a supplier registers with the environment under a name of its own (`processEnvironments.register`), giving its part of the key, read as a holder's environment is built, and at each spawn its variables and their release. The key is empty while no supplier is registered; otherwise it names the injection answer and, on `allow`, each supplier's part, in the order they registered. The answer is asked once per run, as its adapter is asked for it, and once per terminal, as it opens, of a seam handed the session, the account its runs go through and who started it (a client, for a terminal); its preset answers `allow`, and a seam that fails answers `deny`. Every supplier is asked at once at a spawn; where two name one variable, the one registered later wins; a supplier whose key or variables fail is left out and logged, nothing supplied in its place. Claude layers the variables after its scrub and before its own (the project directory's name, the client app, the account's directory), a stripped variable never set. The pool releases what a spawn was supplied as it lets the process go, before its adapter stops it, whatever the reason, an exit on its own included, and as a later spawn on the same process replaces it (a changed key); a release runs once, whoever calls it first, and a spawn supplied after its process was let go is released at once. A turn the provider opens on its own runs in what its process was spawned with. A terminal's variables go over its clean base and under the client's; its shell starts once they are supplied, or without them, logged, when they cannot be had, what is typed meanwhile is typed then (up to 64 KiB, the rest dropped and logged once), a terminal closed meanwhile exits at once (code -1) and starts none, and it releases them as it is closed or its shell exits, whichever comes first.
- **Chosen defaults not decided on a ticket, from the runs' injection (#315)**: the ForgeService's supplier registers as `forge` when the environment has an `agent-harness` command for git to name as its helper, as `serve` always gives it; without one no run or terminal gets the forge's variables, as the harness's own git fails there. It reads nothing of a holder's scope, so every run and terminal, whatever started it, gets the same set. Its part of the key lists, per injected forge account in the order they were added, its id, the origins it is served on (the canonical origin, then its verified aliases), slug, kind, primary flag and credential generation: how many credentials it has been given since it was added (each `forge.accounts.update` with a credential, a Move's included), so a verification that finds nothing new, a problem that leaves it injected or a capability learned changes nothing. With none injected the part is an empty list and a spawn is supplied nothing. At each spawn the secret is minted naming the injected set and every token is read at once, for the holder's life: a `gh` or key-manager token is registered for scrubbing until the release, which also voids the secret; one that cannot be read leaves out its token variables, logged, and keeps its URL, kind and helper. A holder numbers supplied git configuration after the entries it inherits, the count covering both (a Claude process inherits the service's own environment; a terminal's clean base has none). The Claude scrub drops every inherited `FORGE_*`, whatever the injection answer. Where an enabled denied path covers an absolute path of the helper's command (the launcher's shim under the data directory, or node and the entry it runs), that path's directory joins an unattended run's exempt directories, and so does each path the command reads as it runs that an enabled denied path covers (#705): `serve` passes them beside the command, since only the CLI knows the shim's layout, and the shim reads the service state and the versions directory, the whole directory rather than the active version's folder, since an update may switch the active version while a provider process lives and an unattended run's projection is its kept process's spawn key. Under a launcher with no shim (one started by hand), the helper is the running version's Node and CLI entry, and `serve` also declares the versions directory as a read (#1080), so the CLI's package metadata, the other workspace packages and `node_modules` are readable beyond the command's own directories. A `serve` in the foreground declares no extra reads. Nothing else of the data directory joins them. The service state is a file among the exempt directories, which the pinned sandbox re-binds read-only on Linux as it does a directory (`--ro-bind`, 0.3.283). Verified on the pinned SDK's CLI (0.3.283): its Bash tool runs a command in the CLI's own environment, sandboxed or not (bubblewrap without `--clearenv`, adding the sandbox's proxy variables; the CLI's own subprocess credential scrub is on only with `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` or its `local-agent` entrypoint, neither of which the harness sets); the sandbox's `no_proxy` names `localhost` and `127.0.0.1`, so the helper calls the environment directly: on macOS the profile lets a contained command reach loopback when local binding is allowed, as `workspace` allows it, and on Linux the command runs in a network namespace of its own, where nothing answers. So when its connection to the environment fails before any answer, the helper answers a `get` from its slug's `FORGE_<SLUG>_TOKEN` under the username `x-access-token` (it holds no login, and Forgejo 16.0.3 took a token as the password under any username on 2026-09-29), losing live rotation only there; an answer, a refusal or a timeout is never passed over. At `workspace-no-network` git still reaches nothing, the helper's answer or not.

### The helper and the credential route

- `agent-harness git-credential` speaks git's credential protocol. On `get` it posts git's attributes and its slug to the credential route with the secret and prints username and password; when it cannot (no secret, environment unreachable, credential unavailable, origin outside the secret's set, fifteen seconds passed) it prints `quit=1`, so git neither asks another helper nor prompts, and one line on standard error naming the origin and the fix (Set up, Forges). On `erase` it reports and forgets nothing (ADR 0020): `forge.account.git-rejected`, then a verification. `store` is ignored.
- **The credential route**: `POST /api/internal/git-credential`, loopback sockets only, behind the Host check, the secret a bearer credential compared in constant time; no client session, no scope (ADR 0020). It serves only the canonical origins and verified aliases of forge accounts in the secret's set still held, resolving per request so a rotation is live at once, rate-limited, `unauthorized` otherwise. A removed forge account stops being served at once; its token stays in a live process's variables until the next run lets the process go.
- **The harness's own git** (bank checkouts, skill sources, a new repository's first push) uses the same helper with a secret per operation and `GIT_TERMINAL_PROMPT=0`, against the canonical origin's URL, never a configured remote (ADR 0020). On an origin with no forge account the chain is reset with no helper, so it reads anonymously.
- **No forge account** (ADR 0020): a harness operation reads anonymously first; a refusal is `forge_account_missing` (the origin, and step `forges` for the deep link), a client notice and a Forges health failure. `forge.origin-missing` is recorded at most daily per origin and counts for seven days, until a forge account covers the origin (chosen default), or until the operation its last record names reads the repository it names anonymously after all, recorded as `forge.origin-answered`, which clears the record and withdraws the client's notice for it (#1891): a public repository the forge refused once in passing needs no forge account. The record names the refused repository where the operation names one; another repository read under the same operation clears nothing, since an operation names a kind of work (`sync a memory bank`) that a private and a public repository on one origin can share, and a record naming no repository is never answered. A 403 whose message names a rate limit or abuse detection (GitHub's secondary limits send neither `Retry-After` nor a spent `X-RateLimit-Remaining`) is a forge that cannot answer now, like a spent limit, never a refusal.
- **Chosen defaults not decided on a ticket, from the helper (#314)**: the helper finds the environment in `AGENT_HARNESS_ADDRESS` (its loopback host and port) and the secret in `AGENT_HARNESS_RUN_SECRET`, names without `_TOKEN` so the Claude scrub leaves them; the secret is base64url. git's configuration names the helper as a shell snippet (`!` then each word quoted for `sh`), a Windows path written with forward slashes for Git for Windows' `sh`. The route finds the forge account by the origin among the secret's set, so a slug renamed while a process lives keeps being served; the slug names the helper's line. Its rate is a burst of 300 a minute per secret, and requests with no secret it holds share one bucket at the exchanges' ten a minute; off loopback it answers 403 `unauthorized`; a forge account whose credential cannot be read, or whose login a Forgejo or Gitea username needs is not known yet, is `credential_unavailable` (503) naming the origin; an `erase` is answered 204. The helper honours `no_proxy` as curl does (the host, a domain it is in, or `*`), takes `http_proxy`, then `HTTP_PROXY`, then `all_proxy` or `ALL_PROXY` when it names an http proxy, and goes direct past a SOCKS one. The harness's git also sets `GIT_ASKPASS` empty, since git asks an askpass the machine's configuration names (`core.askPass`, `SSH_ASKPASS`) with terminal prompts disabled (seen on git 2.39, 2026-09-28); it runs untranslated, knows a credential was wanted by git's "terminal prompts disabled", may take five minutes, and resets the chain on the origins of the one forge account it uses. "Daily" and "seven days" run from an origin's last record, which keeps the operation refused last. Under a launcher `serve` names the launcher's `bin` shim (#338, #459), whose one path outlives every version while a provider process lives across an update; a `serve` in the foreground, or under a launcher with no shim, names the command line it runs as (node, its flags, the entry).

### Providers

- **One interface** (ADR 0012): detection, identity, read probes, organisations, repositories (read; create under the user or an organisation), issues, pull requests (create, read, list by head, merge), releases, a file on a branch and the default branch (bank landing's check), the pull-request URL parser. Every write updates its capability; issue bodies pass the scrub registry (ADR 0011).
- **GitHub**: `api.github.com`, or `/api/v3` on an Enterprise origin; bearer tokens; organisations from the memberships endpoint, since the organisation list answers fine-grained tokens with an empty list (forge research, 1.3); token kind from prefix and scope header; expiry from the token-expiration header (chosen default).
- **Forgejo and Gitea**: one provider over the Gitea API under `/api/v1`, kind recorded apart; `token` scheme; the walkthrough names `read:user`, `write:repository`, `write:issue`, `write:organization` (forge research, 5.4).
- **Detection** (chosen order): github.com by name; Forgejo's version route; Gitea's (Forgejo's version carries `+gitea-`); the Enterprise meta route; ADR 0033's GitLab order, answering `kind_unsupported`. It answers origin, kind, version, the token page link and what to name: for GitHub a fine-grained link (Contents, Issues, Pull requests, Administration write) and a classic one (`repo`, `read:org`) (ADR 0012, ADR 0032).
- `Retry-After` and GitHub's reset headers pause a forge account's background work; entity tags make re-reads conditional; `Link` pagination. Repositories and the release channel use the primary forge unless another origin is named (ADR 0012); the release repository is #86's.
- **Chosen defaults not decided on a ticket, from detection and the owners (#313)**: detection asks the origin with no credential, each route once, and the first answering as a forge decides: `/api/forgejo/v1/version`; `/api/v1/version`; `/api/v3/meta`, whose `verifiable_password_authentication` marks GitHub Enterprise and whose `installed_version` is its version; GitLab's discovery document naming its own `api` and `read_repository` scopes, `/api/v4/version` answering 401 with `401 Unauthorized`, and `/api/v4/projects?per_page=1` with an `X-Per-Page` header. A Forgejo or Gitea that asks every caller to sign in answers its version routes 403 with "Only signed in user is allowed to call APIs." (the primary forge, Forgejo 16.0.3, anonymously on 2026-09-29), read as Forgejo on its own route and as Gitea on the Gitea API's alone, with no version; github.com has none either. A route that does not answer, or answers its own error or a rate limit, ends detection `unreachable`. An add without a kind detects it once the store's refusals have passed and before the credential is read or sent; with a kind nothing is detected. The token pages come from contracts (`forgeTokenPages`), the one to offer first at the head: on github.com the fine-grained link, prefilled with `name`, `expires_in=none` (GitHub's own default is thirty days, which the expiring rule flags at once, and ADR 0032 prefers long-lived tokens; #628 asks David), and `contents`, `issues`, `pull_requests` and `administration` at `write`, with All repositories named since no parameter sets it, then the classic link with `description` and `scopes=repo,read:org`; on an Enterprise origin the classic link first and the fine-grained page unfilled, since GitHub documents the prefill for github.com and Enterprise Cloud alone; on Forgejo and Gitea `/user/settings/applications`, which a link cannot fill. `forge.orgs.list` reads the identity endpoint and then the organisations on every call, with the forge account's credential for that call, at most 100, in the order the forge lists them: GitHub's memberships with `state=active`, the Gitea API's `/user/orgs` by `name`. Every organisation listed is offered, a creation it refuses teaching `createRepository`. A refusal of either read, or an answer that is no list, is `verification_failed` with its status; no answer is `unreachable`; a credential that cannot be read, or answers as another user, is `credential_unavailable`. An anonymous read detects too (#470, in the operations' defaults below).
- **Chosen defaults not decided on a ticket, from the operations (#316)**: an operation names a repository as `owner/name` (letters, digits, `.`, `-`, `_`, never a dot segment; a file's path has no empty or dot segment) and an origin in any form a remote takes, or none for the primary forge; none primary is refused `no_primary_forge` naming the Forges step. Every write reads its target first (the repository an issue or pull request opens on, the pull request a merge merges, the organisation a repository is created under; the user's own is the identity the verification reads), so a 404 after it counts as a refusal, and a target that cannot be read sends no write. A write's 2xx is `verified`, 401, 403 or 404 `failed`, any other status (a name taken, a pull request not mergeable) or no answer teaches nothing; a success on a capability already verified appends nothing and moves its verified-at, kept beside the record as a verification's is; a capability shown by a credential replaced meanwhile is not recorded. A pull-request read or list the forge answers 401 or 403 fails `pullRequests`; a 404 there is a pull request not found. An anonymous read's 404 counts as a refusal too, since both APIs hide a private repository behind it; its kind is the one the caller names, else the one detection finds (#470): github.com by name, any other origin asked as an add asks it, once per origin while reads ask at the same time. A kind found is kept for the process; an answer naming none is let go, so the next read asks again rather than a passing fault refusing reads until a restart. Detection finding no forge reads on the Gitea API, as before detection, so a forge walled to anonymous callers (GitHub Enterprise in private mode, a sign-in proxy), which answers every route 401 or 403, is still `forge_account_missing` and counted missing, and the Forges step still suggests adding an account for it; an address that is no forge at all gets the same answer. A GitLab is refused `kind_unsupported`, the add's own answer, and not counted missing, since a forge account could not be added for it (ADR 0020 counts origins refused for want of one). Detection that does not finish (an origin not answering, its own error, a rate limit) answers the read unreachable, and nothing is kept. A forge account whose credential cannot be read, or answers as another user, refuses `credential_unavailable`, with no anonymous try. Titles are checked with bodies; the refusal names the field, and is the environment's in-process type until #363 puts `secret_shaped` in contracts with its rule. Rate limits an operation meets pause the forge account's scheduled verifications and hold no operation back. A refusal quotes the forge's own line, cut at 200 characters. Pull requests by head: GitHub's `head=owner:branch` filter, every state, most recently updated first; the Gitea API, which has no such filter, reads five pages of fifty by recent update and keeps those whose head is the branch in the owner's repository. A merge is a merge commit unless asked otherwise, and answers nothing (a read after says when). An asset downloads on GitHub from the API's asset route as an octet stream, following its redirect to storage without the token, and on the Gitea API from its download address's path (a relative one read from the origin; none readable is failed) on the forge account's canonical origin, whose web routes take the token for downloads; a redirect keeps the token only on the origin the download began on, up to five. The forge has the call's ten seconds to begin answering and fifteen minutes to finish; the bytes stream to a file, answered with their size and SHA-256, and nothing is left of a download cut short. A release is also read by its tag (#346), on both APIs `GET /repos/{owner}/{repo}/releases/tags/{tag}`, a draft answered there read as none (404).

### Wire methods

Scope `admin` unless stated; mutating methods take a `commandId`.

- `forge.accounts.list` (`read`): the records with the exact variable names each injects; never a secret.
- `forge.accounts.add`, a prepared command (it hears from the forge first, as `runs.withdraw` does): id, a URL in any form, optional kind, slug, aliases, primary, `copiedFrom`, and the credential (`stored` with token and provenance, `gh`, `reference`, `none`). A credential the identity call refuses is `verification_failed`, nothing stored; a transient failure keeps the forge account with its problem (chosen default). The first forge account becomes primary (ADR 0012).
- `forge.accounts.update` (prepared): slug, aliases, or a credential, which must answer with the recorded user id, else `identity_mismatch`. The Key manager step's Move (ADR 0028) is this call with a `reference`; its read-back is #91's.
- `forge.accounts.remove`; `forge.accounts.setPrimary` (every other cleared in the same event; removing the primary leaves none until a person chooses).
- `forge.accounts.verify` (one or all): a query at `admin` recording what it finds, as `accounts.refresh` does (env spec).
- `forge.detect`: a query at `admin`, since the environment calls an address the caller chose.
- `forge.gh.probe` (`read`, as `accounts.probe`): installed, version against the minimum, and per signed-in host the login, whether active, the token's kind and scopes.
- `forge.orgs.list` (`read`): owners a forge account may create repositories under, the user first, live, never stored (ADR 0020).
- `forge.pullRequests.link` (`sessions:write`, prepared): a session and a URL, read from the forge (anonymously where uncovered), appended as `session.pull-request-linked`; `not_a_pull_request` when no provider parses it. `forge.pullRequests.unlink` (`sessions:write`). `forge.pullRequests.refresh` (`read`): re-reads a session's pull requests now.
- Errors besides the shared union: `forge_account_missing`, `verification_failed`, `identity_mismatch`, `alias_identity_mismatch`, `credential_source_unavailable`, `kind_unsupported`, `not_a_forge`, `unreachable`, `not_a_pull_request`; `conflict` reasons `origin_held`, `slug_taken`.
- Capability flag `forge` in `hello` and discovery; without it a client shows Forges absent-with-reason (ADR 0004).

### Events

- On session streams, session-state's reserved pull-request events and payloads (url, state, merged-at, closed-at), as `system:forge` or the linking client session.

### Pull-request links and status

- **Found** (ADR 0012; T3 Code's branch lookup): at a run's end, if the workspace's repository is on a non-default branch whose remote (its upstream's, else `origin`) normalises to a forge origin, pull requests with that head are linked when open, or closed or merged since the session was created; so are pull-request URLs on a connected origin in that run's tool outputs and assistant text, twenty at most, each read first. Discovery never relinks a URL whose latest event is an unlink (chosen defaults).
- **Kept current** (chosen defaults): open pull requests read every five minutes while the session is in the active list, hourly otherwise; closed ones daily for fourteen days; merged ones never; unmerged ones also at each run's end and on refresh. `session.pull-request-synced` only on change; a 404 keeps the last state and stops reads. Merged is GitHub's `merged_at` or the Gitea API's `merged`. Settling is session-state's sweep reading `mergedAt` (ADR 0003).
- **Chosen defaults not decided on a ticket, from the pull requests (#317)**: a URL is read by the provider of the forge account serving its origin, else GitHub's on github.com, else by its shape, `/pull/` as a GitHub Enterprise's and `/pulls/` as the Gitea API's; any page of a pull request, a query, a fragment, an alias or another case of its owner and repository names the same one. A session keeps it by its web URL on the origin it was read on (the forge account's canonical origin), its owner and repository as the forge's own page spells them. `link` and `unlink` answer the session's summary, as the session commands do, and are ordered for a client's outbox; `refresh` answers the session's pull requests. A link's read the forge answers 404 with a forge account is `not_found` (kind `pull_request`); any other refusal, or an answer that is no pull request, `verification_failed`; an anonymous read's refusal `forge_account_missing`. A link of one linked already, as the forge answers it now, changes nothing; in another state it is linked again with it. An unlink of one the session does not hold changes nothing. Discovery, from the branch and from the text, looks only on origins a forge account serves, so a run's end on a forge with none asks nothing and records no missing origin. The branch is `HEAD`'s; with an upstream on a remote (not `.`), the head a pull request names is the upstream's branch on that remote, else the local branch on `origin`; a detached head finds nothing. The default branch is the forge's answer for the repository, and the list takes the twenty most recently updated from that head; "since the session was created" is its merged-at, else closed-at, at or after the session's creation. The text is the run's settled assistant text and every string in its tool outputs, subagents' too, in order; the twenty are the first twenty the session neither holds nor last had unlinked, each read in turn, and one whose read fails is not linked. The cadence is looked at every minute; the active list is the active and pinned shelves; fourteen days run from the forge's closed-at, and a closed one without it is not read on the cadence; each next read counts from when the last was asked, which is kept in memory, so a start reads each one due at once. A 404, or an anonymous read's refusal, stops the reads of that pull request until it is linked again or refreshed: a refresh reads every one that has not merged, a stopped one and one closed more than fourteen days ago included; a run's end reads the unmerged ones it held before it that are not stopped, after its discovery.

Its paragraphs, blank-line apart: one line per forge account in the order they were added, `- <slug>: <forge>, login <login>: <status>`, the forge named `GitHub` for github.com and otherwise by its host and port with its kind, the login "not known yet" before the forge has answered, the status "verified, unchanged since <UTC minute>" from `statusSince`, or the problem's words ("credential rejected", "unreachable", and so on) since then followed by the problem's own line; the primary, the rest also connected, and "Repositories go to the primary forge unless the user names another.", or with none primary "No forge is primary here; … Ask the user which forge a new repository goes to."; for each injected forge account its variables (the origin's, then the token's, then the kind's) and its API base; for each injected forge account its writes (issues, pull requests, repositories) failed with their HTTP status and those not known yet, a line only while one is not verified; each forge account left out of runs with its reason, `needs-credential` and `identity-changed`, and `credential-unavailable` as the credential that cannot be resolved, since the text is composed before a spawn reads the token and states the last check; then "Git over https to these origins just works, the harness's credential helper answering for it:" with the origins the helper is given (each injected forge account's canonical origin and verified aliases), that ssh uses the user's own keys, and that other origins have no credential here. - **Chosen defaults not decided on a ticket, from the forges section under a denied injection (#714)**: the section reads the run's injection answer from its instruction scope, the one its process environment is built under (#380), so it never tells a run of what it was not given. ## Testing Decisions

A good test is behaviour seen through the wire, in the helper's output to git or in a real git's result; never the projection's table, the secret map or the vault file, except at the lower seams.

- **Primary seam: the in-process environment with a fake forge.** The env spec's helper (temporary data directory, loopback port 0, scripted fake provider, typed client over a real WebSocket) plus a **scripted fake forge** on loopback port 0: the slice of GitHub's REST API (as an Enterprise origin) and of the Gitea API the providers use, each token's answers scripted per route (401, 403, 404, no scope header, the empty organisation list, rate-limit and expiry headers), and git's smart HTTP through `git http-backend` behind basic auth. Through it: every method, error and event above, verification on an injectable clock, and pull requests found, synced until merged and settling their session. The fake provider reports its spawn environment and runs a scripted command in it, so a real `git clone` and `git push` prove the chain reset (a hostile helper in a temporary global configuration, `GIT_TERMINAL_PROMPT=0` under a timeout, as the 2026-09-18 memory checks), the helper, the variables, a respawn after a change and a stopped process's secret refused. Prior art: T3 Code's `apps/server/src/server.test.ts` (`buildAppUnderTest`, `withWsRpcClient`) and `sourceControl/GitHubSourceControlProvider.test.ts`.
- **Lower seams**: the helper verb against a scripted route, as the CLI's pairing tests script the network (the verbs, `quit=1` and its line, the timeout); each provider against the fake forge without the wire (mapping, paging, rate limits).
- **Contract tests**: one scope per forge method; the normaliser over a table of remote forms (https with userinfo, http with port, ssh with port, scp, `ssh.github.com`, `git://`, a local path); slug and variables; URL parsers; the Forges entry's checks and actions from ADR 0031's vocabulary; the JSON Schema round trip.
- **Framework**: Vitest, listener files serially. **Not tested here**: live forges, a real `gh`, the sandbox proxy, the Windows helper path (verify first), key managers (#91).
