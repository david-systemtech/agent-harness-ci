# Spec: Set up: the step registry and the eleven milestone-1 steps

Milestone 1 (Switch-over), phase B (daily use), with the steps whose features land in phases C and D filling their entries as they are built. Written 2026-09-28 from map ticket 88 of `david/agent-harness`. ## Problem Statement

Setting up a machine today is a desktop-only dialog of fifteen panes whose health nobody checks: a key-manager token expires, a skill source stops syncing or a Chrome runs an old extension, and the first sign is a run that fails. A headless server is set up by hand and never checked at all. The step registry on `main` is a stub: four of eleven steps, health checks written as functions over setting values that only a client could run, no budget, no cadence, no cache, no subscription, and "skipped" defined as something a person does although four feature specs already derive it from state. Seven steps have no card anywhere: Account, Carry over, Your machines, Memory bank, Skills, Instructions and Appearance each had their behaviour decided on a ticket, and none has the command, the copy or the check a build session needs. The terminal UI's `/setup` answers "cannot be read from here yet".

## Solution

Set up is a checklist of eleven steps that every client renders from the same environment state. Each feature registers one step: the settings and state it writes, the checks that say it holds, the budget and cadence of those checks, the events that re-run them, the row it lives on, whether it may be skipped and when. The environment runs every check itself, on start, when a client opens Set up or a step's pane, on Check again and Check everything again, when the feature's own event fires, and otherwise hourly (fifteen minutes for the three steps the orientation block reports on). It keeps the latest result per step across restarts and publishes each change on the environment stream, so the desktop's Set up pane, the terminal's `/setup` line and a headless machine's health all read the same answer. A result is pending while waiting for its first scheduled read (#1326), done, needs attention with one line and the actions that fix it, or skipped, which a step with nothing set up reports on its own. On first launch Set up is the whole window; afterwards it is the first row of Settings, and every step links to the pane that owns it. Steps whose artefact has to be written, a bank's `BANK.md` and orientation, mint a normal session that the card embeds and whose result the step's own check detects. A headless machine is installed by one script, paired from any client, and checked from there.

## Implementation Decisions

Every rule cites its decision; a rule marked chosen default was left open by the tickets and is listed again under Further Notes.

### Modules

- **Contracts**: the registry's phase-B shape and entries (`steps.ts`), the result and action vocabulary (`setup.ts`), the methods below (`methods/setup.ts`, `methods/carry-over.ts`, `methods/state-import.ts`), the step prompts (`setup-prompts.ts`), the notices, the new settings keys, the contract tests.
- **Environment**: the **SetupService** (`environment/src/setup/`): the check runner (budgets, awaited state checks, the last good result), the **result cache**, the **scheduler** (start, cadence, triggers), the notice publisher, `setup.mint`; the **CarryOverService** (the session import and memory copy of ADR 0021); the **StateImport** orchestrator (ADR 0036), whose source reader alone may name the source's folders.

- **GUI** and **terminal UI**: rendering, per the sections below.

### The registry entry

The stub's shape is replaced, never its entries (the stub's own rule). A **step** is:

- `id`, from `STEP_ORDER` (unchanged: account, carry-over, your-machines, forges, key-manager, memory-bank, skills, instructions, browser, permissions, appearance).
- `home`: the row id it lives on (ADR 0027; the GUI spec's table), replacing `{pane, band}`. `links`: further row ids and step links, replacing the mixed `PaneLink` pairs, whose two existing entries disagreed on which field held the band.
- `writes` (settings keys), `writesState` (method and parts), `confirms`, `checks` (a value check per key written), `stateChecks` (id `<step>.<what>`, the sentence that holds, actions): as the stub.
- `done`: the step's line when every check holds, one short sentence of what was found, never its state checks' sentences joined: those are the rules a check applies, and their alternatives ("X, or Y") say what would pass rather than what is there (#1698). Its words are [setup-copy.md](setup-copy.md) §5's ("All 2 accounts are signed in."). The environment says more where it finds more: Carry over names earlier work in a source data folder or terminal-client state folder nothing was brought over from yet, with what the data folder holds ("Found earlier work you can bring over: 3 profiles and 1 notebook."), else when its last import finished ("Brought over yesterday."); Your machines says it is ready and how it is kept up to date ("{name} is ready. It updates itself."), the version and its reach going in `details`; Permissions names the sandbox as it is, never "enforced" when it is off, and each always-ask list a person emptied ("Set. Agents are not sandboxed. You emptied the paths always-ask list."). A check that holds and says what it found follows the line: a bank's landing awaiting review, or its BANK.md held by a pull request awaiting review (named once when both are the same pull request). The Set up list shows each line on one row, its whole text on hover and on keyboard focus.
- `budget`: `local` (5 s), `network` (10 s) or `git` (30 s) (ADR 0031).
- `cadence`: minutes, 60 unless a `reason` is given (ADR 0031: David set the hour).
- `triggers`: the event and notice types whose arrival re-runs the step's check at once (ADR 0031).
- `skip`: for a skippable step, the one state check whose failure means "nothing is set up here", answered as skipped (below); absent on a step that is never skipped.
- `llm`: for a step with an authoring conversation, its prompt id (ADR 0019).
- A state check answers synchronously or with a promise; the runner awaits it within the step's budget (the forge spec's owed awaited answer).

### Results, the cache and the subscription

- **Pending scheduled reads (#1326)**: a check awaiting its first scheduled read reports `pending`, with its reason and no failing checks or repair actions. Both renderers say "Checking" and use a neutral dot; header attention counts exclude it. A real failing check on the same step takes precedence. Your machines waits for the first release-channel read two minutes after start, allowing the network check's ten-second budget; beyond that, an unread channel needs attention as overdue. A failed first read needs attention immediately. An existing successful read retains its 24-hour freshness rule across restarts, and an old read gets no new startup grace. Pending is never a last good result. This new strict result state raises the wire protocol to 2: protocol-1 clients receive the existing protocol mismatch response before a result they cannot read.

- **`StepResult`** keeps its fields (step, state, reason, failing, actions, checkedAt) and gains `lastGood`, present only on a result that timed out or could not check: the previous result that passed, done or skipped, with its state, reason and checked-at, which the client shows beneath, dated (ADR 0031; #308 built it from the results since the start, and #571 reads it from the cache, so it survives a restart). It gains `targets` too, present only when a check that failed named the items its actions apply to: each with the action it serves, a kind from the closed list in contracts (account, forge account, key-manager connection, tool, skill source, Chrome, session, bank, denylist section, environment), an id and a label, each once, so Sign in again opens that account's sign-in and Try again continues that session (#568; optional, as an added field is, so no protocol bump). It gains `times` too, present only when a failing check's reason names a past time: each the words of the reason that say when, in the environment's terms ("more than an hour ago, at 2026-10-06 16:24 UTC"), and the instant, which a client replaces with its own words for a past time, its age and its clock time where it is, "2 h ago, at 16:24", the day and time on one line, counting the age again each minute while it shows the line; a client that reads no `times` shows the reason as it is (#1742; the host-side updater's last poll, which read as a raw ISO timestamp in UTC, broken inside its date on a phone). The CLI's `update status` says that poll the same way. It gains `details` too, present only when a check has technical facts the person may need to diagnose or report a problem (a check id with the error it threw, an HTTP status, a path, an address, a version, a program's own words): each one line, kept out of `reason`, which stays the plain line of setup-copy.md, and shown behind the step's Details and in its Copy details (setup-copy.md §3); a client that reads no `details` shows the reason alone (optional, as an added field is, so no protocol bump). Its `step` is any step of the milestone-1 order, not only one the reader's build registers: each entry that lands grows the registry and no protocol bump marks it, so a client built before an entry landed reads a newer environment's answer, snapshot and notices whole, where a registered-only step made `setup.check`'s whole answer unreadable to it (#672). `setup.check`'s `step` parameter stays a registered step. A verb added to the actions, a kind added to the targets' list and a step a later milestone adds move no protocol version either, so a reader takes a newer environment's result in a vocabulary its build lacks and leaves out only what it cannot act on (#693): an action it does not know, a target serving one or of a kind it does not know, and an action it knows whose every target it left out, since carried out on no item it would act on another (Update naming no tool updates this machine); `targets` is absent once none is left. `setup.check`'s answer and the snapshot's `setup` pass over a result of a step past the milestone-1 order and read the rest; a notice of one is a notice the reader does not know. `SetupAction` and `SetupTargetKind` stay closed lists, which an environment's checks are typed by, so a new verb or kind is still a contracts change; only reading a result is looser.
- **The cache** is a table beside the event log, one row per step, holding the latest result; it survives a restart with its checked-at (ADR 0031's chosen default). It is not the state a check checks, so writing it breaks no rule.
- **Publishing**: a result whose state, reason, failing, actions or targets differ from the cached one is a notice `setup.result-changed` (the result) on the environment stream; a result that only refreshes checked-at updates the cache and publishes nothing, so an hourly pass that finds nothing new is silent (the key-managers spec's rule for its verifications). A client following the stream never hears such a re-check, so it says a result it follows is unchanged since its checked-at and never ages it against the cadence; no event is published per re-check (David, 2026-10-01, #671). `environment.subscribe`'s snapshot gains `setup`, every registered step's cached result in order, as it gained the environment's name, icon and colour (workspace-picker spec). This is ADR 0031's `setup` subscription: no new stream method, since the env spec allows two named subscriptions and `environment.subscribe` (chosen default).
- **Chosen defaults not decided on a ticket, from the cache (#569)**: the cache is migration 7's `setup_results`, a row per step holding the result's JSON, checked-at included, written with its notice in one transaction. "Differs" is anything but the top-level checked-at, `lastGood` included (the ticket's words). The cache holds the result of a step's latest check: a step's check runs one at a time (#571), so no earlier check can answer after a later one. A row the build cannot read (another version's shape) counts as never checked: absent from the snapshot, and the next result is noticed as a first. A row a newer version wrote in a vocabulary this build lacks (a rollback's) reads with what it does not know left out (#693), and "differs" is judged against the row as written, so a result without the newer verb is noticed. `lastGood` comes from the cache (#571): the cached result when it passed, else the one the cached result carried, so a check that failed in between (needs attention, no `lastGood`) leaves the next timeout none. The snapshot's `setup` is optional in the schema, absent from an environment without the flag; one with it always sends it, empty before any check.
- **`setup.check`** stays a `read` query (one step or all): it runs the checks now and answers once each is done or its budget ends. A check that has to verify something (a forge account, a key-manager token) runs the feature's own verification as `system:setup`, which records what it finds as those queries already do; the caller's scope never rises (chosen default). Program pairings can read health; no check writes the state it checks.
- **A check in flight** is the client's: a client that has waited half a second on its own `setup.check` shows the step pending (ADR 0031's half second; where it shows is a chosen default). Checks the environment starts itself show nothing until their result.
- **Chosen defaults not decided on a ticket, from the client runtime (#570)**, detailed in the client-runtime spec. A step is registered once the environment has given a result for it. A check naming no step makes all eleven steps pending until its answer. An environment without the flag is asked every step's check each time its projection comes to be followed. Stale covers every result while the environment cannot be reached, and a followed result until the stream is live again. The age is counted on the environment's clock against the cadence in the client's registry. From #671: an answer to the client's own check is one it asked for until its step's cadence passes on an environment with the flag, which has checked the step again unasked by then; past that, and for the stream's results, the result is followed. A notice carrying the very result the client's own check answered, checked-at included, is that check, so asked. The client waits for `setup.check` as long as the longest budget plus 30 seconds.

### Skipped (David)

- **Drawn as "Not set up".** The wire state stays `skipped`; every client's word for it is "Not set up" (setup-copy.md §3's state words: done "Done", needs-attention "Needs a fix", skipped "Not set up", pending "Checking").
- **Derived from state, never recorded.** A skippable step declares `skip`, a state check meaning "something is set up here": when it fails, the step answers skipped with the check's line and runs nothing else; when it holds, the other checks run and the step is done or needs attention. Nothing a person does records a skip.
- The skip checks: Carry over, `carry-over.present` (an adopted account with something to carry, or a source data folder or terminal-client state folder found); Forges, `forges.present` (at least one forge account); Key manager, `key-manager.present` (a connection); Memory bank, `memory-bank.present` (a registered bank); Skills, `skills.present` (a tracked source or a skill in the own directory); Browser, `browser.present` (a paired Chrome). Account, Your machines, Instructions, Permissions and Appearance are never skipped (ADR 0018, ADR 0025, ADR 0030, ADR 0031).
- **"Skip for now"** on a first-launch card moves the rail to the next step and records nothing (ADR 0019's words, kept for its meaning).
- The stub's `check.ts` comment and `StepState`'s description ("a person skipped") change to this rule.

### Running checks

- **When**: on environment start (after the launcher's settle, before the scheduler arms routines), for every step; on `setup.check`, which a client calls when Set up or a step's pane opens, when the window regains focus while Set up shows a step (that step alone, at most once in ten seconds, so a cause fixed outside the app shows without Check again; #1860), on Check again (one step) and on Check everything again (every step), which replace the clients' "Check now" and "Re-run"; within a second of a trigger arriving (repeated triggers inside that second run one check); and when a step's cadence elapses since its last result (ADR 0031).
- **Chosen defaults not decided on a ticket, from the scheduler (#571)** (`environment/src/setup/scheduler.ts`): the start pass runs past the update coordinator's settle and before the wire opens, not awaited, so a check that hangs holds nothing up past its budget; the in-process handle's `setup.startPass` settles once every step has answered, for the routines start pass (#535) to follow. A trigger has its step checked one second after it arrived, every trigger inside that second joining the one check. The cadence or `setup.check` that arrives while the step's check runs takes that run's result (the ticket's words). A trigger that arrives while it runs is heard again as the run ends, so the step is checked once more after that run (David, #678, option 3): the run read the settings as it started and each state check as it asked it, so a change that lands mid-run is never absorbed by a result that read the state before it. That is any trigger, what the check's own verification records included, so a Forges check whose verification found a change (`forge.account.verified`, appended only on a change) is followed by one more, as is a Key manager check that signed in afresh or found a change, a cost David accepted; the check after finds nothing new to record, so it ends there (a Forges check after reads that verification's findings, younger than its cadence, and asks the forge nothing, #680). Every trigger during one run is heard as one, and the check after it goes through the trigger's second, run a second after the run ends with every trigger inside that second joining it (chosen default). A step is due a cadence after its cached result's checked-at, whichever check wrote it; a cached checked-at later than now (a clock set back) counts as due, so no step waits past its cadence. `settings.updated` triggers a step when its `values` name a key the step writes. The environment's checks append their results as `system:setup`, as `setup.check`'s do; a verification a check runs is recorded as that verification records it (`system:forge` for a forge account, #319; `system:key-manager` for a key-manager connection, #383), never as the caller. A change a step's checks read that no event records is named to the scheduler in process and triggers the step as an event would: each check of the release channel as it ends, for Your machines (#679). Each state check is told how old a finding of its feature's own schedule may be to be read rather than asked again: the step's cadence on the environment's own checks, none on a client's `setup.check`, which checks fresh (#680; the Forges checks read their verifications this way).
- **Budget**: a check past its budget answers needs attention, "Checking took too long. Choose Check again." with `details` "Stopped after N seconds.", action `check-again`, with `lastGood`; an answer that throws answers "agent-harness could not finish checking this step. Choose Check again." with `details` "<id>: <error>" the same way (the stub's rule; the words are setup-copy.md §3's).
- **Check everything again**: `setup.check` of every step on the picked environment, then the client jumps to the first needing attention with its actions; done and skipped pass (ADR 0031).
- **Unreachable** is the client's to see: a check cannot run on an environment the client cannot reach, so the card and the rows say "This app cannot reach <name> (since <time>). These results may be out of date." from the client runtime's connection state, the cached results beneath marked stale (setup-copy.md §3) (ADR 0025; chosen default, since ADR 0031's rule assumes a reachable environment).

### Actions

The vocabulary (`SETUP_ACTIONS`) gains the verbs the decisions name that it lacked: `start-service` (the local environment down, ADR 0025), `import-again` (a Carry over or state import that failed part way, ADR 0021), `try-again`, `write-it-myself`, `start-over` and `revise` (ADR 0019), `check-certificate` (a key-manager connection whose certificate does not verify, #1852), and `how-to-set-up` (a container's host-side updater that has never polled, #1883). A client maps each action to a command or a row: `sign-in-again` opens the item's sign-in, `pull-now` calls `skills.sources.pull`, `check-again` calls `setup.check`, `unpair` and `pair-another` the browser's methods, `install` and `update` `tools.run`, `reload` shows the Chrome line, `set-up-this-machine` switches the picker, `restore` the step's restore method, `move` opens the Move card, `check-certificate` Key managers, where each connection's certificate check is, `start-service` `connections.startService`, `import-again` the step's import with `dryRun: false` again, `how-to-set-up` on Your machines the host-side updater's setup, its commands to copy.

### The LLM step and minted sessions

- **`setup.mint`** (`admin`, prepared command): step, subject (a bank id for Memory bank), variant `first` or `revise`, optional account, model and effort. It creates a session through `sessions.create` in process: the workspace the step names (for a bank, a writable worktree of it on a branch `setup/describe-<date>`, never the bank's checkout, as the banks spec settled; `scratch` otherwise, workspace-picker spec), tags `setup` and the step id, title "Set up: <step> (<subject>)" (both chosen defaults; ADR 0019 asks only for a tag naming the step), the account, model family and effort from the call, else the environment's defaults (ADR 0018); then `runs.start` with the step's prompt, or the prompt as the session's draft when no account or model resolves (ADR 0019). It answers the session id. The picker's change is remembered by the client for the rest of this checklist run.
- **Prompts** live in `contracts/src/setup-prompts.ts`, one per LLM step and variant, rendered by the environment from live facts (the bank's name, kind, entities, the scope folders, the orientation caps) and versioned with the bank validator they must satisfy (ADR 0019, ADR 0013).
- **Detection is the step's check.** A session tagged `setup` and a step id is a trigger for that step at every run end (`run.ended`), so the check runs when the conversation stops; a clean end with the check still failing names what is missing.
- **The card** embeds the session's transcript and composer from the client runtime under a status line (running, waiting for you, landed, landed and awaiting review) with Open in the main window; a parked prompt is answerable on the card. No timeout (ADR 0019).
- **Failure**: an errored or interrupted run leaves the step needing attention with `try-again` (`runs.send` "Continue where you stopped." on the same session), `write-it-myself` (opens the artefact: the bank's checkout folder in the file pane, or the Instructions editor), `start-over` (`setup.mint` again; the old session stays). A done step offers `revise` (`setup.mint` with `revise`).
- In milestone 1 the only LLM steps are the bank's describe conversations (ADR 0035, ADR 0037). Tailoring an instruction with the model (ADR 0019's second example) was not taken up by ADR 0030 and is out of scope.

### The checklist in the GUI

- **Words and the step's shape** are [setup-copy.md](setup-copy.md)'s: every card is the shared step page of its §3 ("Step n of 11", the title, one "why" line, "What is this?", the controls, one "More options" fold and the status line), and a status line that needs a fix has Details with **Copy details**, which copies the app's and the computer's versions, the step and its state, when it was checked, the line, the failing check ids and `details`, one per line (setup-copy.md §3).
- **First launch** (GUI spec): while the client-local first-launch mark is unset, the introduction takes the whole window from the first frame, while the environment on this machine starts ([look.md §13](look.md#13-set-up)). It stays visible through starting, ready and failure, with Try again and Connect to another computer; a stopped environment offers Try again without claiming to start unasked, and opted-out or unavailable local services explain why and offer pairing; the technical cause sits behind Details with Copy details (setup-copy.md §4.1). Begin set up is enabled once a home environment is ready and opens Account, then the rail of eleven steps with dots, the card beside it and the environment picker. Continue past Account is disabled until one account is signed in, including when reopening the checklist (ADR 0018); every other step has Continue and, when skippable, Skip for now. Finishing the last step or closing sets the mark; without a signed-in account, Close, Finish or leaving the introduction asks “Leave set up without an account?” once per action, with “Leave for now” and “Keep setting up”; "Open Set up" brings it back.
- **The Set up pane** (row `setup.checklist`, ADR 0027): every step with its dot and one-line reason, choosing it opening Set up at that step (setup-copy.md §4.5), counts (ADR 0027; the wording "8 done · 1 needs a fix · 2 not set up", setup-copy.md §4.5), Check everything again, Open Set up, the environment checked with its picker, and "Set up another computer", which opens Your machines' Add a device. Results come from `projections.setup`. A result the client follows says since when it is unchanged ("No change since 09:14."), never its age, since a re-check that finds nothing new publishes nothing; one it asked for itself shows its age once older than its cadence ("Last checked 3 hours ago.") (David, 2026-10-01, #671).
- **The rail's dots** show on home rows only, the worst state of the steps homed there; the Set up row shows the worst of all, for the environment last picked (GUI spec). The header's Set up line shows while a step on the home environment needs attention.
- **Cards** are this spec's; a card may reuse its home pane's components (GUI spec). Each is registered by step id in the window's frame (`packages/gui/src/setup/cards.ts`), and a step with none keeps the fallback card of #413 (#573).

### Phone Set up and pairing

Pairing opens sessions directly; Set up remains available with the same eleven
registered steps. On phone widths use full-height Settings, row/step drawer
navigation, long-card scrolling and a sticky Back/Continue/Finish footer above
the keyboard/safe areas. No browser local service/bootstrap attempt is offered.
Default Phone lacks admin: explain re-pairing instead of weakening row scopes.
With an explicit admin grant or My own client, sign-in opens the provider's
verification page from a tap, returns to paste a code and resumes streamed
status. Provider credentials stay environment-owned. Codes last ten minutes;
link/QR use the configured HTTPS origin and actual grant disclosure. QR scanning
has denial/Cancel/manual fallback and stops tracks on exit. Custom expansion is
deliberate and cannot exceed the minter's grant (web-client spec).

### Provider sign-in on another environment (#1648)

Every environment keeps its own provider sign-in. Pairing a client to two
environments does not copy a credential or relay a sign-in through the other
environment. Accounts offers “Sign in this account here too” for an identity
signed in on another paired environment and absent here. It adds a local
account label and starts the chosen environment's normal sign-in; the person
chooses that identity on the provider page. The provider's status read decides
which identity actually signed in.

On a desktop's local environment, the provider CLI opens its own loopback
authorisation page. The client leaves that browser flow alone and follows
completion: it must not also automatically open the printed manual-code URL.
The CLI owns the random-port, loopback-only listener, state and proof key,
exchanges the code itself and closes the listener when done; cancellation and
the environment's ten-minute expiry stop the CLI and its listener. If the
service cannot open a browser, the manual page remains available.

For a headless environment or a client on another device, the manual page is
also a QR. It always names the environment being signed in. “Paste code from
clipboard” reads only on a deliberate tap and submits the full `code#state`
value once its shape and the published URL's state agree. Refused clipboard
access leaves the ordinary paste field available. A phone's provider login
can ease authorisation; it never becomes an environment credential itself.

### The terminal UI

`/setup [environment]` draws one line per registered step from `projections.setup`: its label, state glyph and word (setup-copy.md §3), and reason when it needs attention; skipped steps dim and read "Not set up". With no name it uses the session environment. While a step on that environment needs attention the header carries "Set up on <environment>: N of M done, K need a fix (<step names>)." ("1 needs a fix" for one) and the closing line "Press Enter on a step to run its fix, or open Set up in the desktop app." (setup-copy.md §4.5), with M its registered steps (eleven with every entry built). Snapshots and notices redraw both without a call. After accepted writes the terminal issues itself (`/pair`, `/mode`, `/containment`, a sign-in) it calls `setup.check` for that step. Actions needing no card (`check-again`, `pull-now`, `restore`, `update`, `start-service`) run from the line with Enter; the first offered action is selected by default and `picker.preview` (Space, remappable) previews the next. A tool's Update is absent with its reason where the environment does not serve it, otherwise opening its tool terminal in the pane. Other actions point at the desktop (ADR 0016). Unreachable results stay cached, marked stale with "This may be out of date: <name> cannot be reached." (setup-copy.md §3). #572 implements this, preserving #261's check on opening without the stream flag.

#### 3. Your machines (ADR 0025)

- **Entry**: writes `updates.*` (launcher-update spec), the three session keys the GUI placed on `environments.service` (moved here from Appearance; the session-state spec allowed the move), and two new keys, `network.bindTailnet` (preset on when a tailnet address is found) and `network.bindLan` (preset off), each applied at the next start (env spec's binding rule; chosen default); `writesState` `environment.rename`, `setIcon`, `setColour`; links `environments.service`, `environments.access` and the Permissions step; state checks as registered (`not-root`, `named`, `updates`, `release-channel`, `host-updater`) plus `your-machines.ready` (discovery answers `ready`, not draining past its cap, `check-again`) and `your-machines.lan` (LAN binding off, or naming an address the machine holds now, `check-again`; #773); triggers the `environment.update-*` notices, `environment.renamed`, `environment.icon-set`, `environment.colour-set`, `settings.updated` for its keys. A check of the release channel appends nothing, yet changes what `release-channel` and `updates` answer, so each check that ends, read or failed, triggers the step in process (the channel checks' `onChecked`, heard by the scheduler's `trigger`): it is checked within a second, as on any trigger, and a new machine's step reads done a second after the first read, two minutes after the start, not at its cadence an hour on (#679).
- **Chosen defaults not decided on a ticket, from the entry (#574)**: `your-machines.ready` reads the environment's own status document on its clock: it holds while the environment is ready, or has drained for no longer than the drain's thirty-minute cap, a drain within it being an update or a restart under way; past the cap it fails naming since when the environment drains (and a start not yet ready, which a check never meets, fails saying so). A native drain closes the environment at its cap, so what it meets is a container's update drain waiting on the host-side updater's stop, or a close that hangs. `network.bindTailnet` is a boolean preset on, which binds the tailnet address when one is found and nothing when none is; `network.bindLan` is null (off, the preset) or an IPv4 or IPv6 address, never the wildcard, which its schema refuses; `settings.update` writes both. The start reads them at its listen step, and the start options `bindTailnet`, `bindLan` and `lanAddress` override them (a `bindLan` option takes its own `lanAddress`, or none). The LAN address must be one the machine holds: the addresses of its network interfaces, read each time they are asked, but loopback, link-local and Tailscale's ranges (100.64.0.0/10, fd7a:115c:a1e0::/48); a start that finds another binds loopback and the tailnet without it, saying so in one line on standard error that names it and the addresses the machine holds (decided on #773, replacing the failed start #574 chose: no client could reach a stopped environment to turn the key off). `your-machines.lan` then needs attention with the same naming, read against the settings and the interfaces each time it runs, so turning LAN binding off or picking an address the machine holds clears it at once, as a rejoined network does on Check again; either key change applies at the next start. `environment.status`, and the status in `environment.subscribe`'s snapshot, gains `binding`: `tailnet` (the address bound and its tailnet name, or null), `lan` (the address bound, or null) and `lanAddresses` (those the machine holds now); optional in the schema, absent from an environment that predates it.
- **Card per environment**, This machine first: name, icon and colour; reachability (tailnet name or address; loopback only with the Tailscale warning "Your other devices cannot reach this computer yet. Install Tailscale here and on your other devices.", Get Tailscale and Check again, and the LAN switch "Also allow devices on this Wi-Fi network" naming the address it would bind with "Anyone on this network could try to connect. They still need a pairing code.", the words setup-copy.md §5.4's); version, channel and auto-update with the idle window, deferral cap and pin under Advanced; Update now when behind or when this client is newer; containment availability with a link to Permissions; Manage access (`environments.access`). Unreachable: "This app cannot reach <name> (since <time>). These results may be out of date." with Try again; the local environment down: "agent-harness is not running on <name>. These results are from before it stopped." with `start-service` (setup-copy.md §3). No tailnet address is a standing notice on the card, never a failure (ADR 0025).
- **Add a device** (was Add a machine; setup-copy.md §5.5): Paste a link or code (and scan a QR on platforms with a camera), then the exchange; or **Install agent-harness on another computer**: the one-line script per platform (launcher-update spec's `install.sh` and `install.ps1`, and the container compose snippet with its link to the host-side updater's documentation), parameterised with this environment's channel and an optional name, ending by printing the link, ASCII QR and code (ADR 0025).
- **Pairing codes** from this machine for another client: **My own client** (preset): every scope and the ceiling `bypassPermissions` (ADR 0025), also valid on a phone without automatic downgrade; **A program**: `read`, `sessions:write`, `runs:drive`, a ceiling picker preset `acceptEdits`, label preset to the program's name; **Phone**: fixed `read`, `sessions:write`, `runs:drive` at `acceptEdits`; **Custom**: scope ticks and a ceiling. The card calls `access.pairings.create` with scopes and ceiling explicit, shows what the code grants beside it and its ten-minute countdown.
- **Set up this machine** on a new card switches the checklist's picker to it and jumps to its first step needing attention; **Forget** revokes this client's session when reachable, else forgets locally and says the session stays until revoked there; the local environment cannot be forgotten (ADR 0025).
- **Chosen in building the Your machines card (#576)**: the card is the Your machines row's, registered for the step with the step's status above it; its reachability line and binding switches read `environment.status`'s `binding` and write the two keys through `settings.update`, the Tailscale warning shown for loopback alone while `network.bindTailnet` is on, and Check again reading the status again rather than checking the step, whose checks do not read the binding. Set up this machine stays on the card Add a machine made, as ADR 0025 has it. The GUI spec has the words.
- **Decided on #861 (David, 2026-10-01; the second of three choices)**: the environment looks for its Tailscale address at its start's listen step and binds it only there, so a Tailscale installed after the start is bound at the next start. `environment.status`'s `binding` says such an address as `tailnetFound`: a Tailscale address the machine holds that the environment does not bind, found since its start or found at it with `network.bindTailnet` off, looked for again (`tailscale ip -4`) at each `environment.status` request while no tailnet address is bound; the launcher's queries and the subscription's snapshot read it as last looked for (the step's checks do not read the binding). It is null when a tailnet address is bound or none is found, and absent from an environment that predates it. The card says, in place of the Tailscale warning, "Tailscale address <address> found: <name> binds it at its next start.", with Check again, which finds the address bound once the environment has started again. Not chosen: the card's words alone saying a restart binds it, since the status could not tell whether Tailscale was found; and binding the address without a restart, which David wants after milestone 1 (#1015).

### The headless path

A headless machine is installed by the script from Your machines' Add a machine, which ends by printing the pairing link, QR and code (or, in a container, prints them to the log until the first exchange). Any client pairs with it as My own client, the new card offers Set up this machine, and the checklist runs against it; its checks run on it hourly whether or not a client is connected, and `/setup` in the terminal reads the same results (ADR 0016, ADR 0025).

### Wire methods, events and notices

- `setup.check` (`read`, query; unchanged but for awaited checks, budgets and `lastGood`). `setup.mint` (`admin`, prepared command). `carryOver.inventory` (`read`, query), `carryOver.run` (`admin`, prepared), `carryOver.assignMemory` (`admin`, command). `stateImport.detect` (`read`, query), `stateImport.run` (`admin`, prepared; #94's build).
- **Notices** on the environment stream (`ENVIRONMENT_NOTICE_TYPES`): `setup.result-changed`, `carry-over.imported`, `state-import.finished`; the client runtime's request cache refreshes `carryOver.inventory` on the second and `stateImport.detect` on the third.
- **Events**: `carry-over.imported` on the environment stream (`system:setup` for none; the caller's client session for the command); session events of an import use the session-state spec's types with origin `import`.
- **Snapshot**: `environment.subscribe` gains `setup`.
- **Settings**: `network.bindTailnet`, `network.bindLan`.
- **Errors**: `setup.mint`: `not_found` (subject), `conflict` reasons `no_llm_step`, `bank_missing`; `carryOver.run`: `conflict` reasons `not_adopted`, `import_in_progress`; `stateImport.run`: `conflict` reasons `no_source`, `import_in_progress`.

## Testing Decisions

A good test is behaviour seen through the wire: what `setup.check` answers, what the snapshot and notices carry, what a card's command appended; never the cache table or the scheduler's timers except at the lower seam.

- **Primary seam: the in-process environment** (env spec's helper: temporary data directory, loopback port 0, the typed client over a real WebSocket, the injectable clock) with a test registry of scripted steps: a check that holds, fails, throws, hangs past its budget, and answers late; through it, the three states, `lastGood`, the budget per class, the cadence on the clock, triggers (and one check for a burst inside a second), the run on start, the cache across a restart, silence when only checked-at changes, and `setup.result-changed` otherwise; the skip rule for each skippable real entry against fixture state.
- **Real entries**: each of the eleven against fixture state as its feature is built, through its home row's data: Account against the scripted sign-in; Carry over against a fixture adopted directory (sessions archived and not, a gone workspace, memory with an unmappable folder, skills with a checkout), including the dry run, deduplication on re-run and nothing written in the directory; the state import against a fixture source data folder with the four report groups; Memory bank against a fixture bank repository (valid, invalid, awaiting review) and a minted session's run end; Your machines against a draining and a behind environment.
- **`setup.mint`**: a scripted provider run ending with and without the artefact; the draft when no account resolves; `try-again`, `start-over`, `revise`.
- **Contract tests** in contracts: every `STEP_ORDER` id registered before the switch-over's done checklist passes (#94 runs it; until then, only registered ids are checked); every entry names exactly one home row, and the row registry lists that row as home to that step (a row may home several, as `accounts.accounts` homes Account and Carry over), a budget, a cadence of 60 or a reason, triggers that are known event or notice types, a skip check iff skippable, actions from the vocabulary; `writesState` parts disjoint across steps (the denylist's four sections are the Permissions step's alone); every settings key on exactly one step (existing rule); the prompts render for every LLM step.
- **Client runtime**: `projections.setup` from a snapshot and notices; the first-launch mark.
- **Not tested here**: a real Chrome, a real forge or key manager, the install scripts on each platform (a manual checklist item, as the service install).
