## Problem Statement

Memory banks are what David calls the harness's most important feature, and today they work by accident. A session sees 46 of notebook's 226 in-scope memories, chosen by path order, because a flat index is capped and split evenly between banks; notebook gains about thirty memories a day into folders already too big for any flat list (index research). Nothing says what a bank is for, so a fact about a brand can land in a personal bank. The registry is a per-machine file keyed by profile ids with one default per machine, and creating, joining, verifying or forgetting a bank exists only in one desktop (core audit, section 4). Bank checkouts are attached writable to Codex runs, so a run can edit a bank without draft, validation or review. Two validators disagree: notebook's CI runs its own Python CLI, meadowstudios's only scans for secrets, and the draft-time checks live in a third place. A team bank's review rule is a hope, since a free private repository has no branch protection. And `INDEX.md` is regenerated on every landing for readers who no longer need it.

## Solution

A bank is a git repository with a `BANK.md` that says what it is: personal or team, a one-line purpose, the entities whose facts belong in it, up to five orientation memories everyone always sees, and for a team its owners. Every bank has the same folders, `projects/{org}/{project}/{area}/`. Each environment keeps a registry of the banks it carries: role, account and repository scope, default write target per account, pins, and for a team bank the teammate's own review override and private-copy switch. One BankService on the environment creates, joins, verifies, syncs, lands, splits and forgets banks for every client. Runs see banks as a breadcrumb trail rendered in tiers whose caps are enforced when something is written, never by cutting when it is read: every bank's line and orientation, every folder as a pointer with a count (or one read away when the budget collapses a bank or org to its line), and a folder's memory lines only when it is relevant to the session. They read and write through five memory tools on every provider, never by editing a checkout, which is attached read-only. One validator, built from the contracts package, runs when a memory is drafted, when it is promoted, in each bank's CI as a vendored file, and in the BankService. Before a run starts, stale banks are brought up to date within three seconds. notebook and meadowstudios move onto the contract on switch-over day.

## Implementation Decisions

Every rule cites its decision; a rule marked chosen default was left open by the tickets and is listed again under Further Notes.

### Modules

- **Contracts**: the `BANK.md` and folder-file schemas; the pointer syntax; the **validator** as pure functions over a bank's files (no I/O), its rule ids and messages; the two templates; the memory-tool schemas; the methods, events, errors and notices below; the Memory bank step's entry (setup spec). The same validator builds to one Node file for bank CI.
- **Environment**: the **BankRegistry** (records and events), the **BankService** (create, register, join, preview, publish, verify, sync, forget, split, credential, migrate, validator update), the **Lander** (worktree, branch, pull request, merge rule, verify), the **Syncer** (before-run and scheduled fetches), the **IndexRenderer** (tiers, relevance, the render ladder), the **BankLayer** (the instruction layer's bank part), the **MemoryBlock** writer (the marked block in `MEMORY.md`), the **memory tool server**, and the orientation block's banks provider.
- **Client runtime**: `banks.list` in the request cache, refreshed on `bank.updated`; the bulk registry copy.
- **CLI**: `agent-harness bank validate|search|read|draft|promote`.

### BANK.md and the folders

- **Frontmatter** (ADR 0010, 0034, 0035, 0037): `name` (the bank's name: 1 to 40 characters of lower-case letters, digits and hyphens, unique per environment; chosen default); `kind` (`personal` or `team`); `purpose` (at most 160 characters; the bank line); `entities` (each `name`, `aliases`, optional `folder:` naming the scope folder a match expands); `orientation` (at most five memory names); `owners` (team banks: forge logins, at least one); `memories` (`glob`, `scope`, `schema`); `docs` (`globs`); `write` (`place`, the path template a memory is written to, `projects/{org}/{project}[/{area}]/memories/[{topic}/]{name}.md`; `land` `pull-request` or `commit`; `merge`). `description`, `index` and every key the new ones replace are refused by the validator after the migration (ADR 0034).
- **`write.merge`** (ADR 0035; its shape a chosen default): `memories` `auto` or `review`; `reviewed` the classes that always wait: `orientation`, `decisions`, `status`, `manifest`; the templates preset memories `auto`.
- **Folders** (ADR 0037): `projects/{org}/{project}/{area}/`, the area optional. `ORG.md` carries `line:`; `PROJECT.md` and `AREA.md` carry `line:` (at most 100 characters), `topics:` (a map of topic to one-liner) and `repos:` (repository identities). Memories live at `projects/{org}/{project}/memories/` or `…/{area}/memories/`, optionally one topic deeper. The scope labels are `org`, `project` and `area`. The bank's home folder for orientation is `projects/<first org>/bank/` in a team bank and `projects/personal/memory-bank/` in a personal one (ADR 0034, 0037).
- **A memory** keeps the existing schema: frontmatter `name`, `description` (60 to 160 characters), `metadata.type` (`user`, `feedback`, `project`, `reference`), optional `metadata.applies_to` (repository identities); the body at most 6,000 characters. `[[name]]` links a memory.
- **Pointers** (ADR 0013): `bank:path/` names a folder or topic, `bank:name` a memory, printed identically in index lines, search results and reads.
- **Templates**: the personal and team drafts of ADR 0034, rewritten to the three levels and `owners:`, their bodies rendered without placeholders into the README. The body reaches a run only through the rendered bank layer, never verbatim (ADR 0034).

### The validator

- **Refuses** (ADR 0013, 0034, 0037), each with a rule id: a description outside 60 to 160 characters, equal to the name re-cased, or not unique in its folder; a body over 6,000 characters; a folder without a parsing `ORG.md`, `PROJECT.md` or `AREA.md` carrying `line:` of at most 100 characters (and `topics:` on a project or area); a folder or topic index over 40 lines after the write; a new scope folder that would make the root breadcrumbs exceed 40 lines unless the root is re-tiered to orgs; unknown scope labels or undeclared topics; a `BANK.md` without kind, purpose, entities with aliases, or (team) owners; an orientation list over five names, naming a missing memory, or over 600 bytes each or 1,500 in all; `repos:` or `applies_to` entries that are not repository identities; a retired key; a secret-shaped string or a registered value, as `secret_shaped`, naming the rule and field, never the value (key-managers spec).
- **Warns**: a description not opening with a trigger word; two banks claiming one alias (in the BankService, which sees both); an unresolved `[[link]]`.
- **Where it runs** (ADR 0013): `memory_draft` (refuses with reasons); `memory_promote` (again, against the bank's current main); the BankService on `BANK.md` and registry changes; and the bank's CI.
- **Bank CI** (David): the validator builds to `validate.mjs`, a single Node file stamped with its contracts version, vendored into each bank at `.agent-harness/validate.mjs` with a workflow for its forge (`.forgejo/workflows/validate.yml` or `.github/workflows/validate.yml`) that runs it on every pull request and push to main, beside the bank's own secret scan. When the environment's validator version is newer than a bank's stamp, the BankService opens a pull request updating the file (`banks.validator.update`, also offered on the bank's card), which lands through the bank's review path.

### The registry

- **A record** (ADR 0010, 0035, 0037): client-minted id; name (from `BANK.md`); origin and repository path (a remote identity) or local-only; checkout path; kind (from the manifest); role `read-write` or `read-only`; enabled; account scope (`all` or account ids); repository scope (`all` or repository identities); `defaultFor` (account ids for which this bank is the default write target; one bank per account); `pins` (registry pins: folder pointers expanded in every session in scope); for team banks `mergeOverride` (`none` or `review-memories`, the teammate's stricter rule, ADR 0035) and `privateCopy` (off, ADR 0034); the credential source (`forge`, the forge account matched by origin, ADR 0020; `stored`, a vault token; `reference`, a key-manager reference); status (reachable, manifest valid, orientation valid, last sync, landing, each with since); `importedFrom`, `copiedFrom`; created-at.
- **Defaults** (ADR 0035): a created personal bank is read-write, enabled, every account, every repository, the default write target for each account on the environment without one, memories auto. A joined team bank's role is read-write when the forge account can push, else read-only; accounts as the teammate ticked; never a default target (ADR 0037).
- **The 8 KB rule** (ADR 0013): `banks.registry.update` and every add refuse a scope under which an account and repository would carry more than 8 KB of fixed tiers, `conflict` reason `index_too_large`, naming the banks.
- **Checkouts**: a created or joined bank clones to `<data dir>/banks/<name>/`; a registered one keeps its path (the state import). A checkout is the BankService's; landing never writes in it (chosen default).

### Rendering the index

- **Tiers** (ADR 0013, 0037): T0 the bank line (`## <name> (<kind>, <role>) — N memories in M folders — <purpose>`); T1 orientation, always; T2 root breadcrumbs, one per project or area holding memories (`- <bank>:<org>/<project>/<area>/ (N) — <line>`), grouped under an org header (`### <bank>:<org>/ (N) — <ORG line>`); T3 a folder's index (at most 40 lines of `- name — description`, topics as breadcrumbs), expanded whole or not at all. Session total at most 150 lines and 20 KB. Counts are an invariant: children sum to the parent.
- **The ladder** (ADR 0013): T0 and T1 for every bank; T2 for every bank, signalled banks first; T3 in relevance order until the budget; a bank with no signal collapses to its line; an org group may collapse to its header; a relevant folder that does not fit stays a breadcrumb marked `[matches this repository]`. A line is never cut from a group.
- **Relevance** (ADR 0013): pin (registry, then session), repository identity (a folder's `repos:` against the session's identity), entity match (aliases and names, whole-word and case-insensitive, against the first message and the repository identity), recent use (folders this session read, searched into or drafted into through the tools), ties by fewer lines.
- **Placement** (ADR 0013; David): a bank scoped to every account renders its session-independent tiers (T0, T1, T2, and T3 expansions by repository identity or registry pin) into the per-repository auto-memory `MEMORY.md` (claude-adapter spec's directory, shared by every account, ADR 0018), inside one block the harness owns, between `<!-- agent-harness:banks -->` and `<!-- /agent-harness:banks -->` (markers a chosen default), rewritten whole and never touching Claude's own lines or Carry over's pointer lines. A bank scoped to chosen accounts renders all its tiers in the run's instruction layer, where the account is known. Session-dependent expansions (entity, session pin, recent use) are always in the instruction layer. Providers other than Claude get everything in the instruction layer.
- **When**: the block is rewritten when a bank in scope lands, syncs a change, or has its registry changed, for the repositories that bank reaches, and when a run starts in a repository with no block yet. A kept provider process reads `MEMORY.md` at its own start, so a changed block reaches the next process; the auto-memory directory stays out of the spawn key (chosen default).
- **The bank layer** in the instruction layer (skills-instructions spec's order: user, team bank, project, session): for each bank in scope its name, kind, purpose and role; the entity lines ("Facts about Moon-Gems go to meadowstudios."); for a team bank with a personal bank beside it, "You may also keep a private copy of a team fact in <personal bank>: off" (or on) (ADR 0034); the tools contract (name a bank when several are writable; scope by org, project and area; one fact per memory; point, do not restate); then the account-scoped and session-dependent tiers. Rendered from state without a clock, so unchanged state gives byte-identical text (skills-instructions spec); the counts change only when a bank does.
- **The seams** gain `repositoryIdentity` on `ToolServerScope` and `InstructionScope`, set from the session's workspace (workspace-picker spec), which relevance needs.

### The memory tools

- **One in-process tool server `memory`** (its name a chosen default), from the tool-server factory for every run whose account has a bank in scope (ADR 0010: every provider; Claude in milestone 1, the others with their adapters). Tools, as `mcp__memory__<tool>`:
  - `search {query, bank?, scope?, limit?}`: memories, folder and topic one-liners, orientation and entity aliases (ADR 0013), each hit as its pointer and one line, then "n of N".
  - `read {pointer?}`: no pointer, every bank's line; a bank, its root (T0 to T2); a folder or topic, exactly its T3 text; a memory, its file. A read ends with its folder pointer and count, so reads lead sideways.
  - `draft {bank?, scope, topic?, name, description, body, type, appliesTo?}`: runs the validator and queues the draft for this session; refused `bank_required` when the account has several writable banks in scope and none is named (ADR 0010: no auto-routing), and `bank_read_only` when the bank named is read-only. A draft of an existing name updates it.
  - `promote {bank?}`: lands the session's queued drafts for that bank (below) and answers each file's state on main.
  - `retire {bank, name, reason}`: queues a removal, landed by the next promote.
- **Drafts** are environment state per session and bank (chosen default), so an interrupted run loses none; `banks.drafts.list` shows them.
- **Access**: the tools are ordinary calls under the run's mode (the browser spec's rule for in-process tools); a pointer is not a path, so the denylist reads nothing in them (permissions spec).

### Landing

- **The Lander** (ADR 0010, 0035): in a detached worktree of the bank's fresh main under the environment's temporary directory, writes the drafts, validates, commits as the account's forge identity, pushes a branch `memory/<session short id>-<n>` (chosen default) through the credential helper, and opens a pull request through the ForgeService. **The merge rule**: the stricter of the bank's `write.merge` and the teammate's `mergeOverride`. A change of only memories under `auto` waits for the bank's `validate` check (up to ten minutes, chosen default), merges, and checks every file is on main. A change that touches a reviewed class, or holds memories under `review` (the bank's rule or the teammate's override), waits as a reviewed change: on a team bank with two or more owners, the BankService merges it once an owner who is not its author has approved it on the forge (read through the ForgeService); on a team bank with one owner, and on a personal bank, whose one owner is the user, it waits for that owner to merge it by hand, the card showing "awaiting your review" with the pull request (ADR 0035, ADR 0037). A local-only bank commits on its main (`write.land: commit`). The pull request goes to the forge the bank's origin names, one forge account per origin (ADR 0012, ADR 0020).
- **Answers**: landed (with the files on main), awaiting review (with the pull request), failed (the step and the reason, `bank.landing-failed`). A landing refreshes the checkout at once. A failed landing holds until one lands, except one refused for want of a forge account on the bank's own origin: a verification that finds the bank reachable with a forge account here covering that origin clears it (#1900).
- **Local-only** (ADR 0035): a git repository under `<data dir>/banks/<name>/`; follow-ups are files in `issues/` with the tracker's done-when shape; **Publish** (`banks.publish`) creates the private repository on the primary forge, pushes, switches `write.land` to `pull-request` by a first reviewed change, and offers to move `issues/` into the tracker. Refused while a landing is in flight.

### Sync

- **Before a run** (David): each bank in the run's scope whose last fetch is older than 60 seconds is fetched and fast-forwarded, the run's start awaiting them all for at most 3 seconds together; past that the run starts on the checkouts as they are and the fetches finish in the background. Never a merge: a checkout that cannot fast-forward is reset to its origin's main, since nothing is written in it (chosen default).
- **Scheduled**: every bank at environment start and every 30 minutes (chosen default), so an idle machine's `MEMORY.md` stays current. `banks.sync` (Pull now) at `read`, recording what it finds, as `forge.accounts.verify` does.
- **Credentials** (ADR 0020): harness git uses the credential helper against the canonical origin, never a configured remote; a stored bank token is served by the helper for the BankService's own git on that bank's origin only, never to runs (owed to the forge spec's helper route).

### Read-only attach

Each enabled bank in scope is attached to Claude runs as an additional directory with deny rules for the edit and write tools under its checkout (ADR 0010, the #24 Resolution); the checkout is outside the containment's writable set; the data directory's denylist preset exempts `banks/` for reads, as it exempts the skill-set directories (workspace-picker spec owed this root). At containment `off` a shell command can still write there; containment is a separate switch (ADR 0006), and the next sync resets the checkout.

### The BankService's methods

Scope `admin` unless stated; mutating methods take a `commandId`; calls carrying a credential are sent directly and never queued (key-managers spec's rule).

- `banks.list` and `banks.get` (`read`): records with status, counts and the rendered bank line; never a credential.
- `banks.create` (prepared): personal (name, the two seed answers, local-only or not) or team (forge account, owner, repository name, team name, first projects) (ADR 0035, 0037, setup spec). It writes `BANK.md`, the skeleton, the home folder, the README and the vendored validator as the first commit, creating the private repository through the ForgeService unless local-only, then registers the bank with the defaults. Owner pickers read `forge.orgs.list`.
- `banks.register` (prepared): an existing checkout by path, with role, scopes, default and `importedFrom` (the state import, ADR 0036); a repeated `importedFrom` answers the existing id. A checkout without `BANK.md` registers and shows needs attention until the migration.
- `banks.join.preview` (`read`, query, git budget): shallow-clones the URL to a temporary directory with the forge account by origin and answers the bank line, orgs, projects and entities, orientation names, owners, the merge rule, the shared-bank rules, and whether the account can read or push (ADR 0037). `banks.join` (prepared): clones and registers with the accounts ticked (none preset).
- `banks.publish` (prepared), `banks.registry.update` (role, enabled, scopes, `defaultFor`, registry pins, `mergeOverride`, `privateCopy`), `banks.pin {sessionId, pointer, pinned}` (`runs:drive`: a session pin; registry pins go through `banks.registry.update`; chosen default), `banks.forget {removeCheckout}` (the checkout stays unless asked, and never for a registered path).
- `banks.verify` and `banks.sync` (`read`, queries that record what they find, as `system:banks`).
- `banks.credential.set` (a stored token, sent directly; only on an origin with no forge account, ADR 0035) and `banks.credential.swap {bankId, reference}`, the Move card's swap for the target `<base>/bank-<name>` (key-managers spec, ADR 0028).
- `banks.split.propose {pointer}` (`read`): clusters from name prefixes; `banks.split.apply {pointer, topics}`: a reviewed change that declares the topics and `git mv`s the memories, keeping names and links (ADR 0013).
- `banks.drafts.list` (`read`), `banks.validator.update` (prepared), `banks.migrate {bankId, dryRun}` (prepared; below).
- **Errors** besides the shared union: `bank_required`, `bank_read_only`, `validation_failed` (the rule ids), `secret_shaped`, `forge_account_missing`, `conflict` reasons `name_taken`, `index_too_large`, `landing_in_progress`, `not_local_only`, `registered_path`.
- **Events** on the environment stream, as the forge's are: `bank.added`, `bank.updated`, `bank.pinned`, `bank.forgotten`, `bank.synced` (only when the head moved), `bank.verified` (only when a status changed, as `system:banks`), `bank.landed`, `bank.landing-failed`, `bank.awaiting-review`; notice `bank.updated`. The Memory bank step and the Instructions step trigger on them (setup spec).
- **Capability flag** `banks`.

### The Memory bank step and the orientation block

- The step's entry, checks and cards are the setup spec's (`memory-bank.present`, `.reachable`, `.manifest`, `.orientation`, `.owners`, `.landing`), answered from the records' status on the environment (ADR 0031); the describe conversation is `setup.mint` with the bank as subject. The minted session works in a writable worktree of the bank on a branch `setup/describe-<date>` (chosen default) inside its own workspace, never the attached checkout, and lands through the bank's review path with the run's forge variables (ADR 0019); the step detects the result. Describe worktrees use a separate bare repository under `<data dir>/worktrees/bank-describe/`, copied without shared objects from the checkout and refreshed from its main before minting, with the bank's remote as origin. Its writable git metadata stays outside the attached checkout; verification also reads its describe branches for awaiting review. After a clean run end, verification submits committed local-only describe artefacts to the environment-owned Lander, validating them and refusing to overwrite independently changed main files. Remote sessions push and open a pull request with their run forge variables; verification adopts that pull request into the Lander's durable reviewed path and refreshes the real checkout after landing (#1034).
- The orientation block's banks section (key-managers spec) comes from a provider registered here: each bank's name, kind, role, and whether landing works as a status with since, never a time the clock gives.

### The migration (phase D)

`banks.migrate` prepares, as reviewed pull requests on each bank, what ADR 0013, 0034 and 0037 require, and the switch-over lands them on switch-over day (David):

- **notebook**: kind, purpose, entities and orientation added (orientation memories written fresh as pointers, drafted by the build for David to approve); `ORG.md` per org; `description` to `purpose`, `summary:` to `line:`, `code:` to `repos:`; directory-name scopes rewritten to repository identities (118 of 187 today); the two unparsable `PROJECT.md` files fixed; topics proposed for the five over-cap folders, applied as David accepts each; `INDEX.md` and the index keys removed; the vendored validator and workflow added, replacing the Python CLI's check.
- **meadowstudios**: the same, plus the move from `brands/<brand>/<system>/` to `projects/meadowstudios/<brand>/<system>/`, the holding company's shared facts to `projects/meadowstudios/holding/<system>/`, `SYSTEM.md` to `AREA.md`, product lines as topics, and `owners: [david-systemtech]`. Before it lands, an issue on the bank tells the team owner what moves and when.

## Testing Decisions

A good test is behaviour seen through the wire, in a rendered `MEMORY.md` or instruction layer, in a tool's answer, or in a fake forge's record of calls; never the registry's tables or the renderer's intermediate structures, except at the lower seam.

- **Primary seam: the in-process environment** (env spec's helper) with a **fake forge** (the forge spec's: repositories, branches, pull requests, checks, reviews, merges) and **fixture banks** as git repositories on disk: a personal and a team bank on the new structure, one over its caps, one without `BANK.md`, a local-only bank. Through it: create, register, join with preview, publish, forget; the before-run sync's 60-second staleness and 3-second await on the injectable clock, and the background finish; the render ladder at every budget edge, a bank with no signal collapsing, an org group collapsing, the `[matches this repository]` marker, counts summing; placement by scope, the `MEMORY.md` block rewritten whole beside Claude's and Carry over's lines; byte-identical instruction text for unchanged state; the five tools through a scripted provider (search counts, reads leading sideways, `bank_required`, read-only refusal, drafts surviving a restart); landing under each merge rule, owner approval, a sole owner, a failed check, local-only commits; the 8 KB refusal; split proposals; the migration's dry run on copies of notebook's and meadowstudios's trees (counts, renamed keys, moved folders, links intact).
- **The validator** as pure functions: every rule id with a passing and a failing case, including `secret_shaped`, and the built `validate.mjs` run by Node against a fixture bank giving the same verdicts as the functions.
- **Contract tests**: the templates validate; the tool schemas; one scope per method; the pointer syntax round trip; the JSON Schema export.
- **Not tested here**: live GitHub or Forgejo, a real bank's CI runner (a manual checklist item at the switch-over).
