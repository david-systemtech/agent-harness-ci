# Spec: Environment service: wire, event log and pairing

Milestone 1 (Switch-over), phase A (the spine). Written 2026-09-23 from map ticket 78 of `david/agent-harness`. Decisions it implements: ADR 0001 (one environment per OS user, every client remote), ADR 0002 (the environment owns an event log that holds transcripts), ADR 0003 (clients hold no organisation state), ADR 0004 (one client runtime, the terminal UI in the server artefact, absent-with-reason capability flags), ADR 0006 (ceilings set at pairing, the access log), ADR 0007 (idle, drain, the activation gate), ADR 0015 (the log is the adapter's only event sink), ADR 0017 (phase, placeholder name). Peers read: T3 Code at 96c4bfa0 (`packages/contracts`, `apps/server/src/ws.ts`, `persistence/`, `serviceLauncher.ts`), Artemis at 443cf2e (`packages/core/src/server`, `packages/protocol/src/remote.ts`, `adapters/artemis/adapter.ts`). The product name is the placeholder `agent-harness` throughout; the rename is a find-and-replace before the first build session.

## Problem Statement

David runs coding agents on several machines and reaches them from a desktop window, a terminal and, later, a browser. In Artemis every one of those paths is a translation of the desktop's own IPC onto some wire, so a session archived from one client is not archived on another, a run dies when the window that started it closes, a headless machine needs a different server with a different client, and every served bug of September 2026 came from that translation. Nothing on the machine outlives the window, nothing is the single record of what happened, and adding a client means re-implementing the desktop.

## Solution

One **environment** per OS user on every machine: a server installed as a user-level service that owns the event log, the accounts, the workspaces and the runs, and that every client, the desktop window on the same machine included, reaches over one typed JSON-RPC contract on a WebSocket. The environment keeps a SQLite event log with a global sequence; every change a client makes is a command with a receipt, an event on the log and a projection, and every client learns of it through a subscription that replays from its cursor or sends a snapshot. A client proves once, by pairing, that it may connect, and holds a revocable client session with a scope set and a ceiling from then on. A local client of the same OS user authenticates through a grant file the service writes. The environment answers a well-known discovery URL and a health URL, tells its launcher when it is ready, and reports when it is idle or draining. Everything above the wire (session fields, runs, terminals, accounts) is another workstream's specification; this one is the spine those ride on.

## User Stories

9. As David, I want every change to a session, wherever it was made, to reach every client within a second, so that the desktop and the terminal never disagree.
10. As David, I want the environment to keep the transcript of every run itself, so that a second client can show a conversation without rebuilding it from the provider's files.
11. As David, I want an environment to have a stable identity that survives a change of address, so that my saved connections keep working when Tailscale renumbers a machine.
12. As David, I want a headless machine set up by one install script and paired from any client, so that a container or a server never needs a desktop.
13. As David, I want the environment to say when it is idle, so that the updater and I know when a restart costs nothing.
14. As David, I want the environment to drain, refusing new runs and finishing running ones, before it restarts, so that an update never cuts a run off mid-turn.

16. As David, I want an access log of every pairing, connection, scope grant and ceiling change, so that I can answer "what connected to this machine and when".

20. As Seth, I want the terminal UI on my machine to authenticate without pairing, so that opening a terminal never asks me for a code on my own computer.
21. As a client developer in another language, I want the wire to be a documented JSON frame with published schemas, so that I can write a client without the TypeScript packages.
22. As a client developer, I want every method to declare its scope and every error to be typed, so that I know what a client session may do before I call anything.

27. As a routine, I want to run with no client connected and have every event of my firing in the log, so that a client that connects later sees the whole firing.
28. As a provider adapter, I want one place to write my events and nothing else to write to, so that the log is the only source of truth.
29. As a build session, I want to start an environment in-process on a temporary directory and drive it with a real client, so that every behaviour above is a test I can run in seconds.

31. As David, I want the desktop's own connection to its local environment to be replaced each time the desktop starts, so that a stale desktop session never lingers as a second client.

## Implementation Decisions

### Packages and processes

- **Three deliverables**: the `contracts` package (schemas, method registry, scope table, error union, frame codec; no runtime dependency on the server), the `environment` package (the server: log, auth, subscriptions, lifecycle, adapter host), and the `agent-harness` CLI whose `serve` verb runs the environment and whose `service`, `pair` and `status` verbs manage it. The terminal UI is a second entry point of the same artefact (ADR 0004) and is specified in the TUI workstream.
- **One process per environment**, started by the launcher (ADR 0007) as its child in a service install, or directly by `serve` in the foreground. The launcher's update mechanics are the launcher workstream; this workstream provides the child's side of the handshake: a `prepared` signal on the launcher's channel, and the idle and drain queries.
- **Data directory** per environment, under the platform's user state directory by default (XDG state on Linux, Application Support on macOS, LocalAppData on Windows) with an override for a second environment on one machine (ADR 0001). It holds the environment record (persistent id, created-at, name, icon and colour once the picker workstream sets them), the SQLite database, the harness-owned account directories (Claude adapter workstream), the vault (a 0600 file on a headless machine, the OS keychain on a desktop), the bootstrap grant file, and logs. Nothing is written outside it except the service definition the install writes and, on a desktop, the vault entries kept in the OS keychain.
- **Service install**: a launchd agent, a `systemd --user` unit, or a Task Scheduler logon task, each written by `service install` and removed by `service uninstall`; `service status` reports installed, running, ready. The desktop app bundles the server artefact and calls the same verbs to install or repair (ADR 0001); the headless install script downloads the artefact and calls them. The service never runs as root: `serve` refuses to start as uid 0, in a container as anywhere else (ADR 0006; the permissions specification treats a declared container as the outer boundary, never as a reason to run as root).
- **Environment identity**: a UUID generated on first start and stored in the environment record; a signing key for client sessions generated at the same time and stored in the vault. Both survive address changes and re-installs that keep the data directory.

### Binding and discovery

- Bind loopback always. Bind the tailnet interface when the machine has a Tailscale address and the tailnet setting is on, which is the preset when one is found; the Your machines step warns when none is found. LAN binding is a setting that is off, behind the wizard's warning, and names the LAN address it binds (on with none given, the start fails saying so); the wildcard address is never used. No TLS in milestone 1: loopback is local and the tailnet is encrypted by the transport.
- Requests must carry a Host header naming loopback, an address the environment is bound to, or, while the tailnet address is bound, the environment's own tailnet name, against DNS rebinding.
- `GET /.well-known/agent-harness/environment`, unauthenticated: environment id, name, harness version, protocol version, capability flags, auth policy (`local-only` or `tailnet`), and readiness (`starting`, `ready`, `draining`). `GET /health` for the launcher and the checklist: status and version only. Both answer before commands are accepted, with readiness saying so.
- Two unauthenticated exchange endpoints, each rate-limited and answering only with a client session or a typed error: `POST /api/pair` takes a pairing code plus the client's kind, label and protocol version and returns a client session token with its scopes and ceiling; `POST /api/bootstrap` takes the bootstrap grant secret plus kind and label, is accepted over loopback only, and returns a `local` client session token. Both write their access-log events.
- Every other HTTP path is the WebSocket at `/ws`, the completions surface (adapter workstream), and the static client bundle route reserved for milestone 2. The pairing link's `/pair#<code>` is a path a client parses (the code never leaves the fragment); the environment serves no page there in milestone 1, so a plain `GET /pair` is a 404, and the web client of milestone 2 is where a page would live.

### The wire

- **One WebSocket per client connection**, JSON text frames, one message per frame. The frame kinds, in the contracts package:
  - `auth` (client, first message): the client session token obtained from `/api/pair` or `/api/bootstrap`, the client's protocol version, kind and harness version. No token ever travels in a URL. A protocol version the environment does not speak is answered with `bye: protocol` naming both versions; an invalid, foreign or unknown token with `bye: unauthorized`; an expired one with `bye: expired`.
  - `hello` (server, in reply to a valid `auth`): protocol version, capability flags, environment id and name, the client session's id, scopes and ceiling, server time.
  - `request` `{id, method, params}` and its `response` `{id, result}` or `{id, error}`.
  - a `request` on a method whose registry entry is a stream is a subscription. Its response is the `subscribed` variant `{id, subscription}`. The environment then sends subscription messages, each carrying the subscription id: `snapshot {subscription, sequence, payload}` (at most one, first, when replay is out of bounds), `event {subscription, sequence, event}`, `synchronized {subscription, sequence}` (once, when catch-up is complete), and `end {subscription, reason}` (`unsubscribed`, `overflow`, `revoked`, `closed`). `unsubscribe {subscription}` from the client ends one and is answered by `end` with reason `unsubscribed`.
  - `ping` and `pong` every 15 seconds from the server; a client arms a 45-second watchdog only after the first `ping` (Artemis's measured numbers).
  - `bye {reason}` before a server-side close: `unauthorized`, `expired`, `revoked`, `protocol`, `draining`, `updating`.
- **Method registry**: every method has a name (`area.verb`, for example `environment.status`, `access.pairings.list`), a params schema, a result schema, an error union, a stream flag, and exactly one required scope. The registry is a typed table in the contracts package; a method without a scope entry is a type error, and a test asserts every method has exactly one. Client libraries and the server are both generated from the registry. A JSON Schema export of every schema is published with each release for non-TypeScript clients.
- **Scopes**, from the topology decision: `read` (list and subscribe), `sessions:write` (organisation commands), `runs:drive` (start, send, interrupt, answer prompts), `terminal`, `admin` (pairings, client sessions, drain, rebuild, settings). Scope is checked in one place, before the handler, for requests and streams alike.
- **Errors**: one union every method may return: `unauthorized`, `forbidden` (scope), `unavailable` (not ready or draining), `invalid_params` (with the schema issues), `not_found`, `conflict`, `internal`; plus each method's own members. Errors carry a stable `code`, a message, and structured `data`.
- **Protocol version** is one integer, 1 at launch, bumped only on a breaking frame or schema change; `hello` and the discovery URL both carry it; a client whose version differs is closed with reason `protocol`. **Capability flags** are a set of strings in `hello`; absent means unsupported and the client degrades absent-with-reason (ADR 0004). Adding a method or an optional field never bumps the version.
- **Commands**: every mutating method takes a client-generated `commandId`, a UUID. Receipts are keyed by the actor (the client session, routine or system component) together with the command id, so one client can never read or block another's receipt. The environment writes the receipt (actor, command id, aggregate, status, resulting sequence or error) in the same transaction as the events it produces; the same actor repeating a command id gets the receipt back without re-applying; a malformed id is `invalid_params`. Receipts are kept for 30 days. A command whose target no longer exists is rejected with a receipt of status `rejected` and reason `not_found`.
- **Events and streams**: an event has a global sequence, an event id, a stream kind and id, a stream version, a type, an occurred-at time, the command id and causation and correlation ids when any, an actor (the client session, routine, adapter or system that caused it), a payload and metadata. Which event types exist for sessions and groups is the session-state workstream; transcript event types are the adapter workstream; this workstream owns the envelope and the `environment` and `access` streams.
- **Subscriptions**: two named ones in milestone 1, the session list and one per session (ADR 0003), plus `environment.subscribe` for environment-level notices (updated-to, draining, account status). A subscription takes an `afterSequence` cursor. When the events after the cursor are within the replay bound (1,000 events or 8 MiB for that stream, measured in SQL before decoding), the environment sends them, then a `synchronized` marker, then live events. Otherwise it sends one `snapshot` message, then `synchronized`, then live. The live feed is attached before catch-up begins and the client deduplicates by sequence, so nothing between the read and the attach is lost. A subscription whose client falls too far behind ends with reason `overflow`; the client resubscribes from its cursor.

### The event log

- One SQLite database per environment in WAL mode with foreign keys on, opened by the environment alone. Tables: `events` (sequence autoincrement primary key, unique event id, stream kind, stream id, stream version, type, occurred-at, command id, causation and correlation ids, actor, payload JSON, metadata JSON; unique on stream kind, stream id and stream version; indexed by stream and sequence), `command_receipts`, `projection_state` (one cursor per projector), the projection tables each feature workstream declares, `snapshots` (stream id, sequence, payload), and the auth tables below.
- **Append** is one insert that computes the stream version inline; the global sequence is the autoincrement. Append, the projection writes and the receipt happen in one transaction; the in-memory publish to subscribers happens after commit. What a commit sets off and appends in a transaction of its own is published after the events of the commit that set it off, so subscribers hear sequences in order.
- **Projectors** are named, each with its own cursor in `projection_state`; startup resumes every projector from its cursor so the log is never replayed whole. An `admin` command `environment.rebuildProjections` drops the projection tables and replays. A projector whose declared tables are missing, or whose statements in the database differ from the ones it declares (a version that added a column), is rebuilt from the log when it registers, so an upgrade never runs on an older table shape.
- **Compaction**: transcript events of a session with no run, command or event in 90 days are folded into a snapshot that replaces them for replay; organisation events are never compacted; the snapshot lives until the session is deleted. The number is a chosen default for the specification and is a setting.
- **Deletion**: a `session.deleted` event hides the session at once; a maintenance job purges its events, snapshots and projections after the grace period the session-state workstream sets; a command aimed at it meanwhile is rejected with a receipt.
- **The log is the only sink**: adapters (ADR 0015) receive an append function scoped to their run's stream and nothing else; there is no second feed and no in-memory ring that a client reads.

### Pairing, client sessions and the access log

- **Auth policy** is derived from the bind: `local-only` when only loopback is bound, `tailnet` otherwise. Under both, a request without a valid client session is refused; the `unsafe-no-auth` policy T3 offers does not exist here.
- **Bootstrap grant**: on start the environment writes a 0600 grant file in its data directory holding a fresh one-time secret. Any process of the same OS user may read it and exchange it at `/api/bootstrap`, over loopback, declaring its kind (`desktop` or `tui`) and a label, for a `local` client session with every scope and the environment's top ceiling. The desktop and the terminal UI on the same machine authenticate this way. Replacement is keyed by kind: a new desktop exchange revokes the previous `desktop` local session, so one desktop holds one session; terminal UI exchanges are not replaced, since several terminals run at once, and a `tui` local session is revoked when its connection has been closed for an hour. The grant secret rotates after each exchange. This is how the OS user boundary becomes the trust boundary (ADR 0001).
- **Pairing**: `pair` on the CLI or `access.pairings.create` (scope `admin`) mints a one-time pairing code that expires in ten minutes, rendered as a link with the code in its fragment, a QR of that link, or the short code alone for typing. The client exchanges it, over HTTP, for a client session: a signed token with a 30-day lifetime that the client refreshes while in use, the scope set and ceiling chosen at creation (preset: every scope, and the environment's default ceiling; the ceiling values are the permissions workstream's), a client kind (`desktop`, `tui`, `web`, `program`: a script or bot driving the wire) and a label. A pairing code is single use and its creation, exchange and expiry are events. The refresh is `access.sessions.refresh` (scope `read`, on the caller's own client session): a fresh token and 30 more days; expiry belongs to the client session, so an earlier token stays valid to the same time.
- **Client sessions** are listed and revoked through `access.sessions.list` and `access.sessions.revoke` (scope `admin`). The list returns every client session, oldest first, each with its id, kind, label, created, last seen, expiry, revoked-at, scopes, ceiling and local flag; `live: true` leaves out the revoked and expired ones. Revocation closes any open connection with `bye: revoked` and refuses the token from then on. Tokens are signed with the environment's key and are opaque to clients; verification needs no database read, revocation is checked against a small in-memory set loaded from the auth tables.
- **The access log** (ADR 0006) is the `access` stream in the event log, one stream whose id is the environment's id: pairing created, exchanged and expired (`pairing.created`, `pairing.exchanged`, `pairing.expired`; the code itself is never logged); client session created, refreshed, revoked (`client-session.created` with how it was made, `bootstrap` or `pairing`; `client-session.refreshed`; `client-session.revoked` with the reason, `requested`, `replaced` or `idle`); connection opened and closed with the client session (`socket.opened`, `socket.closed`); scope grant and ceiling change (`scope.granted`, `ceiling.changed`). Payload schemas are in the contracts package. `access.log.list` reads it (scope `admin`) after a cursor, oldest first, 100 events unless asked for up to 1,000.

### Lifecycle

- **Startup order**: open the database and apply migrations; bootstrap projectors from their cursors; load the environment record and the auth tables; start the adapter host; bind the listeners; signal `prepared` to the launcher; only then accept `auth` frames and requests. Before that point the discovery URL reports `starting` and a request is answered `unavailable`. The gate exists so a trial version that cannot serve is rolled back by the launcher within its deadline (ADR 0007).
- **Idle** is computed as the glossary defines it: no run starting or running and no run started or ended in the last ten minutes, with a run parked on a prompt counting as busy for ten minutes only. `environment.status` reports `idle`, `busy` and `draining` with the reason and, for a parked prompt, when it stops counting as busy.
- **Drain**: `environment.drain` (scope `admin`) and the launcher's channel both start a drain: new runs are refused with `unavailable`, running ones are allowed to finish up to the cap ADR 0007 sets, connected clients receive `bye: draining` at the end, and the process exits. `SIGTERM` starts the same drain.
- **Parked prompts survive a restart** because they are events: on startup the projection of open prompts is what clients receive, exactly where each was (ADR 0007).
- **Containers**: when the environment detects it is running in a container without a launcher, `environment.status` reports that updates are managed outside, and the host-side updater uses the discovery URL and the status method (launcher workstream).

### What this workstream does not decide

- The session and group event vocabulary and projections (session-state workstream); the client runtime's caches and outbox (client runtime workstream); run and transcript events and provider processes (adapter workstream); the mode and ceiling values (permissions workstream); terminals, files and diffs, which will take the reserved `terminal` scope (renderer workstream); the launcher, versions, channels and rollback (launcher workstream).

## Testing Decisions

- **What a good test is**: a behaviour visible through the wire or the discovery URL, asserted from a client's point of view, never an assertion on a table or a private structure. The exception is the store seam below, where the behaviour is the bound itself.
- **Primary seam: an in-process environment and a real client.** A test helper starts an environment on a temporary data directory, bound to loopback on port 0, with the adapter contract satisfied by a scripted fake provider, and returns a thin typed client built from the contracts package over a real WebSocket. Every story above is a test through this seam: bootstrap grant exchange and rotation; pairing creation, exchange, single use and expiry; scope refusal on a method and on a stream; protocol version mismatch closing with reason; `hello` contents; command receipts on retry and on a deleted target; session-list and per-session subscriptions with replay, snapshot, `synchronized`, live-before-catch-up and deduplication; overflow ending a subscription; ping and `bye` reasons; the access log; readiness before and after the gate; idle and drain states; a parked prompt present again after a stop and start on the same directory; a projection rebuild giving the same read models. Prior art: T3 Code's `buildAppUnderTest` with partial service overrides and `withWsRpcClient` over a Node WebSocket in its server test suite, and Artemis's port-0 server helper in its run-stream claim tests.
- **Lower seam: the event store against in-memory SQLite.** Replay bounds by event count and by bytes, compaction of an old session into a snapshot, projector cursors after a restart and after a rebuild, receipt retention, and the unique stream-version constraint under concurrent appends. Prior art: T3 Code's event store tests against its in-memory persistence layer and its projection pipeline tests.
- **Contract tests in the contracts package**: every method has exactly one scope (T3 Code's authorization test is the model); every session-summary field has a command (ADR 0003, owned by the session-state workstream but run here); the JSON Schema export round-trips every schema; a frame decoder rejects every malformed frame kind with `invalid_params`.
- **Framework**: Vitest, as both peers use; the environment's suite runs files serially because each starts a listener; a fake provider adapter lives beside the tests and is the model for the adapter workstream's own fake.
- **Not tested here**: the launcher's rollback (launcher workstream), the desktop's service install on each platform (manual checklist in the wizard workstream), Tailscale itself.

## Out of Scope

- The launcher, versions directory, channels, trial and rollback, and the container host-side updater (launcher workstream, ADR 0007).
- The session and group commands, events, projections, auto-settle and the offline outbox semantics (session-state and client-runtime workstreams, ADR 0003).
- Runs, transcripts, provider processes, the Claude adapter and the completions surface (adapter workstream, ADR 0015).
- Mode and ceiling values, containment, the denylist and parked-prompt TTLs (permissions workstream, ADR 0006).
- Terminals, files and diffs; the GUI and TUI (renderer workstreams, ADR 0004).
- The web client bundle route beyond reserving it, a relay, environment peer lists, SSH-launched environments, LAN exposure beyond the off-by-default setting, and TLS (fog and milestone 2).

## Further Notes

- Chosen defaults that were not decided on a ticket and may be revisited in review: replay bound 1,000 events or 8 MiB per stream (T3 Code's measured values); pairing code expiry ten minutes; client session lifetime 30 days with refresh; receipt retention 30 days; transcript compaction after 90 days untouched; the 15-second ping and 45-second watchdog (Artemis's measured values).
- Chosen defaults not decided on a ticket, from the pairing build (#109): a pairing code is ten characters of `23456789ABCDEFGHJKMNPQRSTVWXYZ` (no 0, 1, I, L, O or U; about 49 bits), shown in two groups of five and read in any case with spaces and hyphens ignored; the link is `http://<tailnet name or address>:<port>/pair#<code>`; the default ceiling a pairing gives is the top one until the permissions workstream sets it; the environment finds its Tailscale address and name through the `tailscale` CLI on its PATH; `POST /api/pair` shares the bootstrap exchange's rate, 10 a minute per address, in a bucket of its own.
- Chosen default not decided on a ticket: the environment listens on port 7433 unless told otherwise (`serve --port`, `DEFAULT_PORT` in the environment package); saved connections need a stable port, and a second environment on one machine passes its own.
- Chosen default not decided on a ticket: `serve` refuses a real uid of 0 as well as an effective uid of 0, since a process whose real uid is root can take root back.
- Chosen defaults not decided on a ticket, from subscriptions (#110): the `environment` stream's id is the environment id, and every start the launcher accepts appends `environment.started` to it, after the handshake and before the wire opens; `subscribed` is sent once catch-up has been read, together with it, so a snapshot that fails is answered as an error before any subscription exists; `snapshot` and `synchronized` carry the log's head; a cursor past the head is answered with a snapshot; an `unsubscribe` naming no subscription of that socket is ignored; a subscription has fallen too far behind when the live frames it has sent and the socket has not yet flushed would pass the replay bound; a close the environment starts ends every subscription (`revoked` for a revocation, `closed` otherwise) before its `bye`. The log keeps an event's actor as one `kind:id` string.
- Chosen defaults not decided on a ticket, from the lifecycle (#112): `environment.status` (and `environment.subscribe`'s snapshot) answers the status document `{readiness, activity, updatesManagedOutside}`, where `activity` is `{state: idle}`, `{state: busy, reason, busyUntil?}` or `{state: draining, drainingSince}`. The busy reasons are `run-starting`, `run-running`, `parked-prompt` and `recent-activity`; `busyUntil` is when the environment stops counting as busy if nothing else happens (ten minutes after the parked prompt, or after the latest start or end of any run, a parked one included), and the reason given is the one that holds longest, a parked prompt on a tie; a window ends at its instant. Runs are read through a run registry the adapter host fills (`runs`, `onChange`, `refuseNewRuns`, `admit`); it keeps an ended run for ten minutes, and the host calls `admit` before starting a run, which throws `unavailable {readiness: draining}` once the drain has refused new runs. A drain has three triggers, `command` (`environment.drain`), `launcher` and `signal` (SIGTERM, and SIGINT in the foreground; a second signal stops the process at once); how a drain began, `DrainStarted {drainingSince, trigger}`, is the answer to `environment.drain`, the payload of the `environment.draining` notice (appended once) and the launcher's `draining` reply, and a second trigger joins the drain under way and gets the same answer. The cap is `DRAIN_CAP_MS`, 30 minutes on the environment's clock. The drain waits for runs starting or running, not for runs parked on a prompt, which survive the restart as events (ADR 0007), then takes one turn on the clock so the answer to what started it leaves before its `bye`. While draining only new runs are refused; every other method keeps answering, so a person can still answer a prompt, interrupt a run or join the drain. The launcher's messages on its IPC channel come in pairs: `{type: "idle?"}` is answered `{type: "idle", ...status}` with the status document, and `{type: "drain?"}` is answered `{type: "draining", ...DrainStarted}`; other messages are ignored (the launcher module's doc comment is their one definition in code). `environment.rebuildProjections` answers the projectors it rebuilt and the log's head. A container is detected by `/.dockerenv` or `/run/.containerenv`, with a container runtime in PID 1's cgroup as a fallback; a launcher is present when the launcher channel says so (the IPC channel a launcher spawned the environment with); updates are managed outside when there is a container and no launcher.
- Chosen defaults not decided on a ticket, from command receipts (#111): a command's `response` carries `{receipt, result}` (the contracts' `CommandReceipt` and `commandResponse`, published as `methods/<name>/response.json`), where the receipt is `{status: accepted, sequence, changed}` or `{status: rejected, sequence, changed: false, reason, error}` (the reason is the error's code), `sequence` being the log's head once the command committed, and `result` is present only when that request applied the command: a retry answered from the stored receipt and a rejection carry the receipt alone, since results are not stored (a pairing code never is). A rejection is a normal response carrying its receipt, never an error response, because the receipt is what a client's outbox retires a command on; an error response (`invalid_params`, `forbidden`, `unavailable`, `unauthorized`, `internal`, or any `ContractError` a handler throws) stores no receipt, so its retry runs again. The wire runs every command through the log's `command`: the actor is the client session (`client_session:<id>`) and the command id is kept in lowercase, so a UUID written in either case is one key; a key with a receipt is answered without calling the handler, otherwise the handler runs inside the command's transaction (it is given the command id, the actor and the transaction, and answers at once, never later) and names its aggregate with its result and events, or with its rejection, `{code, message?, data?}`, the code one of the method's own error codes, the message a plain one when none is given; `changed` is whether the command appended any event, so a projection rebuild, or a drain joined while one is under way, is accepted unchanged. Retention is exact: a receipt more than 30 days old is never answered, whether or not the minute sweep, which prunes the table, has run. `access.sessions.revoke` on an unknown client session is a rejection with reason `not_found`.
- The wire's `readiness` field (`starting`, `ready`, `draining`) reuses a word the glossary gives to skills (**Readiness**: ready, setup needed, unsupported); the contracts type is named `EnvironmentReadiness` to keep them apart, and the overlap is flagged for domain-modeling.
- "Client session" (the revocable credential a pairing or the bootstrap grant produces, with its scopes and ceiling) and "bootstrap grant" (the 0600 file and one-time secret a local client exchanges for a `local` client session) are terms this specification and the code use that the glossary lacks; neither is the glossary's **Session** or **Connection**, and the code calls the wire's live WebSocket a socket to keep them apart. Flagged for domain-modeling.
- The bootstrap grant is the answer to "how does a local client avoid pairing": the OS user's file permissions are the credential. A second OS user on the same machine is a different environment by design.
- T3 Code's DPoP sessions and WebSocket tickets were read and not carried: the harness never puts a token in a URL, so a ticket is unnecessary, and DPoP's sender-binding is more than a tailnet-only surface needs in milestone 1. If a public relay arrives, revisit both.
- The completions surface and the WebSocket share the port; the completions surface authenticates with the same client-session tokens under the same ceiling (ADR 0015), which the adapter workstream specifies.
