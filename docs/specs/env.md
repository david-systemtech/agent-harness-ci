# Spec: Environment service: wire, event log and pairing

Milestone 1 (Switch-over), phase A (the spine). Written 2026-09-23 from map ticket 78 of `david/agent-harness`. Decisions it implements: ADR 0001 (one environment per OS user, every client remote), ADR 0002 (the environment owns an event log that holds transcripts), ADR 0003 (clients hold no organisation state), ADR 0004 (one client runtime, the terminal UI in the server artefact, absent-with-reason capability flags), ADR 0006 (ceilings set at pairing, the access log), ADR 0007 (idle, drain, the activation gate), ADR 0015 (the log is the adapter's only event sink), ADR 0017 (phase, placeholder name). Peers read: T3 Code at 96c4bfa0 (`packages/contracts`, `apps/server/src/ws.ts`, `persistence/`, `serviceLauncher.ts`). The product name is the placeholder `agent-harness` throughout; the rename is a find-and-replace before the first build session.

## Problem Statement

The owner runs coding agents on several machines and reaches them from a desktop window, a terminal and a browser in milestone 1. Today, every one of those paths is a translation of the desktop's own IPC onto some wire, so a session archived from one client is not archived on another, a run dies when the window that started it closes, a headless machine needs a different server with a different client, and every served bug of September 2026 came from that translation. Nothing on the machine outlives the window, nothing is the single record of what happened, and adding a client means re-implementing the desktop.

## Solution

One **environment** per OS user on every machine: a server installed as a user-level service that owns the event log, the accounts, the workspaces and the runs, and that every client, the desktop window on the same machine included, reaches over one typed JSON-RPC contract on a WebSocket. The environment keeps a SQLite event log with a global sequence; every change a client makes is a command with a receipt, an event on the log and a projection, and every client learns of it through a subscription that replays from its cursor or sends a snapshot. A client proves once, by pairing, that it may connect, and holds a revocable client session with a scope set and a ceiling from then on. A local client of the same OS user authenticates through a grant file the service writes. The environment answers a well-known discovery URL and a health URL, tells its launcher when it is ready, and reports when it is idle or draining. Everything above the wire (session fields, runs, terminals, accounts) is another workstream's specification; this one is the spine those ride on.

## Implementation Decisions

### Packages and processes

- **Three deliverables**: the `contracts` package (schemas, method registry, scope table, error union, frame codec; no runtime dependency on the server), the `environment` package (the server: log, auth, subscriptions, lifecycle, adapter host), and the `agent-harness` CLI whose `serve` verb runs the environment and whose `service`, `pair` and `status` verbs manage it. The terminal UI is a second entry point of the same artefact (ADR 0004) and is specified in the TUI workstream.
- **One process per environment**, started by the launcher (ADR 0007) as its child in a service install, or directly by `serve` in the foreground. The launcher's update mechanics are the launcher workstream; this workstream provides the child's side of the handshake: a `prepared` signal on the launcher's channel, and the idle and drain queries.
- **Data directory** per environment, under the platform's user state directory by default (XDG state on Linux, Application Support on macOS, LocalAppData on Windows; in a container the install declared with `AGENT_HARNESS_CONTAINER`, the image's `/data`, where its `serve` runs, #1725) with an override for a second environment on one machine (ADR 0001). It holds the environment record (persistent id, created-at, name, icon and colour once the picker workstream sets them), the SQLite database, the harness-owned account directories (`accounts/<account id>/`, 0700, one per account `accounts.add` made; deleted only by `accounts.remove` with `deleteDirectory` or a sign-in refused as a duplicate identity, and what such a deletion or an add that did not commit left is removed at the next start; an adopted account's directory is the machine's own and never under it; Claude adapter workstream, #134), the per-repository auto-memory directories (`auto-memory/`, shared by every account; #121), the attachment stage (`attachments/`, 0700: the bytes of queued messages' attachments until a run reads them, one 0600 file each; Claude adapter workstream, #185), the vault (a 0600 file on a headless machine, the OS keychain on a desktop), the bootstrap grant file, and logs. Nothing is written outside it except the service definition the install writes and, on a desktop, the vault entries kept in the OS keychain.
- **Service install**: a launchd agent, a `systemd --user` unit, or a Task Scheduler logon task, each written by `service install` and removed by `service uninstall`; `service status` reports installed, running, ready. The desktop app bundles the server artefact and calls the same verbs to install or repair (ADR 0001); the headless install script downloads the artefact and calls them. The service never runs as root: `serve` refuses to start as uid 0, in a container as anywhere else (ADR 0006; the permissions specification treats a declared container as the outer boundary, never as a reason to run as root).
- **Environment identity**: a UUID generated on first start and stored in the environment record; a signing key for client sessions generated at the same time and stored in the vault. Both survive address changes and re-installs that keep the data directory.

### Binding and discovery

- Bind loopback always. Bind the tailnet interface when the machine has a Tailscale address and the tailnet setting is on, its preset whether or not one is found (with none found, nothing binds beside loopback); the Your machines step warns when none is found. LAN binding is a setting that is off, behind the wizard's warning, and names the LAN address it binds (on with none given, the start fails saying so; an address the machine no longer holds is skipped, the start binding loopback and the tailnet and saying so, #773); the wildcard address is never used. Phone use in milestone 1 requires the configured external HTTPS origin and a separately managed TLS endpoint; tailnet encryption alone does not make a browser secure context. Native environment TLS termination is not required (web-client spec).
- Chosen defaults not decided on a ticket, from the binding keys (#574): the tailnet and LAN settings are `network.bindTailnet` (preset on) and `network.bindLan` (null for off, the preset, or the address), which the Your machines step writes and each start reads, its start options overriding them; the LAN address must be one the machine's network interfaces hold. A start that finds it does not (a laptop on another network, a DHCP lease that changed) binds loopback and the tailnet without it and says so in one line on standard error, and the Your machines step needs attention naming it (David, on #773: a failed start left no running environment to turn the key off with); and `environment.status` says what the environment binds beside loopback, which LAN addresses it could bind, and a Tailscale address the machine holds that it does not bind, looked for again at each status while no tailnet address is bound (#861) (setup spec, "3. Your machines").
- Requests must carry a Host header naming loopback, an address the environment is bound to, the environment's configured tailnet name or the hostname of the configured external HTTPS origin, against DNS rebinding. The external hostname is accepted for a loopback-only HTTPS proxy deployment; it is not inferred from forwarded headers. Origin remains an independent exact-origin check.
- `GET /.well-known/agent-harness/environment`, unauthenticated: environment id, name, harness version, protocol version, capability flags, auth policy (`local-only` or `tailnet`), and readiness (`starting`, `ready`, `draining`). `GET /health` for the launcher and the checklist: status and version only. Both answer before commands are accepted, with readiness saying so.
- Two unauthenticated exchange endpoints, each rate-limited and answering only with a client session or a typed error: `POST /api/pair` takes a pairing code plus the client's kind, label and protocol version and returns a client session token with its scopes and ceiling; `POST /api/bootstrap` takes the bootstrap grant secret plus kind and label, is accepted over loopback only, and returns a `local` client session token. Both write their access-log events.
- HTTP also serves the WebSocket at `/ws`, the completions surface (adapter workstream) and the packaged, version-matched shared client at `/` and `/pair` in milestone 1. Pairing codes stay in `/pair#<code>` fragments, scrubbed before browser rendering/network activity. Only declared app routes/public assets are served; API misses stay 404, with traversal/symlink protection, Host validation and restrictive CSP. Pairing and WS upgrades accept the configured web Origin, the desktop scheme and origin-less CLI/TUI; additional exact origins require trusted-admin allowlisting. Canonical same-host HTTP on the actual listener remains supported for existing local use; phones use HTTPS. See [web-client.md](web-client.md) for the full origin boundary and browser tests.

### External web origin

`serve --web-origin` / start option `webOrigin` configures one canonical HTTPS
origin, including any non-default port, without path, query, fragment or
credentials. Phone links and QR codes use it rather than forwarded headers;
existing desktop/TUI HTTP is retained. The coordinator configures managed
tailnet HTTPS forwarding to loopback; builders prove serving/Host/Origin policy
and packaged assets in hosted CI. Explicit extra-origin policy is the #1549
leaf; it denies all before that implementation. See [web-client.md](web-client.md).

### The wire

- **One WebSocket per client connection**, JSON text frames, one message per frame. The frame kinds, in the contracts package:
  - `auth` (client, first message): the client session token obtained from `/api/pair` or `/api/bootstrap`, the client's protocol version, kind and harness version. No token ever travels in a URL. A protocol version the environment does not speak is answered with `bye: protocol` naming both versions; an invalid, foreign or unknown token with `bye: unauthorized`; an expired one with `bye: expired`.
  - `hello` (server, in reply to a valid `auth`): protocol version, capability flags, environment id and name, the client session's id, scopes and ceiling, server time.
  - `request` `{id, method, params}` and its `response` `{id, result}` or `{id, error}`.
  - a `request` on a method whose registry entry is a stream is a subscription. Its response is the `subscribed` variant `{id, subscription}`. The environment then sends subscription messages, each carrying the subscription id: `snapshot {subscription, sequence, payload}` (at most one, first, when replay is out of bounds), `event {subscription, sequence, event}`, `synchronized {subscription, sequence}` (once, when catch-up is complete), and `end {subscription, reason}` (`unsubscribed`, `overflow`, `revoked`, `closed`, and `deleted` when what the subscription follows is deleted: a session's own subscription, per the session-state specification). `unsubscribe {subscription}` from the client ends one and is answered by `end` with reason `unsubscribed`.
  - `ping` and `pong` every 15 seconds from the server; a client arms a 45-second watchdog only after the first `ping` (measured numbers).
  - `bye {reason}` before a server-side close: `unauthorized`, `expired`, `revoked`, `protocol`, `draining`, `updating`.
- **Method registry**: every method has a name (`area.verb`, for example `environment.status`, `access.pairings.list`), a params schema, a result schema, an error union, a stream flag, and exactly one required scope. The registry is a typed table in the contracts package; a method without a scope entry is a type error, and a test asserts every method has exactly one. Client libraries and the server are both generated from the registry. A JSON Schema export of every schema is published with each release for non-TypeScript clients.
- **Scopes**, from the topology decision: `read` (list and subscribe), `sessions:write` (organisation commands), `runs:drive` (start, send, interrupt, answer prompts), `terminal`, `admin` (pairings, client sessions, drain, rebuild, settings). Scope is checked in one place, before the handler, for requests and streams alike.
- **Errors**: one union every method may return: `unauthorized`, `forbidden` (scope), `unavailable` (not ready or draining), `invalid_params` (with the schema issues), `not_found`, `conflict`, `internal`; plus each method's own members. Errors carry a stable `code`, a message, and structured `data`.
- **Protocol version** is one integer, 1 at launch and 2 since #1326 added the strict pending setup state, bumped only on a breaking frame or schema change; `hello` and the discovery URL both carry it; a client whose version differs is closed with reason `protocol`. **Capability flags** are a set of strings in `hello`; absent means unsupported and the client degrades absent-with-reason (ADR 0004). Adding a method or an optional field never bumps the version.
- **Commands**: every mutating method takes a client-generated `commandId`, a UUID. Receipts are keyed by the actor (the client session, routine or system component) together with the command id, so one client can never read or block another's receipt. The environment writes the receipt (actor, command id, aggregate, status, resulting sequence or error) in the same transaction as the events it produces; the same actor repeating a command id gets the receipt back without re-applying; a malformed id is `invalid_params`. Receipts are kept for 30 days. A command whose target no longer exists is rejected with a receipt of status `rejected` and reason `not_found`. What the environment records of its own reading of the world is not a command: the account store's reads (at startup, on each account's fifteen-minute timer, on `accounts.refresh`, and the fresh read a run's identity cross-check sets off) append `account.status-changed` and `account.identity-set`, and the duplicate-identity removal a first signed-in read can find, as `system:account-store` with no command id and no receipt, since they record what the provider reported rather than a change a client asked for (claude-adapter spec, #134). So `accounts.refresh` is a query at `read`, not a command: it asks for a read the timer would make anyway, a repeat reads again and appends only what changed since, which is what a retry wants, and its `account.updated` notices follow the commit as a command's do.
- **Events and streams**: an event has a global sequence, an event id, a stream kind and id, a stream version, a type, an occurred-at time, the command id and causation and correlation ids when any, an actor (the client session, routine, adapter or system that caused it), a payload and metadata. Which event types exist for sessions and groups is the session-state workstream; transcript event types are the adapter workstream, and so is the `account` stream (one per account, the account store's seven event types, #134); this workstream owns the envelope and the `environment` and `access` streams, whose notices the other workstreams may add to (`account.updated`, #134; `signin.updated` and `signin.executable-chosen`, #135; `prompt.parked` and `prompt.resolved`, #130; `usage.updated`, #136).
- **Subscriptions**: two named ones in milestone 1, the session list and one per session (ADR 0003), plus `environment.subscribe` for environment-level notices (updated-to, draining, account status, the sign-in, parked prompts, plan usage). A subscription takes an `afterSequence` cursor. When the events after the cursor are within the replay bound (1,000 events or 8 MiB for that stream, measured in SQL before decoding), the environment sends them, then a `synchronized` marker, then live events. Otherwise it sends one `snapshot` message, then `synchronized`, then live. The live feed is attached before catch-up begins and the client deduplicates by sequence, so nothing between the read and the attach is lost. A subscription whose client falls too far behind ends with reason `overflow`; the client resubscribes from its cursor.

### The event log

- One SQLite database per environment in WAL mode with foreign keys on, opened by the environment alone. Tables: `events` (sequence autoincrement primary key, unique event id, stream kind, stream id, stream version, type, occurred-at, command id, causation and correlation ids, actor, payload JSON, metadata JSON; unique on stream kind, stream id and stream version; indexed by stream and sequence), `command_receipts`, `projection_state` (one cursor per projector), the projection tables each feature workstream declares, `snapshots` (one per stream, a compaction's and written by nothing else: stream kind and id, sequence, payload, the stream version it folded to and how many events it removed), and the auth tables below.
- **Append** is one insert that computes the stream version inline; the global sequence is the autoincrement. Append, the projection writes and the receipt happen in one transaction; the in-memory publish to subscribers happens after commit. What a commit sets off and appends in a transaction of its own is published after the events of the commit that set it off, so subscribers hear sequences in order.
- **Projectors** are named, each with its own cursor in `projection_state`; startup resumes every projector from its cursor so the log is never replayed whole. An `admin` command `environment.rebuildProjections` drops the projection tables and replays. A projector whose declared tables are missing, or whose statements in the database differ from the ones it declares (a version that added a column), is rebuilt from the log when it registers, so an upgrade never runs on an older table shape.
- **Compaction**: transcript events of a session with no run, command or event in 90 days are folded into a snapshot that replaces them for replay; organisation events are never compacted; the snapshot lives until the session is deleted. The number is a chosen default for the specification and is a setting, `sessions.transcriptCompactAfterDays`. A stream's snapshot stands in for its events at or below its sequence: a subscription whose cursor is below it is sent the snapshot, then the events after it, and the replay bound is counted from the snapshot; a cursor at or above it replays as ever. What #123 chose is in the Further Notes.
- **Fork history** (#242, ADR 0022): the source's visible transcript is copied into `session.forked.history` in the same command transaction as the fork's creation and provider-store copy. This is an event seed, not a write to the compaction-owned `snapshots` table. The session fold retains it as a `forked` snapshot item, including after compaction. The fork owns its seed; source deletion and purge cannot remove it.
- **Deletion**: a `session.deleted` event hides the session at once; a maintenance job purges its events, snapshots and projections after the grace period the session-state workstream sets; a command aimed at it meanwhile is rejected with a receipt.
- **The log is the only sink**: adapters (ADR 0015) receive an append function scoped to their run, which appends to the run's session's stream with the run's id on every event of the run (a session's fork and rewind events belong to no run and carry none) (the claude-adapter spec's Further Notes), and nothing else; there is no second feed and no in-memory ring that a client reads. The one exception is a terminal's output, which the renderer workstream keeps out of the log on purpose (tui spec, "Terminals, files and diffs"): each terminal's bounded scrollback is its own feed, and `terminals.subscribe` reads it with the same frames and rules, over the terminal's own sequence (#124, Further Notes).

### Pairing, client sessions and the access log

- **Auth policy** is derived from the bind: `local-only` when only loopback is bound, `tailnet` otherwise. Under both, a request without a valid client session is refused; the `unsafe-no-auth` policy T3 offers does not exist here.
- **Bootstrap grant**: on start the environment writes a 0600 grant file in its data directory holding a fresh one-time secret. Any process of the same OS user may read it and exchange it at `/api/bootstrap`, over loopback, declaring its kind (`desktop` or `tui`) and a label, for a `local` client session with every scope and the environment's top ceiling. The desktop and the terminal UI on the same machine authenticate this way. Replacement is keyed by kind: a new desktop exchange revokes the previous `desktop` local session, so one desktop holds one session; terminal UI exchanges are not replaced, since several terminals run at once, and a `tui` local session is revoked when its connection has been closed for an hour. The grant secret rotates after each exchange. This is how the OS user boundary becomes the trust boundary (ADR 0001).
- **Pairing**: `pair` on the CLI (`--preset own-client`, `program`, `phone` or `custom` for a pairing preset's grant, the Set up spec's) or `access.pairings.create` (scope `admin`) mints a one-time pairing code that expires in ten minutes, rendered as a link with the code in its fragment, a QR of that link, or the short code alone for typing. The client exchanges it, over HTTP, for a client session: a signed token with a 30-day lifetime that the client refreshes while in use, the scope set and ceiling chosen at creation (each when left out at creation: the creating client session's own scopes, and the environment's default ceiling; the ceiling values are the permissions workstream's, and a ceiling above the creating client session's own is refused, #180). A requested scope the creating client session does not hold is refused with `forbidden`, `data.reason` `scope`, and `data.scope` naming that requested scope (#247, decided by the owner on 2026-09-28); the bootstrap grant's local sessions hold every scope and may still mint any scope set. The exchanged client session also carries a client kind (`desktop`, `tui`, `web`, `program`: a script or bot driving the wire) and a label. A pairing code is single use and its creation, exchange and expiry are events. The refresh is `access.sessions.refresh` (scope `read`, on the caller's own client session): a fresh token and 30 more days; expiry belongs to the client session, so an earlier token stays valid to the same time.
- **Client sessions** are listed and revoked through `access.sessions.list` and `access.sessions.revoke` (scope `admin`). The list returns every client session, oldest first, each with its id, kind, label, created, last seen, expiry, revoked-at, scopes, ceiling and local flag; `live: true` leaves out the revoked and expired ones. Revocation closes any open connection with `bye: revoked` and refuses the token from then on. Tokens are signed with the environment's key and are opaque to clients; verification needs no database read, revocation is checked against a small in-memory set loaded from the auth tables.
- **The access log** (ADR 0006) is the `access` stream in the event log, one stream whose id is the environment's id: pairing created, exchanged and expired (`pairing.created`, `pairing.exchanged`, `pairing.expired`; the code itself is never logged); client session created, refreshed, revoked (`client-session.created` with how it was made, `bootstrap` or `pairing`; `client-session.refreshed`; `client-session.revoked` with the reason, `requested`, `replaced` or `idle`); connection opened and closed with the client session (`socket.opened`, `socket.closed`); scope grant and ceiling change (`scope.granted`, `ceiling.changed`). Payload schemas are in the contracts package. `access.log.list` reads it (scope `admin`) after a cursor, oldest first, 100 events unless asked for up to 1,000.

### Terminals

`terminals.open` starts an interactive login shell in a pseudo-terminal. `terminals.run`
(#265) starts one command with pipe output, closed stdin and no controlling terminal,
using `/bin/sh -c` on POSIX or PowerShell with `-NoProfile -NonInteractive -Command`
on Windows. Its parameters are a command id, terminal id, session id, command,
optional cwd, env and display size. cwd defaults to the session workspace; relative
paths resolve from it, and an absolute cwd may name another directory. It requires
`terminal` scope, admits the terminal in the receipt, and sends output and the exit
code on `terminals.subscribe` through `terminal.output` and `terminal.exited`.

A run shares open's session owner, id deduplication, sixteen-terminal limit, bounded
scrollback, scrubbed output, process environment, workspace availability check and
close/delete/restart lifecycle. It works without node-pty. No login greeting, prompt,
echo or marker is part of its output. Writes are ignored because stdin is closed;
resizes only change its display size. Failure to spawn ends it with code -1 and cause
`failed`. Closing it signals its process group on POSIX, and its process on Windows.
`!` displays this output; `!!` collects it, with the existing size and time limits.
Interactive commands belong in an ordinary or tool terminal.

A run uses the cached login PATH the Managed tools registry resolved, with the
session's process environment and explicit env laid over it; it does not run a
login profile for each command. When the command exits, pipe output drains before
the exit event, for at most 100 ms if a background descendant keeps the pipes open.
Output after that bound is discarded, so descendants cannot delay completion.

Both terminal panes answer a newly opened login shell's first snapshot and live
queries for one second even without focus. Afterwards they answer only focused live
output. Reused terminals and reconnect snapshots receive no startup exception.

### Lifecycle

- **Startup order**: open the database and apply migrations; bootstrap projectors from their cursors; load the environment record and the auth tables; start the adapter host; bind the listeners; signal `prepared` to the launcher; only then accept `auth` frames and requests. Before that point the discovery URL reports `starting` and a request is answered `unavailable`. The gate exists so a trial version that cannot serve is rolled back by the launcher within its deadline (ADR 0007).
- **Idle** is computed as the glossary defines it: no run starting or running, no terminal whose shell runs a command in its foreground (since #343), and no run started or ended within the idle window, nor the environment's own start (since #445), with a run parked on a prompt counting as busy for the idle window only. The window is the `updates.idleWindowMinutes` setting (preset ten minutes, since #342). `environment.status` reports `idle`, `busy` and `draining` with the reason and, for a parked prompt, when it stops counting as busy.
- **Drain**: `environment.drain` (scope `admin`) and the launcher's channel both start a drain: new runs are refused with `unavailable`, running ones are allowed to finish up to the cap ADR 0007 sets, connected clients receive `bye: draining` at the end, and the process exits. `SIGTERM` starts the same drain. The update coordinator starts one for an update (since #343): its clients receive `bye: updating` instead, and the launcher is then asked to switch versions (launcher-update spec, "Draining").
- **Parked prompts survive a restart** because they are events: on startup the projection of open prompts is what clients receive, exactly where each was (ADR 0007).
- **Containers**: when the environment detects it is running in a container without a launcher, `environment.status` reports that updates are managed outside, and the host-side updater uses the discovery URL and the status method (launcher workstream).

### What this workstream does not decide

- The session and group event vocabulary and projections (session-state workstream); the client runtime's caches and outbox (client runtime workstream); run and transcript events and provider processes (adapter workstream); the mode and ceiling values (permissions workstream); terminals, files and diffs, which will take the reserved `terminal` scope (renderer workstream); the launcher, versions, channels and rollback (launcher workstream).

## Testing Decisions

- **What a good test is**: a behaviour visible through the wire or the discovery URL, asserted from a client's point of view, never an assertion on a table or a private structure. The exception is the store seam below, where the behaviour is the bound itself.
- **Primary seam: an in-process environment and a real client.** A test helper starts an environment on a temporary data directory, bound to loopback on port 0, with the adapter contract satisfied by a scripted fake provider, and returns a thin typed client built from the contracts package over a real WebSocket. Every story above is a test through this seam: bootstrap grant exchange and rotation; pairing creation, exchange, single use and expiry; scope refusal on a method and on a stream; protocol version mismatch closing with reason; `hello` contents; command receipts on retry and on a deleted target; session-list and per-session subscriptions with replay, snapshot, `synchronized`, live-before-catch-up and deduplication; overflow ending a subscription; ping and `bye` reasons; the access log; readiness before and after the gate; idle and drain states; a parked prompt present again after a stop and start on the same directory; a projection rebuild giving the same read models. Prior art: T3 Code's `buildAppUnderTest` with partial service overrides and `withWsRpcClient` over a Node WebSocket in its server test suite.
- **Lower seam: the event store against in-memory SQLite.** Replay bounds by event count and by bytes, compaction of an old session into a snapshot, projector cursors after a restart and after a rebuild, receipt retention, and the unique stream-version constraint under concurrent appends. Prior art: T3 Code's event store tests against its in-memory persistence layer and its projection pipeline tests.
- **Contract tests in the contracts package**: every method has exactly one scope (T3 Code's authorization test is the model); every session-summary field has a command (ADR 0003, owned by the session-state workstream but run here); the JSON Schema export round-trips every schema; a frame decoder rejects every malformed frame kind with `invalid_params`.
- **Framework**: Vitest, as T3 Code does; the environment's suite runs files serially because each starts a listener; a fake provider adapter lives beside the tests and is the model for the adapter workstream's own fake.
- **Not tested here**: the launcher's rollback (launcher workstream), the desktop's service install on each platform (manual checklist in the wizard workstream), Tailscale itself.

## Out of Scope

- The launcher, versions directory, channels, trial and rollback, and the container host-side updater (launcher workstream, ADR 0007).
- The session and group commands, events, projections, auto-settle and the offline outbox semantics (session-state and client-runtime workstreams, ADR 0003).
- Runs, transcripts, provider processes, the Claude adapter and the completions surface (adapter workstream, ADR 0015).
- Mode and ceiling values, containment, the denylist and parked-prompt TTLs (permissions workstream, ADR 0006).
- Terminals, files and diffs; the GUI and TUI (renderer workstreams, ADR 0004).
- A relay, environment peer lists, SSH-launched environments and LAN exposure beyond the off-by-default setting remain deferred. Phone HTTPS and packaged static serving are milestone 1 requirements in [web-client.md](web-client.md); the TLS endpoint is coordinator deployment configuration, not native environment TLS implementation.

## Further Notes

- Chosen defaults that were not decided on a ticket and may be revisited in review: replay bound 1,000 events or 8 MiB per stream (T3 Code's measured values); pairing code expiry ten minutes; client session lifetime 30 days with refresh; receipt retention 30 days; transcript compaction after 90 days untouched; the 15-second ping and 45-second watchdog (measured values).
- Chosen defaults not decided on a ticket, from the pairing build (#109): a pairing code is ten characters of `23456789ABCDEFGHJKMNPQRSTVWXYZ` (no 0, 1, I, L, O or U; about 49 bits), shown in two groups of five and read in any case with spaces and hyphens ignored; with a configured external HTTPS origin, the link is `<external-origin>/pair#<code>` including its non-default port; without it the existing desktop/TUI link remains `http://<tailnet name or address>:<port>/pair#<code>`; the default ceiling a pairing gives is the setting `permissions.defaultCeiling`, preset `acceptEdits` (#129; it was the top one until then); the environment finds its Tailscale address and name through the `tailscale` CLI on its PATH, then on macOS through `/Applications/Tailscale.app/Contents/MacOS/Tailscale` (`ip -4` and `status --json`, with `TAILSCALE_BE_CLI=1`); without a CLI address it also looks for a non-internal IPv4 address in `100.64.0.0/10` on any interface whose name starts with `tailscale`, checking the lowest-numbered first (`tailscale0`, `tailscale1`, …; #1265, #1316), so a Linux container sharing its host network binds the host's tailnet without a CLI or daemon socket; on macOS a numbered `utun` interface must also hold a non-internal IPv6 address in Tailscale's device prefix `fd7a:115c:a1e0::/48` on that same interface (#1377). A readable CLI status whose backend is not `Running` vetoes the macOS fallback, including retained kernel addresses after stopping or signing out. CGNAT alone, an unrelated tunnel's IPv6 or an internal IPv6 never corroborates ownership. The paired addresses preserve app-only discovery with neither CLI, but do not prove live connectivity when both CLIs are unreadable: retained dual-stack addresses or another VPN deliberately reusing the Tailscale prefix remain uncertain. IPv6 disabled or ownership undetermined means no tailnet address is reported or bound; installation detection stays independent, and pairing uses an address actually bound. The name still needs the CLI, otherwise pairing uses the IP. `environment.status.binding.tailscaleInstalled` distinguishes an installed CLI or macOS app whose address could not be read from a missing installation; older environments may omit it. LAN choices put private IPv4 first, then unique-local IPv6, other IPv6 and other IPv4, preserving interface order within each group (#1322); temporary or deprecated addresses are excluded when the interface reader exposes those flags. Node currently exposes neither flag, so the card warns that an IPv6 choice may change; `POST /api/pair` shares the bootstrap exchange's rate, 10 a minute per address, in a bucket of its own.
- Chosen default not decided on a ticket: the environment listens on port 7433 unless told otherwise (`serve --port`, `DEFAULT_PORT` in the environment package); saved connections need a stable port, and a second environment on one machine passes its own.
- Chosen default not decided on a ticket: `serve` refuses a real uid of 0 as well as an effective uid of 0, since a process whose real uid is root can take root back.
- Chosen defaults not decided on a ticket, from subscriptions (#110): the `environment` stream's id is the environment id, and every start the launcher accepts appends `environment.started` to it, after the handshake and before the wire opens; `subscribed` is sent once catch-up has been read, together with it, so a snapshot that fails is answered as an error before any subscription exists; `snapshot` and `synchronized` carry the log's head; a cursor past the head is answered with a snapshot; an `unsubscribe` naming no subscription of that socket is ignored; a subscription has fallen too far behind when the live frames it has sent and the socket has not yet flushed would pass the replay bound; a close the environment starts ends every subscription (`revoked` for a revocation, `closed` otherwise) before its `bye`. The log keeps an event's actor as one `kind:id` string.
- Chosen defaults not decided on a ticket, from the lifecycle (#112): `environment.status` (and `environment.subscribe`'s snapshot) answers the status document `{readiness, activity, updatesManagedOutside}`, where `activity` is `{state: idle}`, `{state: busy, reason, busyUntil?}` or `{state: draining, drainingSince}`. The busy reasons are `run-starting`, `run-running`, `terminal-running` (since #343: a terminal's shell runs a command in its foreground, or since #362 a tool terminal's command has not exited; it outranks the windows, as a run under way does, and yields to a run starting or running), `parked-prompt` and `recent-activity`; `busyUntil` is when the environment stops counting as busy if nothing else happens (the idle window after the parked prompt, or after the latest start or end of any run, a parked one included, or after the environment's own start, since #445), and the reason given is the one that holds longest, a parked prompt on a tie; a window ends at its instant. Runs are read through a run registry the adapter host fills (`runs`, `onChange`, `refuseNewRuns`, `admit`); it keeps an ended run for the longest idle window the setting can name, 120 minutes (#342), and the host calls `admit` before starting a run, which throws `unavailable {readiness: draining}` once the drain has refused new runs. A drain has four triggers, `command` (`environment.drain`), `launcher`, `signal` (SIGTERM, and SIGINT in the foreground; a second signal stops the process at once) and `update` (the update coordinator, since #343, whose drain ends with `bye: updating` and the launcher's `switch?` unless the environment's own close cut it short); how a drain began, `DrainStarted {drainingSince, trigger}`, is the answer to `environment.drain`, the payload of the `environment.draining` notice (appended once) and the launcher's `draining` reply, and a second trigger joins the drain under way and gets the same answer. The cap is `DRAIN_CAP_MS`, 30 minutes on the environment's clock. The drain waits for runs starting or running, not for runs parked on a prompt, which survive the restart as events (ADR 0007), then takes one turn on the clock so the answer to what started it leaves before its `bye`. While draining only new runs are refused; every other method keeps answering, so a person can still answer a prompt, interrupt a run or join the drain. The launcher's messages on its IPC channel come in pairs: `{type: "idle?"}` is answered `{type: "idle", ...status}` with the status document, and `{type: "drain?"}` is answered `{type: "draining", ...DrainStarted}`; since #336 the channel also carries the launcher workstream's pairs (`prepared {version}` answered `committed`, and the environment's `install?`, `switch?` and `versions?`), and a message either side does not know is ignored; the contracts' launcher module is their one definition in code. `environment.rebuildProjections` answers the projectors it rebuilt and the log's head. A container is one the install declared, `AGENT_HARNESS_CONTAINER` set non-empty by its compose (#133), or one detected by `/.dockerenv` or `/run/.containerenv`, with a container runtime in PID 1's cgroup as a fallback; the containment probe reads the same rule (`serve/container.ts`) and reports declared and detected apart; a launcher is present when the launcher channel says so (the IPC channel a launcher spawned the environment with); updates are managed outside when there is a container and no launcher.
- Chosen defaults not decided on a ticket, from transcript compaction (#123):
  - **Untouched**: a session is compacted when it is not deleted, has no run in the runs table still `running` and no parked prompt, and the last event on its stream is older than the window (strictly, as auto-settle counts: a session exactly the window old waits for the next pass), leaving out the events the shelf's sweep appends (`system:settle-sweep`: auto-settle and snooze expiry), which happen because the session was left alone and would otherwise hold every idle session back by the auto-settle span. A session whose latest rewind not undone can still be undone (no run has started on it since, `undoableRewind` in `sessions/fork-rewind.ts`) is left out however old, and compacted as any other once a run starts after the rewind. The fold keeps each rewind standing where it cut, not undoable, with what it hid (`rewinds`, the per-session snapshot's; claude-adapter spec, #260's notes), so the fold stays drawable after the events are removed. (History: #218 added the skip when the fold kept nothing of what a rewind hid, so a compaction inside the undo's window would have left `sessions.undoRewind` nothing to show again, and what a rewind hid was folded away with the removed events once the undo was gone. Since #260 the fold carries it, so the skip is no longer needed for the undo; it is kept to keep #260 narrow, and lifting it is owed.) A command that changed nothing appended nothing and left only a receipt, kept 30 days, shorter than the window, so the rule reads events alone. The window is `sessions.transcriptCompactAfterDays`, whole days from 1 to 3,650, preset 90, never null (ADR 0002: pruning is owed), under the Appearance step's Sessions band beside the auto-settle keys; a change takes effect at the next pass.
  - **Folded and removed**: the snapshot folds every event of the session's stream up to its last (its sequence is that event's), organisation events included since the fold reads a run's start and end and a rewind, into `{runs, items, parkedPrompts, rewinds}` as the per-session snapshot holds them (a fold stored before #260 has no `rewinds` and reads as none standing), going on from an earlier compaction's fold. It reads a delta only for where its item was opened: a settled assistant item sits at its first delta's sequence, as a client that heard the deltas places it (#260). It removes only transcript types, and of those only what no projector reads, so a rebuild gives the same read models: `assistant.delta`, `assistant.text`, `assistant.thinking`, `tool.started`, `tool.updated`, `tool.ended`, `command.ran`, `usage.reported`, `plan.limit`, and every `tasks.changed` but each run's last (`COMPACTION_REMOVES` in `sessions/compaction.ts`). Kept besides every organisation event: the `list`-flagged `run.started` and `run.ended` (the summary's run fields and the runs table), the `message.*` events (the runs projector's queue), a run's last ledger, and the `session.*` types of the transcript vocabulary (`session.provider-linked`, the resume id; `session.forked`; `session.rewound`), which compaction treats as session events, and `session.rewind-undone` with them (#218).
  - **Versions and sequences**: the log gives nothing back. The snapshot row records the stream version of the last event it folds, and an append numbers the stream above both its last event and that version, so a stream's versions keep rising with gaps where events were removed; the purge removes the snapshot first, so its tombstone is still version 1. The head is untouched and a compaction appends nothing, so no subscriber hears of it: a client holding the session has lost nothing, and its cursor is at or past the fold.
  - **Replay**: the snapshot frame of a compacted session sent to a cursor below the fold carries the fold's sequence, not the head (the one exception to #110's rule), and its payload is the per-session snapshot with that sequence, the summary read at the head (a summary cannot be read at an older sequence; the list patches replayed after it set their fields again and end where the head is). A fresh client (cursor 0) gets the same. When the events after the fold would pass the replay bound, the snapshot at the head is sent instead, its transcript folded on from the compaction's fold; so is a cursor past the head. A source without a way to render its stream's snapshot is sent its head snapshot for such a cursor. The session list is unaffected: every type it carries is kept.
  - **Cadence**: the sweep runs at startup, before the wire opens (after the purge and the shelf's pass), then once a day on the environment's clock, each session in a transaction of its own, a failure rolled back, logged by the session's id and left for the next pass. It is not run on a settings change. A restore does not undo a compaction; the purge removes the snapshot with the session's events, and nothing else does.
- Chosen defaults not decided on a ticket, from command receipts (#111): a command's `response` carries `{receipt, result}` (the contracts' `CommandReceipt` and `commandResponse`, published as `methods/<name>/response.json`), where the receipt is `{status: accepted, sequence, changed}` or `{status: rejected, sequence, changed: false, reason, error}` (the reason is the error's code), `sequence` being the log's head once the command committed, and `result` is present only when that request applied the command: a retry answered from the stored receipt and a rejection carry the receipt alone, since results are not stored (a pairing code never is). A rejection is a normal response carrying its receipt, never an error response, because the receipt is what a client's outbox retires a command on; an error response (`invalid_params`, `forbidden`, `unavailable`, `unauthorized`, `internal`, or any `ContractError` a handler throws) stores no receipt, so its retry runs again. The wire runs every command through the log's `command`: the actor is the client session (`client_session:<id>`) and the command id is kept in lowercase, so a UUID written in either case is one key; a key with a receipt is answered without calling the handler, otherwise the handler runs inside the command's transaction (it is given the command id, the actor and the transaction, and answers at once, never later; a command that must first hear from outside the log, `runs.withdraw` asking the provider whether it still holds a message and `sessions.rewind` waiting for what the host is still handing back to the session's queue after a run's end (#245), is a prepared command whose `prepare` runs before the transaction and only when no receipt answers the key; its outcomes are receipts like any command's, a `not_found` included, so a retry under the same key is answered from the receipt and never asks again, claude-adapter spec, #228; a request under a key whose `prepare` still runs, the outbox's resend after a dropped socket, waits for it and is answered from its receipt without preparing, and prepares only when that one stored none, #448) and names its aggregate with its result and events, or with its rejection, `{code, message?, data?}`, the code one of the method's own error codes, the message a plain one when none is given; `changed` is whether the command appended any event, so a projection rebuild, or a drain joined while one is under way, is accepted unchanged. Retention is exact: a receipt more than 30 days old is never answered, whether or not the minute sweep, which prunes the table, has run. `access.sessions.revoke` on an unknown client session is a rejection with reason `not_found`.
- Chosen defaults not decided on a ticket, from terminals (#124): a subscription's source is the log's or a feed of its own, and a terminal is the one feed. `terminals.subscribe` sends the same frames as a log subscription: its output chunks are `event` frames whose envelope has stream kind `terminal`, the terminal's id, type `terminal.output`, actor `system:terminals`, and as `sequence` and `streamVersion` the terminal's own chunk sequence from 1 (never the log's; the `event` frame's `sequence` is the subscription's sequence); the catch-up is a snapshot from cursor 0, from a cursor the scrollback no longer reaches whole, from a cursor past its end, or when more than 1,000 chunks follow the cursor, else a replay of the chunks after it; the overflow rule is the log's. The subscription ends after one `terminal.exited` event with the existing reasons: `deleted` when the terminal closed with its session's deletion, `closed` when its shell exited or `terminals.close` closed it (the `closed` reason's description now says "the connection closed, or the terminal it follows did"). No end reason was added, so no client's decoder meets an unknown one.
- The wire's `readiness` field (`starting`, `ready`, `draining`) reuses a word the glossary gives to skills (**Readiness**: ready, setup needed, unsupported); the contracts type is named `EnvironmentReadiness` to keep them apart, and the overlap is flagged for domain-modeling.
- "Client session" (the revocable credential a pairing or the bootstrap grant produces, with its scopes and ceiling) and "bootstrap grant" (the 0600 file and one-time secret a local client exchanges for a `local` client session) are terms this specification and the code use that the glossary lacks; neither is the glossary's **Session** or **Connection**, and the code calls the wire's live WebSocket a socket to keep them apart. Flagged for domain-modeling.
- The bootstrap grant is the answer to "how does a local client avoid pairing": the OS user's file permissions are the credential. A second OS user on the same machine is a different environment by design.
- T3 Code's DPoP sessions and WebSocket tickets were read and not carried: the harness never puts a token in a URL, so a ticket is unnecessary, and DPoP's sender-binding is more than a tailnet-only surface needs in milestone 1. If a public relay arrives, revisit both.
- The completions surface and the WebSocket share the port; the completions surface authenticates with the same client-session tokens under the same ceiling (ADR 0015), which the adapter workstream specifies.
