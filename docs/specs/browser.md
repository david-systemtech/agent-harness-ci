# Spec: Browser: extension, relay and headless Chromium

Milestone 1 (Switch-over), phase C (the organs). Written 2026-09-28 from map ticket 93 of `david/agent-harness`. Implements ADR 0014 (pairing with the local environment, the relay through the client, the browser as a session field, the denylist on every frame, the headless Chromium and its tab rules) and ADR 0024 (the unpacked folder, the port file, the unpaired signal, the version comparison, paired Chromes as environment state, the page-policy settings), with ADR 0017 for the phase and the placeholder. Cites ADR 0001, 0003, 0006, 0007, 0015, 0016, 0027, 0031 and 0036, the Resolutions of #27 and #53, David's decision of 2026-09-28 on this ticket that milestone 1 includes `web_read`, and #292's research (the `web-readability` write-up in `david/notebook`), whose measurements and milestone-1 recommendation are this specification's input. Built on main at a70b82f without re-deciding it: the env, session-state, client-runtime (the client-call registry and #142's placeholder names), claude-adapter (in-process tool servers, #139), permissions (the denylist matcher, #132; the tool gate, #140), GUI (the dock, the shell's `webView`), workspace-picker, launcher-update and forge specs. Peers read: the code being ported, as the surfaces port audit (section 2) describes it: the MV3 extension, the page-driver contract and bridge protocol, the tool set, the CDP driver with its tab rules and navigation policy, and the relay; Playwright's injected aria snapshot; Mozilla Readability 0.6.0. The product name is the placeholder `agent-harness` throughout.

## Problem Statement

David's agents cannot read much of the web, and what they read they cannot act on. The browser tools being ported read a page as the top document's `innerText`, cut at 40,000 characters, and act by a CSS selector the model has never been shown (#292). `innerText` leaves out shadow roots and never enters frames, so his own Home Assistant dashboards, built with Lit, come back empty (their fetched shell is 5 tokens of text), embedded frames go unread, and a long article loses everything after the cut with no way to ask for the rest. No verb scrolls, waits for content, or clicks where a screenshot shows something. The provider's own fetch does worse on long pages and PDFs: Claude Code's WebFetch cut Wikipedia's "World Wide Web" 44% of the way in, refused reddit.com, rejected a 39 MB PDF, and answered through a small model's paraphrase. The agent's browser pointed at Reddit in his own Chrome left 24 reCAPTCHA tabs in seven minutes on 2026-09-01. Both drivers enable the protocol's `Runtime` domain on every page, which a stealth vendor says anti-bot services detect.

The extension itself is the best-separated code audited, but it works from one place. Its listener, pairing store and driver live in the desktop window's main process, so only that window can answer a browser verb; the terminal UI has no browser at all; pairing is per desktop install; the listener takes a fixed port a second instance cannot share; installing means saving a zip, unzipping it and loading the folder by hand; an outdated extension shows only as a suffix on its row; and a window served by another machine can pair nothing (ADR 0024, surfaces audit). A conversation served by another machine reaches David's Chrome only through the one window that started it. The headless browser beside a server has good tab rules, but it is configured by environment variables and runs only where someone wrote a compose service by hand.

## Solution

The environment on David's machine unpacks its own extension into a folder in its data directory, writes its listener port into that folder, and the Browser step walks him through loading it in Chrome and pairing it with a code, on one card that ticks itself. The paired Chrome belongs to that environment: every client on the machine, the desktop window and the terminal UI alike, sees it, can pick it for a session, and answers a browser verb on it for a run on any environment through the browser relay. Each session has a browser: a paired Chrome, the run environment's headless Chromium, or, in the desktop window, the browser dock. Whichever it is, the agent gets the same tools to read and act (the debugging verbs where that browser has them), and they read pages the way agents now read them: an accessibility snapshot with element refs to click and type by, a reader that returns an article as paged Markdown, screenshots with clicks at a point, scrolling and waiting, and, on every run, `web_read`, a fetch reader on the run's environment for pages and PDFs that need no browser. Every page-derived result arrives framed as untrusted content with secrets redacted. The denylist's browser section is checked on every address and every frame in every mode; a top-level navigation into a listed site is put to David; a bot check or a login is handed to him, never solved or retried. The headless browser starts when a run first needs it, closes idle tabs, exits when empty and is watched for memory, whether it is a Chromium the environment launches itself or a browser container beside it.

## User Stories

1. As David, I want the environment on my machine to put the extension in a folder I load in Chrome, so that there is no zip to save and unzip.
2. As David, I want the extension to find its environment's port by itself, so that two environments on one machine can each pair a Chrome.
3. As David, I want the Load step to tick the moment Chrome opens the extension's socket, so that I know it loaded before I pair.
4. As David, I want to pair a Chrome by typing a short code into the extension's options page, so that nothing else on my machine can drive my browser.
5. As David, I want each paired Chrome named ("Work", "Personal") and renameable, so that I choose the right signed-in profile.
6. As David, I want to see which paired Chromes are connected now and unpair one, so that a profile I no longer use cannot be driven.
7. As David, I want to be told when a Chrome runs another version of the extension than my environment ships, with the one action that fixes it, so that an update never silently breaks the browser.
8. As David, I want the extension folder replaced when the environment updates itself, so that Reload in Chrome is all an update asks.
9. As David, I want to choose per session whether the agent uses my Chrome, the headless browser or the browser dock, so that my signed-in browser is used only where I meant it.
10. As David, I want an account's reach setting to make My Chrome the default for its new sessions, so that I do not pick it every time.
11. As David, I want a run on SAMPLE-SERVER started from my desktop to drive my desktop's Chrome, so that the agent reads my signed-in pages wherever it runs.
12. As Milo, I want the terminal UI to answer browser verbs on a Chrome paired with my environment, so that I have the browser the desktop window has.
13. As David, I want the agent to click and type by the refs a snapshot gave it, so that it never guesses a CSS selector.
14. As David, I want the agent to read my Home Assistant dashboard and pages with frames, so that shadow DOM and embedded frames are not blind spots.
15. As David, I want a long article returned to its end in pages, so that nothing after 40,000 characters is lost.
16. As David, I want a screenshot to lead to an action, with clicks at a point, scrolling and waiting, so that canvas apps, lazy lists and slow pages are reachable.
17. As David, I want the agent to read a plain URL or a PDF without any browser, verbatim and paged, for every provider, so that a page that needs no browser costs no Chromium.
18. As David, I want `web_read` to say when a page needs a browser, so that the agent opens one instead of summarising an empty shell.
19. As David, I want every page-derived result marked as untrusted content, so that instructions on a page are never read as mine.
20. As David, I want password, card and one-time-code values and token-shaped secrets removed from what the agent reads, so that a snapshot never puts a credential in a transcript.
21. As David, I want password managers, payment processors and banks refused on every frame and address in every mode, with a top-level navigation into one put to me, so that a prompt injection cannot spend my signed-in sessions.
22. As David, I want cookie values, storage and JavaScript limited to the sites I am developing unless I widen it, so that my session cookies stay mine.
23. As David, I want a captcha or a login handed to me rather than solved or retried, so that my Chrome never fills with challenge tabs again.
24. As David, I want the extension to leave the page's script-debugging domains off until a verb needs them, so that my own browser looks less automated.
25. As David, I want the headless browser to close idle tabs, exit when empty and close a tab that holds too much memory, so that a forgotten session never holds gigabytes.
26. As David, I want the headless browser and `web_read` refused internal addresses unless I name them, and cloud metadata addresses always, so that a browsing agent cannot reach my LAN admin pages or the host's credentials.
27. As David, I want one setting per environment that says whether runs may drive its headless browser, so that a server I do not want browsing never does.
28. As David, I want the dock in the desktop window to be a browser a run can drive with the same tools, so that I can watch a page the agent works on.
29. As a routine, I want my firing's runs to use my environment's headless browser, so that unattended work reads the web with no client connected.
30. As a program on the completions surface, I want no browser in my run unless I ask for the headless one, so that a bot that brings its own browser is not handed a second one.
31. As the browser relay, I want a verb addressed to the client that started the run, its answer back on the same connection and a deadline on both, so that a run never waits on a closed laptop.
32. As the setup checklist, I want the environment to report the folder, the port or the port-in-use error, an unpaired connection, the paired Chromes and the version each runs, so that the Browser card and its health check need nothing else.
33. As the launcher, I want the extension folder to follow the version that starts, so that the extension moves with the environment and has no update of its own.
34. As a provider adapter, I want the browser tools as an in-process tool server that says what each call reaches, so that the tool gate rules on the browser's addresses rather than reading them as opaque input.
35. As a build session, I want an in-process environment, a fake extension and a scripted CDP peer driven over the real wire, so that pairing, the relay and the tab rules are tests that run in seconds.
36. As a client developer in another language, I want the bridge protocol and the client-call frames published as schemas, so that I can write a client that answers browser verbs.

## Implementation Decisions

### Packages and pieces

- **contracts** gains the page-driver contract (the verbs, their results and refusals), the bridge protocol between an environment and its extension, the page policy and the standing of an address (read with the permissions spec's matcher, #132, so the extension, the drivers and the gate read an address alike), the extension's fixed id, the session field's value, the `chrome` stream's events, the notices, the methods and the `browser.*` settings. It stays free of DOM and Node types.
- A new **browser** package holds what runs in every browser: the in-page scripts (the vendored aria snapshot with its role and name computation, the reader and its Markdown conversion, the serialiser's redaction, challenge detection) and the CDP page driver written once against a small CDP session interface (send a command to a target, hear its events, attach to child targets). The environment runs it over a WebSocket or a pipe to Chromium, the extension over `chrome.debugger`, the desktop shell over Electron's `webContents.debugger`; #292 found all three speak the same protocol. It holds no policy (each host passes the one it enforces) and imports no Node or environment code, so the extension depends on it and the contracts package only.
- **environment** gains the browser service: the extension folder and its port file, the listener and pairing store, the extension driver, the headless browser manager, the relay's run side, the browser tool server, `web_read`, the methods below and the Browser step's state checks. Its data directory gains the extension folder and the headless browser's throwaway profiles.
- **extension**: the MV3 extension, ported with the changes below, built into every server artefact (launcher-update spec) instead of being released as a zip.
- **client-runtime** gains the relay's client half, a `browser.chrome` handler every client registers, and `projections.browsers`; **gui** registers `browser.dock` over the shell's `webView`, which gains a debugger channel (the GUI spec owes both to this workstream).

### One page driver for three browsers

- The contract is the existing one, ported as it is (ADR 0014): every verb resolves to a value or a refusal sentence the model can act on, never an exception; a function the driver runs in a page that throws reaches the model as its error's name and message, never its stack (#696). A driver acts on one session's page, named by a **page key** the environment derives from the run environment's id and the session id and the browser sees as opaque; no verb takes a tab id, so a run cannot reach another session's page.
- Three kinds, with the abilities they have today: `chrome` (every verb; cookie values, storage and evaluate only where the page policy allows), `headless` (every verb on every site: it is signed in to nothing), `dock` (reading and acting, none of the deep verbs).
- **Implemented once** as CDP calls and in-page scripts (#292 item 1). Scripts run in an isolated world the driver creates per frame, so reading needs no `Runtime.enable` and the page's own scripts can neither see nor change them. Cross-site frames are separate targets under site isolation; the driver attaches to them as child targets and stitches their results into one.
- **Lazy domains** (#292 item 7): `Page` at attach; `Runtime`, `Log` and `Network` on the first console, network, cookies, storage or evaluate verb, or at attach on a dev site, where debugging is the point. The headless driver also enables `Network` at attach, because its navigation policy reads the address each document was served from; it holds no logins and passing bot checks is not its purpose.
- The viewport is 1280 by 800 and a screenshot is a JPEG at quality 70 of the viewport (ported), 1,334 visual tokens at the provider's patch rate (#292).

### The tools

One in-process tool server named `browser` on every run (claude-adapter spec, #139), so its tools appear as `mcp__browser__<tool>`, a name permission rules and skills can address. The descriptions carry the kind's wording (whose browser it is, what being signed in means there, the per-site rule: the existing copy, product name as the placeholder) and the layer order (#292 item 8): a snapshot to act, `browser_read` for prose, a screenshot for visual questions, `web_read` before opening a browser for a plain URL, a captcha or a login means asking the person, a bot check is never retried, and reddit.com is never opened in a browser, since it challenges automated browsing every time. A browser verb is an ordinary tool call under the run's mode (ADR 0014, ADR 0006).

- **`browser_open`** (address optional; `browser`, a paired Chrome's name, offered only when the session's browser is the plain My Chrome) and **`browser_navigate`** (address), ported.
- **`browser_snapshot`** (new): the page as an accessibility tree, one element per line with its role, name, state and value, and a ref (`e12`, prefixed for a child frame) on each element that can be acted on; frames stitched, open shadow roots included; `filter` `interactive` (preset) or `all`; `depth`; `ref` to focus on one subtree; `maxChars`, preset 30,000 and at most 200,000, cut at the last line boundary within it, or mid-line when no line ends within it, with the full size and the cut stated and focus suggested. Refs live in a map in the isolated world; a ref from an older snapshot, or whose element has left the page, is refused with "take a new snapshot". After `browser_open`, `browser_navigate`, `browser_click`, `browser_click_at` and `browser_type` the result carries an interactive snapshot capped at 12,000 characters unless the call says `snapshot: false`, as Hermes and Playwright's MCP server do.
- **The snapshot's source is Playwright's injected aria snapshot, vendored** (Apache-2.0, pinned to a commit, its notice kept) with its role and name computation, run in the isolated world. Chosen over CDP's `Accessibility.getFullAXTree` because it is one plain script for all three browsers, its walk descends into shadow roots and slotted nodes, the code that assigns refs is the code that resolves them, and it can report boxes for coordinate labels later; the protocol's accessibility domain is experimental, fetched per target, and unverified on shadow content. The fallback is the per-frame accessibility tree; the build's first task confirms the choice on #292's page set (Further Notes).
- **`browser_click`** and **`browser_type`** take `ref`, or `selector` as the second way (ported); the element is scrolled into view and real input is dispatched at its centre (ported); typing replaces the field's contents (ported).
- **`browser_read`**, rebuilt as the reader: Readability 0.6.0 run in the page on a clone of the rendered document, converted to Markdown with link targets dropped unless `links: true`; paged by `offset` at 24,000 characters a page with the total length and the next offset stated, replacing the 40,000-character cut. When Readability judges the page not readerable (an app, a result page) it returns the snapshot's text in `all` mode and says which it returned. Readability over Defuddle and Trafilatura on #292's evidence: the best-benchmarked JavaScript reader (F1 0.947 against 0.930 for Defuddle re-run there and 0.679 for `innerText`-like text), native to the browser, Apache-2.0; it used 19% to 72% of the tokens of whole-page Markdown on the four articles measured. A page that breaks the reader (an element named after a DOM method it calls takes that method's place, #696) is refused with a sentence that says to take a snapshot or a screenshot instead.
- **`browser_screenshot`** (ported) gains three companions: **`browser_click_at`** (x and y in screenshot pixels), **`browser_scroll`** (a direction and an amount in viewports, or to a ref) and **`browser_wait_for`** (text to appear, a ref to exist, or a number of milliseconds; bounded at 30 seconds, preset 10).
- **Deep verbs**, offered only where the driver has the ability (ported): `browser_console`, `browser_network` (`failedOnly`), `browser_cookies` (values only where the policy allows deep reads), `browser_storage` and `browser_evaluate` (where allowed).
- **`browser_close`** (new): lets go of the session's page when the agent has finished with it, so a headless context is given back before the idle rule would; in a Chrome or the dock the tab stays for the person (ported: a tab in the person's own browser is never closed for them).
- **`web_read`** (below) is on every run's server. The other tools are there when the run's resolved browser is not none, the deep verbs only where its kind has the ability.
- **The adapter contract gains two things** for in-process tools: a tool may declare what a call reaches (`browse` with the address for `browser_open` and `browser_navigate`, `fetch` with the URL for `web_read`, `other` for the rest), which the adapter hands the tool gate in place of the opaque reading of a tool server's input (permissions spec, #140's tool map); and a result may carry images beside its text, which the Claude adapter passes as image content.
- **A kept provider process** serves a later run with the server it started with when the tools are the same (#139), so the tools look up the session's live run and its resolved browser at each call, never the run that built them. A session whose browser changes kind gets tools with other descriptions, so its next run starts a fresh process, resumed from the store.

### Model-boundary hygiene

- **Framing** (#292 item 6): every page-derived result (snapshot, reader, `web_read`, console, network, cookies, storage, evaluate) opens with a line naming the address and saying the text is untrusted page content and not instructions from the user, inside a boundary token random per result that closes it again, so page text cannot end the frame. Prompt injection stays unsolved: the provider's best published figure is about 1% attack success against an adaptive attacker.
- **Redaction** in the serialiser, whatever the page reports: the values of password inputs and of fields whose `autocomplete` is a `cc-` value or `one-time-code`, and token-shaped strings (the common provider key and access-token prefixes, AWS access key ids, JSON web tokens, PEM private key blocks), each replaced by a marker naming what was removed; then the scrub registry, as every tool output passes it (91).
- **Challenges**: a page showing a reCAPTCHA, hCaptcha or Turnstile frame, a known bot-check vendor's markers or a JavaScript challenge is named in the result with one instruction: stop, ask the person to complete it in a browser they can see (from the headless browser, suggest choosing their Chrome), and wait. No tool retries a challenge (#292: never stealth, never captcha solving).

### `web_read`

- `web_read` (an address, `offset`, and `pages` for a PDF) fetches on the run's environment, HTTP and HTTPS only, following at most five redirects, each hop checked as the first, within 30 seconds, reading at most 20 MB of HTML or text and 50 MB of PDF.
- HTML goes through Readability on jsdom (the pairing #292 measured: 40 to 858 ms a page), falling back to the document's text when not readerable; a PDF through pdf.js text per page (Apache-2.0), `pages` a range; any other type is refused with a sentence. The output is Markdown, verbatim, paged at 24,000 characters by `offset`, framed and redacted as above. Extraction runs in a fresh worker thread per call with a 512 MB heap limit, one at a time per environment, so a large page's memory goes when the call ends (#292 measured jsdom and Readability at 326 MB over fifteen pages).
- **It says when a page needs a browser**: a shell (under 200 characters of text beside a `noscript` element, an "enable JavaScript" line, or an app's empty custom element, which is all a Lit app's served page has), a challenge's markers, a 403 or 429, or a 202 challenge is answered with a sentence pointing at `browser_open`, never an empty page.
- **Gated as a fetch** (the permissions spec's `fetch` access: the denylist's hosts section, denied at `workspace-no-network`), with the environment's address rules on every hop: the name resolved, internal addresses refused unless listed in `browser.internalHosts`, cloud metadata addresses always, and the connection made to the address that was checked, so a name that rebinds between check and fetch gains nothing.
- It identifies itself as `agent-harness` reading for an agent in its user agent (#292: identify as an agent; a chosen default).

### The browser as a session field

- **The field** (ADR 0014, ADR 0003): the session summary gains `browser`, null (none chosen) or one of `{kind: chrome, environmentId, chromeId}` (a null `chromeId` is the plain My Chrome: whichever of that environment's Chromes is connected), `{kind: headless}`, `{kind: dock}` and `{kind: none}`. It is set by `sessions.setBrowser` (scope `runs:drive`, since it chooses what the next run may drive, as `sessions.rewind` and `permissions.mode.set` do) and recorded as `session.browser.set` (list-flagged: the value, and who chose it, a person, the agent answering the several-Chromes question, or the reach default). `sessions.create` takes an optional `browser` and records the first value, as it does the mode; the field table's owner is `sessions.setBrowser`.
- **Forks** (#793): `sessions.fork` carries the source's current browser, including who chose it, as the fork's first `session.browser.set` immediately after `session.created`. The latest browser event supplies both, and survives transcript compaction. A source with no browser chosen, including one cleared back to null, gives its fork null and no browser event. Anchored forks, forks onto another account and forks of forks follow the same rule. The completions surface then records its own choice on a fork it makes: `none`, or `headless` when the request says `agent-harness.browser: headless`, chosen by `completions`, even when the inherited value is the same. Its run resolves that choice.
- **Reach** (ADR 0014, ADR 0024): `browser.reach`, kept on each account's environment for each of its accounts: `per-session`, the preset (no Chrome until one is chosen in the session), or a Chrome always (`{chrome: {environmentId, chromeId}}`, a null `chromeId` being the plain My Chrome of that environment, as in the field). A client creating a session presets the browser from it (`projections.newSession` gains the chip, workspace-picker spec), sending that Chrome only when its environment is the client's own local environment or the session's, which drives it directly (below); otherwise the field stays null.
- **Resolution at run start**, recorded as `run.browser.resolved` (the run, the value, and why) before the run's first tool call: a Chrome, headless or the dock as the field names it; null resolves to the run environment's headless browser when `browser.headless.allowRuns` is on and one is available, else to none. An unattended run, a firing's among them, never gets a Chrome or the dock: a null field resolves as above, and a session naming either resolves to none for that run, with the reason, since nobody is there to watch a signed-in browser (ADR 0014: routines and bots use the headless browser on their environment). The completions surface creates its sessions with `none` unless the request says `agent-harness.browser: headless` (the claude-adapter spec's browser fields; a chosen default, since a program brings its own tools).
- **Several Chromes** (ported rule): the plain My Chrome uses the one connected Chrome; with several connected the first verb is refused naming them and telling the model to ask the person, whose answer comes back as `browser_open`'s `browser` argument, and the environment records it as `session.browser.set` chosen by the agent. A session that names a Chrome is never moved by the model: naming another is refused.
- **The picker**: `projections.browsers(environmentId, sessionId)` in the client runtime, which both renderers draw: a row for each Chrome paired with the client's local environment or with the session's (connected, or dimmed with the reason), the plain My Chrome when more than one is paired, the session environment's headless browser with its availability, the browser dock when the shell has `webView`, and the default with what it resolves to. The labels and notes are the existing picker copy (ADR 0024). It reads `browser.chromes.list` from the local environment and `browser.status` from the session's, both in the request cache and refreshed on `chrome.updated`.

### The extension, its folder and its listener

- **The folder** (ADR 0024): the server artefact carries the built extension. At startup, and again when `browser.status` finds it missing, the environment copies it to `extension/current` in its data directory when absent or of another version, through a staging folder and a rename, so the path Chrome loads always holds one whole version. An update replaces it as the new version starts, so Chrome needs only Reload. The manifest carries the harness version as its version name.
- **The port file**: once bound, the environment writes a small file into the folder with its listener port, its environment id and name, and the harness version. The extension reads it from its own folder at each connection attempt (its content policy admits only itself and loopback), so a port that changed across a restart is found without Reload. The options page shows the port and keeps its override for odd cases.
- **The listener**: loopback only, on 47615, else the next free port up to 47634 (a chosen default), else not listening, with the port-in-use error the card shows. An upgrade must carry a loopback Host and the extension's Origin, its fixed id (a new manifest key, the id written in the contracts package). Two environments on one machine unpack two folders with two ports; a Chrome profile loads one of them, since both share the id.
- **The bridge protocol**, version 2 in the contracts package, keeps version 1's messages with three changes. An extension that holds no credential dials anyway and opens with `announce` (its protocol and extension versions and the name it would pair as); the environment answers with its id and name and keeps the socket. That is the **unpaired signal**: an `extension.seen` notice and `browser.status`'s unpaired flag, which tick the card's Load sub-step (ADR 0024); `pair` (the code, the name) then comes on the same socket. `hello` and `challenge` carry the environment id, so an extension that finds another environment on its port says so on its options page instead of proving to it. The proof is unchanged: HMAC-SHA256 of the challenge nonce keyed by the secret's bytes, in lowercase hex. The environment accepts its bridge version and the one before, so an update that bumps it leaves a Chrome working until Reload; an older one is refused with the Reload sentence.
- **Pairing**: `browser.pairing.code` (scope `admin`, a query that mints) answers the live code and its expiry, minting one when none is live: eight characters of the environment spec's pairing alphabet, good for five minutes, single use, void after five wrong guesses (ADR 0024). A good code makes a paired Chrome: an id, a 32-byte secret kept in the environment's vault and never in the log, and the name, trimmed, at most 80 characters, with control and invisible characters removed and "A browser" when empty (ported). A later `hello` never overwrites a name (ported). For a machine with no desktop window, the CLI gains `browser pair`, which prints the folder's path, the Chrome lines and a code with its countdown through the bootstrap grant, and waits for the paired Chrome (the terminal UI's own `/browser pair` stays in ADR 0024's fog).
- **Paired Chromes are environment state** (ADR 0014): a `chrome` stream per Chrome, its id the Chrome's, carrying `chrome.paired`, `chrome.renamed`, `chrome.version-reported` (appended when a connection reports another extension version than the last recorded) and `chrome.unpaired`; the projection holds the id, name, pairing time, last connection time and last reported version. Being connected is live state: the listener knows which Chromes hold a proved socket. `browser.chromes.list` (`read`) answers each Chrome with `connected` and `outdated` (its last reported version differs from the folder's); `browser.chromes.rename` and `browser.chromes.unpair` (`admin`, commands) change them; unpairing forgets the secret and closes the socket with a refusal, and the extension returns to unpaired. Every change, connection and disconnection raises `chrome.updated` on `environment.subscribe`.
- **The page policy the extension holds**, enforced in the browser against the address the tab has now, before every verb and after every load (ported): the environment's `browser.devSites`, `browser.evaluateEverywhere` and `browser.deepReadEverywhere` and the enabled entries of the denylist's browser section, sent on `ready` and again on every change. Loopback and private addresses count as dev sites without being listed; the Chrome Web Store is refused whatever the policy, since Chrome forbids extensions there (both ported). A verb carrying a one-time allowance (below) may open that one host, once.
- **The tab group and the debugger** (ported): one tab per page key in a tab group titled with the product name; the extension reaches no other tab. Chrome shows its debugging banner while attached; a managed profile whose policy blocks the debugger answers every verb with that sentence.

### The browser relay

- **When it is used**: for a Chrome paired with an environment other than the run's, and for the dock. A Chrome paired with the run's own environment is driven by that environment directly, whoever started the run, so the run keeps its browser when its client closes (a chosen default inside ADR 0014, where the client would only ask that same environment).
- **The call**: the run's environment appends `client.call` to its `environment` stream, the names #142 built as placeholders becoming final: `{callId, clientSessionId, kind, payload}`, `kind` `browser.chrome` or `browser.dock`, the payload holding the Chrome's environment and id (for `browser.chrome`), the page key, the verb and its arguments, a one-time allowance when a person allowed a denylisted address, and the deadline. It is addressed to the client session that started the run, or, for a run the environment started itself, to the one that started the session's latest run a client started. When that client session holds no live socket the verb is refused at once with the sentence naming the client, and nothing is appended. A call carries a verb's arguments and never its answer, so the stream grows by a few hundred bytes a verb.
- **The client half**: the client runtime registers `browser.chrome` in every client. Its handler checks it holds a local connection (made by the bootstrap grant) to the named environment and calls `browser.chromes.perform` there (scope `runs:drive`; any client session that is not local is refused `forbidden` with reason `local`, the contract's reason for a method only a local client session may ask (#335, #552), so only a client on the Chrome's machine drives it), then answers. The GUI registers `browser.dock` and drives the session's dock, creating it hidden when the session has no pane open. A client with no handler for the kind answers `unsupported`, which the run reads as a sentence.
- **The answer**: `client.answer` (scope `runs:drive`, a request that appends nothing, from the addressed client session only, else `forbidden`) with `{callId, ok: true, result}` or `{callId, ok: false, error}`. An answer for an unknown, expired or answered call is accepted with `taken: false`, so the runtime's resend after a reconnect is harmless. A result is at most 8 MiB. Only the tool's result enters the transcript.
- **Deadlines** (ported, per verb): 20 seconds for open, navigate, click and click-at, 18 for a screenshot, 5 for letting go of a page, a wait's own bound plus 5 seconds, and 12 for the rest; a late answer is dropped and the model reads the timeout sentence naming the client.

### The headless Chromium

- **Two sources.** An operator's browser beside the environment, named by `browser.headless.endpoint` (a CDP address); the published compose file gains a `browser` service under an opt-in profile: Debian's Chromium under new headless as a non-root user, `restart: unless-stopped`, an init process, a 1 GiB memory limit and its port published on loopback only (the ported image). Or, with no endpoint set and the environment not in a declared container, a Chromium or Chrome the environment finds (`browser.headless.executable`, else the platform's usual install locations and PATH) and launches itself under new headless, with a throwaway profile in its data directory, over a pipe rather than a port. With neither, the headless browser is absent with that reason.
- **The tab rules, none of which can be switched off** (ADR 0014; the ported numbers, together in `browser.headless.limits`): one context per session; a context with no tool call for 10 minutes closed, the run told so on its next call; at most 2 live contexts, a third session refused with a sentence saying other sessions hold the browser and to wait (their contexts go after ten idle minutes, or at their `browser_close`) or tell the person; the process asked to exit after 5 minutes with no context (a launched one is ended; an endpoint gets `Browser.close`, its restart policy brings it back, and the next open reconnects with twelve one-second retries); a watchdog every 30 seconds closing a tab past 500 MB of heap, least recently used first; on connecting, every target and context it does not own closed. A session's deletion closes its context.
- **The navigation policy** (ported): the public internet open; loopback, private, link-local, CGNAT and unique-local addresses and `.local`, `.internal` and `.lan` names refused unless listed in `browser.internalHosts` (preset: `localhost`, `127.0.0.1`, `::1`); cloud metadata addresses refused always. It is applied to the name, to the addresses the name resolves to before navigating, and to the address each document was actually served from, in every frame; a page one of whose frames is refused is refused whole.
- **`browser.headless.allowRuns`** is the operator setting ADR 0014 names: off, no run on this environment gets its headless browser.

### The denylist on every frame

- **Before the call**: the gate reads `browser_open`'s and `browser_navigate`'s address as `browse`, matched against the browser domains and the hosts (permissions spec); a match opens a `denylist` prompt on an attended run and is denied on an unattended one. A person's allow reaches the driver as a one-time allowance for that host on that call, found by the call's id on the prompt the gate opened. The gate gains one input for the rule below: a `browse` check may carry a match the browser made, which the gate treats as a match of its own.
- **In the browser**: the driver judges every frame's arrival against the browser section of the policy it holds: a Chrome its environment's, the headless browser its own environment's beside the address rules, the dock the GUI's home environment's, read through `permissions.denylist.get` and matched with the contracts' matcher. A **sub-frame** into a listed domain refuses the page whole at once (it goes to `about:blank`), and the verb answers which frame and entry (the permissions spec's chosen default, carried here). A **top-level navigation** the agent did not name (a redirect, a click, a script) is held: the page goes to `about:blank`, the verb answers a refusal carrying the address and the entry, and the tool server hands the gate of the session's live run that address with the entry the browser matched, which the gate rules on as a denylist match whether or not its own list holds the entry (a `denylist` prompt on an attended run, a denial on an unattended one); allowed, the tool server navigates there with the one-time allowance and answers the verb; denied by the person, the unattended rule or the TTL, the model reads the refusal. The tool call waits while the prompt is parked. The same holds when the browser refuses an address the agent named.
- **A relayed Chrome is judged by two lists**: the run environment's gate on the address named, and the extension on the policy of the Chrome's own environment. A refusal names the environment whose entry matched, and an entry only the Chrome's environment lists still reaches the person through the rule above, never the run environment's silence.

## Testing Decisions

- **A good test** drives the browser through the wire, the extension's socket or the tool server a fake provider calls, and asserts what a client, the extension or the model sees: a `chrome.paired` event with no secret in it, a refusal sentence, a `client.call` addressed to one client session, a page's text with its boundary and its redactions. Never an assertion on a projection table or the listener's private maps.
- **Primary seam: the in-process environment** of the environment spec (a temporary data directory, loopback port 0, a scripted fake provider, the typed client over a real WebSocket), with two fakes this workstream adds: a **fake extension** (a WebSocket client that reads the port file from the unpacked folder, speaks bridge version 2 with the extension's Origin and answers verbs from a script) and a **scripted CDP peer** (a loopback WebSocket or a pipe answering the commands and sending the events the driver uses). The listener's preferred port is a seam tests set to 0, and time is a manual clock. Cases: the folder unpacked, replaced whole and re-made; the port file, the next-free rule and the port-in-use error; Origin and Host refusals; `announce` raising `extension.seen`; pairing by a good, a guessed-at, an expired and a spent code; the proof with and without the secret; a rename a later `hello` leaves alone; unpairing; `outdated`; the policy pushed on a change; the step's state checks through `setup.check`; `sessions.setBrowser` and its patch; resolution for attended, unattended, firing and completions runs; every tool on the direct path to the fake extension and to the scripted CDP peer; a redirect into a listed domain parking a `denylist` prompt that is allowed, denied, or denied at once when unattended; each tab rule on the clock; `web_read` against a loopback HTTP server (an article paged to its end, PDF pages, a shell and a challenge detected, a redirect into a metadata address refused, rebinding through a resolver seam, no-network denied by the gate).
- **The relay seam**: two in-process environments and one client runtime connected to both, local to one through the grant, with the fake extension paired to the local one and the fake provider on the other calling `browser_navigate`: the `client.call` addressed to the starting client session, `browser.chromes.perform` on the local environment, the answer, the tool's result; a verb refused at once when the client is gone; a deadline passing; a second answer taken false; a session that is not local refused `forbidden` with reason `local`.
- **Lower seams**: the pure parts (the bridge codec and handshake state machine, the standing of an address, the snapshot serialiser's budget and ref names, redaction, the frame, the reader's paging and Markdown, challenge detection on fixed HTML) as unit tests; the in-page scripts against a real Chromium on fixture pages (open shadow roots, same-site and cross-site frames, password and card fields, a long article, a canvas) in a suite that runs where a Chromium is present and skips with that reason elsewhere; the extension's worker against a fake `chrome` API, as the existing extension's handshake, proof, policy, tab-book and manifest tests do.
- **Client runtime**: the `browser.chrome` handler and `projections.browsers` against the scripted fake wire the existing client-call tests use, and against in-process environments.
- **Contract tests** in the contracts package: every new method has one scope; every `browser.*` key is written by the `browser` step; the summary's `browser` field is owned by `sessions.setBrowser`; the bridge and client-call schemas round-trip through the JSON Schema export; the extension imports nothing from the workspace but the contracts and browser packages.
- **Manual** (#292, section 5): the fixed page set in the headless browser (a browser container on LAB with the limits, not the shared agent container) and in David's Chrome with him present, against the pass lines: refs act on every page but the bot checks; Home Assistant's card values appear in the snapshot; `browser_read` returns Wikipedia to its end; no secret field value appears in any snapshot; every interactive snapshot fits under 15,000 tokens or states its full size. The first real pairing on each platform David uses.
- **Prior art**: T3 Code's `buildAppUnderTest` and `withWsRpcClient`; the existing relay suite (25 cases), extension suite (15 files, with an end-to-end test), CDP driver integration test and headless-browser suite the surfaces audit counts. Vitest, serial where a listener is bound.
