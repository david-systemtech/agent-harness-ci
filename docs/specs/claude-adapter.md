# Spec: Claude adapter, the adapter contract and the completions surface

Milestone 1 (Switch-over), phase A (the spine). Written 2026-09-23 from map ticket 82 of `david/agent-harness`. Decisions it implements: ADR 0015 (the adapter contract, environment-owned provider processes, the served adapter retired, the completions surface with client-tool passthrough), ADR 0009 (the instruction channel, skills through a plugin directory, the `project` settings source behind the trust gate), ADR 0018 (accounts as environment-owned directories, environment-driven sign-in with the SDK-bundled binary, identity from auth status, the session store, one auto-memory directory per repository, the stripped variables: five, with the scrubbed families), ADR 0019 (a minted session is an ordinary session), ADR 0006 (modes, ceilings, prompts as events), ADR 0002 (the log holds transcripts), ADR 0017 (phase, placeholder name), with rules that also cite ADR 0001 (opaque unknown kinds), ADR 0005 (usage pooled by identity), ADR 0007 (drain, prompts surviving a restart), ADR 0011 (the orientation block) and ADR 0016 (the step registry), and the Resolutions of tickets 28, 29, 40 and 51. It builds on the environment-service (ticket 78), session-state (79) and client-runtime (80) specifications on main and re-decides none of them. Peers read: Artemis at 443cf2e (the adapter seam, the environment composer, the Claude adapter, the plan-usage read, sign-in on both paths, the completions handlers, the headless host's tests), the core port audit, the Claude Code and Hermes inventories, the Agent SDK reference and session-storage pages, the CLI reference and the headless page. The product name is the placeholder `agent-harness` throughout.

## Problem Statement

Every Claude run David starts in Artemis is one turn of a process the run owns, so a process dies with the window that started it, a turn pays a cold start unless the last one is still holding work, and a routine on the headless server gets a different host around the same adapter. The audit found the seam sound and Electron-free, with four faults around it: every query passes an empty settings list, so a repository's own instructions, hooks and rules never load; the adapter is one 6,136-line file; three of its types live in the desktop's IPC contract; and the plan gauge is read by name lookup on an experimental SDK method. Accounts share history and memory only through a script of nine symlinks nobody runs on the server, and an account has no identity, so one login on two machines is two gauges. Sign-in is a copied command on the desktop and a driven subprocess on the server. The completions surface, which is how the Hermes bots bill on David's subscriptions, marks a caller's `tools` as honoured and never reads them, so Hermes's memory, skill and cron tools never run; any token may ask for bypass; a disconnect interrupts the run; and a quiet stream looks like a dead socket.

## Solution

One adapter contract on the environment, with the Claude adapter as its first implementation. An adapter declares what it can do and how its credential is scoped, and turns a run into transcript events that go into the environment's log and nowhere else; sessions resume, fork and rewind through it; plan usage carries an account identity so the laptop and SYSTEM-SERVER show one gauge for one login; models come with tiers; commands are listed from the provider; standing instructions and always-on skills ride the provider's own instruction channel; tool servers are built per run; and a permission prompt is a parked event any client can answer. Claude's per-conversation process belongs to the environment: started on the first run, reused by the next, kept through a client's disconnect, drained for an update, stopped after thirty idle minutes. Accounts are directories the environment adopts or owns, signed in by the environment itself with the SDK's bundled binary. Transcripts reach any account's process through the SDK session store, auto memory is one environment-owned directory per repository, and a trusted repository's own settings load. The completions surface keeps its OpenAI shape on the same port, authenticated by client-session tokens under their ceiling, and turns a caller's tools into real tool-call round trips, so Hermes runs its own tools again.

## Implementation Decisions

Every rule cites its decision; a rule marked chosen default was left open by the tickets and is listed again under Further Notes.

### Modules and ownership

- The **contracts package** gains the transcript event vocabulary and the per-session snapshot shape; the `runs`, `accounts`, `models`, `commands` and `providers` registry entries with scopes; the account, plan-usage, model catalogue, sign-in state and completions schemas; the settings keys below. The three types the audit found in the IPC file (run suggestion, send response, delegated-work row) land here as transport-neutral schemas (ticket 28).
- The **environment package** gains the **adapter host** (adapter registry, provider-process pool, permission broker, tool-server factory, the instruction composer's seam, the SDK session store, the account store, the sign-in director) and the **Claude adapter**, split along the seams the audit named (ADR 0015): options, process, turn, mapper (pure), history, titles, the config-directory queue (serialising the SDK's standalone helpers, which read the config directory from the process environment), plan usage and sign-in. The **completions surface** is a module of the same package on the same port as the WebSocket.
- The contract is an in-process interface of live objects, as in Artemis; it never crosses the wire. The vocabulary and the methods below do.

### The adapter contract

An adapter provides (ADR 0015, ticket 28):

- **A capabilities descriptor**, static: interactive prompts, partial messages, a provider queue (`providerQueue`: the provider holds messages sent during a turn; absent, the environment holds them and reads them when the turn ends, ADR 0022), mid-run steering (the provider folds a queued message into the running turn; presupposes `providerQueue`), resume, fork, rewind, session listing, subagents and their transcripts, provider titles (read and write), transcript delete, plan usage, live model listing, commands listing, image and file input, a live mode change (`modeChange`: a running run's `setMode`, permissions spec), the instruction channel kind (`system-prompt-append`, `developer-instructions`, `prompt`, none) with its character cap, and the modes it maps, each available or not with the reason. Every optional method pairs with a flag; the host refuses a call the flag does not cover with `invalid_params`, `data.reason` `unsupported` and the missing flag named in `data.capability` (the environment spec's error union has no `invalid_request`; Further Notes).
- **A credential spec**: the config-directory variable, the credential variables it strips and never sets (ADR 0018's three plus `IS_SANDBOX` and `CLAUDE_CODE_BUBBLEWRAP` from the permissions spec: five), the sign-in, status and logout argv, and a parser from status output to `{signedIn, authMethod, email, orgName, subscriptionType, error}`. A run's environment is the host environment with the provider's credential, backend-selection and storage variables scrubbed (by family: see the #121 notes below) and the account's directory variable layered on top (Artemis's composer, ported and widened).
- **`createRun`**, taking a resolved input (session and run ids, account directory, workspace and repository identity, model, effort, mode, the composed instruction text, the resume, fork or rewind target, the factory's tool servers, the trust decision, the prompt with attachments) and returning a run: an event stream consumed once, lossless, ending with exactly one end event on every exit path; `send` (steer or queue, with a message id), `withdraw` (a queued message by id, through the provider's cancel-by-id control), `interrupt` (with cancel: the result names the message ids the provider still held, which the host re-owns into the environment's queue, ADR 0022), `answerPrompt`, `stopTask`, `dispose`, `release`. The host is the only consumer and appends each event through the scoped append function and nothing else.
- **Sessions**: list, resume, fork, rewind, read a subagent transcript, delete a transcript; **titles**: read the generated title, write a user title. **Plan usage** per window with an **account identity** (provider plus email, and organisation when present), so the client runtime pools by identity (ADR 0005, ADR 0018). **Models** with a family and an ordinal tier the adapter supplies plus effort levels, a live listing flagged `live` when the provider can enumerate, else the static list flagged as such. **Commands** for an account and workspace, without spending tokens. **An adoption hook** for turns the provider opens on its own; the host registers them as runs of the same session (ticket 28).

The host supplies the scoped **append**; the **tool-server factory** (per run, closing over account, workspace and session: memory tools, browser, the completions surface's client-tool server); the **instruction composer** (ADR 0009: the four layers, a bot's persona, always-on skills and the orientation block of ADR 0011, composed once on the environment for every run origin; in phase A only a session's own instructions and the orientation block exist); the **permission broker**; the **process pool**.

### The transcript event vocabulary

Stream kind `session`, stream id the session id, the environment spec's envelope; every event of a run carries the run's id in its payload (`runId`) and as the envelope's `correlationId`, and the session's fork and rewind events carry none. Types the session-state spec flags `list` are marked.

- `run.started` (`list`): run id, account id and identity, model, effort, the clamped mode, workspace, origin (`client`, `routine`, `completions`, `provider`), prompt message id (and the queued message ids a read-now run carries, ADR 0022), resumed-from or forked-from.
- `message.sent`: message id, text, attachments (kind, name, media type, size; bytes staged on the environment, never in the log), delivery (`prompt` when the message starts a run, `queued` during a live one), for a queued one who holds it (`provider` or `environment`), and the ceiling of the connection that sent it; `message.delivered` when a queued message is read, with delivery `steered` (folded into the running turn) or `prompt` (a turn opened with it) (ADR 0022); `message.withdrawn` when one is taken back (its text goes to the session's draft, a session field); `message.requeued` whenever a message comes back to the environment's queue (ADR 0022: nothing is lost): what the provider still held when an interrupt or any end but the adapter's own completion cut its run, a message the provider refused to take, what a provider-opened turn was to read when the host does not adopt it, and every message a run was launched with when its adapter never received them (its creation failed); always the host's (`system:adapter-host`), and the next start reads them first, in the order they were sent.
- `assistant.delta`: a batch of text or thinking fragments for the open item, flushed every 100 milliseconds or 512 bytes (chosen default); `assistant.text` and `assistant.thinking` close the item, with `aborted: true` when an interrupt cut it short so the partial text stays in the snapshot (ADR 0022). Deltas are ordinary events; the snapshot holds settled items only and a client applies deltas to the open item.
- `tool.started` (tool call id, name, input, agent id and parent call when nested, title), `tool.updated`, `tool.ended` (status `ok`, `error` or `cancelled`, output, duration); `command.ran` for a slash command.
- `prompt.raised` (`list`): prompt id, kind (`tool`, `plan`, `question`), tool call id, the provider's payload, the mode at the time; `prompt.answered` (`list`): decision and who answered (a client session, the unattended rule, the denylist, the TTL sweep; a routine's prompts are answered by the unattended rule). The permissions workstream owns the decision vocabulary, the TTL and the denylist; this one owns the events and the broker.
- `tasks.changed`: the delegated-work ledger as rows. `usage.reported`: tokens, cost, context window per model; `plan.limit`: a rate-limit verdict with window and reset.
- `session.provider-linked` (the provider's session id, on first init), `session.forked` (with the anchor message id when the fork took one), `session.rewound` (to a user message id; later items stay in the log and the projection hides them), `session.rewind-undone` (only before a run starts on the rewound session; afterwards the cut branch stays hidden under a fold, ADR 0022).
- `run.ended` (`list`): reason (`completed`, `error`, `interrupted`, `disposed`, `drained`), cause on `interrupted` (`user`: a person's `runs.interrupt`, or an interrupt the host made that failed; `read-now`: the interrupt of `runs.readNow`; `restart`: the recovery sweep's end for a run a restart cut, #120; `parked`: a process stopped while its run was parked on a prompt, #120; null when an adapter ends a run interrupted on its own and names no cause), error, usage snapshot, duration, turn count, result text.

The **snapshot** carries `{sequence, summary, runs, items, parkedPrompts}` (`parkedPrompts` after the session-state spec's "parked" naming, conflict X4): items are user messages, assistant text and thinking, tool calls with updates folded, prompts with state, plans, commands and subagent rows; an unknown kind is opaque (ADR 0001). Subagent transcripts are read on demand, not logged (chosen default).

### Wire methods

Scope `runs:drive` unless stated; every mutating method takes a `commandId`.

- `runs.start`: session id, text, attachments, optional model, effort and mode; account, workspace and defaults come from the session (session-state's `sessions.create` delegates account, model and mode validation to this module). The mode is clamped to the connection's ceiling and the clamp recorded on `run.started` (ADR 0006). `unavailable` while draining; `conflict` reason `run_active` (send is the way in) or `account_unavailable`.
- `runs.send` (on a live run the message is queued and the result says where it is held, `provider` or `environment`; whether it is later steered into the turn or delivered at its end is reported by events, never at send time; on an adapter without `providerQueue` the environment holds it and starts the next run with the queue when the turn ends), `runs.readNow` (session id: interrupt with cancel, re-own what the provider still held, start the next run with the whole queue in order), `runs.withdraw` (message id: cancelled at the provider where it holds it, else removed from the environment's queue; `not_found` once read), `runs.interrupt` (re-owns the provider's still-queued messages into the environment's queue, never drops one; idempotent on an ended run: a no-op that re-owns nothing) and `runs.stopTask` (idempotent on a finished task). ADR 0022. `runs.answerPrompt` (prompt id, decision): the first answer settles the prompt; any later answer, on a live or an ended run, is `conflict` reason `already_answered`; an unknown id is `not_found`.
- `sessions.fork` (scope `sessions:write`): source id, client-minted new id, optional `atMessageId` (a user message: the fork holds history up to but excluding it and its text becomes the new session's draft; without it the whole session), optional account id and title; creates the record through session-state, carrying the source's title until the provider's summary replaces it, its tags, group and workspace (never archive, pins or settle), and marks the first run a fork; allowed while the source runs (ADR 0022). Forking onto another account is the hand-off on one environment (ADR 0015); across environments is milestone 2. `sessions.rewind` (session id, user message id; scope `runs:drive`, a chosen default, since it changes what the next run does rather than a summary field), recorded as `session.rewound`; `conflict` reason `run_active` while a run is live; a rewind to the first message is refused with `use_new_session` and the client starts a new session with the text as draft; files are never restored. `sessions.undoRewind` (session id; `runs:drive`) until a run starts on the rewound session, recorded as `session.rewind-undone` (ADR 0022). `sessions.subagentTranscript` (scope `read`).
- Scope `read`: `accounts.list`, `accounts.probe` (the ambient directory: present, signed in, identity), `accounts.signin.get`, `accounts.usage`, `accounts.handoff.recommend` (the ported threshold, load and recommendation functions over cached readings, so every client shows one offer), `accounts.refresh`, `models.list`, `commands.list` (account, workspace), `providers.list`.
- Scope `admin`: `accounts.adopt`, `accounts.add` (label; creates an owned directory and starts a sign-in), `accounts.relabel`, `accounts.remove` (with `deleteDirectory`, refused on an adopted account), `accounts.signin.start`, `accounts.signin.code`, `accounts.signin.cancel`, `providers.processes.list`, `providers.processes.stop` (chosen default).
- Settings keys through session-state's `settings.get` and `settings.update`: `accounts.defaultAccount`, `accounts.defaultModelFamily`, `accounts.defaultEffort` (ADR 0018; preset by the Account step to the highest tier at `high`), `providers.processIdleMinutes` (preset 30, ADR 0015); all four under the Account step's registry entry (ADR 0016).
- Notices on `environment.subscribe`: `account.updated`, `signin.updated`, `usage.updated`; the client runtime refreshes its request cache on them.

### Environment-owned provider processes

One Claude process per session, owned by the pool (ADR 0015). States: `starting`, `idle` (no turn), `busy` (a turn running), `parked` (a turn waiting on a raised prompt), `stopping`, `stopped`. The first `runs.start` on a session starts it, the next reuses it, a client disconnect changes nothing (ADR 0006). It stops when idle for `providers.processIdleMinutes` with no held work (a live background task or a registered schedule holds it, Artemis's retention rule), on `session.deleted`, on `providers.processes.stop`, or on drain. A process parked for the same idle time is stopped too: its run ends `interrupted` with cause `parked`, the prompt stays raised, and an answer later takes the resume path below (chosen default). On drain the host refuses `runs.start`, lets running turns finish up to the cap ADR 0007 sets, stops every process and reports to the launcher; a run cut by the cap ends `drained`. On startup a recovery sweep appends `run.ended` (`interrupted`, cause `restart`) for any run without an end event; its prompts stay raised (ADR 0007) and an answer given later starts a run that resumes the session and delivers the decision (Further Notes, item 7). Cold start after a stop is by store resume; no pre-warmed process in phase A (chosen default).

### The Claude adapter, ported after the audit's fixes

- **SDK and binary**: the pinned Agent SDK (0.3.280 or later; the store needs 0.3.234) with its bundled Claude Code binary, which also runs sign-in and status. The user's own `claude` is never spawned for runs.
- **Options per run**: workspace as `cwd`, `projectConfigRoot` for a worktree's checkout; model, effort; `permissionMode` from the harness mode (same names; bypass with the SDK's explicit allow flag); the `claude_code` preset with the composed instruction text as `append` (ADR 0009); `settingSources` `['project']` when the repository passed the trust gate, `[]` otherwise, never `user` or `local` (ADR 0009, ADR 0015; excluding `local` is a chosen default, so the CLI's own permanent approvals never leak in); `strictMcpConfig` on, so only the factory's servers load; `plugins` with the account's skill-set plugin directory (ticket 89); `settings` carrying `autoMemoryDirectory`; `sessionStore` always, with `resume`, `forkSession` or `resumeSessionAt` as the run asks; partial messages on; `canUseTool` wired to the broker; `CLAUDE_CODE_PROJECT_DIR_NAME` set to the harness session id so a resume never depends on the working directory; the bundled executable path.
- **Mapper**: Artemis's pure translation, extended for the vocabulary, with deltas batched. **Process**: Artemis's prompt pump, permission table, task ledger and settle grace, moved into the pool's process object; the turn is the run.
- **The unsampled queries** (models, commands, plan usage) keep no transcript (`persistSession: false`); only the commands listing loads the account's plugins, and a trusted repository's project settings.
- **Plan usage**: a control-channel read on an unsampled query under the account's directory, through a tolerant lookup over `usage`, `getUsage` and the experimental name, degrading to unavailable on a rename and re-checked against the pinned SDK before build; in-flight reads shared; readings aged out after six minutes (Artemis's number); `plan.limit` verdicts fold in. Every reading carries the identity.
- **Titles**: a user title is mirrored through the SDK's rename after commit, best-effort (session-state spec); the generated title is reported after a run ends when the store-backed listing exposes it (verify first), else no provider title in phase A. **Identity**: from `auth status --json` after sign-in and on each status read; the run's `accountInfo` cross-checks it, and a mismatch is recorded as `account.updated` with a warning. **Modes**: `acceptEdits`, `plan`, `auto`, `bypassPermissions`; `default` and `dontAsk` are not offered (ADR 0006). Containment is passed when the permissions workstream sets it.

### Queue, read-now, fork and rewind on the Claude adapter (ADR 0022)

Claude declares `providerQueue`, `fork` and `rewind`. A mid-run `send` pushes an `SDKUserMessage` with the harness message id as its `uuid` onto the streaming input, as Artemis does; delivery is observed from the CLI's echo (`user_message_uuids` on the turn's first reply) and reported `steered` when it lands inside the running turn, `delivered` when a queued turn opens with it. `interrupt` sends the SDK's interrupt with `cancel_queued`, and the ids it reports still queued are re-owned by the host as `message.requeued`; a turn the provider opens on its own is still adopted through the adoption hook, but after ADR 0022 the host never expects one from an interrupt. `withdraw` uses the cancel-by-id control (`cancel_async_message`); if the provider reports the message already consumed the call is `not_found`. Read-now's next run passes the queue as the run's prompt messages in order. A fork resumes the source's provider session with `forkSession` and, when an anchor is given, `resumeSessionAt` set to the entry before the anchored prompt; the fork's provider ids are its own (the SDK remaps them). A rewind resolves `resumeSessionAt` to the entry before the user message and `resumeDropsTurn` when everything after it belongs to that one turn, as Artemis's `resolveRewindPoint` does; the SDK's file checkpointing is never enabled, since it cannot be combined with the session store. The build session verifies the cancel-by-id control and the interrupt's still-queued report on the pinned SDK before either is relied on; absent, `providerQueue` is declared false and the environment holds the queue for Claude too.

### The account store

Stream kind `account`: `account.adopted`, `account.added` (a directory under the environment's data directory), `account.identity-set`, `account.status-changed` (signed in, signed out, expired, unreadable; appended only on change), `account.relabelled`, `account.removed`, `account.directory-deleted` (owned directories, on the explicit second choice). Record: id, provider, label (preset to the email, unique per environment ignoring case), directory kind (`adopted`, `owned`) and path, identity, status with checked-at, created-at. One account per identity per environment: a sign-in yielding an identity already held is refused with "already added as <label>" and the new owned directory is deleted (ADR 0018). Status is re-read when the Account step or Accounts pane opens and at most every fifteen minutes otherwise, and carried into the orientation block (ADR 0011).

### Sign-in and status through the bundled binary

The **sign-in director** runs one sign-in per environment (ADR 0018): `accounts.signin.start` spawns the bundled binary with `auth login`, `CLAUDE_CONFIG_DIR` at the account's directory and the five stripped variables (and the scrubbed families) absent, stdin a pipe, stdout read incrementally. States: `starting`, `awaiting-code` (the verification URL published as `signin.updated`), `submitting`, then `done`, `failed`, `expired` (ten minutes) or `cancelled`. `accounts.signin.code` writes the code from any client; a second start is refused naming the account that has the floor; `done` triggers a status read and `account.identity-set`. The exact fallback command (POSIX and PowerShell renderings, the directory quoted) is part of the sign-in state, so every client shows it. Subscription only: `--console` is never passed; a Console user runs the fallback with it (ADR 0018). If the bundled binary does not run `auth login`, the managed tool `claude` is the fallback executable, chosen once per environment and recorded.

### The SDK session store and auto memory

The environment implements the SDK's `SessionStore`: `append`, `load`, `listSessions`, `listSessionSummaries` (folded with the SDK's helper inside `append`, serialised per session), `delete` (cascading to subkeys and the summary), `listSubkeys`. Entries are opaque provider state, so they are not events: they live in a `provider_transcripts` table beside the log, keyed by the harness session id, purged with the session's tombstone. This is the chosen reading of "over the environment's log": the log holds the events clients read; the store holds the entries the provider reads back. Every run passes the store; from a session's second run onward the run resumes from the store, which is then the durable copy, and the SDK deletes the temporary directory it ran in; a fresh session's first transcript file stays in the account's directory, written by the CLI as it always does. Resume on another account works because the SDK seeds that temporary directory with the credentials of the directory the run names, which ADR 0018 relies on and the build session verifies first. **Auto memory**: one directory per repository under the environment's data directory, keyed by repository identity (else the workspace path), passed through `settings`, shared by every account (ADR 0018); the Carry over step copies an adopted directory's per-repository memory into it (ticket 51).

### The permission broker

`canUseTool` hands each request to the broker, which appends `prompt.raised`, holds the deferred answer, and settles it on the first `runs.answerPrompt` from any client session with `runs:drive`, on the unattended rule, on a denylist match, or on the TTL sweep, appending `prompt.answered` with who answered (ADR 0006). Plan approvals and questions are prompts of kind `plan` and `question` on the same path. Dispose of a process denies every prompt it holds in memory but leaves a raised prompt raised in the log (ADR 0007); a later answer is `conflict` reason `already_answered` only once `prompt.answered` exists.

### The completions surface

Kept for programs (ADR 0015, ticket 29), on the same port as the wire.

- **Routes**: `POST /v1/chat/completions`, `GET /v1/models`, `GET /v1/models/{id}`; other OpenAI paths answer `501` with a sentence.
- **Authentication**: `Authorization: Bearer <client session token>` from a pairing of client kind `program` (added to the environment spec's kinds; chosen default) with scopes `read`, `sessions:write`, `runs:drive` and a ceiling set at pairing. `401` unauthorized, `403` scope, `503` draining.
- **Model ids**: `<account label slug>/<model or family>`, the slug slash-free; `GET /v1/models/{id}` matches the rest of the path, so an id from the listing is fetched as is; a bare id resolves to the default account; `/v1/models` lists every signed-in account's catalogue with `agent-harness.account`, `family` and `tier` beside each id.
- **The extension namespace** is `agent-harness` (the ADR 0017 placeholder rename), with `artemis` accepted as an alias until the switch-over ends, the namespaced key winning when both are present (ticket 29). Fields: `sessionId`, `permissionMode`, `systemPrompt` (append-only, 200,000 characters, after the environment's composed instructions), `alwaysOnSkills` (accepted and reported as ignored on the first chunk until ticket 89 lands, then honoured through the skill set), `forkSession`, `rewindToMessageId`, `attachments`, `thinking` (effort; `reasoning_effort` is its alias), `workspace` (a directory the environment has, else a scratch workspace per session), `attended` (default false), `after`, `ignoreUnsupported`. Browser fields return with the browser workstream.
- **`permissionMode`** is clamped to the connection's ceiling and the clamp reported as `agent-harness.clamped` on the first chunk (ADR 0006). **Prompts**: a completions run is unattended unless `attended: true`, so prompts are answered by the unattended rule and recorded, never parked (ADR 0006); with `attended`, they park and any client answers.
- **Messages**: the trailing user message is the turn; system and developer messages append after the composed instructions; earlier messages ride as an "earlier in this conversation" preamble on a fresh session and are dropped on a resumed one (Artemis's rule). No session id means a fresh session; the response carries the session id in the namespace.
- **Client-tool passthrough** (ADR 0015): a caller's `tools` become an in-process SDK MCP server named `client` for that run, one tool per declared function with its schema. When the model calls one, the surface emits an OpenAI `tool_calls` delta (ids minted by the environment, names without the server prefix), ends the stream with `finish_reason: tool_calls`, and parks the handler. The follow-up request's `tool` messages are matched to parked handlers by `tool_call_id` regardless of session id, so Hermes's loop works unchanged; the handlers resolve and the same turn streams on. A parked handler expires after ten minutes (chosen default) with an error result to the model. `tool_choice: none` withholds the tools; `required` and a named choice are rejected, or ignored under `ignoreUnsupported`. The agent's own tools never appear as `tool_calls`; they ride `agent-harness.activity` on empty-delta chunks, as in Artemis.
- **Streaming**: OpenAI's chunk order; every chunk carries `agent-harness.seq`, the log sequence of the event it renders; an SSE comment every fifteen seconds while quiet (Artemis's pacing); a mid-stream failure is a final chunk, never a bare close. A disconnect does not interrupt the run (ADR 0006); a later request naming a session whose run is going attaches from `after` and its trailing message is a steer.
- **Parameters**: `max_tokens`, `stop`, `stream`, `stream_options` honoured; `response_format`, `temperature`, `top_p`, `seed`, `n`, `logprobs`, the penalties and `logit_bias` rejected with `400` unless `ignoreUnsupported`; `user`, `metadata`, `store`, `service_tier`, `parallel_tool_calls` ignored and reported (Artemis's policy).
- **Non-streaming** returns the whole message, with `tool_calls` when parked and `usage` from `usage.reported`. Every turn is an ordinary run on an ordinary session: logged, listed, tagged `completions`, under the same ceilings, denylist and instructions.

Decided in building the adapter contract, the host and the run methods (#119):

- **The run's stream is its session's** (ADR 0015 reconciled with #118): ADR 0015 and user story 22 speak of an append scoped to the run's stream, but the purge (#118) removes a session by removing its stream's events, so a transcript on a stream of its own would outlive the purge or need a second one. The transcript therefore lives on the session's stream, and the host's scoped append is scoped to one run of one session: it appends to the session's stream only, stamps the run's id into the payload (`runId`) and the envelope's `correlationId`, checks each event against its payload schema, and takes only the types an adapter reports (`message.delivered`, `assistant.*`, `tool.*`, `command.ran`, `tasks.changed`, `usage.reported`, `plan.limit`, `session.provider-linked`). `run.started`, `run.ended`, `message.sent` and `message.requeued` are the host's, appended with the run's id. `session.forked` and `session.rewound` belong to no run and carry no run id, so they cannot pass the scoped append: the host appends them to the session's stream on the `sessions.fork` and `sessions.rewind` commands, which #137 builds. The adapter's actor is `adapter:<provider>`; the host's own ends, every `message.requeued` and the runs it starts from the queue are `system:adapter-host`.
- **`invalid_request` is `invalid_params`**: a call the descriptor's flags do not cover (plan usage, commands, a task stop without `subagents`, on a live or an ended run, an image or file the adapter does not take, a transcript delete) is the union's `invalid_params`, with an issue at the param that asked and `data` `{reason: "unsupported", capability, provider}`, so a client tells it from a malformed request and degrades absent-with-reason. No method-own member is added. The purge reads the same reason as the tombstone's `unsupported`, which is also what it records when the session's provider is not known on the environment.
- **One `run.ended` per run on every path**: the host appends it for the adapter's end event; and itself, as `error`, when the stream throws, stops without an end (code `no_end`), reports an event its schema refuses, or `createRun` throws (one microtask later, so a run launched after its command's commit is heard ending after the command's events); as `interrupted` (cause `user`) when the adapter's interrupt fails; as `disposed` when the session is deleted or the environment closes; as `drained` when the environment closes while draining (the drain's cap); as `interrupted` with cause `parked` when its process has been parked for the idle time, and with cause `user`, recorded as the admin's, when `providers.processes.stop` stops its process (#120). A run the host ends is disposed, never released, since its stream may still be open; whatever it yields after its end is dropped. Cause `user` says a person ended the run, and the host alone sets it, on two paths: the run was interrupted (`runs.interrupt`), when its end carries `user` whatever cause the adapter named, recorded as the adapter's, or as the host's own when the interrupt failed; or an admin stopped its process (`providers.processes.stop`), recorded as the admin's. Otherwise an adapter's own `interrupted` end names its cause, or none, and the host's own name theirs: `parked` for the parked stop, `restart` for the recovery sweep. If the end cannot be appended, the host tries once more; if that fails too, the run is over here all the same (let go, ended in the run registry, no longer the session's live run, so a new start is taken), the failure is logged loudly, and `runs.interrupt` on it answers `ended: true` with `unrecorded: true`; the log's missing end, and any message its provider still held, are the recovery sweep's (#120) at the next start. A provider-opened turn the host is asked to adopt for a session deleted since is not adopted: it is disposed and what it was to read is taken back.
- **The send, per ADR 0022**: `runs.send` answers `{runId, messageId, delivery, heldBy}` with delivery `prompt` (no run was live; it started one) or `queued` (held by the provider when the adapter declares `providerQueue`, else by the environment); a steer is reported only by `message.delivered`. The environment's queue starts the next run when a run completes or fails, never after an interrupt. **Nothing is lost**: whenever a run ends other than by its adapter completing it (whose provider reads what it holds in a turn of its own, adopted), the messages its provider still held come back to the environment's queue as `message.requeued`, in the transaction of the `run.ended` and just before it, so a client that starts a run on seeing the end finds them queued; the same happens to what an interrupt reports still queued, to a message the provider refused to take, and to what a provider-opened turn was to read when the host will not adopt it (a drain, the environment closing, the session deleted). A run whose adapter never received its input (a seam, the adapter lookup or `createRun` threw) has every message it was launched with queued again, bytes and all, and no run starts on its own after it, so a failing adapter cannot loop: the next start reads them. The runs projector keeps every message sent (`read` once a run has it) so such a message can be queued again. A message's attachment bytes are kept, whoever holds it, until a run reads it (a steered message on its `message.delivered`): in memory and staged on disk under the data directory, so a restart keeps them (#185's notes below); a deleted session's are kept for a restore and removed when it is purged. `message.requeued` is in the vocabulary now; `message.withdrawn`, `runs.readNow`, `runs.withdraw` and `session.rewind-undone` are left to the tickets that build those verbs.
- **A queued message carries its sender's ceiling**: `message.sent` records the ceiling of the connection that sent it, and a run that reads queued messages has its mode clamped to the ceiling of whoever started it and to each queued sender's, so a run of the environment's queue is never above the lowest of them (the clamp is #129's policy resolver).
- **Commit hooks and delivery order**: the log delivers what a commit hook appends after the events of the transaction that committed (the same change #117 makes), so the host's work after a command's commit (a launch, a requeue) is never heard before the command's own events.
- **`runs.interrupt` and `runs.stopTask`** answer `{runId, ended}` (and `taskId`; and `unrecorded: true` on an interrupted run whose end the log could not take): on an ended run, or a settled task, the command is accepted with no event and `ended: true`. An attachment is standard padded base64, at most `MAX_ATTACHMENT_BYTES` (20 MiB) decoded; the export publishes the grammar as one pattern, while the environment checks it as a flat pattern plus the length rules, since the grammar's repeated group overflows a backtracking engine's stack on a 20 MiB string. A run command on a deleted session is `not_found` kind `session`; on a purged session's run, kind `run`.
- **The snapshot's transcript part is folded on read**: `runs`, the settled `items` and the `parkedPrompts` are folded from the session's stream when a snapshot is sent, reading every event but `assistant.delta` (the settled text carries it whole), rather than kept as a table; the `runs` table beside it (with the environment's queue and the delegated-work rows) is what the run methods decide on. The fold is not bounded for a live session: compaction (#123) folds only sessions long left untouched (ADR 0002), and a compacted session's fold goes on from its compaction's snapshot. An event of a type the environment does not know becomes an item of kind `opaque` naming its type; the item schema keeps any unknown kind as it is, and holds a known kind to its own schema (the opaque kind's pattern excludes the known ones).
- **Transcript compaction** (#123, the environment spec's Further Notes): the transcript vocabulary is what compaction may fold, but it removes only what no projector reads, the assistant's items, tool calls, commands, usage and plan limits and all but each run's last `tasks.changed`; `run.started`, `run.ended` and the `message.*` events stay for the projectors, and `session.provider-linked`, `session.forked` and `session.rewound` stay as session events (the resume id, the fork's origin, the rewind a fold reads), though they remain in the vocabulary's table. The fold going on from a compaction's snapshot differs from folding every event only for an event aimed at an item a rewind hid before the fold (it is not in the fold to update, and stays hidden either way); `session.rewind-undone` (#137) must bring back items a compaction folded while hidden, which the fold as stored does not keep, and ADR 0022 keeps a cut branch in the log as rewound, shown under a fold, whose transcript events a compaction removes; so #137 either stores the hidden items with the fold or leaves a rewound session uncompacted. No path appends `session.rewound` before #137.
- **The run registry** (#112) is filled by the host: a run is `starting` from its command's commit, `running` from its first event, `ended` with its end; `admit` gates `runs.start` and a `runs.send` that would start a run, so a message for a live run is taken while draining. `activeRuns()` lists the live ones. An account's status and model probes give up after five seconds, so a hung probe cannot hang startup.
- **Seams and presets**: the mode clamp `(requested, ceiling) => {mode, clamped}` was the identity until #129, which replaced it with the policy seam (`{actor, requested, accountModes} => policy`, the permissions spec's resolver, where the actor carries the ceiling the caller reduced to the lowest of its own and each queued sender's, and the settings are read inside) and `run.policy.resolved` after `run.started`, which records `{requested, effective, clamped}`; the descriptor's modes carry their availability and a `modeChange` flag pairs with a live run's `setMode` (permissions spec, Further Notes); the broker placeholder denies every prompt at once without recording it, until #130; the instruction composer joins the orientation block (empty until #91) and a session's own instructions; the tool-server factory builds none; `trusted` is false until #89; `sessions.create` delegates its account, model and mode to the host's `validateSessionInput` (the account on this environment, the model in its catalogue, the mode among its adapter's). Until the account store (#134), accounts are configuration: a run uses the session's account, else the environment's default (the first configured), and the session's model, else the catalogue's highest tier (since #134, the store's default account and the default family: its notes below); effort is the command's, else the model's own, since a session has no effort field. `prompt.opened` and `prompt.answered` are reserved and `runs.answerPrompt` is not registered (conflict X1); #130 corrects the `prompt.raised` bullet and the broker section.
- **Owed**: nothing of #119's. Built since: the startup recovery sweep for runs cut by a restart (#120) and the attachment bytes it keeps (#185), their notes below, and the run-start and run-end companion events (#122): every start and end, the recovery sweep's included, goes through the session module's `appendRunEvents` (session-state spec, #122's notes).
- Verify-first item 9 held: the environment spec's helper takes an injectable manual clock, the client kinds include `program`, and `sessions.create` delegates to this module.

Decided in building environment-owned provider processes (#120):

- **The process handle**: the contract gains `Adapter.stopProcess(sessionId, {kill?})`, required, and a `process` port on the run context: `hold` and `unhold` of a `task` or a `schedule` by a non-empty id (an empty id is logged and ignored), and `exited()` for a process that died on its own. The adapter keeps the provider's process keyed by session: `createRun` starts it when the session has none and reuses it otherwise, `release()` now means keep it for the next run, and `stopProcess` stops whichever process the session has at the call. The pool (`adapter/pool.ts`) keeps the environment's record of it and makes every stop. A port stays valid for the life of the process it was handed with, so a hold outlives the run that took it. Codex's per-home daemon (a pool entry keyed by home) is not modelled: phase A keys by session.
- **States and transitions**: `starting` from a cold run's begin to its first event; `busy`; `parked` while the session's live run has a prompt unanswered, entered from `starting` as from `busy` when the provider asks before its first event, its parked wait armed then; the first event on a parked process leaves it parked, and answering its last prompt makes it `busy`, whether or not an event came first; `idle` when a run its adapter ended is released; `stopping` from the stop until the adapter's `stopProcess` settles; `stopped`, listed for ten minutes and then dropped on a timer. A run the host ends itself (every `error` it records, a failed interrupt, `disposed`, `drained`, a parked stop, an admin stop) is disposed and its process stopped, for a reason the host must name, since after a dispose the provider's state is unknown: the next run starts cold, and a turn the stopped process opened meanwhile is not adopted but let go, what it opened with queued again. A process that exits on its own is recorded `stopped`, reason `exited`, with no `stopProcess`. The stop reasons are `idle`, `parked`, `deleted`, `admin`, `drain`, `closed`, `failed` and `exited`. A provider-opened turn the host lets go (its session deleted, the drain, the policy, a start the log would not take) is disposed and its process stopped the same way, for `deleted`, `drain` or `failed`, unless another run is live on it.
- **Parking follows the prompt, not the broker's promise**: the host hands a session's runs a broker that parks the session's run live when a request is made (a turn the provider opened on its own asks through the context of the run it followed, so it parks too), under the prompt's id, the adapter's own when it names one in the request or one the host mints, which the broker receives. The prompt is answered, and the run unparked once its last is, when the request settles or when the host answers it through `AdapterHost.answerPrompt(runId, promptId, decision)`, which hands the answer to the adapter's `answerPrompt` (`interactivePrompts`), whichever comes first. #130's answer method goes through `answerPrompt`; an answer given any other way must settle the request.
- **The idle time** counts from the end of the last turn or the release of the last hold, whichever is later. Each wait is one timer on the environment's clock, armed when it begins, rather than the minute sweep, so a stop falls on its instant and nothing wakes while nothing waits. The time is read from `providers.processIdleMinutes` as a wait begins, so a change applies to the waits that begin after it; a value outside 1 to 1,440 is logged and the preset used. The key is a row of the settings table (`ProcessIdleMinutes`, preset `PROCESS_IDLE_MINUTES_PRESET`, 30) under the Account step's registry entry, in its `default-model` band (ADR 0027's `accounts.default-model` row, which absorbs Artemis's Runs pane): the step-registry test demands a registered step for every key, so the entry is registered here writing this key alone, and #134 adds the default account, model family and effort to it. The environment reads the value from the settings store; a test may pass its own through the `processIdleMinutes` seam.
- **Who ends a parked run**: the pool's parked timer hands the session to the host, which ends the run `interrupted` with cause `parked` as its own end (`system:adapter-host`, the requeue rule applied) and stops the process with it; the pool stops the process itself only when the host finds no live run. No prompt event is appended, so the prompt stays raised in the log. The ten-minute rule stays the run registry's (#112), which the host now fills with parking too: a parked run counts as busy until ten minutes after it parked, while its process stays parked for the whole idle time.
- **An admin stop**: `providers.processes.stop` is a command on the session's stream that appends nothing of its own and answers `ended: true` when the session has no process running; a run live on the process ends `interrupted` with cause `user`, since a person stopped it, its `run.ended` recorded as the admin's client session under the command's id, and its prompts stay raised. A deleted or unknown session is `not_found` kind `session`, and the deleted-command sweep covers the method.
- **The drain**: as it begins, new runs are refused first and then the host stops every idle process with no held work; a busy one stops as its turn ends; a held one keeps its background work going through the drain's wait and stops when its last hold is let go or the environment closes. A parked run is not waited for (#112) and ends `drained` with any run the cap cut when the environment closes. Closing ends the live runs and waits for every stop under way, including that of a process a cold start has since replaced, for at most `PROCESS_STOP_TIMEOUT_MS` (ten seconds) on the environment's clock, then kills what is left through `stopProcess(sessionId, {kill: true})` and goes on. The event log closes after, and the launcher's channel last (#112): its closing is the report that every provider process has stopped or been killed after the timeout. No message was added to the channel.
- **The recovery sweep** (`adapter/recovery.ts`) runs first in the `adapter-host` startup step, before the host exists and so before the wire opens: every run the runs table holds as running gets, in one transaction, a `message.requeued` for each message its provider still held and then `run.ended` (`interrupted`, cause `restart`) as `system:adapter-host`, its duration measured to the restart on the environment's clock. A run whose end cannot be appended is logged loudly and left for the next start. Nothing answers its prompts. The queued messages' attachment bytes are read back from the stage on disk after it, in the same step (#185's notes below), so a message it hands back keeps them.
- **The prompt stays open**: no end the host appends answers a prompt. The wire tests park through a broker that records `prompt.opened` as #130's will, and read the prompt back from the snapshot after the parked stop and after the recovery sweep; the fold's own test shows a prompt staying parked across an `interrupted` end with cause `parked` or `restart`.
- `providers.list` answers `{providers}`, the adapters' descriptors; `providers.processes.list` answers `{processes}`, each with its state, live run, start, last busy instant, parking, holds, `stopsAt`, and its stop's instant and reason.
- **Owed by the Claude adapter (#121)** when it merges with this: implement `stopProcess` (stopping the session's process at the call, killing it at once with `kill`) and make `release()` keep the process for the next run rather than let it go; turn its own idle timer (`idleMs`) off, since the pool's idle stop replaces it; map its task ledger and schedule flag onto the port: a `hold("task", taskId)` per live background task and `unhold` as each settles (or, from a count, one level hold under a fixed synthetic id held while the count is above zero), and `hold("schedule", <its id or a fixed synthetic one>)` while the session has a schedule registered; call `exited()` when its process dies on its own (a transport failure, a refused dispose); and name its permission table's id as `promptId` in each broker request, so an answer through `answerPrompt` names the same prompt. *Done in #121's merge with this*: see the Claude adapter's notes below.

Decided in building the Claude adapter (#121):

- **What a Claude process inherits**: the environment is copied once, when the adapter is made, and every process is handed its account's directory explicitly (an account with none gets the ambient default, the host's `CLAUDE_CONFIG_DIR` else `~/.claude`, resolved once), so the config-directory queue's temporary write can never reach a composed environment. Stripped and never set: the five variables. Scrubbed besides: every `ANTHROPIC_*`, `CLAUDE_CODE_USE_*` and `CLAUDE_CODE_OAUTH_*`, every name holding `_TOKEN` or ending `_FILE_DESCRIPTOR` (a forge token included: runs reach forges through the harness's credential helper, ADR 0020), `CLAUDE_CODE_API_BASE_URL`, `CLAUDE_CODE_CUSTOM_OAUTH_URL`, the secure-storage directory, `CLAUDE_CODE_SIMPLE`, `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_PROJECT_DIR_NAME` (both set from the run). Kept: the numeric limits that only share the word token (`*_TOKENS`, the idle and resume token thresholds, the token-usage attachment and total-tokens reminders), which carry no credential; the SDK needs no `ANTHROPIC_*` variable for a subscription login, and sets what it needs itself (`CLAUDE_CODE_ENTRYPOINT`), beside the harness's `CLAUDE_AGENT_SDK_CLIENT_APP`.
- **Where it lives**: `packages/environment/src/adapters/claude/`, split along the audit's seams: `options.ts` (pure), `credentials.ts` (the spec, the scrub, the status parser and runner), `sign-in.ts` (the argv; the director is #135), `mapper.ts` (pure) with `delta-batcher.ts` and `tasks.ts` (the ledger), `process.ts` and `turn.ts`, `history.ts` (the rewind and fork points; replay is #137), `config-dir-queue.ts`, `plan-usage.ts`, `control-query.ts`, `models.ts`, `executable.ts`, `workspace.ts`, `index.ts` (the factory, provider id `claude`). `startEnvironment` registers it as the preset adapter, with auto memory under `<data dir>/auto-memory/`, one directory per repository identity (else workspace path), named by a slug and a hash. The SDK is pinned exactly at 0.3.281; every option the spec names exists under the spec's name (`projectConfigRoot` included, and passed only for a trusted repository: an untrusted one loads nothing of its project, from the branch or its checkout; a bare repository's worktree has no checkout and gets none), and the adapter also sets `permissionPrompts: 'host'` (permissions spec) and `extraArgs: {'thinking-display': 'summarized'}` (Artemis: an SDK-driven CLI otherwise sends every thinking block empty).
- **The process and the turn**: a turn is a run; the process holds the query, the prompt pump, the permission table, the ledger and the settle grace, and outlives its turns. Whose turn the CLI opened is read from the stream: the bundled CLI narrates (`msg_lifecycle_v1`) and stamps a turn's first reply with the uuids of the prompts it consumed, and every prompt is stamped with the harness's message id, so an `init` is held until a message names its owner; a turn naming a waiting run's prompt is that run's, any other is the provider's own and goes to the adoption hook with the sent messages it opened with. A spawn that started a conversation (`fresh`) takes its first turn as its run's whatever it names. The SDK omits the owners on a delivery-failure or zeroed result (and the synthetic assistant message a delivery failure writes): such a turn is the waiting run's when exactly one run waits and no queued message, settle, live task or scheduled job (whose firing is a turn with no message behind it) could be what the turn is about. A watchdog ends every waiting run `error` (code `not_opened`) when its prompt sits unopened for a minute while the CLI serves no turn, and when an `init` is followed by nothing for a minute (the init is dropped then, so it holds nothing busy), so no run pins a process for ever. A run sent to while it runs reports `message.delivered` `steered` when a reply names the message. A subagent's prompt arriving when no turn is open gets a turn of the provider's own to carry it, adopted like any; it is not the CLI's current turn, stays open across the CLI's own turns, and ends once its prompts are answered (or, interrupted, denies them); a message sent to it is refused, since no turn of the CLI's could read it and its interrupt could not take it back, so the environment holds it for the session's next run. The broker is asked once the host has adopted the turn and named its run, never with an empty run id. The host is told nothing new about ends: the result ends the turn through the mapper, and every process-side ending (transport failure, a prompt withdrawn from the CLI's queue, launch failure) goes through the same idempotent end.
- **Kept across turns, on the pool's port** (#120): `release()` keeps the process for the next run and the pool decides when it stops; the adapter's own idle timer is gone. `stopProcess(sessionId)` disposes the session's process and resolves once its pump has ended and its child exited; with `kill` it sends the child SIGKILL at once (the adapter spawns the CLI itself through the SDK's `spawnClaudeCodeProcess`, so it holds the child) and waits for nothing. What holds the process from the pool's idle stop goes through the run context's `process` port: `hold("task", taskId)` per live background task from the SDK's `background_tasks_changed` level and `unhold` as each leaves it; one `hold("schedule", "claude-schedules")` while a cron job (until `CronDelete` removes it) or a wakeup (until a turn of the provider's own with no message behind it opens) is registered, each counted when its tool call ends `ok` (a denied or failed one registers nothing), and the counts set from the CLI's own list of the session's jobs (`session_crons`, the only place the pinned SDK reports them) at each turn's Stop hook, so a one-shot job that fired or expired lets the hold go. A process that dies on its own (a transport failure, a launch that failed, a run interrupted before anything spawned, an interrupt that forced it down) lets its holds go and calls `exited()`; one the pool stops does not. `onClosed`, the adapter's forgetting of a process, runs on every close, so twice for a disposed process whose pump ends later: it forgets only the process it names, so a replacement is never lost. While it is kept, the conversation's next run attaches to it (same account directory, trust and tool servers, resuming its provider session, not asking for a bypass the spawn lacked), moved onto the run's model, mode and effort through the SDK's setters, each under a timeout. A run it cannot serve lets a process held only by a schedule or a grace go and spawns fresh, handing the fresh process the queued messages the old one never opened a turn with; a turn open or waiting, a parked prompt or a live task refuses the run instead. Queued ids are kept after a turn ends, so a turn opening later still reports reading them.
- **Contract extensions**: `Adapter.commands` takes `{trusted}` (a trusted repository's commands load with its project settings; the host passes nothing until #89); `PromptRequest.signal` (aborted when the provider withdraws the tool call: the host's wrapped broker counts the prompt answered then, at once for a signal aborted before the request, and once per request, so the run is unparked and a later prompt reusing the id stays parked; each request also names the permission table's id as `promptId`, so an answer through `AdapterHost.answerPrompt` settles the same tool call); `ProviderTurn.onAdopted(runId)` (the host tells an adopted turn its run id once the run is registered, so a prompt it asks at once parks it, and never tells a turn it lets go; a subagent's prompt turn asks the broker only once it has one); `UsageReading.unavailableReason` (a reading with no windows says why) and `UsageWindow.verdict` (a folded `plan.limit`). `Adapter.stopProcess` is #120's, with `kill`; the adapter's own `close` and the host's `session.deleted` call are gone, the pool's stops replacing them.
- **The interrupt**: the pinned SDK's `interrupt` takes `{cancelQueued: true}` at run time (its declarations omit the argument, as they omit `cancelAsyncMessage`) and answers `{still_queued, cancelled}`: the interrupt withdraws everything the CLI still holds in the same request, so no queued message can run as the next turn before the host takes it back (ADR 0022: interrupt re-owns the queue and starts nothing). The ids in `cancelled` that this process sent go back to the host as still queued, whichever run they were sent during, since the CLI's queue is the process's (a message a replaced process handed on is among them): the host takes back each the provider holds for the session, under the run it was sent during; ids the CLI queued itself are ignored. Both undeclared controls are detected once per process (the method's arity and presence, and `interrupt_cancel_queued_v1` on `init`), a missing one said once as a diagnostic, and a test holds a real `query()` to having them; without the cancel, the adapter falls back to the plain interrupt and the one-by-one `cancelAsyncMessage`, which can lose the race. A run whose prompt the CLI has not opened is withdrawn by id, together with what was sent onto it or handed on at its spawn (reported still queued, so the host takes them back and the CLI never runs them), and ends there; if it cannot be withdrawn it is marked and interrupted when the CLI opens it, never by stopping the turn the CLI runs ahead of it. `providerQueue` and `steering` are declared on that footing (the bundled 2.1.281 advertises `interrupt_receipt_v1` and `interrupt_cancel_queued_v1`).
- **The config-directory queue is one per process, not one per directory**: the helpers read `CLAUDE_CONFIG_DIR` from `process.env` at call time and after their awaits, so two helpers on two directories running together would read each other's; calls run one at a time, each answered within thirty seconds of being asked or refused, and the variable is restored after each. The pinned SDK's helpers take no abort signal, so a helper refused for its time may still run and read the variable after its awaits: its directory stays installed, and the queue waits, until it settles; a call whose time runs out while it waits is refused and never runs.
- **The unsampled queries** (models, commands, plan usage) keep no transcript (`persistSession: false`); only the commands listing loads the account's plugins, and a trusted repository's project settings.
- **Plan usage**: keyed by the account's directory (one account per identity, ADR 0018); the identity from `accountInfo()` on the same unsampled query, else the status command; a reading that failed is not kept; a verdict with no reading to fold into is dropped, since the next read is newer, and one that arrives while a read is in flight is folded into that read's reading, which began before it. The usage method is called with `skipBehaviors: true`.
- **An answer that reaches no tool call is refused, not dropped**: the adapter denies its run's parked prompts itself as the run ends, however it ends (the Claude adapter at a turn's end, a transport failure, a dispose), since the host refuses an answer for a run no longer live without asking it; the adapter's `answerPrompt` throws `PromptClosed` (reason `run_ended` when the prompt's run has ended, whose tool call it then denies rather than let run; `not_open` when it holds no such prompt), and `AdapterHost.answerPrompt` refuses the answer `conflict` with reason `run_ended` when the run is no longer live (checked first), or `prompt_not_open` when the live run has not raised the prompt or it is answered already (the host's own record, whatever the adapter would say), or the adapter holds it no longer, thrown when the adapter answers at once and as the rejection of the promise it returns when the adapter answers asynchronously (any other failure of the adapter's is logged and refused `internal`, the same both ways), so #130's answer method can say so and deliver a prompt kept open across a run's end another way.
- **Images** go to the CLI labelled with their own media type, which must be one the SDK's image block takes (`image/jpeg`, `image/png`, `image/gif`, `image/webp`); another is refused before anything spawns, or when sent.
- **Declared false for now**: file attachments (Artemis stages them; not ported), session listing, subagent transcripts, titles and transcript delete (#137, #122).
- **Modes** (#129's mapping): each of the four modes is the SDK `permissionMode` of its name, every one listed available; `allowDangerouslySkipPermissions` is set when the run's ceiling is `bypassPermissions`, whatever its mode, and a kept process serves a run under a bypass ceiling only when it was spawned with the opt-in, so a later change to bypass is refused by the provider as well as clamped below that ceiling. `modeChange` is declared: a live run's `setMode` (the host's, already clamped to the run's ceiling) calls the SDK's `setPermissionMode` under the control timeout, which moves the CLI's every later turn too, since the process has one mode; made before the spawn, it is the mode the spawn takes; bypass on a process spawned without the opt-in, and a change on an ended run, are refused; a timeout leaves the mode as it was recorded, and the host logs it.
- **Deviations, each with its follow-up**:
  - Unknown SDK message types, and known ones the vocabulary has no event for (`compact_boundary` among them), are dropped: ADR 0001 is about a reader keeping an unknown kind rather than failing on it, and the adapter contract has no opaque adapter event that would carry one to the log. Follow-up: an opaque adapter event type in the contract (the scoped append's accepted types and the snapshot's `opaque` item), and a compaction marker in the vocabulary.
  - `command.ran` is not produced; the mapper reads no slash-command envelope. Follow-up: map the CLI's command envelopes and `local_command_output`.
  - `startEnvironment` passes no `sessionStore` and no `plugins` directory: the options carry both whenever the adapter is given them, and the store is #137's and the skill-set directory ticket 89's.
  - Only `test/fixtures/sdk/signed-out.json` is recorded from the bundled binary; the other fixtures are shaped from the declarations. The ownership handshake (the owners on a turn's first reply naming the uuid-stamped prompts) rests on the declarations' description until a signed-in streaming-input turn with uuid-stamped prompts, a mid-turn send and a queued turn is recorded. Follow-up: record it on an account and replay it through `adapter.test.ts` before the handshake is trusted.

Decided in building attachment staging (#185):

- **Where the bytes wait**: `<dataDir>/attachments/<messageId>/<index>` (`adapter/attachment-stage.ts`), a directory of the environment's own, 0700 with 0600 files: one directory per queued message with attachments, named by its id, and one file per attachment named by its index, holding its bytes alone. The kind, name, media type and size are read back from the message's own `message.sent` (`run_messages.sequence` names that event); the bytes are never in the log. A write goes to a `.partial-*` directory, each file synced, then is renamed into place and the rename synced, so a message's directory is there whole or not at all. A message's attachments never change, so staging it again (a run that never received it) leaves bytes already whole as they are; bytes that are not whole are replaced with the old directory set aside (`.aside-<messageId>`) until the new one is in, and startup puts an aside copy back when a crash left nothing in its place. The host's in-memory map stays the fast path; the disk is what a restart reads.
- **Written before the answer**: `runs.send` stages a queued message's bytes inside its command, before it appends anything, so a receipt means they are on disk. A message that starts a run is not staged, since its run reads it at once, unless its adapter never received it: the host stages it as it queues it again (`requeueUnread`), logging loudly if it cannot. A stage that fails refuses the send with `internal`, thrown, so nothing is appended, no receipt is kept, and the same command id succeeds once the disk takes the bytes; `unavailable` was not used since its data names only `starting` and `draining`, nor a receipt's rejection, which would be kept under the command id so a retry could never succeed. The write is synchronous inside the command's transaction, so a large attachment (at most 20 MiB each) holds the log's write lock while it is written and synced.
- **Removed** once a run has read the message (its adapter's `createRun` returned with it at a launch, a steer's `message.delivered`, a provider-opened turn adopted with it) and when its session is purged; a deleted session's stay for its restore. A removal that fails is logged, and the next start removes the bytes.
- **Read back after the recovery sweep** (`recoverStagedAttachments`, in the `adapter-host` step after `recoverCutRuns`, so a message the sweep hands back is the environment's again): what a crash left half written is dropped; a message the log still holds as queued, by the provider or the environment, a deleted session's included, gets its bytes back into the host's map; a message a run has read, one the log never recorded (its command did not commit after its bytes were staged) or one purged since has its bytes removed; bytes that are not whole (a file missing, or a size unlike the record's) are removed loudly, and the message is read by its text alone.

Decided in building the account store (#134):

- **Where it lives**: `packages/environment/src/accounts/`: `account-store.ts` (the `accounts` projector over the `account` streams, one stream per account, its id the account's), `account-service.ts` (the rules, the probes, the fifteen-minute reads, the notices, and the lookup the host reads), `sign-in.ts` (the seam #135 fills) and `methods.ts`; the contracts' `accounts.ts` and `methods/accounts.ts`. A removed account keeps its row, marked removed, so its provider stays known (a purge routes a transcript delete by it, and a title mirror still reaches its adapter) and a recorded directory deletion that did not happen is finished at the next start; partial unique indexes on the live accounts' labels (ignoring case) and identities back the checks the service makes before it appends.
- **The host's seam** (#119's): `createAdapterHost` takes `accounts`, the store's lookup (`facts`, `defaultId`, `defaults`, `providerOf`, `crossCheck`), in place of the configured list; the host no longer probes, so its `refresh()`, `PROBE_TIMEOUT_MS` and `probeTimeoutMs` moved to the account service (the same five seconds); the run context gains `reportIdentity`; `validateSessionInput` answers a verdict (`RunParametersVerdict`) that can say the account cannot run. Nothing of the broker or the prompt path changed.
- **#119's configured accounts are kept as the migration**: `startEnvironment({accounts})` is adopted in place, under each configured id and with the id as its label, the first time the environment starts with a store that has never held an account, and ignored after (an entry repeating an earlier one's id, or its label ignoring case, is left out); every run reads the store. Production passes none; the test helper carries its `claude-max` over this way, since some thirty tests name that id. New accounts get a version 4 UUID the environment mints (`AccountId` is a non-empty string of at most 200 characters so a carried-over id fits).
- **The label**: 1 to 200 characters on one line with no space at either end; unique among the accounts the environment holds, compared lowercased, so a removed account's label is free again and relabelling an account to its own label in another case is allowed; the label an account has already changes nothing. `accounts.add` takes a label (there is no email to preset it from until the sign-in); `accounts.adopt` presets it to the email.
- **Adopt reads nothing itself**: a command runs inside its transaction and answers at once, so `accounts.adopt` uses the machine's own directory as it was last read (at startup, or by `accounts.probe`, which the Account step calls first). It is refused `conflict` with reason `ambient_unavailable` unless that read found the directory there and signed in, `already_added` ("already added as <label>") when an account holds the directory or the identity it is signed in as, and `label_taken`. It appends `account.adopted`, `account.identity-set` and `account.status-changed` (signed out to signed in) in one command. The directory is the adapter's `ambientDirectory()` (Claude's: the host's `CLAUDE_CONFIG_DIR`, else `~/.claude`, resolved once); a directory that is not there is never status-read, since a read may create what it names.
- **Add** makes `<data dir>/accounts/<id>` (0700) inside the command, before it commits, so a receipt means the directory is there; an add that does not commit leaves a directory the store never held, which the next start removes with any directory whose deletion was recorded, keeping whatever a held account or the machine's own directory uses, whatever its name. The account is handed to the sign-in director once the command has committed, when the director's `ready` says a sign-in can start; the preset says sign-in is not built yet (#135) and names the directory, and `accounts.add` answers what it said (`signIn: {started, message}`).
- **One identity is one account** (ADR 0018): an identity is the provider, the email ignoring case, and the organisation. The refusal runs where a status read first gives an owned account that has never read as signed in an identity (the store records the first signed-in read on the account's row, since a lapsed login's status no longer shows it), which is what the director's `finished` asks for and also what `accounts.refresh` does after a sign-in made by hand in the directory: the account is removed (`account.removed`, reason `duplicate-identity`) and `account.directory-deleted` appended, the directory deleted once that has committed, an `account.updated` notice (change `removed`) carries the warning, and the director's port answers `identity_held` with "<identity> is already added as <label>." A read that gives an account that already had an identity, or had ever read as signed in without one (it may have run, whatever it reads now), or an adopted one, an identity another account holds only warns (change `identity-mismatch`) and leaves its identity as it was. Deleting refuses any path outside the environment's own account directories, and any that a held account's directory or a provider's own directory is, holds or lies inside.
- **Status**: four states. `unreadable` when the probe throws, times out or reports an error (the error is the status's `detail`); `expired` only when the adapter says so, through `AuthStatus.expired`, optional, added here: Claude's `auth status --json` cannot say, so a lapsed Claude login reads `signed-out` until a run's authentication failure is mapped onto it (a follow-up). Read at startup, when `accounts.refresh` asks, and otherwise by one timer per account on the environment's clock, armed for fifteen minutes at every read, so no two timed reads are closer than that; reads of one account in flight are shared. `account.status-changed` and `account.identity-set` are appended only on a change, as `system:account-store`. The store records changes only, so a record's `checkedAt` is the last read's time kept in memory, and after a restart, until the first read, the time of the last change. The machine's own directory is read at startup and by `accounts.probe`, never by the timer.
- **Notices**: `account.updated` (`{accountId, change, warning}`) on the environment's stream once the change has committed, one per command or read; the reads startup makes before the wire opens notice nothing, since `environment.started` follows them.
- **The cross-check**: the Claude process asks the SDK's `accountInfo` once, after its first `init`, and reports it through `reportIdentity`; an identity unlike the one the store holds for the run's account (the email ignoring case, and the organisation only when both name one, since `accountInfo` and `auth status` need not both carry it) is an `account.updated` with change `identity-mismatch` and a warning naming both, and a fresh status read, which is the only way the store's identity changes. Nothing is recorded when the store holds no identity yet.
- **What cannot run is refused**: `runs.start` and `sessions.create` read the account through the host's seam against the store, and an account the store does not hold (never, or removed) or that is not signed in is `conflict` with reason `account_unavailable`. For `sessions.create` that is now a receipt, where #119 answered `invalid_params` at the account's path; a model the account does not offer and a mode its adapter lacks stay `invalid_params`. A session whose account was removed stays on it: forking onto another account (#137) is the way off.
- **The defaults**: `accounts.defaultAccount` names the default account while the environment holds it, else the first account adopted or added that it still holds; `settings.update` does not check the value against the store (the generic methods have no per-key rule), and removing the default does not clear it. `accounts.defaultModelFamily` and `accounts.defaultEffort` apply when a run starts: with no model from the command or the session, the strongest model of the default family when the catalogue has one, else the strongest; with no effort from the command, the default effort when the model takes it, else the model's own. All three are preset to null; the Account step (#88) presets the family to the highest tier's and the effort to `high`. They sit with `providers.processIdleMinutes` under the Account entry's Default account and model band, each checked done on any valid value.
- **Models** are read at startup, on `accounts.refresh`, after an adopt and after a sign-in, and at the fifteen-minute read while a failed read has left them unknown, and kept in memory; `models.list` reads an account never read first. `commands.list` goes through the host's `commands` (refused `invalid_params`, reason `unsupported`, without the capability; `not_found` for an account not held) and passes no `trusted` until #89. `providers.list` is #120's, unchanged.
- **Not guarded**: removing an account, or deleting an owned directory, while a run is live or a provider process is kept on it; the run goes on and the next start on that account is refused.
- **Owed**: to #135, the director (its states, the published URL, the code, expiry, cancel, the fallback command), `accounts.signin.*` and `signin.updated`, calling the port's `finished(accountId)` when `auth login` succeeds, and whether the label follows the email after a sign-in; to #136, `accounts.usage` and `usage.updated` (the host's `usage` already reads the account through the store, and the identity a reading carries is the one the store records); to #137, forking onto another account; to #138, `/v1/models` over every signed-in account's catalogue and a bare model id resolved on `defaultId()`; to #88, the Account step's health from the store (every account signed in) and presetting the defaults; to #91, the account status in the orientation block; to the clients, calling `accounts.refresh` as the Account step or the Accounts pane opens and refreshing the cache on `account.updated`.
