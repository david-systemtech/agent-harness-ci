# Spec: Claude adapter, the adapter contract and the completions surface

Milestone 1 (Switch-over), phase A (the spine). Written 2026-09-23 from map ticket 82 of `david/agent-harness`. Decisions it implements: ADR 0015 (the adapter contract, environment-owned provider processes, the served adapter retired, the completions surface with client-tool passthrough), ADR 0009 (the instruction channel, skills through a plugin directory, the `project` settings source behind the trust gate), ADR 0018 (accounts as environment-owned directories, environment-driven sign-in with the SDK-bundled binary, identity from auth status, the session store, one auto-memory directory per repository, the three stripped variables that would outrank a login), ADR 0019 (a minted session is an ordinary session), ADR 0006 (modes, ceilings, prompts as events), ADR 0002 (the log holds transcripts), ADR 0017 (phase, placeholder name), with rules that also cite ADR 0001 (opaque unknown kinds), ADR 0005 (usage pooled by identity), ADR 0007 (drain, prompts surviving a restart), ADR 0011 (the orientation block) and ADR 0016 (the step registry), and the Resolutions of tickets 28, 29, 40 and 51. It builds on the environment-service (ticket 78), session-state (79) and client-runtime (80) specifications on main and re-decides none of them. Peers read: the core port audit, the Claude Code and Hermes inventories, the Agent SDK reference and session-storage pages, the CLI reference and the headless page. The product name is the placeholder `agent-harness` throughout.

## Problem Statement

Every Claude run David starts today is one turn of a process the run owns, so a process dies with the window that started it, a turn pays a cold start unless the last one is still holding work, and a routine on the headless server gets a different host around the same adapter. The audit found the seam sound and Electron-free, with four faults around it: every query passes an empty settings list, so a repository's own instructions, hooks and rules never load; the adapter is one 6,136-line file; three of its types live in the desktop's IPC contract; and the plan gauge is read by name lookup on an experimental SDK method. Accounts share history and memory only through a script of nine symlinks nobody runs on the server, and an account has no identity, so one login on two machines is two gauges. Sign-in is a copied command on the desktop and a driven subprocess on the server. The completions surface, which is how the Hermes bots bill on David's subscriptions, marks a caller's `tools` as honoured and never reads them, so Hermes's memory, skill and cron tools never run; any token may ask for bypass; a disconnect interrupts the run; and a quiet stream looks like a dead socket.

## Solution

One adapter contract on the environment, with the Claude adapter as its first implementation. An adapter declares what it can do and how its credential is scoped, and turns a run into transcript events that go into the environment's log and nowhere else; sessions resume, fork and rewind through it; plan usage carries an account identity so the laptop and SAMPLE-SERVER show one gauge for one login; models come with tiers; commands are listed from the provider; standing instructions and always-on skills ride the provider's own instruction channel; tool servers are built per run; and a permission prompt is a parked event any client can answer. Claude's per-conversation process belongs to the environment: started on the first run, reused by the next, kept through a client's disconnect, drained for an update, stopped after thirty idle minutes. Accounts are directories the environment adopts or owns, signed in by the environment itself with the SDK's bundled binary. Transcripts reach any account's process through the SDK session store, auto memory is one environment-owned directory per repository, and a trusted repository's own settings load. The completions surface keeps its OpenAI shape on the same port, authenticated by client-session tokens under their ceiling, and turns a caller's tools into real tool-call round trips, so Hermes runs its own tools again.

## Implementation Decisions

Every rule cites its decision; a rule marked chosen default was left open by the tickets and is listed again under Further Notes.

### Modules and ownership

- The **contracts package** gains the transcript event vocabulary and the per-session snapshot shape; the `runs`, `accounts`, `models`, `commands` and `providers` registry entries with scopes; the account, plan-usage, model catalogue, sign-in state and completions schemas; the settings keys below. The three types the audit found in the IPC file (run suggestion, send response, delegated-work row) land here as transport-neutral schemas (ticket 28).
- The **environment package** gains the **adapter host** (adapter registry, provider-process pool, permission broker, tool-server factory, the instruction composer's seam, the SDK session store, the account store, the sign-in director) and the **Claude adapter**, split along the seams the audit named (ADR 0015): options, process, turn, mapper (pure), history, titles, the config-directory queue (serialising the SDK's standalone helpers, which read the config directory from the process environment), plan usage and sign-in. The **completions surface** is a module of the same package on the same port as the WebSocket.
- The contract is an in-process interface of live objects; it never crosses the wire. The vocabulary and the methods below do.

### The adapter contract

An adapter provides (ADR 0015, ticket 28):

- **A capabilities descriptor**, static: interactive prompts, partial messages, a provider queue (`providerQueue`: the provider holds messages sent during a turn; absent, the environment holds them and reads them when the turn ends, ADR 0022), provider-held withdrawal (`withdraw`: cancel one message by id; environment-held withdrawal is always available), mid-run steering (the provider folds a queued message into the running turn; presupposes `providerQueue`), resume, fork, rewind, session listing, subagents and their transcripts, provider titles (read and write), transcript delete, plan usage, live model listing, commands listing, image and file input, a live mode change (`modeChange`: a running run's `setMode`, permissions spec), the instruction channel kind (`system-prompt-append`, `developer-instructions`, `prompt`, none) with its character cap, and the modes it maps, each available or not with the reason. Every optional method pairs with a flag; the host refuses a call the flag does not cover with `invalid_params`, `data.reason` `unsupported` and the missing flag named in `data.capability` (the environment spec's error union has no `invalid_request`; Further Notes).
- **A credential spec**: the config-directory variable, the credential variables it strips and never sets (ADR 0018's three plus `IS_SANDBOX` and `CLAUDE_CODE_BUBBLEWRAP` from the permissions spec: five), the sign-in, status and logout argv, and a parser from status output to `{signedIn, authMethod, email, orgName, subscriptionType, error}`. A run's environment is the host environment with the provider's credential, backend-selection and storage variables scrubbed (by family: see the #121 notes below) and the account's directory variable layered on top (the existing composer, ported and widened).
- **`createRun`**, taking a resolved input (session and run ids, account directory, workspace and repository identity, model, effort, mode, the composed instruction text, the resume, fork or rewind target, the factory's tool servers, the trust decision, the prompt with attachments) and returning a run: an event stream consumed once, lossless, ending with exactly one end event on every exit path; `send` (steer or queue, with a message id), `withdraw` (a queued message by id, through the provider's cancel-by-id control), `interrupt` (with cancel: the result names the message ids the provider still held, which the host re-owns into the environment's queue, ADR 0022), `answerPrompt`, `stopTask`, `dispose`, `release`. The host is the only consumer and appends each transcript event through the scoped append function and nothing else; a denial report it records through its own `append` (below).
- **Sessions**: list, resume, fork, rewind, read a subagent transcript, delete a transcript; **titles**: read the generated title, write a user title. **Plan usage** per window with an **account identity** (provider plus email, and organisation when present), so the client runtime pools by identity (ADR 0005, ADR 0018). **Models** with a family and an ordinal tier the adapter supplies plus effort levels, a live listing flagged `live` when the provider can enumerate, else the static list flagged as such. **Commands** for an account and workspace, without spending tokens. **An adoption hook** for turns the provider opens on its own; the host registers them as runs of the same session (ticket 28).

The host supplies the scoped **append**; the **tool-server factory** (per run, closing over account, workspace, the session and its repository identity (banks spec, "The seams"): memory tools, browser, the completions surface's client-tool server); the **instruction composer** (ADR 0009: the four layers, a bot's persona, always-on skills and the orientation block of ADR 0011, composed once on the environment for every run origin; in phase A only a session's own instructions and the orientation block exist); the **permission broker**; the **process pool**.

- **Denial reports (#131)**: a run's event stream is its transcript events and its provider's **denial reports**, then exactly one end. A denial report (`{type: 'denial', toolCallId, toolName, by, reason}`, `by` one of `rule`, `classifier`, `mode`, `provider`) says the provider denied a tool call itself, without asking the broker; it is not a transcript event and never passes the scoped append: the host records it through its own `append`, attributed to the adapter, as the call's `tool.decision` (permissions spec, "Events"), unless the call has one already. The host derives the rest of the tool decisions from the transcript's tool events, and appends a `tool.decision` in the transaction of a `tool.ended` whose call ended `ok` with nobody asked, and at the run's end for the calls still undecided.

### The transcript event vocabulary

Stream kind `session`, stream id the session id, the environment spec's envelope; every event of a run carries the run's id in its payload (`runId`) and as the envelope's `correlationId`, and the session's fork and rewind events carry none. Types the session-state spec flags `list` are marked.

- **Prompt suggestions (#251, David, 2026-09-28)**: turn on the pinned Agent SDK's `promptSuggestions` option. In SDK 0.3.283, `SDKPromptSuggestionMessage` is `{type: 'prompt_suggestion', suggestion: string, uuid, session_id}`; at most one arrives after `result`, so the process keeps reading after the run's stream has ended. The adapter maps it to `run.suggested` through the host's optional `RunContext.reportSuggestion` callback. The host stamps the run id and accepts only the latest completed run on a session that still exists. No `suggest_task` tool is added.
- `run.suggested` (unflagged): `RunSuggestion` (`{runId, suggestion}`), the provider's predicted next message verbatim. The session snapshot carries the latest offer in `suggestion` (null when none; absent on older environments); the snapshot fold and `projections.session` clear it at the next `run.started` or a rewind and ignore an older run's late offer. The terminal UI's `1` sends it on a deliberate press with an empty composer; `2`–`4` remain text until a tool offers more. A suggestion never starts a run on arrival.
- `run.started` (`list`): run id, account id and identity, model, effort, the clamped mode, workspace, origin (`client`, `routine`, `completions`, `provider`), prompt message id (and the queued message ids a read-now run carries, ADR 0022), resumed-from or forked-from.
- `message.sent`: message id, typed text, optional `skill {name, origin}` when a client run command or completions turn resolves a leading slash to a skill-set member at send time (the adapter receives its invocation text for that run; queued messages resolve again against the receiving run's set, so the recorded skill does not promise the same resolution at delivery), attachments (kind, name, media type, size; bytes staged on the environment, never in the log), delivery (`prompt` when the message starts a run, `queued` during a live one), for a queued one who holds it (`provider` or `environment`), and the ceiling of the connection that sent it; `message.delivered` when a queued message is read, with delivery `steered` (folded into the running turn) or `prompt` (a turn opened with it) (ADR 0022); `message.withdrawn` when one is taken back (its text goes to the session's draft, a session field); `message.requeued` whenever a message comes back to the environment's queue (ADR 0022: nothing is lost): what the provider still held when an interrupt or any end but the adapter's own completion cut its run, a message the provider refused to take, what a provider-opened turn was to read when the host does not adopt it, and every message a run was launched with when its adapter never received them (its creation failed); always the host's (`system:adapter-host`), and the next start reads them first, in the order they were sent.
- `assistant.delta`: a batch of text or thinking fragments for the open item, flushed every 100 milliseconds or 512 bytes (chosen default); `assistant.text` and `assistant.thinking` close the item, with `aborted: true` when an interrupt cut it short so the partial text stays in the snapshot (ADR 0022). Deltas are ordinary events; the snapshot holds settled items only and a client applies deltas to the open item.
- `tool.started` (tool call id, name, input, agent id and parent call when nested, title), `tool.updated`, `tool.ended` (status `ok`, `error` or `cancelled`, output, duration); `command.ran` for a slash command. Beside them, `tool.decision` (the permissions spec's, one per tool call: who allowed or denied it), which the host appends and an adapter never reports: with a prompt's answer, for a denial report, in the transaction of a `tool.ended` whose call ended `ok` unasked, or at the run's end (#131).
- `prompt.opened` (`list`): the permissions spec's prompt (conflict X1): prompt id, kind (`permission`, `denylist`, `question`, `plan`), tool name and tool call id, input, a one-line summary, blocked path, the provider's reason, the question set, the plan text, the remember-suggestions, the subagent, a denylist prompt's matches (#132), the run's mode and ceiling, `ttlExpiresAt`; `prompt.answered` (`list`): decision, message, a question's answers, edited input, a plan's mode, remember, `decidedBy` (a client session id or `{auto}`: `unattended`, `bypass`, `ttl`, `run_ended`, `reviewer`, `cancelled`) and where the answer went (`live`, `next-run`, or null for an automatic answer no run was waiting for: `run_ended` and `cancelled`). The permissions workstream owns the vocabulary, the TTL and the denylist; the host appends them for the broker, as the ask reaches it (#130).
- The run context gains `gate`, the tool gate (permissions spec, #132, #133): an adapter asks it before the provider's own evaluation of every tool call, and the ruling is final when it denies. The Claude adapter asks it from the SDK's in-process `PreToolUse` hook, which the CLI runs before its own evaluation of every tool call in every mode, bypass included, with the hook's signal, so a denylist prompt opens from inside the hook before the provider's own evaluation; `canUseTool` asks it only about what the hook did not let through as it is (the sandbox's ask for a host, a call another hook rewrote) (#140).
- `tasks.changed`: the delegated-work ledger as rows. `usage.reported`: tokens, cost, context window per model, the run's own (*since #1949*: a kept process's result counts its spend since the process started, so the run's is the difference from the last result the same process gave, a model that spent nothing since left out, and a new process counts from nothing; a run stopped before it spent anything reports none); `plan.limit`: a rate-limit verdict with window and reset.
- `session.provider-linked` (the provider's session id, on first init), `session.forked` (with the anchor message id when the fork took one), `session.rewound` (to a user message id; later items stay in the log and the projection hides them under the rewind's fold), `session.rewind-undone` (naming the rewind it undoes, its message id and the `session.rewound`'s sequence; only before a run starts on the rewound session; afterwards the cut branch stays hidden under a fold, ADR 0022; #218).
- `run.ended` (`list`): reason (`completed`, `error`, `interrupted`, `disposed`, `drained`), cause on `interrupted` (`user`: a person's `runs.interrupt`, or an interrupt the host made that failed; `read-now`: the interrupt of `runs.readNow`; `restart`: the recovery sweep's end for a run a restart cut, #120; `parked`: a process stopped while its run was parked on a prompt, #120; null when an adapter ends a run interrupted on its own and names no cause), error, usage snapshot, duration, turn count, result text.

The **snapshot** carries `{sequence, summary, runs, items, parkedPrompts, rewinds}` (`parkedPrompts` after the session-state spec's "parked" naming, conflict X4): items are a fork's source and anchor (`forked`, #632), user messages, assistant text and thinking, tool calls with updates folded, prompts with state, plans, commands and subagent rows; an unknown kind is opaque (ADR 0001). `rewinds` are the rewinds standing, each with what it hid, and read as none when an older environment leaves them out (#260, below); an assistant item sits at the sequence of its first delta. Subagent transcripts are read on demand, not logged (chosen default).

### Wire methods

Scope `runs:drive` unless stated; every mutating method takes a `commandId`.

- `runs.start`: session id, text, attachments, optional model, effort and mode; account, workspace and defaults come from the session (session-state's `sessions.create` delegates account, model and mode validation to this module). With no model it goes out on the session's `runChoice` (#1961: what `sessions.setModel` last chose, else what the latest run took), else the model the session was created with, else the account's default; with no effort, on the session's effort while on the session's model, the model's own included, else `accounts.defaultEffort` when the model takes it.
- `sessions.setModel` (`runs:drive`, #1961): session id, model and effort (null for the model's own), recorded as `session.model-set`, list-flagged, patching the summary's `runChoice`, which each `run.started` writes too; the choice the session has appends nothing. A model the account's read catalogue lacks, or an effort the model does not take, is `invalid_params`; a live run is `conflict` `run_active`; a session not here `not_found`. The mode is clamped to the connection's ceiling and the clamp recorded on `run.started` (ADR 0006). `unavailable` while draining; `conflict` reason `run_active` (send is the way in) or `account_unavailable`.
- `runs.send` (on a live run the message is queued and the result says where it is held, `provider` or `environment`; whether it is later steered into the turn or delivered at its end is reported by events, never at send time; on an adapter without `providerQueue` the environment holds it and starts the next run with the queue when the turn ends), `runs.readNow` (session id: interrupt with cancel, re-own what the provider still held, start the next run with the whole queue in order; with no run live, the run of the environment's queue starts in the command's own transaction, on the model and effort of the run before it; with nothing queued, accepted with no event and a live run left alone, a chosen default), `runs.withdraw` (message id: cancelled at the provider where it holds it and taken back into the environment's queue at once, then removed from it, `message.withdrawn` and the text into the session's draft in one transaction; any client session at `runs:drive` may withdraw any queued message of a session; `not_found` once read, withdrawn or unknown; `conflict` reason `draft_full` when the draft has no room for the text), `runs.interrupt` (re-owns the provider's still-queued messages into the environment's queue, never drops one; idempotent on an ended run: a no-op that re-owns nothing) and `runs.stopTask` (idempotent on a finished task). ADR 0022. A prompt is answered with the permissions spec's `permissions.prompts.answer` (conflict X1; there is no `runs.answerPrompt`): the first answer settles the prompt; any later answer, on a live or an ended run, is `conflict` reason `already_answered`; an unknown id is `not_found`.
- `sessions.fork` (scope `sessions:write`): source id, client-minted new id, optional `atMessageId` (a user message: the fork holds history up to but excluding it and its text becomes the new session's draft; without it the whole session, except a source no run of which has linked a provider session inherits its own fork anchor and the draft saved with it, including a fork that starts fresh before the first message, #273), optional account id and title; creates the record through session-state, carrying the source's title until the provider's summary replaces it, its tags, group and workspace (never archive, pins or settle), and marks the first run a fork; allowed while the source runs (ADR 0022). Forking onto another account is the hand-off on one environment (ADR 0015); across environments is milestone 2. `sessions.rewind` (session id, user message id; scope `runs:drive`, a chosen default, since it changes what the next run does rather than a summary field), recorded as `session.rewound` with the message's text as the draft; `conflict` reason `run_active` while a run is live, and reason `queued_messages` while the environment holds queued messages for the session (#137's notes); a rewind to the first message is refused with `use_new_session` and the client starts a new session with the text as draft, unless the session is a fork that carried its source's provider session in (#137's notes); files are never restored. `sessions.undoRewind` (session id; `runs:drive`) until a run starts on the rewound session, recorded as `session.rewind-undone` (ADR 0022): it undoes the session's latest rewind not undone, shows what that rewind hid again and puts back the draft it replaced while the draft still holds its text; `conflict` reason `run_active` while a run is live and `run_started` once a run has started since the rewind, `not_found` (data kind `rewind`) with no rewind to undo (#218's notes). `sessions.subagentTranscript` (scope `read`).
- Scope `read`: `accounts.list`, `accounts.probe` (the ambient directory: present, signed in, identity), `accounts.signin.get`, `accounts.usage`, `accounts.handoff.recommend` (the ported threshold, load and recommendation functions over cached readings, so every client shows one offer), `accounts.refresh`, `models.list`, `commands.list` (account, workspace), `providers.list`.
- Scope `admin`: `accounts.adopt`, `accounts.add` (label; creates an owned directory and starts a sign-in), `accounts.relabel`, `accounts.remove` (with `deleteDirectory`, refused on an adopted account), `accounts.signin.start`, `accounts.signin.code`, `accounts.signin.cancel`, `providers.processes.list`, `providers.processes.stop` (chosen default).
- Settings keys through session-state's `settings.get` and `settings.update`: `accounts.defaultAccount`, `accounts.defaultModelFamily`, `accounts.defaultEffort` (ADR 0018; preset by the Account step to the highest tier at `high`), `providers.processIdleMinutes` (preset 30, ADR 0015); all four under the Account step's registry entry (ADR 0016).
- Notices on `environment.subscribe`: `account.updated`, `signin.updated`, `usage.updated`; the client runtime refreshes its request cache on them.

### Environment-owned provider processes

One Claude process per session, owned by the pool (ADR 0015). States: `starting`, `idle` (no turn), `busy` (a turn running), `parked` (a turn waiting on a raised prompt), `stopping`, `stopped`. The first `runs.start` on a session starts it, the next reuses it, a client disconnect changes nothing (ADR 0006). It stops when idle for `providers.processIdleMinutes` with no held work (a live background task or a registered schedule holds it), on `session.deleted`, on `providers.processes.stop`, on drain, or when its session is rewound (stop reason `rewound`, #137), which stops it whatever holds it, so a live background task ends with it. A process parked for the same idle time is stopped too: its run ends `interrupted` with cause `parked`, the prompt stays raised, and an answer later takes the resume path below (chosen default). On drain the host refuses `runs.start`, lets running turns finish up to the cap ADR 0007 sets, stops every process and reports to the launcher; a run cut by the cap ends `drained`. On startup a recovery sweep appends `run.ended` (`interrupted`, cause `restart`) for any run without an end event; its prompts stay raised (ADR 0007) and an answer given later starts a run that resumes the session and delivers the decision (Further Notes, item 7). Cold start after a stop is by store resume; no pre-warmed process in phase A (chosen default).

### The Claude adapter, ported after the audit's fixes

- **SDK and binary**: the pinned Agent SDK (0.3.280 or later; the store needs 0.3.234) with its bundled Claude Code binary, which also runs sign-in and status. The user's own `claude` is never spawned for runs.
- **Options per run**: workspace as `cwd`, `projectConfigRoot` for a worktree's checkout (a workspace at a linked worktree's root or below it, under trust; that checkout then supplies the native skills too, skills spec, #998); model, effort; `permissionMode` from the harness mode (same names; bypass with the SDK's explicit allow flag); the `claude_code` preset with the composed instruction text as `append` (ADR 0009); `settingSources` `['project']` when the repository passed the trust gate, `[]` otherwise, never `user` or `local` (ADR 0009, ADR 0015; excluding `local` is a chosen default, so the CLI's own permanent approvals never leak in); `strictMcpConfig` on, so only the factory's servers load; `plugins` with the run's skill-set generation as its one local plugin, none without one (#495); `settings`, the flag layer, carrying `autoMemoryDirectory` and each native name the skill set hides as `off` in `skillOverrides` (#495); `sessionStore` always, with `resume`, `forkSession` or `resumeSessionAt` as the run asks; partial messages on; `canUseTool` wired to the broker; the tool gate's `PreToolUse` hook on every tool (#140); `CLAUDE_CODE_PROJECT_DIR_NAME` set to the harness session id so a resume never depends on the working directory; the bundled executable path.
- **Mapper**: the existing pure translation, extended for the vocabulary, with deltas batched. It reports the SDK's denials as the contract's denial reports (#131): a `permission_denied` frame (`tool_use_id`, `tool_name`, `decision_reason_type`, `decision_reason`, `message`) as the call's denial by the reason's kind (`rule`, `classifier`, `mode`, anything else `provider`), just before the call's `tool.ended`; and the result's `permission_denials` (`tool_name`, `tool_use_id`, `tool_input`: the CLI's authoritative record, which also holds what no frame reports, a path-scoped deny rule on a file tool or a race) as a rule's, before the end, for each call the turn saw and no frame reported. A denial of a call the broker was asked about is left to the prompt's answer by the host. **Process**: the existing prompt pump, permission table, task ledger and settle grace, moved into the pool's process object; the turn is the run.
- **The unsampled queries** (models, commands, plan usage) keep no transcript (`persistSession: false`); only the commands listing loads the skill set's generation as its plugin with its hidden native names off, and a trusted repository's project settings (#495).
- **Plan usage**: a control-channel read on an unsampled query under the account's directory, through a tolerant lookup over `usage`, `getUsage` and the experimental name, degrading to unavailable on a rename and re-checked against the pinned SDK before build; in-flight reads shared; readings aged out after six minutes (measured); `plan.limit` verdicts fold in. Every reading carries the identity.
- **Titles**: a user title is mirrored through the SDK's rename after commit, best-effort (session-state spec); the generated title is reported after a run ends when the store-backed listing exposes it (verify first), else no provider title in phase A. **Identity**: from `auth status --json` after sign-in and on each status read; the run's `accountInfo` cross-checks it, and a mismatch is recorded as `account.updated` with a warning. **Modes**: `acceptEdits`, `plan`, `auto`, `bypassPermissions`; `default` and `dontAsk` are not offered (ADR 0006). Containment is the SDK's `sandbox`, and on unattended runs the denylist's paths and command patterns are its `filesystem.denyRead` and the disallowed shell rules (#140).

### Queue, read-now, fork and rewind on the Claude adapter (ADR 0022)

Claude declares `providerQueue`, `fork` and `rewind`. A mid-run `send` pushes an `SDKUserMessage` with the harness message id as its `uuid` onto the streaming input; delivery is observed from the CLI's echo (`user_message_uuids` on the turn's first reply) and reported `steered` when it lands inside the running turn, `delivered` when a queued turn opens with it. `interrupt` sends the SDK's interrupt with `cancel_queued`, and the ids it reports still queued are re-owned by the host as `message.requeued`; a turn the provider opens on its own is still adopted through the adoption hook, but after ADR 0022 the host never expects one from an interrupt. `withdraw` uses the cancel-by-id control (`cancel_async_message`); if the provider reports the message already consumed the call is `not_found`. Read-now's next run passes the queue as the run's prompt messages in order. A fork resumes the source's provider session with `forkSession` and, when an anchor is given, `resumeSessionAt` set to the entry before the anchored prompt; the fork's provider ids are its own (the SDK remaps them). A rewind resolves `resumeSessionAt` to the entry before the user message and `resumeDropsTurn` when everything after it belongs to that one turn; the SDK's file checkpointing is never enabled, since it cannot be combined with the session store. The build session verifies the cancel-by-id control and the interrupt's still-queued report on the pinned SDK before either is relied on; absent, `providerQueue` is declared false and the environment holds the queue for Claude too.

### The account store

Stream kind `account`: `account.adopted`, `account.added` (a directory under the environment's data directory), `account.identity-set`, `account.status-changed` (signed in, signed out, expired, unreadable; appended only on change), `account.relabelled`, `account.removed`, `account.directory-deleted` (owned directories, on the explicit second choice). Record: id, provider, label (preset to the email, unique per environment ignoring case), directory kind (`adopted`, `owned`) and path, identity, status with checked-at, created-at. One account per identity per environment: a sign-in yielding an identity already held is refused with "already added as <label>" and the new owned directory is deleted (ADR 0018). Status is re-read when the Account step or Accounts pane opens and at most every fifteen minutes otherwise, and carried into the orientation block (ADR 0011).

### Sign-in and status through the bundled binary

The **sign-in director** runs one sign-in per environment (ADR 0018): `accounts.signin.start` spawns the bundled binary with `auth login`, `CLAUDE_CONFIG_DIR` at the account's directory and the five stripped variables (and the scrubbed families) absent, stdin a pipe, stdout read incrementally. States: `starting`, `awaiting-code` (the verification URL published as `signin.updated`), `submitting`, then `done`, `failed`, `expired` (ten minutes) or `cancelled`. `accounts.signin.code` writes the code from any client; a second start is refused naming the account that has the floor; `done` triggers a status read and `account.identity-set`. The exact fallback command (POSIX and PowerShell renderings, the directory quoted) is part of the sign-in state, so every client shows it. Subscription only: `--console` is never passed; a Console user runs the fallback with it (ADR 0018). If the bundled binary does not run `auth login`, the managed tool `claude` is the fallback executable, chosen once per environment and recorded.

### The SDK session store and auto memory

The environment implements the SDK's `SessionStore`: `append`, `load`, `listSessions`, `listSessionSummaries` (folded with the SDK's helper inside `append`, serialised per session), `delete` (cascading to subkeys and the summary), `listSubkeys`. Entries are opaque provider state, so they are not events: they live in a `provider_transcripts` table beside the log, keyed by the harness session id, purged with the session's tombstone. This is the chosen reading of "over the environment's log": the log holds the events clients read; the store holds the entries the provider reads back. Every run passes the store; from a session's second run onward the run resumes from the store, which is then the durable copy, and the SDK deletes the temporary directory it ran in; a fresh session's first transcript file stays in the account's directory, written by the CLI as it always does. Resume on another account works because the SDK seeds that temporary directory with the credentials of the directory the run names, which ADR 0018 relies on and the build session verifies first. **Auto memory**: one directory per repository under the environment's data directory, keyed by repository identity (else the workspace path), passed through `settings`, shared by every account (ADR 0018); the Carry over step copies an adopted directory's per-repository memory into it (ticket 51).

### The permission broker

`canUseTool` first asks the tool gate, whose containment denial is final and asks nobody (permissions spec, #133's note on the gate), unless the `PreToolUse` hook, which runs first for every call, let the call through as it is (#140), then hands each request to the broker, which appends `prompt.opened` (the permissions spec's names and fields, conflict X1), parks the run, and settles the request on the first `permissions.prompts.answer` from any client session with `runs:drive`, or on an automatic rule (the unattended rule, a bypass residual, the TTL sweep: #131), appending `prompt.answered` with who answered (ADR 0006). Plan approvals and questions are prompts of kind `plan` and `question` on the same path. **The boundary on a prompt whose run ends**: a run that ends on its own (its adapter's end, whatever its reason, or an error the host records) closes its open prompts with `auto: 'run_ended'`, in the transaction of its `run.ended`; the adapter's `restart` (the recovery sweep) and `parked` (the parked stop) endings, and every other stop the host makes (an admin's stop, a deletion, a drain, the environment closing), leave them parked in the log (ADR 0007): dispose of a process denies every prompt it holds in memory only, and a later answer is kept for the session's next run, whose first message it becomes. A later answer is `conflict` reason `already_answered` only once `prompt.answered` exists.

### The completions surface

Kept for programs (ADR 0015, ticket 29), on the same port as the wire.

- **Routes**: `POST /v1/chat/completions`, `GET /v1/models`, `GET /v1/models/{id}`; other OpenAI paths answer `501` with a sentence.
- **Authentication**: `Authorization: Bearer <client session token>` from a pairing of client kind `program` (added to the environment spec's kinds; chosen default) with scopes `read`, `sessions:write`, `runs:drive` and a ceiling set at pairing. `401` unauthorized, `403` scope, `503` draining.
- **TUI printing admission amendment** (#1179; switch-over spec, phase D): the selected authenticated `tui` client session, local or paired, also uses these same model and turn routes. This supersedes the program-only wording above and in #138's implementation notes below. Model discovery still needs `read`; turns still need `sessions:write` and `runs:drive`. Printing sends `agent-harness.attended: false` and uses that client session's current Ceiling, never a replacement credential. Desktop and web client sessions remain refused. Program tools and same-credential continuations are unchanged; printing declares no caller tools and adds no endpoint, Provider, tool host or namespace alias.
- **Model ids**: `<account label slug>/<model or family>`, the slug slash-free; `GET /v1/models/{id}` matches the rest of the path, so an id from the listing is fetched as is; a bare id resolves to the default account; `/v1/models` lists every signed-in account's catalogue with `agent-harness.account`, `family` and `tier` beside each id.
- **The extension namespace** is `agent-harness` (the ADR 0017 placeholder rename). Fields: `sessionId`, `permissionMode`, `systemPrompt` (append-only, 200,000 characters, after the environment's composed instructions), `alwaysOnSkills` (accepted and reported as ignored on the first chunk until ticket 89 lands, then honoured through the skill set), `forkSession`, `rewindToMessageId`, `attachments`, `thinking` (effort; `reasoning_effort` is its alias), `workspace` (a directory the environment has, else a scratch workspace per session), `attended` (default false), `after`, `ignoreUnsupported`, and `browser` (the browser spec's: `headless` gives a session the turn makes the headless browser, else it has none; #550).
- **`permissionMode`** is clamped to the connection's ceiling and the clamp reported as `agent-harness.clamped` on the first chunk (ADR 0006). **Prompts**: a completions run is unattended unless `attended: true`, so prompts are answered by the unattended rule and recorded, never parked (ADR 0006); with `attended`, they park and any client answers.
- **Messages**: the trailing user message is the turn; system and developer messages append after the composed instructions; earlier messages ride as an "earlier in this conversation" preamble on a fresh session and are dropped on a resumed one. No session id means a fresh session; the response carries the session id in the namespace.
- **Client-tool passthrough** (ADR 0015): a caller's `tools` become an in-process SDK MCP server named `client` for that run, one tool per declared function with its schema. When the model calls one, the surface emits an OpenAI `tool_calls` delta (ids minted by the environment, names without the server prefix), ends the stream with `finish_reason: tool_calls`, and parks the handler. The follow-up request's `tool` messages are matched to parked handlers by `tool_call_id` regardless of session id, so Hermes's loop works unchanged; the handlers resolve and the same turn streams on. A parked handler expires after ten minutes (chosen default) with an error result to the model. `tool_choice: none` withholds the tools; `required` and a named choice are rejected, or ignored under `ignoreUnsupported`. The agent's own tools never appear as `tool_calls`; they ride `agent-harness.activity` on empty-delta chunks.
- **Streaming**: OpenAI's chunk order; every chunk carries `agent-harness.seq`, the log sequence of the event it renders; an SSE comment every fifteen seconds while quiet; a mid-stream failure is a final chunk, never a bare close. A disconnect does not interrupt the run (ADR 0006); a later request naming a session whose run is going attaches from `after` and its trailing message is a steer.
- **Parameters**: `max_tokens`, `stop`, `stream`, `stream_options` honoured; `response_format`, `temperature`, `top_p`, `seed`, `n`, `logprobs`, the penalties and `logit_bias` rejected with `400` unless `ignoreUnsupported`; `user`, `metadata`, `store`, `service_tier`, `parallel_tool_calls` ignored and reported.
- **Non-streaming** returns the whole message, with `tool_calls` when parked and `usage` from `usage.reported`. Every turn is an ordinary run on an ordinary session: logged, listed, tagged `completions`, under the same ceilings, denylist and instructions.

## Testing Decisions

A good test is a behaviour visible through the wire, the completions routes or the contract's own surface, asserted from a client's or the host's point of view; never the pool's map, the broker's table or a row, except at the two lower seams where the store or the fold is the behaviour.

- **Primary seam: the in-process environment with a scripted fake adapter.** The environment spec's helper (temporary data directory, loopback port 0, the thin typed client over a real WebSocket) with the contract satisfied by a scripted fake: a script of events per run, a stub status probe, a static catalogue with tiers, a usage reading with an identity. It is the fake the environment spec names, extended here. Through it: a run's events on the per-session subscription with the `list` patches session-state expects; a run surviving its client's disconnect and a second client attaching; steer, queue and interrupt; a prompt shown to two clients, answered once, the second answer refused `already_answered`; the unattended rule; fork onto another account; rewind; the recovery sweep after a stop and start; drain refusing starts and ending a cut run `drained`; the idle stop under an injectable clock and the hold for a live task; accounts adopted, added, relabelled, refused as a duplicate identity, removed with and without directory deletion; the sign-in state machine with the binary replaced by a scripted process (URL published, code accepted, expiry, cancel, one at a time); readings pooled by identity; the settings keys. Prior art: T3 Code's `buildAppUnderTest` and `withWsRpcClient` in `apps/server/src/server.test.ts` and its `integration/orchestrationEngine.integration.test.ts` with `TestProviderAdapter`.
- **Adapter seam: the Claude adapter with the SDK transport scripted.** The SDK module is replaced with `vi.hoisted` and `vi.mock`: a fake query with a message queue and the control methods, `createSdkMcpServer` and `tool` returning inert descriptors, the session functions stubbed. Tests observe the options `query()` received (settings sources by trust, the append text, `strictMcpConfig`, plugins, the auto-memory directory, the store and resume fields, the environment with the five stripped variables and the scrubbed families absent and the directory variable present) and drive SDK messages through the mapper: init, deltas batched, tool use and result, `canUseTool` parking on the broker, task notifications, a provider-opened turn adopted as a run, the result ending the run, the usage read through each name and its degradation, the process kept and released across turns. Existing cases port with the vocabulary renamed.
- **Completions seam: the surface through the in-process environment with `fetch`.** A `program` pairing; `/v1/models` and the bare id; chunk order, `seq`, the heartbeat under fake timers, the failure chunk; the clamp; `sessionId` continuity, fork and rewind; system messages after the composed instructions; the passthrough round trip with the fake adapter scripting a client tool call (the `tool_calls` chunk, the finish reason, a follow-up with `tool` messages matched by id and no session id, the turn resumed, the expired handler); parameter rejection and `ignoreUnsupported`; attach to a live run.
- **Lower seams**: the session store against in-memory SQLite with the SDK's published conformance suite, plus the purge on a tombstone; the mapper as a pure function over recorded SDK fixtures, unknown message types kept opaque.
- **Contract tests in the contracts package**: every method above has one scope; every `list`-flagged event has a patch schema; the vocabulary and snapshot schemas round-trip the JSON Schema export; the extension schema rejects a mode outside the four.
- **Framework**: Vitest; listener-binding files run serially. **Not tested here**: a live Anthropic account (the verify-first checklist), the Hermes deployment (phase D), containment.

Decided in building the adapter contract, the host and the run methods (#119):

- **The run's stream is its session's** (ADR 0015 reconciled with #118): ADR 0015 and user story 22 speak of an append scoped to the run's stream, but the purge (#118) removes a session by removing its stream's events, so a transcript on a stream of its own would outlive the purge or need a second one. The transcript therefore lives on the session's stream, and the host's scoped append is scoped to one run of one session: it appends to the session's stream only, stamps the run's id into the payload (`runId`) and the envelope's `correlationId`, checks each event against its payload schema, and takes only the types an adapter reports (`message.delivered`, `assistant.*`, `tool.*`, `command.ran`, `tasks.changed`, `usage.reported`, `plan.limit`, `session.provider-linked`). `run.started`, `run.ended`, `message.sent` and `message.requeued` are the host's, appended with the run's id. `session.forked` and `session.rewound` belong to no run and carry no run id, so they cannot pass the scoped append: the `sessions.fork` and `sessions.rewind` commands append them to the session's stream as the client's (#137, `sessions/fork-rewind.ts`). The adapter's actor is `adapter:<provider>`; the host's own ends, every `message.requeued` and the runs it starts from the queue are `system:adapter-host`.
- **`invalid_request` is `invalid_params`**: a call the descriptor's flags do not cover (plan usage, commands, a task stop without `subagents`, on a live or an ended run, an image or file the adapter does not take, a transcript delete) is the union's `invalid_params`, with an issue at the param that asked and `data` `{reason: "unsupported", capability, provider}`, so a client tells it from a malformed request and degrades absent-with-reason. No method-own member is added. The purge reads the same reason as the tombstone's `unsupported`, which is also what it records when the session's provider is not known on the environment.
- **One `run.ended` per run on every path**: the host appends it for the adapter's end event; and itself, as `error`, when the stream throws, stops without an end (code `no_end`), reports an event its schema refuses, or `createRun` throws (one microtask later, so a run launched after its command's commit is heard ending after the command's events); as `interrupted` (cause `user`) when the adapter's interrupt fails; as `disposed` when the session is deleted or the environment closes; as `drained` when the environment closes while draining (the drain's cap); as `interrupted` with cause `parked` when its process has been parked for the idle time, and with cause `user`, recorded as the admin's, when `providers.processes.stop` stops its process (#120). A run the host ends is disposed, never released, since its stream may still be open; whatever it yields after its end is dropped. Cause `user` says a person ended the run, and the host alone sets it, on two paths: the run was interrupted (`runs.interrupt`), when its end carries `user` whatever cause the adapter named, recorded as the adapter's, or as the host's own when the interrupt failed; or an admin stopped its process (`providers.processes.stop`), recorded as the admin's. Otherwise an adapter's own `interrupted` end names its cause, or none, and the host's own name theirs: `parked` for the parked stop, `restart` for the recovery sweep. If the end cannot be appended, the host tries once more; if that fails too, the run is over here all the same (let go, ended in the run registry, no longer the session's live run, so a new start is taken), the failure is logged loudly, and `runs.interrupt` on it answers `ended: true` with `unrecorded: true`; the log's missing end, and any message its provider still held, are the recovery sweep's (#120) at the next start. A provider-opened turn the host is asked to adopt for a session deleted since is not adopted: it is disposed and what it was to read is taken back.
- **The send, per ADR 0022**: `runs.send` answers `{runId, messageId, delivery, heldBy}` with delivery `prompt` (no run was live; it started one) or `queued` (held by the provider when the adapter declares `providerQueue`, else by the environment); a steer is reported only by `message.delivered`. The environment's queue starts the next run when a run completes or fails, never after an interrupt. **Nothing is lost**: whenever a run ends other than by its adapter completing it (whose provider reads what it holds in a turn of its own, adopted), the messages its provider still held come back to the environment's queue as `message.requeued`, in the transaction of the `run.ended` and just before it, so a client that starts a run on seeing the end finds them queued; the same happens to what an interrupt reports still queued, to a message the provider refused to take, and to what a provider-opened turn was to read when the host will not adopt it (a drain, the environment closing, the session deleted). A run whose adapter never received its input (a seam, the adapter lookup or `createRun` threw) has every message it was launched with queued again, bytes and all, and no run starts on its own after it, so a failing adapter cannot loop: the next start reads them. The runs projector keeps every message sent (`read` once a run has it) so such a message can be queued again. A message's attachment bytes are kept, whoever holds it, until a run reads it (a steered message on its `message.delivered`): in memory and staged on disk under the data directory, so a restart keeps them (#185's notes below); a deleted session's are kept for a restore and removed when it is purged. `message.requeued` is in the vocabulary, and `message.withdrawn`, `runs.readNow` and `runs.withdraw` since #228 (its notes below); `session.rewind-undone` and `sessions.undoRewind` since #218 (its notes below).
- **A queued message carries its sender's ceiling**: `message.sent` records the ceiling of the connection that sent it, and a run that reads queued messages has its mode clamped to the ceiling of whoever started it and to each queued sender's, so a run of the environment's queue is never above the lowest of them (the clamp is #129's policy resolver).
- **Commit hooks and delivery order**: the log delivers what a commit hook appends after the events of the transaction that committed (the same change #117 makes), so the host's work after a command's commit (a launch, a requeue) is never heard before the command's own events.
- **`runs.interrupt` and `runs.stopTask`** answer `{runId, ended}` (and `taskId`; and `unrecorded: true` on an interrupted run whose end the log could not take): on an ended run, or a settled task, the command is accepted with no event and `ended: true`. An attachment is standard padded base64, at most `MAX_ATTACHMENT_BYTES` (20 MiB) decoded; the export publishes the grammar as one pattern, while the environment checks it as a flat pattern plus the length rules, since the grammar's repeated group overflows a backtracking engine's stack on a 20 MiB string. A run command on a deleted session is `not_found` kind `session`; on a purged session's run, kind `run`.
- **The snapshot's transcript part is folded on read**: `runs`, the settled `items` and the `parkedPrompts` are folded from the session's stream when a snapshot is sent, reading every event but `assistant.delta` (the settled text carries it whole), rather than kept as a table; the `runs` table beside it (with the environment's queue and the delegated-work rows) is what the run methods decide on. The fold is not bounded for a live session: compaction (#123) folds only sessions long left untouched (ADR 0002), and a compacted session's fold goes on from its compaction's snapshot. An event of a type the environment does not know becomes an item of kind `opaque` naming its type; the item schema keeps any unknown kind as it is, and holds a known kind to its own schema (the opaque kind's pattern excludes the known ones).
- **Transcript compaction** (#123, the environment spec's Further Notes): the transcript vocabulary is what compaction may fold, but it removes only what no projector reads, the assistant's items, tool calls, commands, usage and plan limits and all but each run's last `tasks.changed`; `run.started`, `run.ended` and the `message.*` events stay for the projectors, and `session.provider-linked`, `session.forked`, `session.rewound` and `session.rewind-undone` stay as session events (the resume id, the fork's origin, the rewind and its undo a fold reads), though they remain in the vocabulary's table. The fold going on from a compaction's snapshot differs from folding every event only for an event aimed at an item a rewind hid before the fold (it is not in the fold to update, and stays hidden either way); `session.rewind-undone` can bring back only items the fold holds, so compaction leaves out a session whose rewind can still be undone (#218's notes below); ADR 0022 keeps a cut branch in the log as rewound, shown under a fold, whose transcript events a compaction removes once the undo is gone.
- **The run registry** (#112) is filled by the host: a run is `starting` from its command's commit, `running` from its first event, `ended` with its end; `admit` gates `runs.start` and a `runs.send` that would start a run, so a message for a live run is taken while draining. `activeRuns()` lists the live ones. An account's status and model probes give up after five seconds, so a hung probe cannot hang startup.
- **Seams and presets**: the mode clamp `(requested, ceiling) => {mode, clamped}` was the identity until #129, which replaced it with the policy seam (`{actor, requested, accountModes} => policy`, the permissions spec's resolver, where the actor carries the ceiling the caller reduced to the lowest of its own and each queued sender's, and the settings are read inside) and `run.policy.resolved` after `run.started`, which records `{requested, effective, clamped}`; the descriptor's modes carry their availability and a `modeChange` flag pairs with a live run's `setMode` (permissions spec, Further Notes); the broker placeholder denied every prompt at once without recording it, until #130 built the broker (its notes below); the instruction composer joins the orientation block (empty until #91) and a session's own instructions; the tool-server factory builds none; `trusted` is false until #89; `sessions.create` delegates its account, model and mode to the host's `validateSessionInput` (the account on this environment, the model in its catalogue, the mode among its adapter's). Until the account store (#134), accounts are configuration: a run uses the session's account, else the environment's default (the first configured), and the session's model, else the catalogue's highest tier (since #134, the store's default account and the default family: its notes below); effort is the command's, else the model's own, since a session has no effort field. `prompt.opened` and `prompt.answered` were reserved and `runs.answerPrompt` is not registered (conflict X1); #130 fixed the prompt payloads and corrected the vocabulary's bullet and the broker section.
- **Owed**: nothing of #119's. Built since: the startup recovery sweep for runs cut by a restart (#120) and the attachment bytes it keeps (#185), their notes below, and the run-start and run-end companion events (#122): every start and end, the recovery sweep's included, goes through the session module's `appendRunEvents` (session-state spec, #122's notes).

Decided in building environment-owned provider processes (#120):

- **The process handle**: the contract gains `Adapter.stopProcess(sessionId, {kill?})`, required, and a `process` port on the run context: `hold` and `unhold` of a `task` or a `schedule` by a non-empty id (an empty id is logged and ignored), and `exited()` for a process that died on its own. The adapter keeps the provider's process keyed by session: `createRun` starts it when the session has none and reuses it otherwise, `release()` now means keep it for the next run, and `stopProcess` stops whichever process the session has at the call. The pool (`adapter/pool.ts`) keeps the environment's record of it and makes every stop. A port stays valid for the life of the process it was handed with, so a hold outlives the run that took it. Codex's per-home daemon (a pool entry keyed by home) is not modelled: phase A keys by session.
- **States and transitions**: `starting` from a cold run's begin to its first event; `busy`; `parked` while the session's live run has a prompt unanswered, entered from `starting` as from `busy` when the provider asks before its first event, its parked wait armed then; the first event on a parked process leaves it parked, and answering its last prompt makes it `busy`, whether or not an event came first; `idle` when a run its adapter ended is released; `stopping` from the stop until the adapter's `stopProcess` settles; `stopped`, listed for ten minutes and then dropped on a timer. A run the host ends itself (every `error` it records, a failed interrupt, `disposed`, `drained`, a parked stop, an admin stop) is disposed and its process stopped, for a reason the host must name, since after a dispose the provider's state is unknown: the next run starts cold, and a turn the stopped process opened meanwhile is not adopted but let go, what it opened with queued again. A process that exits on its own is recorded `stopped`, reason `exited`, with no `stopProcess`. The stop reasons are `idle`, `parked`, `deleted`, `admin`, `drain`, `closed`, `failed` and `exited`. A provider-opened turn the host lets go (its session deleted, the drain, the policy, a start the log would not take) is disposed and its process stopped the same way, for `deleted`, `drain` or `failed`, unless another run is live on it.
- **Parking follows the prompt, not the broker's promise**: the host hands a session's runs a broker that parks the session's run live when a request is made (a turn the provider opened on its own asks through the context of the run it followed, so it parks too), under the prompt's id, the adapter's own when it names one in the request or one the host mints, which the broker receives. The prompt is answered, and the run unparked once its last is, when the request settles or when the host answers it through `AdapterHost.answerPrompt(runId, promptId, decision)`, which hands the answer to the adapter's `answerPrompt` (`interactivePrompts`), whichever comes first. #130's answer method goes through `answerPrompt`; an answer given any other way must settle the request. *Since #224* the host's one answer path is #130's `AdapterHost.deliverAnswer`, which hands the answer to the adapter's `answerPrompt` and settles the request; `AdapterHost.answerPrompt`, which settled no request and so left the provider's `canUseTool` waiting until the run ended, is gone from the interface.
- **The idle time** counts from the end of the last turn or the release of the last hold, whichever is later. Each wait is one timer on the environment's clock, armed when it begins, rather than the minute sweep, so a stop falls on its instant and nothing wakes while nothing waits. The time is read from `providers.processIdleMinutes` as a wait begins, so a change applies to the waits that begin after it; a value outside 1 to 1,440 is logged and the preset used. The key is a row of the settings table (`ProcessIdleMinutes`, preset `PROCESS_IDLE_MINUTES_PRESET`, 30) under the Account step's registry entry, in its `default-model` band (ADR 0027's `accounts.default-model` row, which absorbs the Runs pane): the step-registry test demands a registered step for every key, so the entry is registered here writing this key alone, and #134 adds the default account, model family and effort to it. The environment reads the value from the settings store; a test may pass its own through the `processIdleMinutes` seam.
- **Who ends a parked run**: the pool's parked timer hands the session to the host, which ends the run `interrupted` with cause `parked` as its own end (`system:adapter-host`, the requeue rule applied) and stops the process with it; the pool stops the process itself only when the host finds no live run. No prompt event is appended, so the prompt stays raised in the log. The ten-minute rule stays the run registry's (#112), which the host now fills with parking too: a parked run counts as busy until ten minutes after it parked, while its process stays parked for the whole idle time.
- **An admin stop**: `providers.processes.stop` is a command on the session's stream that appends nothing of its own and answers `ended: true` when the session has no process running; a run live on the process ends `interrupted` with cause `user`, since a person stopped it, its `run.ended` recorded as the admin's client session under the command's id, and its prompts stay raised. A deleted or unknown session is `not_found` kind `session`, and the deleted-command sweep covers the method.
- **The drain**: as it begins, new runs are refused first and then the host stops every idle process with no held work; a busy one stops as its turn ends; a held one keeps its background work going through the drain's wait and stops when its last hold is let go or the environment closes. A parked run is not waited for (#112) and ends `drained` with any run the cap cut when the environment closes. Closing ends the live runs and waits for every stop under way, including that of a process a cold start has since replaced, for at most `PROCESS_STOP_TIMEOUT_MS` (ten seconds) on the environment's clock, then kills what is left through `stopProcess(sessionId, {kill: true})` and goes on. The event log closes after, and the launcher's channel last (#112): its closing is the report that every provider process has stopped or been killed after the timeout. No message was added to the channel.
- **The recovery sweep** (`adapter/recovery.ts`) runs first in the `adapter-host` startup step, before the host exists and so before the wire opens: every run the runs table holds as running gets, in one transaction, a `message.requeued` for each message its provider still held and then `run.ended` (`interrupted`, cause `restart`) as `system:adapter-host`, its duration measured to the restart on the environment's clock. A run whose end cannot be appended is logged loudly and left for the next start. Messages still provider-held on ended runs are taken back too, in their send order and under their original run, without another `run.ended` (#263): no process survives a restart. Nothing answers its prompts. The queued messages' attachment bytes are read back from the stage on disk after it, in the same step (#185's notes below), so a message it hands back keeps them.
- **The prompt stays open**: no stop the host makes answers a prompt (#130 closes a prompt `run_ended` only for a run that ends on its own). The wire tests park through #130's broker, and read the prompt back from the snapshot and `permissions.prompts.list` after the parked stop and after the recovery sweep; the fold's own test shows a prompt staying parked across an `interrupted` end with cause `parked` or `restart`.
- `providers.list` answers `{providers}`, the adapters' descriptors; `providers.processes.list` answers `{processes}`, each with its state, live run, start, last busy instant, parking, holds, `stopsAt`, and its stop's instant and reason.
- **Owed by the Claude adapter (#121)** when it merges with this: implement `stopProcess` (stopping the session's process at the call, killing it at once with `kill`) and make `release()` keep the process for the next run rather than let it go; turn its own idle timer (`idleMs`) off, since the pool's idle stop replaces it; map its task ledger and schedule flag onto the port: a `hold("task", taskId)` per live background task and `unhold` as each settles (or, from a count, one level hold under a fixed synthetic id held while the count is above zero), and `hold("schedule", <its id or a fixed synthetic one>)` while the session has a schedule registered; call `exited()` when its process dies on its own (a transport failure, a refused dispose); and name its permission table's id as `promptId` in each broker request, so an answer through `answerPrompt` names the same prompt. *Done in #121's merge with this*: see the Claude adapter's notes below.

Decided in building the Claude adapter (#121):

- **What a Claude process inherits**: the environment is copied once, when the adapter is made, and every process is handed its account's directory explicitly (an account with none gets the ambient default, the host's `CLAUDE_CONFIG_DIR` else `~/.claude`, resolved once), so the config-directory queue's temporary write can never reach a composed environment. Stripped and never set: the five variables. Scrubbed besides: every `ANTHROPIC_*`, `CLAUDE_CODE_USE_*` and `CLAUDE_CODE_OAUTH_*`, every name holding `_TOKEN` or ending `_FILE_DESCRIPTOR` (a forge token included: runs reach forges through the harness's credential helper, ADR 0020), `CLAUDE_CODE_API_BASE_URL`, `CLAUDE_CODE_CUSTOM_OAUTH_URL`, `CLAUDE_CODE_SIMPLE`, `CLAUDE_CONFIG_DIR`, the secure-storage directory (`CLAUDE_SECURESTORAGE_CONFIG_DIR`) and `CLAUDE_CODE_PROJECT_DIR_NAME` (all three set from the run, the secure-storage directory to the account's directory since #229, its notes below), and `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE` (#137's notes). Kept: the numeric limits that only share the word token (`*_TOKENS`, the idle and resume token thresholds, the token-usage attachment and total-tokens reminders), which carry no credential; the SDK needs no `ANTHROPIC_*` variable for a subscription login, and sets what it needs itself (`CLAUDE_CODE_ENTRYPOINT`), beside the harness's `CLAUDE_AGENT_SDK_CLIENT_APP`.

The SDK is pinned exactly at 0.3.281; every option the spec names exists under the spec's name (`projectConfigRoot` included, and passed only for a trusted repository: an untrusted one loads nothing of its project, from the branch or its checkout; a bare repository's worktree has no checkout and gets none), and the adapter also sets `permissionPrompts: 'host'` (permissions spec) and `extraArgs: {'thinking-display': 'summarized'}` (an SDK-driven CLI otherwise sends every thinking block empty).
- **The process and the turn**: a turn is a run; the process holds the query, the prompt pump, the permission table, the ledger and the settle grace, and outlives its turns. Whose turn the CLI opened is read from the stream: the bundled CLI narrates (`msg_lifecycle_v1`) and stamps a turn's first reply with the uuids of the prompts it consumed, and every prompt is stamped with the harness's message id, so an `init` is held until a message names its owner; a turn naming a waiting run's prompt is that run's, any other is the provider's own and goes to the adoption hook with the sent messages it opened with. A spawn that started a conversation (`fresh`) takes its first turn as its run's whatever it names. The SDK omits the owners on a delivery-failure or zeroed result (and the synthetic assistant message a delivery failure writes): such a turn is the waiting run's when exactly one run waits and no queued message, settle, live task or scheduled job (whose firing is a turn with no message behind it) could be what the turn is about. A watchdog ends every waiting run `error` (code `not_opened`) when its prompt sits unopened for a minute while the CLI serves no turn, and when an `init` is followed by nothing for a minute (the init is dropped then, so it holds nothing busy), so no run pins a process for ever. It first withdraws each such run's prompt, and what was sent onto it, from the CLI's queue, as an interrupt of an unopened run does (#299), so a CLI that opens late does not run them after the person sent them again: a run the CLI opens meanwhile goes on, and one whose prompt the CLI does not give back ends saying the CLI may still run it rather than asking for it again. A run sent to while it runs reports `message.delivered` `steered` when a reply names the message. A subagent's prompt arriving when no turn is open gets a turn of the provider's own to carry it, adopted like any; it is not the CLI's current turn, stays open across the CLI's own turns, and ends once its prompts are answered (or, interrupted, denies them; or, when the process dies, denies them and ends with the transport error, as the CLI's turn and the waiting runs do); a message sent to it is refused, since no turn of the CLI's could read it and its interrupt could not take it back, so the environment holds it for the session's next run. The broker is asked once the host has adopted the turn and named its run, never with an empty run id. The host is told nothing new about ends: the result ends the turn through the mapper, and every process-side ending (transport failure, a prompt withdrawn from the CLI's queue, launch failure) goes through the same idempotent end.
- **Kept across turns, on the pool's port** (#120): `release()` keeps the process for the next run and the pool decides when it stops; the adapter's own idle timer is gone. `stopProcess(sessionId)` disposes the session's process and resolves once its pump has ended and its child exited; with `kill` it sends the child SIGKILL at once (the adapter spawns the CLI itself through the SDK's `spawnClaudeCodeProcess`, so it holds the child) and waits for nothing. What holds the process from the pool's idle stop goes through the run context's `process` port: `hold("task", taskId)` per live background task from the SDK's `background_tasks_changed` level and `unhold` as each leaves it; one `hold("schedule", "claude-schedules")` while a cron job (until `CronDelete` removes it) or a wakeup (until a turn of the provider's own with no message behind it opens) is registered, each counted when its tool call ends `ok` (a denied or failed one registers nothing), and the counts set from the CLI's own list of the session's jobs (`session_crons`, the only place the pinned SDK reports them) at each turn's Stop hook, so a one-shot job that fired or expired lets the hold go. A process that dies on its own (a transport failure, a launch that failed, a run interrupted before anything spawned, an interrupt that forced it down) lets its holds go and calls `exited()`; one the pool stops does not. `onClosed`, the adapter's forgetting of a process, runs on every close, so twice for a disposed process whose pump ends later: it forgets only the process it names, so a replacement is never lost. While it is kept, the conversation's next run attaches to it (same account directory, trust and tool servers, resuming its provider session, not asking for a bypass the spawn lacked), moved onto the run's model, mode and effort through the SDK's setters, each under a timeout. A run it cannot serve lets a process held only by a schedule or a grace go and spawns fresh, handing the fresh process the queued messages the old one never opened a turn with; a turn open or waiting, a parked prompt or a live task refuses the run instead. Queued ids are kept after a turn ends, so a turn opening later still reports reading them.
- **Contract extensions**: `Adapter.commands` takes `{trusted}` (a trusted repository's commands load with its project settings), and since #495 `{trusted, skillSet}`, both passed by the host on every call; `PromptRequest.signal` (aborted when the provider withdraws the tool call: the host's wrapped broker counts the prompt answered then, at once for a signal aborted before the request, and once per request, so the run is unparked and a later prompt reusing the id stays parked; each request also names the permission table's id as `promptId`, so an answer through `AdapterHost.answerPrompt`, since #224 `AdapterHost.deliverAnswer`, settles the same tool call); `ProviderTurn.onAdopted(runId)` (the host tells an adopted turn its run id once the run is registered, so a prompt it asks at once parks it, and never tells a turn it lets go; a subagent's prompt turn asks the broker only once it has one); `UsageReading.unavailableReason` (a reading with no windows says why) and `UsageWindow.verdict` (a folded `plan.limit`). `Adapter.stopProcess` is #120's, with `kill`; the adapter's own `close` and the host's `session.deleted` call are gone, the pool's stops replacing them.
- **The interrupt**: the pinned SDK's `interrupt` takes `{cancelQueued: true}` at run time (its declarations omit the argument, as they omit `cancelAsyncMessage`) and answers `{still_queued, cancelled}`: the interrupt withdraws everything the CLI still holds in the same request, so no queued message can run as the next turn before the host takes it back (ADR 0022: interrupt re-owns the queue and starts nothing). The ids in `cancelled` that this process sent go back to the host as still queued, whichever run they were sent during, since the CLI's queue is the process's (a message a replaced process handed on is among them): the host takes back each the provider holds for the session, under the run it was sent during; ids the CLI queued itself are ignored. Both undeclared controls are detected once per process (the method's arity and presence, and `interrupt_cancel_queued_v1` on `init`), a missing one said once as a diagnostic, and a test holds a real `query()` to having them; without the cancel, the adapter falls back to the plain interrupt and the one-by-one `cancelAsyncMessage`, which can lose the race. A run whose prompt the CLI has not opened is withdrawn by id, together with what was sent onto it or handed on at its spawn (reported still queued, so the host takes them back and the CLI never runs them), and ends there; if it cannot be withdrawn it is marked and interrupted when the CLI opens it, never by stopping the turn the CLI runs ahead of it. `providerQueue` and `steering` are declared on that footing (the bundled 2.1.281 advertises `interrupt_receipt_v1` and `interrupt_cancel_queued_v1`).
- **The config-directory queue is one per process, not one per directory**: the helpers read `CLAUDE_CONFIG_DIR` from `process.env` at call time and after their awaits, so two helpers on two directories running together would read each other's; calls run one at a time, each answered within thirty seconds of being asked or refused, and the variable is restored after each. The pinned SDK's helpers take no abort signal, so a helper refused for its time may still run and read the variable after its awaits: its directory stays installed, and the queue waits, until it settles; a call whose time runs out while it waits is refused and never runs.
- **The unsampled queries** (models, commands, plan usage) keep no transcript (`persistSession: false`); only the commands listing loads the skill set's generation as its plugin with its hidden native names off, and a trusted repository's project settings (#495).
- **Plan usage**: keyed by the account's directory (one account per identity, ADR 0018); the identity from `accountInfo()` on the same unsampled query, else the status command; a reading that failed is not kept; a verdict with no reading to fold into is dropped, since the next read is newer, and one that arrives while a read is in flight is folded into that read's reading, which began before it, unless the provider answered the read after the verdict (#136: the read's numbers are newer then). The usage method is called with `skipBehaviors: true`.
- **An answer that reaches no tool call is refused, not dropped**: the adapter denies its run's parked prompts itself as the run ends, however it ends (the Claude adapter at a turn's end, a transport failure, a dispose), since the host refuses an answer for a run no longer live without asking it; the adapter's `answerPrompt` throws `PromptClosed` (reason `run_ended` when the prompt's run has ended, whose tool call it then denies rather than let run; `not_open` when it holds no such prompt), and `AdapterHost.answerPrompt` refuses the answer `conflict` with reason `run_ended` when the run is no longer live (checked first), or `prompt_not_open` when the live run has not raised the prompt or it is answered already (the host's own record, whatever the adapter would say), or the adapter holds it no longer, thrown when the adapter answers at once and as the rejection of the promise it returns when the adapter answers asynchronously (any other failure of the adapter's is logged and refused `internal`, the same both ways), so #130's answer method can say so and deliver a prompt kept open across a run's end another way. *Since #224* these are `AdapterHost.deliverAnswer`'s refusals, `AdapterHost.answerPrompt` being gone, but for two: a run no longer live is handed nothing rather than refused `run_ended` (the answer method checked it in its transaction, and the log keeps the answer), and an adapter without `interactivePrompts` has the request settled alone rather than `invalid_params`.
- **Images** go to the CLI labelled with their own media type, which must be one the SDK's image block takes (`image/jpeg`, `image/png`, `image/gif`, `image/webp`); another is refused before anything spawns, or when sent.
- **Declared false for now**: file attachments (implemented elsewhere; not ported). Session listing is declared since #578 (its notes below). Subagent transcripts, titles and transcript delete are declared since #137 (its notes below).
- **Modes** (#129's mapping): each of the four modes is the SDK `permissionMode` of its name, every one listed available; `allowDangerouslySkipPermissions` is set when the run's ceiling is `bypassPermissions`, whatever its mode, and a kept process serves a run under a bypass ceiling only when it was spawned with the opt-in, so a later change to bypass is refused by the provider as well as clamped below that ceiling. `modeChange` is declared: a live run's `setMode` (the host's, already clamped to the run's ceiling) calls the SDK's `setPermissionMode` under the control timeout, which moves the CLI's every later turn too, since the process has one mode; made before the spawn, it is the mode the spawn takes; bypass on a process spawned without the opt-in, and a change on an ended run, are refused; a timeout leaves the mode as it was recorded, and the host logs it.

Decided in building attachment staging (#185):

- **Where the bytes wait**: `<dataDir>/attachments/<messageId>/<index>` (`adapter/attachment-stage.ts`), a directory of the environment's own, 0700 with 0600 files: one directory per queued message with attachments, named by its id, and one file per attachment named by its index, holding its bytes alone. The kind, name, media type and size are read back from the message's own `message.sent` (`run_messages.sequence` names that event); the bytes are never in the log. A write goes to a `.partial-*` directory, each file synced, then is renamed into place and the rename synced, so a message's directory is there whole or not at all. A message's attachments never change, so staging it again (a run that never received it) leaves bytes already whole as they are; bytes that are not whole are replaced with the old directory set aside (`.aside-<messageId>`) until the new one is in, and startup puts an aside copy back when a crash left nothing in its place. The host's in-memory map stays the fast path; the disk is what a restart reads.
- **Written before the answer**: `runs.send` stages a queued message's bytes inside its command, before it appends anything, so a receipt means they are on disk. A message that starts a run is not staged, since its run reads it at once, unless its adapter never received it: the host stages it as it queues it again (`requeueUnread`), logging loudly if it cannot. A stage that fails refuses the send with `internal`, thrown, so nothing is appended, no receipt is kept, and the same command id succeeds once the disk takes the bytes; `unavailable` was not used since its data names only `starting` and `draining`, nor a receipt's rejection, which would be kept under the command id so a retry could never succeed. The write is synchronous inside the command's transaction, so a large attachment (at most 20 MiB each) holds the log's write lock while it is written and synced.
- **Removed** once a run has read the message (its adapter's `createRun` returned with it at a launch, a steer's `message.delivered`, a provider-opened turn adopted with it) and when its session is purged; a deleted session's stay for its restore. A removal that fails is logged, and the next start removes the bytes.
- **Read back after the recovery sweep** (`recoverStagedAttachments`, in the `adapter-host` step after `recoverCutRuns`, so a message the sweep hands back is the environment's again): what a crash left half written is dropped; a message the log still holds as queued, by the provider or the environment, a deleted session's included, gets its bytes back into the host's map; a message a run has read, one the log never recorded (its command did not commit after its bytes were staged) or one purged since has its bytes removed; bytes that are not whole (a file missing, or a size unlike the record's) are removed loudly, and the message is read by its text alone.

The machine's own directory is read at startup and by `accounts.probe`, never by the timer.

- **The cross-check**: the Claude process asks the SDK's `accountInfo` once, after its first `init`, and reports it through `reportIdentity`; an identity unlike the one the store holds for the run's account (the email ignoring case, and the organisation only when both name one, since `accountInfo` and `auth status` need not both carry it) is an `account.updated` with change `identity-mismatch` and a warning naming both, and a fresh status read, which is the only way the store's identity changes. All three are preset to null; the Account step (#88) presets the family to the highest tier's and the effort to `high`. Decided in building the sign-in director (#135):

- **Where it lives**: `packages/environment/src/accounts/`: `signin-seam.ts` (the seam #134 left as `sign-in.ts`: the director's interface, the port, the provider-neutral `SignInProgram`, and `signInUnavailable`, the preset of an account store made without a director, which replaced #134's `signInNotBuilt`), `signin-director.ts` (the director) and `signin-process.ts` (the process seam, the real spawn and the probe runner); Claude's program in `adapters/claude/signin.ts` (#121's `sign-in.ts`, renamed so every sign-in file is spelled one way; its argv constants moved to `credentials.ts`, which `signin.ts` re-exports, so the program composes its environment from `credentials.ts` with no import cycle); the test fakes in `test/signin.ts`. The contracts' `accounts.ts` gains `SignIn`, `SignInState`, `SignInFallback`, `SignInCode`, `SignInExecutableSource` and `SignInExecutableChosenPayload`; `methods/accounts.ts` the four methods; `notices.ts` two notices. `startEnvironment` runs the director as the preset, over Claude's program, and `signInProcess` (spawn, host environment, bundled binary, managed tool, working directory) is its test seam; the test helper presets a spawn that refuses, so no test starts a real binary.
- **One sign-in per environment**, held in memory: `accounts.signin.get` (`read`) answers the latest since the environment started, running or ended, or null; a restart forgets it (the notices stay in the log). The sign-in is `{accountId, state, url, startedAt, expiresAt, fallback: {posix, powershell}, error}`, with `url` and `error` null rather than absent. Any account the environment holds can sign in, adopted or owned, signed in or not (ADR 0018's "sign in again on its card").
- **A restart** closes a sign-in the last run left running: at the director's start, when the latest `signin.updated` in the log has not ended, a `cancelled` one follows it ("The environment restarted.", as `system:sign-in`), before the wire opens. So `environment.subscribe` never replays an `awaiting-code` whose process is gone, and a client that reads the last notice of a replay reads the truth.
- **The commands** (`accounts.signin.start`, `.code`, `.cancel`, at `admin`) are commands on the environment's stream: each appends its own `signin.updated` in its transaction, with its receipt and the client's actor, and what it sets off (the spawn, the write, the kill) runs once it has committed, in the commit's own synchronous turn, so no process event (an exit, the expiry) can land between a command's notice and its transition (`signin-director.test.ts` pins the ordering); the transition goes through the same guard as the process's changes all the same, so it never overwrites a sign-in that has ended or is completing, nor re-arms its expiry. Each first checks the account: one the environment does not hold is `not_found` (kind `account`), for all three. A second start while one runs is `conflict` with reason `signin_running` and `data.accountId` the holder, the message naming its label; a provider with no sign-in program is `conflict` reason `signin_unavailable`, the message naming the account's directory; `code` is `conflict` reason `not_awaiting_code` unless that account's sign-in is `awaiting-code` and not completing, from any client session; `cancel` of a sign-in that has already ended answers it as it ended, changing nothing, of one that is completing is `conflict` reason `signin_completing`, and of a held account that is not the latest sign-in's is `conflict` reason `no_signin`. `accounts.add` starts the sign-in once it has committed, as `system:sign-in`, unless one runs (its `signIn.message` then names the holder and says to use `accounts.signin.start` after) or the provider has no program. The code is written to stdin with a line break and never recorded: not in an event, a receipt or a log line. `SignInCode` refuses any white space, so a client trims what a person pasted.
- **The process's changes** (`awaiting-code`, `done`, `failed`, `expired`, and the fallback once the executable is chosen) are `signin.updated` notices as `system:sign-in`; the state held in memory changes only once its notice is in the log (an end whose notice cannot be appended still stops the process). The URL is the `https` URL on the `visit:` line, else the first going to `/oauth/authorize`, followed by white space, over the accumulated stdout (the last 64 KiB kept), so a URL split across chunks is read once its line ends; only one `URL.canParse` accepts, so a stray `https` line before it is never published and a bad match never reaches the notice's schema. `awaiting-code` needs the URL, not the prompt after it. Any other exit than 0 is `failed` with stderr's last line, else the spawn error, else stdout's last line; a spawn that throws is `failed`.
- **Completing**: exit 0, from any running state, is the port's `finished`, the store's status read: `done` when it reads the account signed in, else `failed` with the store's message (the duplicate refusal's is "<identity> is already added as <label>."). While that read runs the expiry timer is cancelled and a cancel, a code and a removal are refused or passed over, so a read near the deadline cannot end the sign-in `expired` or `cancelled` after `account.identity-set` was appended; a removal meanwhile makes the read answer the account gone, and the sign-in `failed`. If the log refuses the notice of that outcome, the sign-in stops completing (#223): it is still `submitting` in the log and in memory, the outcome is kept, and the expiry is armed again at the sign-in's `expiresAt`. When it fires it records the kept outcome, not `expired`, and until then a cancel or a removal can end the sign-in. So a failed write never holds the one-sign-in slot until a restart.
- **Expiry**: ten minutes on the environment's clock from the start, and again from the code: a code re-arms it, so a submission gets ten minutes of its own, and a CLI that never finishes after one ends `expired` too ("did not finish within ten minutes of the code"). Expiry and cancel stop the process; its exit after is not read. The environment's close stops it, and any probe in flight, and notices nothing.
- **Removing an account** whose sign-in runs cancels it ("The account was removed.") and sends the CLI SIGTERM, while the removal deletes the directory at once (with `deleteDirectory`, or a duplicate's refusal): a CLI still running may write `.claude.json` back into the directory before it exits. The next start's sweep removes such a directory, since its deletion was recorded.
- **The process** (`signin-process.ts`): `node:child_process`, no shell, stdin, stdout and stderr pipes, UTF-8. Off Windows it leads its own process group (`detached`), and a stop signals the group: SIGTERM, then SIGKILL after five seconds on a timer that is not unref'd, so a closing environment waits for it rather than leaving a CLI or what it started running. The end is read on `exit` and reported when the streams close or half a second later, whichever is first, so a grandchild holding stdout open cannot hold the sign-in. A probe's output is bounded to 64 KiB like the sign-in's.
- **The executable**, chosen once per environment and bundled binary: the bundled binary when `auth login --help` exits 0 and its usage line names `auth login` (the exit code alone says nothing, since a binary without the command also exits 0, printing its parent's usage), else the managed tool when its probe says the same; each probe runs under the sign-in's environment, fifteen seconds on the wall clock. The managed tool is the Managed tools registry's `claude` row (#373): the first executable `claude` on the login shell's PATH, absolute entries only, never inside the harness's own files or the bundled binary's package; on Windows only a `claude.exe` (a `.cmd` shim needs a shell, which is never used). The choice is recorded as a `signin.executable-chosen` notice (`{provider, source, executable, bundled, detail}`), the smallest record that survives a restart: no settings row, since the choice is not a setting a person makes. A later sign-in reads it back instead of probing unless the bundled binary's path differs (an updated harness), and a managed-tool choice reads the registry's `claude` row again for every sign-in, in one run of the environment or after a restart, failing the sign-in when the row has none; the row is the last probe's (at the start, or a refresh from Set up or About), so a `claude` installed or removed since shows at the next probe. A choice that finds neither is not recorded: the sign-in fails, pointing at the fallback command, and the next one probes again.
- **The fallback command**: POSIX `CLAUDE_CONFIG_DIR='<dir>' <exe> auth login`, the directory in single quotes with `'\''` for a quote, the executable quoted only when a shell would split it; PowerShell `$env:CLAUDE_CONFIG_DIR = '<dir>'; & '<exe>' auth login`, each path in single quotes with quotes doubled, the typographic single quotes too (PowerShell reads them as quotes). The executable is the chosen one, else the bundled binary, else `claude`. Neither passes `--console`; a Console user adds it.
- **The label** does not follow the email after a sign-in: `accounts.add` takes a label a person chose, and a relabel is theirs to make.
- **The process's environment**: `composeRunEnvironment`, so the five stripped variables and every scrubbed family are absent and `CLAUDE_CONFIG_DIR` is the account's directory (and, since #229, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, so the login lands in the credential store every later process of the account reads); working directory the home directory.
- **For clients**: the sign-in is whatever the latest `signin.updated` carries, and `accounts.signin.get` the same for a client that did not follow the stream; refreshing a cached account list on `signin.updated` (as on `account.updated`) is owed to the clients.
- **Not built**: a code the CLI rejects while staying alive (re-prompting) is not read back into `awaiting-code`; the sign-in stays `submitting` until the CLI exits or the ten minutes pass (cancel is the way out).
- **Follow-up (owed)**: record a real sign-in on an account with the bundled binary: what `auth login` prints and how it exits after a good code and after a bad one (assumed here: 0 once signed in, non-zero otherwise, a bad code not re-prompted), and the fields `auth status --json` prints when signed in (the parser reads `loggedIn`, `authMethod`, `email`, `orgName`, `subscriptionType`); then replace the assumptions in the director's tests with the recording.

Decided in building plan usage and the hand-off (#136):

- **Where it lives**: `packages/environment/src/accounts/`: `usage-pool.ts` (the pool), `handoff.ts` (the ported policy, pure, with its own tests) and `usage-methods.ts` (`accounts.usage`, `accounts.handoff.recommend`); the contracts' `usage.ts` (`UsageWindow`, `AccountUsage`, `UsageUpdatedPayload`, `HandoffRecommendation` with its reason, basis and trigger), the two methods in `methods/accounts.ts` at `read`, and `usage.updated` among the environment notices. `startEnvironment` makes the pool after the `adapter-host` step, so it hears the log before the wire opens.
- **The pool is what clients read; the adapter's cache stays under it.** One reading per account, read through the host's `usage` (under ten seconds, `USAGE_READ_TIMEOUT_MS`, well inside a client's thirty-second request timeout, so a hung read answers unavailable instead of failing the call; `EnvironmentOptions.usageReadTimeoutMs` sets it, and the pool rather than the host owns it, so `AdapterHostOptions` has no such option), concurrent asks sharing the read in flight (after a timeout the next ask reads again, though the adapter's read may still run, so two can overlap), kept six minutes and read again at the next ask. Six minutes is one comparison everywhere (`isFresh`): fresh while under six minutes old, so the pool reads again, and the ranking and the trigger stop trusting a reading's percentages, at six minutes exactly (a refused window is trusted at any age, the recommendation bullet's exemption: a percentage goes stale and a refusal does not); they differ in what they age. The pool ages a reading from its own `readAt`, the provider's stamp, not from when the pool was handed it; the ranking and the trigger age it from its newest observation, `readAt` or a window's `observedAt`, whichever is later, so a verdict a run reported since the read keeps the reading fresh past the pool's re-read (the recommendation bullet). The pool's stamp rule: Claude's reader (#121) keeps a reading six minutes too, and ageing from the stamp is what stops the two from adding up (a reading the adapter had kept four minutes is kept two more here, by when the adapter's has aged out as well). A stamp in the future, unreadable, or already six minutes old counts from when it was handed over instead, so an adapter's clock cannot make the pool read on every ask, and the reading on the wire says so: its `readAt` and each window's `observedAt` are rewritten to the hand-over. Nothing reads on a timer: a reading is read when `accounts.usage` asks (the client runtime's request cache, refreshed on `usage.updated`), and the two-minute poll and thirty-second poll of a live run's account are not ported.
- **Unavailable, never an error**: an account whose adapter does not declare `planUsage` (the host would refuse `unsupported`), one not signed in (not read at all), a read that throws or times out, and a provider reporting no windows each answer a reading with no windows and `unavailableReason`; the call fails only for an account the environment does not hold (`not_found`). A failed read, and one of an account not signed in, is held (the notice and the hand-off see it) and read again at the next ask, as #121 does not keep a failed read. A failed read is dated when it was asked, not when it failed: it read nothing, so a verdict heard while it was under way is newer than it and folds in (the fold rule), where dating it at the failure would drop that verdict and, holding the failed reading, discard the fold it had earned in the reading it replaces. Each account's read is total: a fault around it outside the adapter's read (the host's account lookup, the store) answers that account unavailable (`Could not read plan usage: …`), logged and not held, so one account's fault never fails the batch.
- **The identity** a reading carries is the store's for the account when the provider's read names the same login (`sameLogin`: the email ignoring case, the organisation only when both name one), else the read's. Claude's read takes the identity from `accountInfo`, which may lack the organisation `auth status` gives, so without this one login could read as two identities on two environments; with it, one login is one deep-equal identity everywhere, which is what the client runtime (#142) pools by. A reading of an account removed or given a new identity is dropped, and a read that finishes after the store gave its account another identity is answered but not held.
- **The fold**: the pool hears `plan.limit` on the session streams, maps the run to its account (the runs it heard start, else the runs table), and folds the verdict into that account's window: the verdict, and the utilisation and reset it names, the rest kept unless the window rolled over before the verdict; a reading unavailable for a reason is replaced by one with the window. Only news folds (a verdict changing, a utilisation moving), since a provider reports on every response, and never a verdict older than the reading's `readAt`: the provider answered that read after the verdict, so its numbers are newer, and a window's `observedAt` is never before its reading's `readAt`. The window's `observedAt` becomes the event's time; the reading's `readAt` does not move, so a fold never makes a reading younger for the six minutes. As #121 decided for the adapter: a verdict with no reading to fold into is dropped (the next read is newer), and one heard while a read is in flight is folded into that read's reading, on the same rule (the Claude reader applies it too, by when the verdict arrived). The Claude adapter still folds into its own cache too, so a reading it keeps already carries the verdict; folding the same verdict again is no news.
- **The notice rule**: `usage.updated` (`{accountId, identity}`) goes on the environment's stream as `system:plan-usage` when a reading differs from the one it replaces in its identity, its `unavailableReason`, or a window's name, utilisation (to a whole percent, what a gauge shows), reset or verdict; the times alone are not a change, and the first reading of an account is one. The payload names the gauge, not the numbers: a client asks `accounts.usage` again. Every change is an event in the log, as `account.updated` is: at most one per account per read, six minutes apart while clients read, plus each verdict that is news.
- **Each window carries `observedAt`** beside the reading's `readAt`: a fold makes one window newer than the rest, and a client pooling two readings of one identity from two environments (#142) should take each window from whichever observed it last (`mergePlanUsage`, per window).
- **The recommendation** reads no provider: it answers from the pool at once, so two clients asking at the same moment get the same answer (the store's order breaks ties). Candidates are the signed-in accounts, each with its held reading and the runs live on it (model and effort, from the `run.started` the pool heard, for the load). Without `fromAccountId` it names the account with the most room of two or more (`most-room`, else `no-target`). With it, the account the work runs on: the threshold it has met (`handoffTrigger`, on a window observed under six minutes ago, by the window's `observedAt` as the ranking judges freshness, so a verdict a run reported since an older read counts, or a refused window of any age, since a percentage goes stale and a refusal does not), and the other account with the most room ("the most room of the others" in the sentence), one other being a choice (`minCandidates` 1), never one whose tightest window the provider is refusing; the reason is `limit-reached` (a refused window), `limit-near` (a threshold met), `most-room`, or `no-target` with `accountId` null. `message` is the sentence every client shows. Readings six minutes old by their newest observation rank nobody, a metered account is never named, an account with no room (a refused window, or a full one) counts among the candidates but is never named, so every one full or refused is `no-target`, and the answer carries the winner's room, its tightest window, how many accounts it was chosen from and the basis. `candidates` counts the accounts ranked, as `recommendProfile` counts its ranked set: signed-in, with plan limits and a fresh reading with a usable number, a full or refused one among them (handing off, a refused other account is ranked and counted, just never named), the account handed from not; an account never read, unavailable, stale, or whose windows have all rolled over is not ranked, so not counted, and `no-target` answers both fewer ranked than make a choice and none ranked with room. The recommendation does not move anything: forking onto the account is the act (#137), and automatic rotation stays rejected (ADR 0015).
- **The port**: `recommendProfile` combines `currentWindow`, `bindingWindow` and `planHeadroom`, with tests for the recommendation and lapsed-window cases. A reading is the wire's `AccountUsage`, so utilisation, thresholds (0.9, 0.98, 0.95), headroom and the reservation (0.0075 of a baseline window) are fractions; a window is named by `window` and dated by `observedAt`; the verdict field is `allowed`; available means no `unavailableReason`; `handoffTrigger` takes the time and ignores a window rolled over since it was read; `planHeadroom` is never below 0; `recommendAccount` (over `rankAccounts`, which also gives the candidate count) takes `minCandidates` 1 and never names an account with no room; freshness is under six minutes; the per-model bucket is matched on the window's name alone, since a window has no label here. Not ported: the plan-weight table, since no reading carries a plan tier (the status probe reads `subscriptionType` and the store drops it), so an entry's `plan` is given by no caller yet and every basis is `percentage`; `mergePlanUsage` (the client runtime's, #142); the meter slots (a renderer's).
- **Chosen defaults, for review**: the ten-second read timeout on the wall clock; the thresholds are the shipped defaults, with `handoffThresholdsWith` ported but no settings key; `ultracode` is never set, since no run asks for it; the notice in the log rather than beside it.
- **Owed**: to #142, pooling the readings by deep-equal identity and merging per window on `observedAt`; to the clients, refreshing `accounts.usage` and asking `accounts.handoff.recommend` again on `usage.updated`; to a follow-up, carrying the plan tier into the reading so the recommendation can weigh plans, and a settings row for the thresholds if one is wanted.
- **Owed: the glossary** (for `/domain-modeling`): **Hand-off** in `CONTEXT.md` is continuing a session on another environment, while `accounts.handoff.recommend` and this spec's user story 10 use it for moving work to another account on the same environment (a fork onto another account, ADR 0015); the two need reconciling. **Reading**, **window**, **verdict** and **headroom**, which the wire now carries, are not defined there either.

The contract's `deleteTranscript` takes those accounts. **The exception, even when the delete asked**: an adopted account's directory is never touched, since it is read and written only by the provider's own CLI (user story 5, ADR 0018, the glossary's adopted account), so the host hands the adapter the owned accounts alone, and only those of its own provider (a session whose runs went through another provider's account never has that directory handed to this adapter; known gap: the purge asks one adapter, the latest run's, so such a session keeps the earlier provider's files and its tombstone reports only the one adapter's outcome; it cannot arise in milestone 1, where Claude is the only adapter that deletes a transcript, and a session changes provider only when it names no account and the default moves to another provider's; owed to the second adapter that declares `transcriptDelete`, milestone 2), and when the session ran under an adopted account the tombstone records `kept` with reason `adopted-directory`, whatever was deleted from owned directories (the adapter is not called at all when every account was adopted).

Auto memory was #121's (`<data dir>/auto-memory/<slug>-<hash>` per repository identity, else workspace path, through `settings`, for every account); #137 adds only that `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE`, which the bundled CLI reads before any setting, is in `CLAUDE_SCRUBBED_VARIABLES`, so no Claude process inherits it.

A source that is itself a fork no run of which has linked a provider session (it never ran, or its runs failed first) is forked from what its own `session.forked` names, its `fromProviderSessionId` and `atMessageId`, whichever message the fork is taken before (whose text is still the draft), since nothing it was sent reached the provider, and its copy of the rows is the one copied; before, such a fork of a fork started fresh. A source with a rewind not yet continued from is forked at the rewind's message, since the provider session still holds what the rewind hid. Allowed while the source runs; the fork capability is checked on the fork's account when there is a provider session to fork. - **Rewind**: the message must be a user message a run has read, in the visible transcript; the session's first is `use_new_session` unless the session is a fork that carried a provider session in; a live run is `run_active`. The message's text becomes the session's draft: `session.draft-set` in the same append as `session.rewound` (ADR 0022). **Queued messages refuse it**: while the environment holds queued messages for the session the rewind is `conflict` reason `queued_messages`, naming their ids, because the next run reads the environment's queue before its prompt, so a message sent before the rewind would reach the provider after a history that hides what it answered. Refusing was chosen over dropping them into the draft: the draft holds one text, while a queued message can carry attachments and its sender's ceiling and there may be several; the client withdraws them (or lets a run read them) and rewinds, as it already stops a live run first. **What the host is still handing back is waited for** (#245): the host can append `message.requeued` after a run's `run.ended` has committed (an interrupt whose answer comes after the turn completed on its own names what the provider still held; a send or a withdraw the provider answers after the end), so a rewind that read the queue in that gap was accepted and the message then reached the next run after the rewound history. `sessions.rewind` is therefore a prepared command (as `runs.withdraw` is): with no run active, its `prepare` waits until the host has nothing of the session's still handing back (the host's `handingBack` and `handedBack`, which track each interrupt's answer, each send and each withdraw the provider has not answered, per session, and stop waiting once a run is active), for at most `REWIND_WAIT_MS`, 10 s on the environment's clock, and its transaction then decides on the log as it stands: after a hand-back that came in time a refusal names messages the environment holds, which the client can withdraw; after one the wait ran out on it names the message the provider still holds (below), which a withdraw cannot reach until the hand-back lands. The wait is bounded because it holds up every later command of the same client, whose outbox sends one at a time; the adapter contract requires those answers to settle in bounded time (`AdapterRun`), and Claude answers an interrupt within its 8 s interrupt timeout, a send at once and a withdraw within its 15 s control timeout. Waiting was chosen over holding the run's `run.ended` until the interrupt answers, which would leave a run live for as long as an adapter takes to answer and moves the end every other reader counts on, and over a new refusal reason for "settling", which would put a transient state on the wire that a client can only retry. **A message the provider still holds refuses it too**, with no run live, while the session's process runs or the host may still hand the message back: a provider that reads its queue opens a turn with it after a completed end (Claude's CLI, for a message written to it as the turn finished), which the host adopts after the rewind, and a hand-back the wait ran out on lands after it. Such messages are named in `queued_messages` with the environment's, since both are sent after the history the rewind keeps. When the current process stops or exits with no run live or turn awaiting adoption, the host takes its provider-held messages back as `message.requeued` (#263); the environment-held queue then refuses the rewind. A late stop of a process a cold start replaced never takes back messages the replacement holds. **A turn waiting on its mode change counts as live** (the host's `runActive`, as a start counts it): it is adopted after a rewind that landed meanwhile, or let go with its messages requeued after it, so the rewind is `run_active`, naming the run the turn followed. The next run is `rewind` (resume at the entry before the message, dropping its turn when that is all that follows, #121's `resolveRewindPoint`) until a later run has linked the provider session and ended `completed` (`session.provider-linked` and `run.ended` both survive compaction, #123), then `resume` as ever; a run that completes without linking one (no Claude run does: a cold run's init links it) never resumed the rewound history. A run that linked the provider session and then failed does not continue the rewind: it may have failed before the provider wrote anything, and a plain resume would then bring back what the rewind hid. When it did write a turn before failing, or was interrupted after replying, the stored chain's latest entry has left the message behind: the Claude adapter finds the message only on an older branch of the stored session and continues the chain as it stands (a plain resume, or for a fork taken at such a rewind a fork of the whole), which is what the transcript shows; a message the store does not hold at all is still refused as not placed. When a rewind commits the host stops the session's process (reason `rewound`) whatever holds it, since a kept process holds the cut provider session and could open a turn of its own on it; a live background task ends with it. Compaction and undo: built by #218 (its notes below), which took the simpler choice named here, leaving a session out of compaction while its rewind can be undone; the undo's window is ADR 0022's, until a run starts after the rewind, which is narrower than "not continued from" above.

The next run can therefore store the session's second visible message as its first provider entry. Previously, rewinding there was accepted and every retry failed at the stored resume-point lookup. Decided in building the completions surface (#138):

- **Where the pieces are**: in `contracts`, `completions.ts`: the paths, the namespace, the extension schema (`CompletionsExtension`, which refuses a mode outside the four), the request, the chunk, the whole completion, the model and its listing, the error body, the parameter lists, the 200,000-character cap and the fifteen-second heartbeat, exported under `completions/`. In the environment, `completions/`: `surface.ts` (the routes, authentication, the turn, the answer's writing), `request.ts` (the request read into a turn), `answer.ts` (the events rendered into chunks), `models.ts` (ids and the listing), `errors.ts` (OpenAI's error body). Blocks elsewhere: `serve/http.ts` gains a prefix route, which `/v1/` takes after every exact route; `serve/start.ts` builds the surface on the account store's catalogue and closes it before the wire and the listeners; the turn goes through the method code the wire's commands use, extracted beside #131's `startRunIn`: `sessions/methods.ts`'s `createSessionIn` (`sessions.create`'s body: the run parameters checked, the mode clamped, the decider over the session's state) and `runs/run-methods.ts`'s `sendIn` (`runs.send`'s); `startRunIn` carries a run's `appendedInstructions` and answers its policy; `runs/run-decider.ts` gains `appendedInstructions` and `originOfActor` (a switch over the actor kinds), and `decideSend` the origin of a run it starts; `adapter/host.ts` hands a run its composed instructions and then its own, and a run it starts from the queue takes the actor's origin (a completions request's queue runs as `completions`, no longer `client`) and the own instructions of the run before it (held in memory, since the log does not record them: after a restart a run of the queue carries none).
- **A run's own instructions reach its process**: Claude fixes the instruction text at spawn (the preset's `append`), so the adapter's spawn key now holds it, and a run whose text differs from the kept process's is served on a fresh process spawned with it (the store resume), never on the kept one; before, a completions request resuming a warm process lost its `systemPrompt`, and one program's instructions carried into later runs.
- **Authentication**: the bearer token is verified as the wire verifies an `auth` frame: none, one not issued here, a revoked or an expired one is 401 with that reason as the code. A client session of any kind but `program` is 403 `client_kind`, whatever its scopes; a missing scope 403 `forbidden`: `read` for the models, `sessions:write` and `runs:drive` for a turn. 503 `unavailable` before the startup gate, for a turn while draining (the models still answer), and for a turn that arrives once the environment has begun to stop (the surface closes before the listeners), checked again after the body is read and after a fork or a rewind, so a turn that was waiting when the surface closed starts nothing. Nothing changed in pairing: `access.pairings.create` and `pair` already take the scopes and the ceiling, and the kind is the exchanging client's, which `/api/pair` takes as `program` since #109, so a program pairs with `--scopes read,sessions:write,runs:drive` and a ceiling.
- **Model ids**: a label's slug is lower case, each run of anything but a letter, digit, dot, underscore or hyphen one hyphen, trimmed of hyphens (`account` when nothing is left); a slug two labels share gets `-2`, `-3` in the accounts' order. The part after the first slash is a model id, else a family (its strongest model). A **bare id** is the default account's on a fresh session, and **the session's own account's** on a request naming a session (a fork's source), so changing the default account never breaks an ongoing conversation that names its model bare. `GET /v1/models/{id}` answers the model under its listing id whatever named it, and 404 for a signed-out account's, as the listing leaves those out; a turn on one is 409 `account_unavailable`. The accounts are the account store's (#134): each record's label, its facts as the host runs it, and the store's default; a bare family is not yet read against `accounts.defaultModelFamily`.
- **The turn is one transaction**: a fresh session is created through `createSessionIn` (tagged `completions`, on the model's account and model, with no mode of its own, in the directory the request names, else `<data dir>/scratch/<session id>`, made 0700, as a `directory` workspace until the workspace workstream adds the scratch kind; the directory is removed if the transaction fails), or the named session is tagged `completions` when it is not; then the run starts through `startRunIn` with origin `completions` and the actor `{kind: completions, attended, ceiling, clientSessionId}`, the ceiling the program's as it is now. The session's events are the program's client session's; the run's are `system:completions`, as #131's `startRun` names them. A named session on another account than the model's is 409 `account_mismatch` (fork it onto the other account instead). A refusal records nothing: the checks a fork or a rewind would outlive (the account signed in, the effort one the model takes, each attachment a kind the model's adapter takes, refused `unsupported` at `agent-harness.attachments.N.kind`, the session here and on the model's account) run before either is asked for. Each of those commits in a transaction of its own, so a refusal the checks do not foresee still leaves it behind: a race (the environment beginning to stop or drain, the account signed out or the session deleted meanwhile), or no mode at or below the ceiling available to the account, which no Claude account meets (every mode is available to each).
- **Session ids** are read in lower case (the request's `sessionId` and `rewindToMessageId` as they are read), so a session named in upper case continues as itself.
- **A turn on a live run is a queued message** (ADR 0022; the glossary's **Queued message**, which the provider may steer): when the named session has a live run, the turn is sent through `sendIn`, and the answer follows the live run from `after` (else from the moment of the request), its first chunk saying `delivery: queued` (a fresh run's says `prompt`, as `message.sent` does). It follows whichever run reads the message (its usage then that run's, never the run followed before): the live one when the provider folds it in (`message.delivered` `steered`), else the run that opens with it (a run of the queue, or a provider-opened turn); it ends with that run. When the run it was sent to ends without reading it and it is left in the environment's queue with nothing to read it (the run was interrupted), the answer ends there, its last chunk naming the message in `agent-harness.waiting`. When the message is withdrawn before any run reads it (`runs.withdraw`, #228), the answer ends at once, `error` with code `withdrawn` (409 for a whole answer): no run will read it, and its text is the session's draft; the runs go on. Whichever run reads the message runs on the live run's model (the live run, a run of its queue, which takes the model of the run before it, or a turn its provider opens), so every chunk and the whole answer name that model, not the one requested (by its bare id once its account has left the listing, removed while the run went on). What a live run cannot take is reported ignored, each by its path: `model` when it names another model than the live run's, `permissionMode`, `systemPrompt` and each system or developer message (`messages.N`), `thinking` or `reasoning_effort`, `attended`. The wire says `delivery` rather than `steered`, since the glossary's **Steer** is a delivery kind the provider decides, not what the request does; the spec's "its trailing message is a steer" reads as "is sent as a queued message".
- **`after`** past the log's head is 400 at `agent-harness.after`; on a session with no live run it has nothing to attach to, is reported ignored, and a new run starts.
- **Messages**: the trailing message must be the user's and have text (else 400 at `messages`; *since #139*, trailing tool messages resume a parked turn instead); system and developer messages, after `systemPrompt`, are the run's own instructions, joined by blank lines after the composed ones, at most 200,000 characters over the three sources together (400 naming the one source past it, `systemPrompt`'s own bound being the extension schema's, else `messages`). On a fresh session the other earlier messages ride as `Earlier in this conversation:`, one `User:`, `Assistant:` (with its tool calls) or `Tool result (<id>):` paragraph each, a `---` line, then the turn, as the prompt's one message. Content parts other than text are 400 `unsupported_content` (images and files go in `agent-harness.attachments`), or ignored and reported as `messages.N.content.P` under `ignoreUnsupported`.
- **The namespace**: a field neither the request nor the run knows (a later version's) is dropped and reported (`agent-harness.<field>`). *Since #550* `browser` is known: `headless` or absent, any other value refused 400 at `agent-harness.browser`.
- **Parameters**: `top_logprobs` joins the refused list beside `logprobs`; `max_completion_tokens` is `max_tokens`'s alias; `tools` and `tool_choice` are ignored and reported until client-tool passthrough (#139), never marked honoured (*since #139* they are honoured: its notes below). `max_tokens` counts four characters a token (no tokenizer runs here). A stop sequence or the budget ends the answer, `finish_reason` `stop` or `length` (`length` when the budget falls before a stop sequence in the same text), and not the run, which goes on to its end in the session as after a disconnect; text that may begin a stop sequence is held back until what follows settles it, and no stop sequence is matched against the blank line the answer puts between two items, or across it. An answer so cut carries no `usage` (the run's spend is not known yet): the whole answer leaves the field out, and a stream sends no usage chunk. `ignored` lists request paths in the order they were read: the refused parameters, the ignored ones, the passthrough ones, the extension's, the content parts, then what the turn itself could not use.
- **The stream**: the first chunk (`delta: {role: assistant, content: ""}`) renders the first event of the followed run and carries the session, run and message ids, `delivery`, the mode, `clamped` (`{requested, effective, ceiling, reason}` or null) and `ignored`. Text comes from `assistant.delta` and, for what the deltas did not carry, `assistant.text`; two items are parted by a blank line; thinking is not rendered. `tool.started`, `tool.ended`, `prompt.opened` and `prompt.answered` ride `agent-harness.activity` on empty-delta chunks (*since #139*, a call to the caller's own tools is a `tool_calls` delta instead, and an answer may end `tool_calls`). The followed run's `run.ended` is the final chunk, `stop` when it completed, else `error` with an OpenAI `error` object beside the choices (the run's error, the end reason as its code) and `agent-harness.ended` (*since #833*, and `agent-harness.waiting` when the run never had a prompt turn's message: its notes below); then the usage chunk when `stream_options.include_usage` asks, then `data: [DONE]`. `seq` never decreases (the final and usage chunks share the end's). The heartbeat is the comment `: keep-alive`, fifteen seconds after the last write on the environment's clock. An answer still open when the environment closes ends with an `error` chunk, code `closing`, and `[DONE]`; one the environment cannot go on with (the session cannot be read back, an event cannot be rendered, where a queued message waits cannot be read) ends the same way with code `internal`: never a bare close, and never an exception thrown on a later turn of the event loop.
- **A client that goes away** stops its answer and nothing else, however far the request got: the surface listens for the connection's close from the request's first moment, and a request whose client left before its turn began starts no run (a fork or rewind it asked for may be recorded by then). A streaming client that stops reading is let go once more than 4 MiB of its answer waits unsent and nothing drains for fifteen seconds (a chosen default: a burst may pass the cap before the socket has had a turn to flush); the run goes on. A whole answer has no such cutoff: it is one write, of a body already held whole while the run went on.
- **The whole answer** is folded from the same chunks: the content, the finish reason, the usage from the run's last `usage.reported` (else its end's), the first chunk's fields with the last `seq`. A run that did not complete is not a 200: 502 for `error`, 409 for `interrupted`, 503 for `drained` and `disposed`, the body naming the session, the run and its end (*since #1045*, and `waiting` when the turn's message still waits: its notes below); an answer the environment stopped is 503 (`closing`), one it could not go on with 500 (`internal`), and one whose queued message was withdrawn 409 (`withdrawn`).
- **Errors**: 400 `invalid_json`, `invalid_params` (the first issue's path as `param`, `agent-harness.permissionMode`), `unsupported` (a capability the adapter lacks, an attachment kind it does not take, from the environment's `invalid_params` with reason `unsupported`), `unsupported_parameter`, `unsupported_content`, `workspace_not_found` (not absolute, or no such directory), 413 `too_large` (the body is capped at 64 MiB, a chosen default); 401 `unauthorized`, `expired`, `revoked`; 403 `client_kind`, `forbidden`; 404 `model_not_found`, `session_not_found`, `message_not_found`; 405 on a route's wrong method (`Allow: POST` for completions, `GET, HEAD` for the models); 409 the conflict's reason (`account_mismatch`, `account_unavailable`, `mode_unavailable`, `run_active`, `queued_messages`, `use_new_session`); 500 `internal`; 501 `not_implemented`; 503 `unavailable`. A `ContractError` the environment throws maps by its code. The types are OpenAI's families by status (`conflict_error` for 409).
- **Fork and rewind** are #137's `sessions.fork` and `sessions.rewind`, run through the method table as the program's client session, so the scopes are checked where every client's are: `forkSession` is `sessions.fork` (with `rewindToMessageId` as its `atMessageId`, and the model's account), then the turn runs on the fork as a continued session, its first run continuing the source's conversation (up to the message, when one is named); `rewindToMessageId` alone is `sessions.rewind` before the turn, whose run then continues from just before the message. A refusal of either names the request's field that asked for it, `agent-harness.forkSession` or `agent-harness.rewindToMessageId`: 400 `unsupported` for an adapter that cannot fork or rewind; for a rewind, 409 `run_active` while a run is live (where a turn alone would be queued to it), `queued_messages` while the environment holds messages for the next run, `use_new_session` for the session's first message; and 404 `message_not_found` at `agent-harness.rewindToMessageId` for a message not in the session's visible transcript. Each sets the draft as it does for any client (the message's text), and the turn leaves it there.

Decided in building read now and withdraw (#228):

- **Where it lives**: the contracts' `runs.readNow` and `runs.withdraw` (`methods/runs.ts`, `runs:drive`, each with a `commandId`) and `message.withdrawn` (`{runId, messageId, heldBy}` on stream kind `session`, not `list`-flagged; `runId` is the run the message was sent during, and the envelope's correlation); the environment's `runs/queue-verbs.ts` (the two handlers, spread into `runMethods`), `decideReadNow` and `decideWithdraw` in `runs/run-decider.ts`, the host's `readNow`, `withdraw`, `settleWithdraw` and `nextRunBasis`, and `AdapterRun.withdraw` with `WithdrawUnsupported` in the contract. The runs projector's `run_messages.held_by` gains `withdrawn` (the table's statement changed, so a database made before rebuilds it from the log at registration), and the snapshot's fold drops a withdrawn message's item: its text is the draft now, and the log keeps it.
- **Read now with a run live**: the command appends nothing (`changed: false`) and answers `{sessionId, interruptedRunId, runId: null}`; once it commits the host interrupts the run with cancel as `runs.interrupt` does, re-owns what the provider reports it held (`message.requeued`, in the order sent, the host's), and records the end `interrupted` with cause `read-now`. The next run starts only when both the interrupt has answered and the end is recorded, so what the interrupt handed back is in the queue it reads: it is the run the environment's queue would have had after this one (`startFromQueue`, `system:adapter-host`, the interrupted run's model and effort, origin `client`), resolved for the caller under the caller's ceiling as it is then and each queued sender's, the lowest of them, and its `run.started` names the queue in the order sent. The interrupt under way is a promise on the live run (`LiveRun.interruption`): a read-now while a person's interrupt is under way waits on it, and its run of the queue starts once that interrupt has answered; a second read-now on the same run changes nothing (one interrupt, one run of the queue); a person's `runs.interrupt` after a read-now is the last word, so the run ends with cause `user` and no run of the queue starts. An interrupt the adapter cannot make ends the run as the host's (cause `read-now` still) and the run of the queue starts after it all the same. A turn the provider opened meanwhile is adopted first, as after any end: it reads what it opened with, once, and the environment's queue waits for the run after it.
- **The launch window reads next, not now**: `createRun` is synchronous, so a live run has no adapter run only when `createRun` threw, and its `error` end follows within a microtask, before any command can land; a read-now in that window has nothing to interrupt, the run's messages come back to the queue (the adapter never received them), and the run of the queue starts after that end. No wire test can reach the window.
- **Read now with no run live**: when the environment's queue holds messages (a plain interrupt left them), the run of the queue starts in the command's transaction, attributed to the caller under the command's id, and the answer names it (`runId`). It is the run the queue would have started after the run before: that run's model and effort (`AdapterHost.nextRunBasis`, the host's own record of the run it last ended, else the log's), for the caller, clamped to the lowest ceiling among the caller and the queued senders; `run.policy.resolved` follows its `run.started` in the command's append (permissions spec, #129's notes). **With nothing queued**, by the provider or the environment, the command is accepted with no event and a live run is left alone (the ticket's chosen default): a read-now that interrupted a run with nothing to read would only lose its work. The decider counts what the log says the provider holds, which is the provider's queue: every message that leaves it is logged (read, taken back at an end or an interrupt, given up to a withdraw), and the queue is the session's, not the live run's, since a replaced process hands its queue on under the runs the messages were sent during. Provider-held messages with no run live to interrupt (a turn the provider opened with them waits to be adopted) are that turn's to read, and count as nothing queued. A read-now that would start a run passes the drain's gate: `unavailable` while draining, no receipt.
- **Withdraw is a prepared command**: a provider-held message is the provider's to give back, and only it can say, asynchronously, whether it still holds it; a command's handler answers inside its transaction, at once. So the method table gained `PreparedCommand` (`serve/methods.ts`) and dispatch runs its `prepare` before the command's transaction, unless a receipt is stored under the command id (a retry is answered from the receipt and the provider is not asked again). A `not_found` for a message the provider says it no longer holds is such a receipt, a rejection, stored, and final for that command id, rightly: either the provider read it (its `message.delivered` follows), or, in the race where another request's cancel took it, the requeue protocol below has already put it back in the environment's queue, where the next command, under a new id, withdraws it. Only a thrown error (`internal`, `unsupported`, `unavailable`) stores nothing, and the same command id then asks again. `runs.withdraw`'s `prepare` asks the provider (the host's `withdraw`, through the session's live run, since the provider's queue is the session's) only for a message the log says the provider holds, of a session still here, whose text the draft has room for.
- **Requeue, then withdraw**: when the provider says it cancelled the message, the host appends `message.requeued` at once, in a transaction of its own, as it does for what an interrupt hands back: the environment holds the message from then on. The command's transaction then withdraws an environment-held message (`heldBy` on the event and the answer is always the holder when the withdraw began: `provider` here, `environment` for a message the environment held all along). So nothing that happens between the cancel and the transaction can lose the message: a transaction that fails leaves it queued, and the retry (the same command id, since no receipt was stored) withdraws it without asking the provider again; a receipt stored under the command id while the provider answers leaves the first answered from that receipt with the message queued and visible, withdrawn by the next command (a second request under the same command id no longer answers first: it waits for the first's `prepare` and is answered from its receipt, the provider asked once, env spec, #448). While the command decides, the host keeps the message out of any run that starts (`settleWithdraw` lets it go once the handler has run, or on the next turn of the event loop when a receipt answered it), so a run that an end starts from the queue meanwhile cannot read it. The Claude process remembers the ids it cancelled, and those whose cancel it sent without hearing back, and answers withdrawn when asked again (a second `cancelAsyncMessage` would answer false, as for a read message), unless a turn has since been seen reading one.
- **A withdraw during an interrupt**: the interrupt cancels the provider's whole queue first (Claude's `cancelQueued`), so a withdraw asked meanwhile hears the provider no longer holds the message while the log still says it does. When the provider says so while its run's interrupt is under way, the host waits for the interrupt, which hands the message back (`message.requeued`), and the command then decides on the log as it stands: environment-held, withdrawn. The message is kept out of the read-now's run meanwhile.
- **Outcomes**: environment-held, or given up by the provider, withdrawn; provider-held and not given up, `not_found` (the provider read it, and its `message.delivered` follows); read, withdrawn already, unknown or purged, `not_found` with data `kind: message`; a deleted session's, `not_found` kind `session` before its state is looked at (the deleted-command sweep names both methods; it now counts a command naming a `messageId` too); a draft with no room, `conflict` reason `draft_full`, the provider not asked (checked after the provider's word, so a message the provider read while the withdraw waited on its answer is `not_found` even when the draft filled meanwhile, never a refusal whose retry could only find it gone). An adapter that throws is answered `internal` with no receipt, so the same command id is tried again; one whose provider has no way to take a message back throws `WithdrawUnsupported` and the withdraw is refused `invalid_params`, reason `unsupported`, capability `withdraw` (ADR 0022: a client draws the verb dim with the reason), never answered as if the provider had read it; an adapter declaring `withdraw` with no method is refused the same way. With no run live to ask, a provider-held message is answered not withdrawn: a turn the provider opened with it is being adopted and reads it.
- **The race with the provider's read** is settled at the provider: whichever of its read and its cancel comes first wins, and the log says which, `message.delivered` for the read or `message.withdrawn` for the withdraw, never both.
- **Who may withdraw**: any client session with `runs:drive`, not only the one that sent the message. No spec rule restricts it (ADR 0022 makes withdraw a verb on the session's queue, ADR 0001 has one person per environment, and the terminal UI's `↑` withdraws the newest queued message whoever sent it); a withdraw only removes a message, so it can never raise a run above a ceiling.
- **The draft**: the withdrawn text goes into the session's draft in the transaction of `message.withdrawn` (`session.draft-set`, not correlated to the run, since the draft is a session field), in place of an empty draft, else after it on a paragraph of its own (`draft + "\n\n" + text`). Nothing is cut: when the result would pass 65,536 characters (UTF-16 code units, the draft's limit) the withdraw is refused `conflict` with reason `draft_full`, the message stays queued and its text stays in the log, and the person clears or shortens the draft and withdraws again; a message whose text alone passes the limit cannot be withdrawn, only read. Verified first against the existing terminal UI: taking back the newest queued message drops it and hands back its text, and the composer asks for it only when the box is empty (`recallOlder`: "Empty box first, and only empty: with anything typed, ↑ is history") and puts the text in the empty box; it never merges. The environment's draft is shared by every client, so it cannot promise an empty composer: it never replaces text already there, and appends instead. **Beside #137's drafts**, the rules are recorded side by side and all hold: a fork writes its anchor's text as the new session's draft (a new session, so nothing is there to keep; cut to the limit, #137); a rewind replaces the session's draft with the rewound message's text, and is refused `queued_messages` while the environment holds queued messages, so no withdrawn text is pending when it lands (#137); a withdraw appends to whatever the draft holds, so a withdraw after a rewind appends after the rewound text, and refuses rather than cuts. Nothing was changed in #137's rules; whether a rewind should keep a draft a person typed, as withdraw does, is #137's to decide. A withdrawn message's attachments do not come back (the draft holds text); their staged bytes are released as a read message's are, on `message.withdrawn`, and the recovery sweep drops a withdrawn message's bytes too.
- **Claude**: `withdraw` takes a message still in the prompt pump out of it at once (the SDK has not read it, so the CLI cannot have it); otherwise, once the owner of any undecided turn is known, a message this process cancelled before, or sent a cancel for without an answer, is withdrawn again without asking; a message a turn has been seen reading (no longer among the process's queued sends) is not withdrawn and the CLI is not asked; any other goes to `cancelAsyncMessage(uuid)` under the control timeout, whose `true` means the CLI dropped it (the process forgets it, so no interrupt hands it back) and `false` that a turn read it. A cancel that times out throws, remembered as sent, so the host's retry hears it withdrawn. Without the control (detected per process, #121) it throws `WithdrawUnsupported`. Verified on the scripted SDK only, as the interrupt's receipt was.
- **Owed**: recording `cancelAsyncMessage` on a signed-in account (its answer for a message queued, one read, and one a turn is opening with) beside the queued-turn recording #121's deviations owe. To the client runtime (#80's outbox and composer): a client that saves its composer with a debounced `sessions.setDraft` can overwrite the text a withdraw appended to the draft, since `sessions.setDraft` is an absolute setter; the composer must take the `draft` patch in before its next save. To the GUI spec (#84): "edit is withdraw then send" loses a message's attachments, since the draft holds text only; Edit on a queued row with attachments should say so, or keep them client-side for the send. To the glossary (for `/domain-modeling`): **prepared command**, a command that hears from outside the log before its transaction (`runs.withdraw` the first).

Decided in building the refresh of an expired login before a cold resume (#229):

- **Verify-first, read on 0.3.281 and the bundled 2.1.281 (no account)**: of the three ways the ticket named, a status read that refreshes is not there (`auth status --json` prints whether a token is present, `loggedIn`, and calls no refresh); the SDK's own refresh path is there but not usable (the undeclared `getOAuthToken` option sets `CLAUDE_CODE_SDK_HAS_OAUTH_REFRESH` and answers the CLI's `oauth_token_refresh` control request with the access token the host's callback returns, but the CLI asks only when its entrypoint is `claude-desktop`, `local-agent` or `claude-vscode`, never the SDK's `sdk-ts`, and only on a 401 with no refresh token, and the callback must mint the token itself, which makes the harness the credential holder ADR 0018 rules out); and no option keeps the refresh token in the temporary copy (the store-backed resume deletes `claudeAiOauth.refreshToken` whatever it is given). Where it equals `CLAUDE_CONFIG_DIR` it changes nothing. A store-backed resume's CLI, in the SDK's temporary directory, then reads the account's own login, refresh token included, refreshes it under the lock every process of the account shares (the CLI reads the login again under the lock and takes a token another process rotated rather than refreshing again), and writes it back where the next process reads it; so a login that lapses while a kept process lives is refreshed too. The pinned SDK passes the variable through to a resumed CLI (it sets it itself on Windows only, and only when the run's environment has none), run against the real `query()` in `sdk-store-resume.test.ts`.
- **No credential file is read; the refresh query runs before every cold resume** (a chosen default, for review): a cold run that continues a provider session through the store (resume, fork, rewind; not a fresh run, and not a resume without a store, whose CLI runs in the account's own directory) first has the CLI refresh the login in the account's own directory, through the usage read on an unsampled query there (`login-refresh.ts`; the query in `index.ts`). The harness never opens `.credentials.json` (ADR 0018: it holds no Claude credential, and an adopted directory is read only by the provider's own CLI), so it cannot tell a fresh login from an expired one beforehand. The cost: one CLI start (bounded by the fifteen-second control timeout) before every cold resume through the store, where reading the token file's expiry would have cost nothing for a fresh login. So the SDK's temporary copy starts with an access token that works, whether or not the variable holds.
- **The verdict comes from the CLI**: an answer that reaches the plan's limits (`rate_limits_available` and a `rate_limits` object, as the plan-usage read takes them) is a usable login. Anything else (no limits reached, no usage method in this SDK build, a CLI that did not start or answer within the control timeout, a read that failed) is settled by the status command in the account's directory: signed out is a lapsed login, since the CLI clears one whose refresh the provider refused; signed in, or unreadable, could not tell (no network, a rate limit), and the run goes on with a diagnostic, its CLI refreshing from the account's own credential store through the variable. No failure message is parsed.
- **Once per account, outside the config-directory queue**: concurrent cold resumes of one account share the query in flight (a map by directory, whose entry goes when the query settles, however it settles), so two sessions resuming together refresh once and never offer a rotated refresh token twice (`login-refresh.test.ts`, with the CLI's refresh scripted to refuse a refresh token used before, as the token endpoint does); a later resume runs its own query, which finds the login fresh, and the CLI refreshes nothing. The query does not run under #121's config-directory queue, against the ticket's wording: the queue serialises the SDK helpers that read `CLAUDE_CONFIG_DIR` from the process's environment, and the refresh query is handed its environment explicitly and reads nothing of the process's, while a CLI start held there would hold every account's helper calls (titles, rewind and fork points, subagent transcripts) for up to fifteen seconds. Across processes, and against the unsampled queries and kept processes of the same account, the CLI's own refresh lock in the credential store serialises refreshes.
- **A lapsed login starts nothing**: the run ends `error` with code `login_expired` and a message naming the account by its label (the host hands the adapter `AccountRef.label`, from `AccountFacts.label`; an empty or blank one names the id) and saying to sign in again; the process is let go as one that never ran; the directory is marked lapsed; and, after the run's end, the run context's `recheckAccount()` has the account store read the account's status again at once (`HostAccounts.recheck`, as the identity cross-check does).
- **The status of a lapsed account**: Claude's status is the binary's, except that a lapsed directory the binary reads signed out reads `expired` (`AuthStatus.expired`, its description updated), so the pickers show it and sign in again is the way back (an expired account is refused new runs, `account_unavailable`). Once the binary reads the directory signed in again (a sign-in from the harness, or the provider's own CLI on an adopted directory) the marking is gone. No refresh is retried behind a status read: the refused login is cleared, so only a new login can recover it, and the store's own reads (at most fifteen minutes apart, for every account whatever its state, and at the end of a sign-in) see one. A sign-in landing while a refresh query is in flight is not marked: the CLI clears only the login it refused, and the status command read after the query sees the new one. Decided in building `sessions.undoRewind` (#218):

- **Where it lives**: the contracts' `sessions.undoRewind` (`methods/sessions.ts`, `runs:drive`, `{commandId, sessionId}`, answering `{sessionId, messageId, rewindSequence}`) and `session.rewind-undone` (`{toMessageId, rewindSequence}`, a transcript type on stream kind `session` beside `session.rewound`, not `list`-flagged, carrying no run id); the command, `latestRewind` and `undoableRewind` in `sessions/fork-rewind.ts`; the fold's undo in `runs/transcript.ts`; the skip in `sessions/compaction.ts`.
- **Which rewind**: the latest `session.rewound` that no `session.rewind-undone` names (`latestRewind`). Rewinds stack: undoing the later of two leaves the earlier standing, still hiding what it hid, still the next run's target when no run has continued from it (`pendingRewind` reads through the same query), and undone in turn by a second undo. The undo names the rewind by its sequence, so the fold and a client match the two without counting.
- **The window is ADR 0022's**: refused `conflict` reason `run_started`, naming the first run started since, once any run has started on the session after the rewind, whatever its end; `run_active` while a run is live, looked at first; `not_found` with data kind `rewind` when no rewind stands. `pendingRewind`'s "continued" (a run that linked the provider session and ended `completed`) was considered as the window and not taken: a run that linked the provider session and then failed, or was interrupted after replying, may have written a turn after the rewind's point, so the provider session's latest chain would run from the rewind's point through that turn, and the plain resume after an undo would continue from that turn while the transcript showed the branch the rewind hid. `queued_messages` is no refusal here: a message in the environment's queue inside the window was sent before the rewind (the host can requeue one after its run's `run.ended` commits, what an interrupt reports still queued or a send whose run had ended), and a message queued before the rewind follows the history the undo restores.
- **The provider side needs nothing done**: the rewind stopped the session's process (#137) and no run has started since, so the provider session still ends where it did before the rewind. The next run's continuation (`runContinuation`) is the ordinary `resume` of the linked provider session, or `rewind` to an earlier rewind still standing and not continued from. The host does nothing on `session.rewind-undone`, which the command appends as the client's, as `sessions.rewind` does.
- **The draft**: the undo puts back the draft from before the rewind (the latest `session.draft-set` before the `session.rewound`, else none), in the undo's append, when the draft still holds exactly what the rewind's own `session.draft-set` wrote; a draft changed since (a client's `sessions.setDraft`, a withdraw's append, #228) stays, and so does one the rewind did not write (a message with no text). The reading: ADR 0022 makes the draft part of the rewind and offers the undo so that one misclick does not lose a branch, which should cost nothing else either, such as a half-typed draft; and leaving the rewound text would keep in the composer a message the transcript shows as sent again, a second send waiting to happen. With two rewinds standing, undoing the later puts back the earlier's text, and undoing that the draft before both.
- **Compaction leaves out a session with a rewind that can be undone** (`undoableRewind`, looked at inside the session's compaction transaction), chosen over storing the hidden items with the fold; the reason is in the environment spec's compaction note. An undo after a compaction taken before the rewind works: what it brings back is in the fold's items or in the events after it.
- **The client runtime's reducer** (`packages/client-runtime/src/projections/session.ts`, #142, which reached main while this was built) learns `session.rewind-undone` here: it keeps what each rewind it heard hid until a run starts, shows it again in sequence order on the undo naming that rewind, and falls back to the earlier rewind still standing as `rewound`, which a run starting has ended for every rewind before it, so it never offers an undo the environment refuses `run_started`. Since #230 a run starting no longer ends a rewind in the reducer: every rewind standing stays, as its rewound fold and as `rewound`, with `undoable` false, which is what the environment's `run_started` refusal says, and the client runtime's undo rewind verb is absent with that reason (client-runtime spec, #230's notes). A client that opened from a snapshot taken while the rewind stood (the environment sends one when the client's cursor is more than the replay bound behind, past the head, or below a compaction's fold) holds no entries for what that rewind hid, so on `session.rewind-undone` the reduction has nothing to show again; the runtime resubscribes the session for a fresh snapshot, folded past the undo, on its own (the session stream kind's `outgrown`, the path the events bound takes, `undoesUnheardRewind` in `streams/kinds.ts`), so no client acts on it.
- **Owed**: to the clients, the verb itself (the terminal UI's `/rewind undo` and `u` on the rewound fold, the GUI's Undo rewind). Not changed here: the snapshot leaves what a rewind hid out entirely, so ADR 0022's "shown under a fold" after a run starts has nothing to draw from the snapshot, and a compaction removes those events once the undo is gone (paid by #260, below).

Decided in carrying the rewinds standing in the snapshot (#260):

- **Where it lives**: the contracts' `StandingRewind` (`transcript.ts`, exported as `transcript/standing-rewind.json`) and `SessionSnapshot.rewinds`; the fold in `runs/transcript.ts` (`foldTranscript`, and `storedTranscriptParts` for a compaction's fold); the client runtime's reducer and session stream kind (client-runtime spec, #260's notes).
- **The shape**: `rewinds` lists the rewinds standing (not undone) that no later rewind cut, oldest first; each is `{sequence, toMessageId, text, undoable, items, rewinds}`: its `session.rewound`'s sequence, the message rewound to and its text, whether it can still be undone (no run has started on the session since it, the `run_started` window), the settled items it hid, and the rewinds standing before it whose fold it cut with the rest, nested the same way. Each hidden item is in exactly one rewind's `items`, the innermost that hid it; a rewind sits among the items beside it at its own sequence, where it cut. This is the client runtime's rewound fold (#230) on the wire, so a client that opens from a snapshot draws the same fold, `rewound` and undo as one that heard the events. Chosen over a flat list naming each rewind's parent, which a reader would have to reassemble and hold consistent, and over a `rewound` item among `items`, which an older client would show as an opaque item and which every reader of `items` on the environment (the rewind's visible messages, the session diff) would have to skip.
- **The fold holds a rewind as the client does**: `session.rewound` names a message the items show (one a rewind already hid hides nothing more, as the reducer has it, and as `sessions.rewind` only takes a visible message); what it hides at that moment goes into its fold, a fold among it nested; `run.started` makes every rewind standing not undoable; `session.rewind-undone` takes the named fold away wherever it is held and puts what it held back in sequence order; `message.withdrawn` takes the message out of a fold as out of the items. Folding on from a fold gives what folding every event does: the fold's hidden items are updated by later events, and an undo after it shows them again.
- **Defaults to none on the wire**: `rewinds` is optional on the wire and reads as `[]` when absent (`z.array(StandingRewind).default([])`; the JSON Schema export leaves it out of `required`, with `default: []`), and the protocol version is not raised: the env spec's rule bumps it only on a breaking change, and an optional field is not one. The failure mode it avoids: were it required, a client from #260 on against an older environment could not parse any snapshot, and every session the environment answers with one (a compacted session below its fold, a cursor past the replay bound, the runtime's own resubscribe past its session bound) would fault on "The snapshot could not be read" and never open. With the default such a client behaves as before #260 against that environment: no fold for a rewind that stood when the snapshot was taken, and a resubscribe on its undo. An older client against a newer environment drops the unknown field (the snapshot is a plain object schema, and the export sets no `additionalProperties: false`) and behaves as before #260. Raising the protocol version was the other way: a clean `protocol` refusal, but no session at all across the skew. The client runtime's cache stays strict (client-runtime spec, #260's notes). A compaction's fold stored before #260 has no rewinds either and is read as one with none standing (`storedTranscriptParts`, at the fold's readers): compaction never folded a rewind that could still be undone (#218), and what an older one hid went with its events.
- **An assistant item sits where it was opened**: the fold places a settled `assistant-text` or `assistant-thinking` item at the sequence of its first delta (per item id and fragment kind), as the client runtime's reducer places the entry it opened from that delta, or at its settled event's when it had no delta. Before, the fold placed it at its settled event, so a message sent while the item streamed sat before the reply in the snapshot and after it for a client that heard the deltas, and a rewind to that message hid the reply only in the snapshot. The read (`readTranscriptEvents`) still leaves the deltas out, but for the first of each item and fragment kind, chosen in the query; compaction folds every event it reads, deltas included, the same way.
- **Known difference: a snapshot taken while an item streams** (after its first delta, before it settles) holds the settled items only, so a client that opens from it places the item at its settle, not its first delta (client-runtime spec, #260's notes). Owed: the snapshot would need the open item, or where it opened.
- **Written twice**: the fold here and the client runtime's reducer hold a rewind the same way and are written twice with the same names (`Fold`, `without`, `unfold`, `listOf`, `everyItem`, `everyFold`), as the whole transcript fold already was; the client runtime's `projections/session-rewinds.test.ts` checks the two agree. Owed: a shared pure module in the contracts (a generic `Fold<T>` with `without`, `unfold` and the snapshot's `rewinds` in and out), which the contracts' other shared pure logic (`shelfOf`, `keyBetween`, `matchDenylist`) has a place for.
- **Compaction keeps what a rewind standing hid**: the fold is the snapshot's transcript part, so a compaction taken after the undo window closes now stores each rewind standing with what it hid, which the events it removes no longer hold; the fold stays drawable after a compaction. The #218 skip of a session whose rewind can still be undone is kept unchanged, though the fold would now carry what the undo shows again (environment spec, compaction note).
