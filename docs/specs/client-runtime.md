# Spec: Client runtime

Milestone 1 (Switch-over), phase A (the spine). Written 2026-09-23 from map ticket 80 of `david/agent-harness`. Decisions it implements: ADR 0004 (one client runtime, renderers are projections, the shell behind capability flags), ADR 0003 (no client organisation state; cursors, snapshots, the outbox), ADR 0001 (every client remote, connections client-local, flags plus one protocol integer), ADR 0005 (badge, default-environment rule, pooled usage), ADR 0006 (the ceiling), ADR 0007 (the updated-to notice), ADR 0008 and ADR 0011 (client notices), ADR 0014 (the client-addressed call), ADR 0017 (phase, placeholder name), ADR 0018 (usage pooled by account identity). Peers read: T3 Code at 96c4bfa0 (`packages/client-runtime` and `docs/internals/connection-runtime.md`), Artemis at 443cf2e (the renderer's remote bridge, the core remote stream, the terminal UI's `RunDriver` seam), and the environment-service specification on branch `specs/78-env` at a740e19, whose wire this runtime consumes. The product name is the placeholder `agent-harness` throughout.

## Problem Statement

David archives a session on his desktop and it is still active in the terminal. He puts sessions into a group and the group exists on one machine only. The surfaces audit traced why: Artemis has no client runtime, it has three. The desktop renderer is a 13,900-line store whose shape is the desktop's IPC vocabulary; Remote mode re-implements that vocabulary over HTTP and stubs what does not map (its `tag` stub is the archive hole); the terminal UI is a third assembly of the engine with its own pin file. Groups and pins live in a per-machine preferences file keyed by a per-machine random profile id. Session-list changes are never pushed; clients poll every 4 or 20 seconds. A retried send is a new message because nothing carries a command id. A closed laptop returns to a transcript rebuilt from a lossy in-memory feed. Each renderer had to fix every one of these separately.

## Solution

One UI-free package, the **client runtime**, that every client renders from and nothing else: the desktop window, the terminal UI and, in milestone 2, the browser tab. It keeps the saved connections, pairs with environments and holds their client sessions, keeps one WebSocket per environment alive through backoff and a watchdog, subscribes to the session list and to open sessions with a cursor per stream so a reconnect catches up exactly, keeps every command in an outbox with a command id so a retry never applies twice, shows David's edits at once and reconciles them by the environment's sequence, and turns the streams into the projections a sidebar, a transcript and a run status read. What only a desktop can do is reached through a small shell interface behind the same capability flags as everything else; absent, a feature says why. The runtime is the parity test's target: whatever the wire expresses, it projects, and both renderers show.

## User Stories

1. As David, I want the session I archive in the terminal to be archived in the desktop window within a second, so that the two never disagree.
2. As David, I want a group I create on my laptop to appear on my desktop with the same sessions in it, so that organisation is a fact about my work, not about one screen.
3. As David, I want the same-named group on two environments to show as one heading with an environment badge on each row, so that a project I work on from two machines reads as one project.
4. As David, I want to open my laptop after a night offline and see my sessions and groups exactly as I left them, then watch them catch up, so that offline never means empty.
5. As David, I want an edit I make while an environment is unreachable to show as pending and apply when it is back, so that I can tidy the sidebar on a train.
6. As David, I want a retried command after a dropped connection to apply once, so that a session is never archived twice or a group created twice.
7. As David, I want an unreachable environment to keep its place in the sidebar with "unreachable since" and its cached sessions, so that I know what is missing and since when.
8. As David, I want to be told when a client of mine has been revoked and why, rather than watching it retry forever, so that a revoked client is a clear state.
9. As David, I want a stale client to tell me to update it, and a newer client to offer to update the environment, so that a version gap is one action.
10. As David, I want to pair a new machine by pasting a link or typing a short code and never see a token, so that pairing is one step.
11. As David, I want a parked prompt on any environment to appear in one "parked asks" list, so that nothing waits unseen.
12. As David, I want the composer draft I typed in the desktop to be there in the terminal, so that a draft is part of the session.
13. As David, I want a feature a desktop cannot offer in a terminal to say why it is absent, so that a missing button is never a mystery.
14. As David, I want a session deleted on one client to vanish from every client at once, and a command aimed at it rejected with a one-line notice, so that deletion is clean.
15. As David, I want to disable a saved environment without forgetting it, and removing one to revoke its session and forget its cache and pending edits, so that both are complete.
16. As Seth, I want the terminal UI to open with my sessions from the cache before the environment answers, so that startup is instant.
17. As Seth, I want the terminal UI to tell me the service is down and offer to start it, and to authenticate on my own machine without a code, so that my own computer never asks me to pair.
18. As Seth, I want a network blip to show as "reconnecting" for a few seconds and then be over, with no lost or doubled transcript lines, so that a flaky link is not a broken transcript.
19. As Seth, I want the answer I give to a permission prompt to reach the run once even if the socket drops as I press the key, so that a decision is never lost or doubled.
20. As a client developer in another language, I want the runtime's rules written down as behaviour, so that a second client can follow them without reading TypeScript.
21. As the setup checklist, I want to read the saved connections with each environment's health and version, pair a new one, and run a step's health check against any of them, so that the Your machines step is a view of the registry.
22. As a routine, I want a client-notice delivery to reach every connected client as a notice, so that a firing's result is seen.
23. As the browser relay, I want a call addressed to the client that started a run to reach that client's runtime and its answer to go back on the same connection, so that a browser verb has a route.
24. As a build session, I want to start the runtime against an in-process environment and against a scripted fake wire, so that every rule above is a test that runs in seconds.
25. As a build session, I want a lint to prove that no session state rides the shell and that no client preference is named after a session field, so that the Artemis bug is impossible rather than fixed.

## Implementation Decisions

### Package and platform

- **One package, `client-runtime`**, depending on the `contracts` package and nothing else at runtime; no React, no Ink, no Electron, no Effect (ADR 0001 rejected Effect RPC for lock-in). Chosen default: its public values are observables with `read()` and `subscribe(listener)`, so React reads them with `useSyncExternalStore` and Ink with the same primitive (ADR 0004).
- **The platform** supplies what the runtime cannot own: key-value document storage (the GUI renderer uses IndexedDB; the terminal UI a directory under the user's state directory, distinct from the environment's data directory), secret storage for client session tokens (the OS keychain through the shell on a desktop, a 0600 file for the terminal UI), a WebSocket factory, a clock, a network signal (online, offline, foreground, background), the client kind (`desktop`, `tui`, `web`) and label, an optional bootstrap-grant reader for a local environment, and an optional **shell** (below). The GUI and TUI workstreams deliver the two platforms; tests use an in-memory one.
- **The runtime is a client.** It defines no wire method. Every `area.verb` name below is either a method of the environment-service specification it consumes or an in-process call of the runtime's own API, marked as such.

### The connection registry

- **A connection is keyed by environment id** (ADR 0001, T3 Code's registry). The record holds the environment id, one address, the kind (`local`, derived every start from the bootstrap grant and never persisted; `paired`, persisted), an enabled flag, the client session id, scopes and ceiling from `hello`, the cached descriptor (name, icon, colour, harness version, protocol version, capability flags, last seen) and a blocked reason when any. The token lives in secret storage, never in the record. Saved connections are client-local in milestone 1 (ticket 16); a peer list is fog.
- **Name, icon and colour** come from the environment, never the client (ADR 0005). The runtime reads the name from discovery and `hello`. Icon and colour stay null until the workspace-picker workstream adds them (with the command that sets them): as built neither `environment.status` nor any notice carries them, and the environment's own stream (`environment.subscribe`) is where the runtime will read them.
- **Client-local preferences** the runtime owns: the ordered environment list, whose first entry is the **primary environment** that orders merged groups (ticket 17), preset to the local environment then pairing order; enabled flags; the last environment used (ADR 0005's default-environment rule). A fixed key schema for this storage is what the ADR 0003 lint inspects: no key may be named after a session field.
- In-process API: `connections.list`, `connections.add` (from a link, or an address plus code), `connections.setAddress`, `connections.setEnabled`, `connections.setOrder`, `connections.remove`, `connections.retryNow`.
- **Removal** revokes the client session through `access.sessions.revoke` when reachable (best effort), then clears the token, caches, cursors and outbox for that environment. **Disable** drops the socket and stops retrying; everything else stays. An **address edit** reconnects; a `hello` whose environment id differs from the key blocks with `different-environment` and keeps the old cache.

### Pairing and the bootstrap grant, client side

- **Pairing** takes a link (`https://<address>/pair#<code>`, code in the fragment so it never reaches a log), a QR of that link, or a short code plus an address (ticket 16, environment-service spec). Steps: parse; `GET` the discovery URL and check readiness, protocol version and environment id; if a connection with that id exists, offer to re-pair it in place; exchange the code over the environment's pairing exchange route with the client kind and label; keep the token; write the record; connect. Failures are typed: `expired-code`, `used-code`, `unreachable`, `protocol-mismatch`, `not-ready`, `different-environment`.
- **The bootstrap grant** (environment-service spec): when the platform provides a grant reader, the runtime reads the one-time secret at start and exchanges it over loopback for a client session of kind `local` with every scope and the top ceiling; the `local` connection is re-derived on every start, so each desktop start replaces the previous desktop session as that spec requires. On a desktop the shell reads the grant file and hands the secret to the runtime, which performs the exchange. When nothing listens, the local environment shows phase `service-down` with an action `service.start` the platform performs (the terminal UI runs the CLI's `service` verb; the desktop calls its shell's `service` member); when discovery answers `starting`, the runtime polls it every two seconds (chosen default) instead of counting failures.
- **Token refresh**: the token has a 30-day life and is refreshed while in use (environment-service spec). The runtime refreshes on connect and daily when fewer than seven days remain (chosen default) through the refresh method that spec names; a failure is reported on the connection and never closes a healthy socket (T3 Code's rule).

### The connection state machine and reconnect

- Per environment, one owner of the socket and one owner of retries (T3 Code's supervisor). Phases: `disabled`, `service-down`, `starting`, `connecting` (`auth` sent, awaiting `hello`), `syncing` (subscriptions attached, before their `synchronized` markers), `ready`, `backoff` (with `retryAt`), `blocked` (reason `protocol-mismatch`, `unsupported-client`, `revoked`, `expired`, `different-environment`), `draining` and `updating` (after those `bye` reasons). `unreachableSince` is set at the first failure after `ready`, or at start when the cache has data, and cleared on `ready`; the sidebar heading shows it (ticket 17).
- **Backoff**: 1, 2, 4, 8, 16 then 30 seconds with up to 25 percent jitter, reset after 30 seconds healthy; a 15-second establishment timeout from socket open to `hello` (chosen defaults after T3 Code's ladder). An offline network signal parks the retry until a wakeup instead of spending attempts; a foreground wakeup on a connected socket probes it with a request (`environment.status`: the wire has no ping from the client) and replaces it only when the probe fails. The local environment, on loopback, is never parked.
- **The watchdog**: the environment pings every 15 seconds; the runtime answers `pong`, arms a 45-second watchdog after the first ping, and on expiry closes the socket and reconnects at once as a transient failure (Artemis's measured numbers).
- **`bye` reasons**: `revoked` and `expired` block, clear the token and raise a notice (`expired` offers re-pair); `draining` and `updating` wait five seconds then follow the ladder while polling discovery for `ready`, and the next `hello` refreshes the descriptor and flags so an "updated to X" notice and new features appear without a restart (ADR 0007); `protocol` blocks as below.
- **Protocol version**: the runtime carries the contracts package's one integer. On discovery and on `hello` it compares: equal connects; the environment newer blocks with `unsupported-client` and "update this client"; the environment older blocks with `protocol-mismatch` and offers "update <environment> to this client's version" when the environment's flags include self-update (the launcher workstream's method, ADR 0007). A block persists with the record and is re-checked against discovery on every launch and on `connections.retryNow` (T3 Code's compatibility check).
- **Transport and freshness are separate** (T3 Code's lesson): `ready` says the socket and `hello` are good; each stream carries its own freshness (`empty`, `cached`, `catching-up`, `live`), and a failed subscription on a healthy socket is a stream fault, never "reconnecting".

### Subscriptions, cursor cache and snapshots

- **Two kinds of subscription per environment plus the environment stream** (ADR 0003, environment-service spec): the session list (every session and group summary change), one per open session (its transcript and run events), and `environment.subscribe` (updated-to, draining, account status, client notices, the client-addressed calls of ADR 0014). The names and vocabulary of the first two are the session-state workstream's; the runtime defines none.
- **Cursor per stream**: `lastSequence` with the snapshot it belongs to, for the list and each cached session, persisted together in one write and only after the update applied, so a cancelled apply never advances the cursor (T3 Code's rule, ADR 0003). Persistence is debounced 500 milliseconds and forced on every `synchronized` marker and on disconnect (chosen defaults).
- **Attach**: subscribe with `afterSequence` at the cursor, or 0 (the cursor before the first event) when the cache is empty. Apply rules: an event at or below the cursor is dropped (the live feed attaches before catch-up, so overlap is expected); a `snapshot` replaces the stream's state and cursor whole; `synchronized` sets freshness to `live`; an `end` with reason `overflow` resubscribes at once from the cursor, after one second if a second overflow arrives within a minute, then on the ladder (chosen defaults). Any other end re-attaches on the next `ready`. A subscription refused, or not answered, on a healthy socket is a stream fault, retried on the next `ready` only, never on a timer. An event or snapshot the stream cannot apply changes nothing, the cursor included, and the stream resubscribes once with `afterSequence` past any head, which the environment answers with its snapshot (the "snapshot please" convention); a held session's stream does the same once it holds more events since its snapshot than a bound (chosen default: 1,000 events or 1 MiB).
- **Reads work from cache offline**: the list and every cached session render from their snapshots with freshness `cached`. **Retention** (chosen defaults after T3 Code): a per-session subscription stays open five minutes after its last renderer consumer leaves; persisted session snapshots are kept for the 50 most recently opened sessions per environment under a 32 MiB cap; the list snapshot is always kept.
- **Server time** from `hello` gives a skew estimate per environment for snooze-until and prompt TTL countdowns, never the client clock alone. "Unreachable since" is on the client's clock, which measured it.
- In-process API: the session-list subscription is implicit while a connection is enabled; `subscriptions.session(environmentId, sessionId)` returns a handle whose release starts the retention timer.

### The offline outbox, receipts and optimistic application

- **Every `sessions:write` and `runs:drive` call goes through the outbox** (ADR 0003, ticket 17); `admin` calls (`access.*`, `environment.drain`, `environment.rebuildProjections`) are direct requests, never queued. `commands.dispatch(environmentId, method, params)` assigns a UUIDv7 command id (chosen default; time-ordered ids keep the outbox readable), validates params against the contracts schema, checks the connection's scopes and flags and refuses absent-with-reason, persists the entry, applies the optimistic rule if one exists, and returns a promise of the receipt.
- **Entry**: command id, environment, method, params, target stream, created at, attempts, state (`queued`, `in-flight`, `acknowledged`, `rejected`). Entries are sent in order, one in flight per environment (chosen default; ordering is worth more than throughput). A socket that drops mid-flight leaves the entry in flight; it is re-sent with the same command id on the next `ready`, and the environment's receipt makes the retry idempotent. A command id is never re-minted for a retry.
- **Receipts**: `accepted` records the resulting sequence and removes the entry; `rejected` removes it, reverts the optimistic value and raises one notice ("<verb> on <session title> was rejected: <reason>"); a target deleted meanwhile arrives as `rejected` with `not_found` (ticket 17). Entries older than seven days are dropped with a notice (chosen default, inside the environment's 30-day receipt retention).
- **Which commands queue**: commands under `sessions:write` (every session field, groups, drafts, routine definitions per ADR 0008) queue while unreachable and show as pending. Commands under `runs:drive` (start, send, interrupt, answer a prompt) never queue: while the environment is unreachable they fail at once with `unreachable` and starting runs is disabled (ticket 17); one already in flight when the socket drops is still re-sent with its id, so a permission answer given as the link dropped applies once (story 19). **Drafts** are session fields (ticket 18); the runtime debounces draft writes one second (chosen default) before dispatching.
- **Coalescing**: while an entry is `queued`, a later entry with the same method and target that sets an absolute value of the same field replaces it and removes the replaced entry's overlay value, since the earlier value would lose by server sequence anyway. Which methods are absolute setters comes from the session-state vocabulary; a contract test fails when a `sessions:write` method is neither a setter nor an ordered command.
- **Optimistic application**: an overlay per stream holds, per field and command id, the value the command will produce (T3 Code's optimistic thread lifecycle). Projections read confirmed state with the overlay on top. An entry leaves the overlay when an event carrying its command id applies, when the cursor passes the receipt's resulting sequence, or on rejection. Conflicts resolve as **last writer wins per field by server sequence** with no merge logic (ADR 0003); a live event from another client changing a field with a pending local command does not displace the overlay, since the local command will be later by sequence. Rows and groups with pending entries carry a `pending` flag while the environment is unreachable. Group creation offline uses a client-generated group id so a queued membership change can reference it (verify-first: whether the session-state vocabulary accepts client ids).
- **Non-mutating calls**, `requests.call(environmentId, method, params)`, never queue: when the connection is not `ready` they fail at once with `unreachable`; the timeout is 30 seconds (chosen default). Results the renderers need continuously (accounts, models, usage, routines, paired Chromes) sit in a per-environment **request cache** with a five-minute TTL (chosen default), refreshed on `ready` and on the matching notice.

### Projections

Every projection is a pure function of stream state, overlays and client preferences, exposed as an observable; renderers never reach the streams (ADR 0004). Field names are the session-state workstream's (ticket 17: `archivedAt`, `pinnedAt` and `pinOrderKey`, `activeOrderKey`, `title`, tags, group membership, `settledAt` and `settledOverride`, `snoozedUntil`, repository identity, the draft, deletion); the runtime holds nothing a summary does not carry.

- **`projections.environments`**: each known environment with phase, `retryAt`, `unreachableSince`, the blocked reason and the action it offers, `refreshFailed`, name, icon, colour, version, flags, scopes, ceiling, pending-command count and the primary mark.
- **`projections.sessionList`**: every summary across enabled environments, each row carrying its environment id for the badge (ADR 0005) and its pending flag, with derived views: active (not archived, settled or snoozed into the future), pinned (merged across environments by `pinOrderKey`), archived, the settled shelf, snoozed, by group, by repository identity, and `projections.search(query)` over titles, tags, group names and repository identity (case-insensitive substring). Ordering keys are fractional-index strings compared as strings, with environment order then id as tie-breakers, so lists merge with no agreement between environments (ticket 17).
- **Merged groups**: same-named groups (equal after trimming, collapsing whitespace and ignoring case: the contracts' `groupNameKey`) from several environments form one heading. Headings the primary environment has come first, in its group order; the rest follow by that key, whatever order the other environments keep; the heading carries the ids of the groups it merges so a command still targets one environment's group; a rename on one environment splits the heading (ADR 0003). The merge is a view; nothing about it is stored.
- **`projections.session(environmentId, sessionId)`**: one session's stream reduced into runs (id, state, started, ended, reason, usage), transcript items (messages, tool calls with their updates folded, permission prompts and questions with their state and where they were asked, plans, subagents), the parked prompt, the draft and the summary fields. The reducer is a pure function of the session-state and adapter vocabularies; an unknown event type is kept as an opaque item rather than failing, so an older client survives a newer environment (ADR 0001).
- **`projections.runs`**: per session the run state (`idle`, `starting`, `running`, `parked`, `interrupted`, `ended`), and across every environment the **parked asks** list with TTL countdowns (ADR 0006); the permissions workstream's unattended-review view reads the same projection.
- **`projections.accounts`, `projections.models`, `projections.usage`**: per environment from the request cache; usage windows pooled by account identity across environments (ADR 0005, ADR 0018).
- **`projections.notices`**: a queue of at most 100 (chosen default) from `environment.subscribe` (updated-to, draining, account status, key-manager verification per ADR 0011, a routine's client-notice delivery per ADR 0008), from receipts (rejections) and from the connection (revoked, expired, mismatch); dismissal is client-local. The runtime also emits attention events (`run ended`, `prompt parked`, `notice arrived`); the renderer surfaces them and the runtime never calls the shell for them.

### Capability flags, ceiling and absent-with-reason

- `capability(environmentId, name)` answers `present` or `absent` with a typed reason: `unsupported` (flag missing in `hello`), `scope` (the client session lacks the method's scope), `unreachable`, `not-ready`, `no-shell` (a shell member the platform did not provide), each with one human line so both renderers say the same thing (ADR 0004). Every renderer affordance asks this; none reads flags or scopes directly, and support is never inferred from a version number (ADR 0001).
- The connection's **ceiling** from `hello` is exposed on `projections.environments` so the mode picker clamps to it and shows the clamp; the mode and ceiling values are the permissions workstream's (ADR 0006).
- **Client-addressed calls** (ADR 0014): a call the environment addresses to the client session that started a run arrives on `environment.subscribe`; the runtime hands it to a handler registered with `clientCalls.register(kind, handler)` and sends the answer through the method the browser workstream names, on the same connection; the client session id is stable across reconnects, so registration survives a blip. The call and answer are opaque to the runtime.

### The desktop shell seam

- The platform's optional **shell** is a small interface of optional members: `dialogs` (open file, open directory, save), `window` (title, focus, badge), `notifications.show`, `tray`, `deepLinks.onOpen`, `webView` (create, attach, navigate, for the browser dock and preview panes), `installer` and `update` (the desktop updater, launcher workstream), `service` (install, start and status of the local environment's service, ADR 0001), `clipboard`, `openExternal`, `localGrant.read`, `secrets`. Each member is a capability with reason `no-shell` when absent; the terminal UI and the browser tab provide none and degrade absent-with-reason (ADR 0004).
- **Nothing about sessions, runs or organisation passes through it.** No member takes or returns a session, run, group, event or summary; a deep link delivers a string the runtime parses (a pairing link, an open-session link); a notification takes a title and body the renderer composed. A lint fails the build when the shell interface module imports any session, run or group type from the contracts package, the cousin of the ADR 0003 lint. Pane layout is the renderer's client-local presentation, not the runtime's (glossary: Pane).

## Testing Decisions

- **What a good test is**: a behaviour visible through the runtime's public surface (projections, `commands.dispatch`, `requests.call`, `capability`, the connection state), asserted from a renderer's point of view; never an assertion on the storage documents, the overlay map or the outbox table. What the cache holds is asserted as a runtime started again on the same storage: what it renders, and the cursor it attaches from. The exceptions are the storage contract test below, where durability is the behaviour, and the cursor cache's own unit suite (`streams/cache.test.ts`, #127), whose behaviour is the documents: the pair in one `set`, the debounce, and retention's order of deletes and meta writes.
- **Primary seam: the runtime against an in-process environment.** The environment-service specification's helper starts an environment on a temporary data directory on loopback port 0 with a scripted fake provider; the runtime runs on an in-memory platform (storage, secrets, a controllable clock, a network toggle, a fake shell) over a real WebSocket. Tests here: pairing from a link and a code, re-pair in place, expiry; the bootstrap grant exchange and the replaced desktop session; `hello` filling scopes, ceiling, flags and name; the list rendering from cache, then `cached`, `catching-up`, `live`; a command dispatched with the network off showing pending and applying once on reconnect; the same command id re-sent after a mid-flight drop applying once; a rejection reverting and raising one notice; two runtimes on one environment where an archive, a pin, a group and a draft made through one appear in the other without polling (the Artemis bug as a test); merged groups splitting on a rename; parked asks across two environments; capability answers for a missing flag, scope and shell member. Prior art: T3 Code's `buildAppUnderTest` and `withWsRpcClient` in `apps/server/src/server.test.ts`, its `EnvironmentRegistry` and `EnvironmentThreads` suites, Artemis's port-0 helper in `runStreamClaim.test.ts`.
- **Second seam: the runtime against a scripted fake wire.** A fake WebSocket server the test drives frame by frame, under fake timers (`testing/fake-wire.ts`, below): silence firing the watchdog; a dropped socket and the ladder's delays within jitter bounds; the establishment timeout; offline parking and foreground probing; every `bye` reason and its phase; a `hello` with a different environment id; discovery answering `starting`; protocol mismatch in both directions and the block clearing; overflow and the cursor-based resubscribe; duplicate sequences across catch-up and live; a snapshot replacing state and cursor. Prior art: T3 Code's `EnvironmentSupervisor` tests with deferred-driven fake connections, Artemis's `remote.test.ts`.
- **The fake wire's API** (#126; #127, #128 and #143 reuse it, so it stays small). `fakeWire({clock, environmentId?, name?, protocolVersion?, capabilities?, address?})` is one scripted environment with no process and no port; hand its `fetch` and `webSocket` to the in-memory platform with the same manual clock. On its own it answers discovery, `POST /api/pair` and `POST /api/bootstrap` (a fresh credential, 30 days on the clock), the grant (`wire.grant`, a `GrantReader` naming its address) and requests for `environment.status`, `access.sessions.revoke` and `access.sessions.refresh`; `wire.answer(method, params => {result} | {error} | Promise<...> | undefined)` replaces or adds a responder (a promise answers when it settles, so a test can hold an answer; undefined leaves the request unanswered, and a method with none is answered `not_found`). `wire.discovery("unreachable" | {readiness, protocolVersion, capabilities, ...})` sets what discovery answers from then on; unreachable fails the exchanges and new sockets too. `wire.link` is a pairing link its exchange accepts. On a socket the fake says nothing until told, through `wire.server`, the environment's side of the socket the client opened last: `expect(type)` resolves with the next frame of that type the client sends (one already sent and not yet expected counts), and `request(method)` with the next request for that method, whatever other requests go before it; `hello(overrides?)` says `hello` from discovery's id, name, protocol and flags (a staged `wire.discovery` override included) and the client session last issued; `accept(overrides?)` is `expect("auth")` then `hello`; `send(frame)`, `ping()`, `bye(reason, {protocolVersion?})` (then a 1000 close), `drop()` (a 1006 close with no `bye`), `silence()` (the link goes dead: nothing arrives, nothing is answered, no close comes) and `received()`. `wire.opened()`, `wire.open()`, `wire.discoveries()` and `wire.credential()` count and show what the client did. Everything lands in microtasks, so a test moves the clock and then `await flush()`. The in-memory platform's `random` is seeded, so jitter is the same on every run.
- **Reducers as pure functions**: the connection state machine (`connections/state-machine.ts`, #126) is one, tested with no socket and no clock; the session and session-list reducers against recorded event fixtures from the session-state and adapter workstreams, including unknown event types and ordering-key merges across environments.
- **Storage contract tests**: one suite every platform runs (in-memory, files, IndexedDB): snapshot and cursor written together, an interrupted write leaving the old pair, secrets never in document storage.
- **Contract tests in the contracts package**, run here: every `sessions:write` method is a setter or an ordered command; every capability name a renderer may ask for is in the flag list; the shell interface imports no session type; no preference key is named after a session field (ADR 0003's lint).
- **Framework**: Vitest, as both peers use; the in-process suite runs serially. **Not tested here**: the renderers, the shell implementations, the service install, the environment's replay bounds.

## Out of Scope

- Everything named under "What this workstream does not decide", in particular the environment side of the wire (78), the session vocabulary (79), the renderers (81, 84) and the browser relay's page driver (93).
- Milestone 2 and later: the browser tab's platform, a relay, a peer list, hand-off, push to a phone, transcript full-text search, SSH-launched environments, auto-balance.

When a paired connection to the same environment exists, the local one replaces it: the paired client session is revoked with the new local one, which holds every scope, then its record and token are forgotten. When its client session is revoked or expires (a `bye` of `revoked`, `unauthorized` or `expired`), the in-memory token is dropped with the block, so the next attempt (`retryNow`, or the next start) exchanges the grant again. The local connection cannot be removed, only disabled.

The local environment's grant exchange fails `refused` for it, which leaves the local connection in `backoff`, not `service-down`.

- Chosen defaults not decided on a ticket, from the reconnect build (#126):
  - **Shape**: one state machine per connection, a pure `reduce(state, input, {now, random})` answering the next state and effects (`poll-discovery`, `describe`, `open-socket`, `attach`, `send`, `probe`, `close-socket`, `arm-timer`, `cancel-timer`, `refresh-token`, `clear-token`, `notice`), and a runner (`connections/runner.ts`) that owns the socket and the timers on the platform clock and feeds back what happened. Every answer names its attempt; an answer to an attempt that is over is dropped. `connections.retryNow`, `setAddress`, `setEnabled(true)`, `add` and `start` settle once the attempt they began has (a discovery read or a socket no longer awaited, and what the machine asked to be written written).
  - **Phases**: an attempt is `connecting` from its discovery read to `hello`, except that `starting`, `draining`, `updating`, `service-down` and `blocked` stay as they are while discovery is read again, so a re-check does not flicker. The local environment's failures (no grant, nothing answering, a grant exchange failing) are `service-down`, retried on the ladder with `retryAt`, with the action `service.start`. After `bye: draining`, nothing answering is the environment gone (`service-down` for the local one, `backoff` otherwise); after `bye: updating` it is part of the restart and stays `updating`; discovery answering `draining` counts on the ladder, `starting` does not.
  - **Ladder**: the delay after the nth failure in a row is rung n (1, 2, 4, 8, 16, then 30 seconds) times one plus 25 percent of a draw in [0, 1), rounded down; the draw comes from the platform's optional `random` (preset `Math.random`; the in-memory platform's is seeded). Thirty seconds ready puts the count back to zero. The watchdog and a failed probe reconnect at once and start the count over, so the reconnect failing waits the first rung. `retryNow` tries at once, even offline, and keeps the count; `connections.startService` starts it over, so a service still coming up is tried again within a second. The establishment timeout (15 seconds) also bounds the discovery read, since `fetch` has no timeout, and runs afresh from opening the socket.
  - **Network**: going offline cancels a scheduled retry and parks it (`retryAt` null); a failure while offline parks too; a wakeup (back online, or to the foreground while online) tries a parked retry, or one waiting out the ladder in `backoff` or `service-down`, at once (the five seconds after `bye: draining` or `updating` and the `starting` polls are not cut short). The local connection is never parked: it is on loopback, which the network signal says nothing about, so offline it connects and retries on the ladder as usual. A foreground wakeup on a ready socket probes it with an `environment.status` request, since the wire has no client `ping` (the environment answers a client `ping` frame with `bye: protocol`); any response, an error one included, proves the socket, and none within 5 seconds gives it up.
  - **Blocks and notices**: `bye: unauthorized` blocks as `revoked`; `bye: protocol` naming the client's own version is no version gap but a fault, retried on the ladder. Revoked and expired clear the token (a local connection's is in memory, so `retryNow` exchanges the grant again, which its notice says instead of "pair again"). A block is re-checked quietly: on launch and on `retryNow` the phase stays `blocked`, with its action, while discovery is read and the socket opened, and a re-check that cannot finish (nothing answering, a malformed answer, `starting`, `draining`, the establishment timeout, the socket closing) leaves it `blocked` with no retry; only `hello` agreeing (or a re-pair in place) clears it, so a record never shows a reason beside another phase. A notice is raised when a block is new to the record, so a block saved and re-checked on every launch says so once; `different-environment` raises none (the record shows it). `expired` offers `re-pair` on a paired connection only. The protocol notices say which side is behind and are worded by the action there is: `update-environment` when the environment's last-seen flags include `self-update`, else that it cannot update itself from here.
  - **`unreachableSince`**: set at the first failure after `ready` (a block included), and at start when the connection has cached data, which since #127 means a cached session list (a cursor on record); cleared on `ready` and when disabled.
  - **Token refresh**: checked on every `hello` and daily while ready; refreshed when fewer than seven days remain or the expiry is not known (a record saved before #126). The new token replaces the old in secret storage (in memory for the local connection) and `expiresAt` on the record; a failure sets the record's `refreshFailed` and raises one `refresh-failed` notice until a refresh succeeds; a request cut by the socket closing is not a failure. A refresh is not waited on by `retryNow` or `start`, since a request has no timeout; an unanswered one is tried again at the next daily check or connect.
  - **Notices**: `projections.notices`, at most 100, newest last, each `{id, environmentId, kind, message, action, at}`; `notices.dismiss(id)` is client-local. The actions are names the renderer maps to calls: `re-pair` (`connections.add(input, {rePair})`), `update-client`, `update-environment` (the launcher workstream's method), `service.start` (`connections.startService`).
  - **Faults**: the runner performs a transition's effects before it tells the registry the state changed, each on its own, and hands what any of them throws (a renderer's listener, a failed background write) to `platform.reportError`, so one fault never costs the connection its timers or its socket. The record's writes (the descriptor from discovery and `hello`, the block, the expiry) are that background work too, so a failed save is reported and never fails `start` or `retryNow`. Removal and a re-pair in place take the ready socket from the runner (`detach`) before revoking, and hold its machine: removal stops it before the revoke, and a re-pair holds it, every input ignored (a retry, an enable, an address edit, a wakeup), until the new socket is adopted. Nothing reconnects with the old token while the revoke (up to 10 seconds) is under way, and the `bye: revoked` it brings about clears no token, saves no block and raises no notice. The pairing's superseding rule (#125) is the machine's: a re-paired connection holds, a first pairing's machine starts only when its socket is adopted, and adopting halts first regardless.
  - **Owed**: a local environment never seen before, whose service is down at the first start, lists nothing (there is no grant to learn its id from and nothing remembered) until a later `start()` finds the grant; retrying the grant while nothing is listed needs a follow-up ticket.
  - **Public surface beyond the specification's list**: `connections.startService(environmentId)` (the platform shell's `service.start`, then a reconnect; refused for a paired connection and without a shell `service`, where the terminal UI runs the CLI's `service start` and calls `retryNow`); `notices.dismiss`; on a record `retryAt`, `unreachableSince`, `refreshFailed`, `action` and `expiresAt`, and on `projections.environments` all but `expiresAt`. The seam `onClose` also hears a socket the watchdog or a probe gave up, and never one this runtime closed on purpose.

- Chosen defaults not decided on a ticket, from the subscriptions build (#127):
  - **Shape**: `streams/` holds one pure reducer for every stream (`stream.ts`: cursor, state, freshness, fault; `step` answers the next state and whether to write it soon, now or not), the three stream kinds (`kinds.ts`: the list as sessions and groups by id, applying the `listPatch` of each event and skipping an event with none; one session as its summary, its snapshot's transcript and every event since, unknown types kept; the environment's status), the cache (`cache.ts`), the subscription mechanics (`attach.ts`), the handles (`session-handles.ts`), the clock skew (`skew.ts`) and their composition (`streams.ts`). The socket routes a subscription's messages to its subscriber by subscription id from the `subscribed` answer on (`LiveSocket.subscribe`), so none can arrive before the id is known. The seams gained `onReady` (heard before the connection publishes `ready`), `subscribe`, `unsubscribe` and `setSyncing`; `createRegistry` takes the cache's `load` and `has`, read before any connection starts.
  - **Freshness**: `empty` or `cached` at rest; `catching-up` from the moment a subscription is asked for, from nothing too; `live` on `synchronized`, which also moves the cursor to the head it names and leaves an empty list cached at it; back to `cached` (or `empty`) on an end, a fault or the socket going. A fault shows beside the freshness until the stream synchronizes again. A session stream that `synchronized` finds holding nothing (no snapshot and no event came) stays `empty`, holding nothing, and is never read as a deleted session; the first event after it makes it `live`. An empty list, by contrast, is a state: `live` and cached at the head.
  - **`syncing`**: the connection shows `syncing` instead of `ready` while its session list is catching up, and `start`, `add`, `retryNow`, `setAddress`, `setEnabled` and `startService` settle once it is not (synchronized, faulted, ended or the socket gone), so a caller that awaits them sees `ready`. Capabilities answer `not-ready` while `syncing`, as #125 wrote.
  - **Faults**: a subscription refused on a healthy socket, or not answered `subscribed` within 30 seconds (the request timeout's default), faults the stream and is tried again on the next `ready`, never on a timer, since a refusal (`forbidden`, `not_found`) does not cure itself; the connection's phase is untouched. Every other error waits for the next `ready` too (no ladder retry for them: a stream fault is rare enough that `connections.retryNow` or the next reconnect is the retry). An event or a snapshot the stream cannot apply (a malformed patch, a `set` for a session it does not hold) changes nothing, the cursor included, and the stream is resubscribed once with a cursor past any head, `Number.MAX_SAFE_INTEGER`, which the environment answers with its snapshot: the "snapshot please" convention; a second failure before `synchronized` waits for the next `ready`.
  - **Overflow**: the nth overflow in a row, each within a minute of the one before, resubscribes from the cursor after `backoffDelay(n - 1)`: at once, then one second, two, four, eight, sixteen and thirty, each with the connection ladder's 25 percent jitter; a minute without one counts the next as the first. Waiting, the stream is `cached`, and the connection `ready`.
  - **The cache documents**: `streams.<environmentId>.list`, `.environment` and `.session.<sessionId>`, each `{format: 1, sequence, snapshot}` with the kind's stored form as the snapshot, written in one `set`; and `streams.<environmentId>.meta`, `{format: 1, skewMs, opened: [{sessionId, openedAt, bytes}]}`, since document storage cannot list its keys. The meta is written only after it has been read, so a read that failed never has an empty index saved over the stored one (a skew measured meanwhile holds in memory); its changes run one after another. A stream's writes go one after another and each reads the committed state when it runs; the debounce is a window from the first change (not reset by later ones), so a stream changing continuously is still written every 500 milliseconds. A document this build cannot read is no cache. The names hold no ADR 0003 word: a cache document is the stream as the environment sent it.
  - **Retention**: a session is opened when a handle is taken. Its snapshot's size is its document's length as UTF-8, taken on each write; while there are more than 50 or they pass 32 MiB, the least recently opened is evicted, skipping any a handle holds or that lingers. The list and the environment's stream are not counted and never evicted. A session whose subscription ends `deleted` loses its snapshot at once; one deleted while not open keeps its snapshot until evicted. A snapshot is deleted before the meta that stops counting it is written, so a crash or a failed delete leaves it counted (evicted again, the next least recent going in its place meanwhile), never a document nothing counts; removing an environment deletes its streams, then the snapshots its meta names, then the meta. Document storage cannot list its keys, so a snapshot the meta does not name is not swept: the one way to leave one is the process ending between a late write of an evicted session's snapshot and the meta counting it again, since a handle records the session before its stream is ever written.
  - **The session bound**: a held session keeps its snapshot's transcript and every event since, for `projections.session` (#142) to fold; past 1,000 events or 1 MiB of them (as UTF-8 JSON) the stream is resubscribed for a snapshot, once per `ready`, so neither memory nor its cache document grows without end. An environment that answers with no snapshot leaves it growing until the next `ready`.

  - **Skew**: `hello`'s `serverTime` minus this client's clock on arrival, kept in the meta document so it holds offline; `runtime.environmentNow(environmentId)` answers the environment's time, and the list reads each snooze against its own environment's.
